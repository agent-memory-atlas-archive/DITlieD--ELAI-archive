# B-29.5: Symbol Graph Scale Benchmark
Objective: prove B-29's SymbolGraphCache + 4 traversal tools scale to
multi-million-LOC codebases — Linux kernel (~36M LOC), Chromium (~35M
LOC), VS Code (~2.45M LOC), Postgres (~1.5M LOC) — without OOM, with
p99 latency under 500ms per traversal, and with stable hop-banded
output across repeated calls.
Estimated effort: 1 session (~6-8 hours, mostly waiting on indexing).
Pre-requisites: B-29 (Symbol-Level Impact Analysis API), B-31 (resumable
indexing — without this, a Linux-kernel index that crashes at 80% costs
hours).
Parallel-safe with: B-31.5 (different metric domains; can share the same
cloned fixture set).

## Context

B-29's algorithmic claims (sharded persistence, LRU-bounded payloads,
hop-banded BFS, lazy-load DFS) are correct on paper. The cache design
explicitly states: "no query loads every symbol or every edge into
memory". But this property has only been verified on the ELAI repo
itself (~140K LOC, 8075 DKG nodes per Phase 1A audit) — three orders
of magnitude smaller than the largest target codebases ELAI is meant
to handle.

SocratiCode's 40M LOC claim is unverified per agent investigation
(largest scale test in their repo covers 200K symbols / ~10K files in
`tests/integration/symbol-graph-scale.test.ts`, NOT millions of lines).
ELAI must not inherit that gap.

This sub-step builds a real benchmark harness against four real
open-source codebases and measures whether B-29's cache stays bounded,
whether the 4 traversal tools meet p99 budgets, and whether the
sharded reverse index actually keeps memory linear in result-set size
rather than total-graph size.

If B-29 fails to scale, this benchmark catches it before users do.
If it passes, the measured numbers go into a published metrics file
that any future audit can reference.

External anchor: B-29's top-k local-focus design has an academic
validation point (FocalAD ELAI, arXiv:2506.11419) showing that
hop-banded / interaction-scored neighbor selection beats globally
aggregated features for downstream decision-making. This benchmark is
the *engineering* counterpart — proves the algorithmic claim translates
to bounded memory + latency at Linux-kernel scale, not just nuScenes
scene-graph scale.

### Phase 2 — Measurement harness (~2 hours)

4. Create `crates/knowledge/benches/symbol_graph_scale.rs` using
   criterion (already a workspace dev-dep per Phase 0):
   ```rust
   use criterion::{criterion_group, criterion_main, Criterion};
   use elai_knowledge::symbol_graph::cache::SymbolGraphCache;

   fn bench_impact_radius(c: &mut Criterion) {
       let mut group = c.benchmark_group("impact_radius");
       group.sample_size(20); // long-running benches; criterion-default 100 too many
       for tier in tiers() {
           let cache = load_cache(&tier).expect("cache must be pre-built");
           // Use a fixed set of high-fan-in target symbols per tier
           // for reproducibility (e.g. for linux: kmalloc, schedule,
           // do_syscall_64; for chromium: NewBrowserContext,
           // BrowserMain; etc).
           for target in high_fanin_symbols(&tier) {
               group.bench_function(format!("{}::{}", tier.name, target),
                   |b| b.iter(|| {
                       let result = pollster::block_on(
                           compute_impact_radius(&cache, target, 3));
                       criterion::black_box(result);
                   }));
           }
       }
       group.finish();
   }

   // Similar bench fns: bench_call_flow, bench_symbol_context,
   // bench_list_symbols
   criterion_group!(benches,
       bench_impact_radius,
       bench_call_flow,
       bench_symbol_context,
       bench_list_symbols,
   );
   criterion_main!(benches);
   ```
   Each tier × tool combo measured separately so we can spot per-language
   degradation (e.g. C++ template-heavy edges may resolve slower than
   plain C).

5. Add memory measurement helper in
   `crates/knowledge/benches/scale_memory.rs`:
   ```rust
   pub struct MemorySnapshot {
       pub rss_bytes: u64,
       pub heap_bytes: u64,
       pub cache_lru_size: usize,
       pub name_index_loaded: bool,
       pub reverse_index_loaded: bool,
   }
   pub fn snapshot(cache: &SymbolGraphCache) -> MemorySnapshot { ... }
   ```
   RSS via `procfs` on Linux, `GetProcessMemoryInfo` on Windows. Heap
   via `jemalloc-ctl` if jemalloc is the global allocator (verify; if
   not, ASK USER before adding jemalloc as dep).

6. Build a workload script `crates/knowledge/benches/workload.rs` that
   simulates a realistic 1000-query mix:
   - 60% impact_radius (depth 2-3)
   - 25% symbol_context (named symbol lookup)
   - 10% call_flow (entry-point traversal)
   - 5% list_symbols (file-scoped enumeration)
   Run after cache is cold-loaded, measure LRU hit rate over the
   workload, peak memory, p50/p95/p99 latency per tool.

### Phase 3 — Run + record (~3-4 hours, mostly waiting)

7. Build the indices for each tier:
   ```bash
   for tier in linux chromium vscode postgres; do
     elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/$tier" \
       --metrics "metrics/phase_b29_5_$tier.toml"
   done
   ```
   Record per-tier:
   - Wall clock time
   - Peak indexing memory (separate from cache memory)
   - Final DKG node/edge count per language
   - Final symbol_graph_meta { symbol_count, edge_count, file_count,
     unresolved_edge_pct }
   This phase is bottlenecked by embedding throughput; expect 1-3 hours
   for Linux + Chromium combined on a typical workstation. B-31's
   resumable indexing is essential here.

8. Run criterion benches:
   ```bash
   cargo bench -p knowledge --bench symbol_graph_scale -- --output-format=json > \
     metrics/phase_b29_5_bench_raw.json
   ```
   Run twice to verify determinism: same target symbol → identical
   `total_files` count + identical hop-band sets.

9. Run workload script:
   ```bash
   cargo run --release --bin scale_workload -- \
     --tier linux --queries 1000 \
     --output metrics/phase_b29_5_workload_linux.toml
   ```
   For each tier, record:
   - p50 / p95 / p99 latency per tool
   - Cache LRU hit rate
   - Peak RSS during workload
   - cache.file_payload_lru.size at end (should be <= 500)

10. Aggregate results into `metrics/phase_b29_5_scale.toml`:

### Phase 4 — Determinism + regression guard (~1 hour)

11. Add `tests/scale/symbol_graph_determinism.rs` regression test:
    - Run impact_radius on `linux::kmalloc` 5 times
    - Assert byte-identical `BTreeMap<u32, Vec<String>>` output across
      runs (BTreeMap chosen in B-29 specifically for this property)
    - Assert truncated flag identical
    - Repeat for vscode::vscode_extension, chromium::BrowserMain,
      postgres::PortalRunMulti

12. Add CI guard `tests/contracts/scale_p99_budget_contract.rs`:
    - Reads `metrics/phase_b29_5_scale.toml`
    - Asserts every tool's p99 across all tiers <= 500ms
    - Asserts cache LRU memory <= 2GB on 16GB machine equivalent
    - Asserts unresolved_edge_pct <= 50% per tier
    Fails CI if any benchmark regresses these bounds.

13. Document the measurement procedure in
    `metrics/phase_b29_5_README.md` so any future audit can reproduce:
    - exact tier commits
    - exact criterion sample size
    - hardware target (CPU, RAM, disk type)
    - expected wall-clock budget per tier

  accept partial coverage (e.g. Linux + VS Code only). Recommend gate

  parity comparison)

  observable_effect. Document what user-facing latency this translates
  to (e.g. "Auditor PostToolUse hook adds <500ms per Edit; tolerable
  under interactive use, gate-fail above").
- Why criterion vs Rust's built-in bench: criterion provides
  statistical analysis + variance detection; built-in is unstable and
  tied to nightly toolchain
- Memory measurement approach: RSS via /proc on Linux + GetProcessMemoryInfo
  on Windows. Whether to add jemalloc-ctl for heap details — ask user
  before adding the dep
- Whether scale benchmark runs in CI on every commit (no — too slow) or
  only nightly (yes — schedule via existing workflow CI)

## Side benefits unlocked

- Published metrics file means future "is ELAI fast enough?" questions
  have grounded answers, not vibes
- Per-language unresolved_edge_pct exposes which extractors (B-30) need
  improvement
- Real-world fixture set unblocks B-31.5 (same fixtures), B-30 multi-
  language verification, and any future Designer / Researcher real-
  world testing
- Sets a precedent: scale benchmarks are required artifacts for any
  knowledge-engine change, not optional
- Catches regressions: if B-30 changes break C++ extraction, the bench
  will show it via degraded chromium unresolved_edge_pct
- Future metric (NOT in this benchmark, but unblocked by it): signal-to-
  noise ratio of impact results — fraction of files in hop band 1 that
  the Auditor actually flagged as relevant vs filtered as noise. FocalAD
  reports a related metric (Top-k coverage on planning-critical
  neighbors); ELAI's equivalent measurement would require tracking
  Auditor decisions per blast-radius entry and is a candidate B-23.x
  self-modification signal.
