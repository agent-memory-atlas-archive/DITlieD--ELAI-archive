# B-31.5: Resumable Indexing Scale Benchmark
Objective: prove B-31's per-batch checkpoint + IndexLock + startup
auto-resume + graceful shutdown actually survive multi-million-LOC
indexing runs — including mid-run kill -9 at 10% / 50% / 90% progress,
concurrent ELAI instances on the same project, and graceful shutdown
under load — producing byte-identical post-resume state and bounded
memory across the full run.
Estimated effort: 1 session (~6-8 hours, mostly waiting on indexing
runs).
Pre-requisites: B-31 (Resumable Indexing + Lock + Startup Auto-Resume).
Reuses fixtures from B-29.5 if both are run.
Parallel-safe with: B-29.5 (different metric domains; share same cloned
fixture set).

## Context

B-31's three patterns — per-batch checkpoint with blake3 content-hash
skip, cross-process IndexLock with stale-PID reclaim, startup auto-
resume with graceful shutdown — are designed to make ELAI survive in
production over hours-long indexing runs. The unit tests in B-31 cover
small-fixture happy paths (fixture project of ~100 files, kill -9 at
single batch boundary). Real failure modes only surface at scale:
- A 50K-file index with 1000+ batch checkpoints exposes amortization
  cost of per-batch SQLite writes (acceptable? or pathological?)
- A multi-hour run is the first time `LockScope::Index`'s 30-second
  refresh cycle is exercised end-to-end
- A two-instance race condition (one ELAI starts, second ELAI starts
  3s later) only matters if the first hasn't released the lock yet —
  which only happens when indexing is in progress
- Graceful shutdown's 60s deadline only matters when there's >60s of
  in-flight work to drain

This sub-step builds a real benchmark across four scenarios on real
codebases (Linux, Chromium, VS Code, Postgres — same as B-29.5) to
verify the patterns hold under load. It is the only way to confirm
ELAI can ship the "indexes 50M LOC repos" claim without inheriting
SocratiCode's unverified-marketing problem.

### Phase 3 — Tier B: Crash-resume identity (~3-4h waiting)

6. Build a kill-injection harness `scripts/scale_test/kill_at_progress.sh`:
   ```bash
   #!/usr/bin/env bash
   # Usage: kill_at_progress.sh <fixture> <kill_at_pct>
   # Spawns elai.bat index <fixture>, monitors progress via SSB rows,
   # SIGKILL when batches_processed / batches_total >= kill_at_pct/100.
   FIXTURE="$1"; PCT="$2"
   PROGRESS_DB="$ELAI_SCALE_FIXTURE_ROOT/$FIXTURE/.elai_cc/.elai/sessions/ssb.db"
   elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/$FIXTURE" &
   ELAI_PID=$!
   while true; do
     sleep 5
     ROW=$(sqlite3 "$PROGRESS_DB" \
       "SELECT batches_processed, batches_total FROM ssb_action_index_checkpoint
        ORDER BY ts DESC LIMIT 1;" 2>/dev/null)
     [[ -z "$ROW" ]] && continue
     IFS='|' read -r BP BT <<< "$ROW"
     CURRENT_PCT=$((BP * 100 / BT))
     if [[ $CURRENT_PCT -ge $PCT ]]; then
       echo "Killing at ${CURRENT_PCT}% (batch $BP/$BT)"
       kill -9 $ELAI_PID
       wait $ELAI_PID 2>/dev/null
       break
     fi
   done
   ```

7. For each tier (Linux + VS Code minimum; Chromium + Postgres
   nice-to-have):

   - Run index (fresh) → kill at 50% → resume → verify identity

   ```bash
   for tier in linux vscode; do
     for pct in 10 50 90; do
   ```

### Phase 4 — Tier C: Cross-process lock (~30 min)

9. Two-instance race test:
   ```bash
   # Instance A
   elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/linux" &
   INST_A=$!
   sleep 3  # let A acquire lock
   # Instance B
   start_b_time=$(date +%s%N)
   elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/linux" 2>&1 \
     | tee metrics/tier_c_instance_b_output.txt
   end_b_time=$(date +%s%N)
   echo "Instance B exit time: $(( (end_b_time - start_b_time) / 1000000 ))ms"
   kill $INST_A
   ```
   Expected: instance B exits within 1 second with stderr containing
   "Another process is already indexing this project, skipping" and
   PID of instance A logged. Lock file `.elai_cc/.index.lock` contains
   instance A's PID.

10. Stale-PID reclaim test:
    ```bash
    # Spawn an indexer, kill -9 (no graceful shutdown), then start
    # another. Second instance must reclaim the orphan lock.
    elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/postgres" &
    INST=$!
    sleep 5  # let lock get acquired
    kill -9 $INST
    # Lock file still present with dead PID
    elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/postgres"
    # Should detect dead PID, reclaim lock, resume.
    ```
    Verify SSB shows `LockContested` followed by `LockAcquired`
    actions; resume completes without manual lock-file deletion.

11. Record in `metrics/phase_b31_5_tier_c.toml`:

### Phase 5 — Tier D: Graceful shutdown under load (~30 min)

12. Graceful shutdown deadline test:
    ```bash
    elai.bat index "$ELAI_SCALE_FIXTURE_ROOT/chromium" &
    ELAI=$!
    sleep 60  # let it get well into indexing
    start=$(date +%s)
    kill -TERM $ELAI
    wait $ELAI
    end=$(date +%s)
    echo "Graceful shutdown took $((end - start))s"
    ```
    Expected: process exits within 65 seconds (60s deadline + 5s
    slack). SSB has `IndexCancel` action with non-zero
