# H-37 -- plan-approval gate at PLANNING -> TESTING_FIRST
- Track 4 (UX + USER-MEMORY) | lever STEERING | grounding STRONG | nature BUILD-on-existing-pre-gate | effort S-M | WAVE 4 | depends H-36 (notification surface reuse, soft)
- Premise: the highest-leverage point to catch a wrong plan assumption is BEFORE it cascades into many edits. Today the FSM edge PLANNING/FEASIBILITY_PROBE -> TESTING_FIRST already runs an unconditional compliance pre-gate (EU AI Act record-keeping) but there is NO point where a human (or, in autonomous mode, the AutonomousGate) is asked "is this the right plan?". H-37 adds an explicit approve/redirect/reject decision riding that exact edge, recorded to SSB, so a misread of the task is stopped at one transition instead of discovered after 30 edits. This is the industry-convergent "plan mode" pattern (Claude Code plan-mode, Devin Interactive Planning).

## Steal/build
BUILD-on-existing. Nothing here is greenfield. Three live ELAI seams are composed, in this order:
1. STEAL the gate machinery: `gate.rs::run_interactive_gate` (orchestrator/src/gate.rs:230) ALREADY implements the full APPROVE/REJECT/MODIFY/REDIRECT protocol incl. risk-gated auto-advance and a max-3 MODIFY re-eval loop. It is WIRE-DARK at the live task_runner (callers are only #[cfg(test)] at gate.rs:733-956). H-37 does NOT reimplement it; it makes one production call to it at the PLANNING->TESTING_FIRST edge.
2. STEAL the install: `CliInteractiveGate` (cli/src/runtime_builder.rs:429, impl InteractiveGate at :431) is ALREADY constructed in production and threaded onto `RuntimeWiring.interactive_gate` (cli/src/run_subcommand.rs:118-126) when `gate_mode == Interactive`. H-37 consumes that already-installed handle; no new construction.
3. STEAL the autonomous path: `AutonomousGate` (orchestrator/src/autonomous_gate.rs) + `GateMode` (autonomous_gate.rs:88) ALREADY map LOW->auto-advance / MEDIUM+->RequestHuman via the six-check `Evidence` snapshot. In AUTONOMOUS mode H-37 routes the plan decision through `AutonomousGate::decide`: LOW-risk plans auto-approve, MEDIUM/HIGH surface to the human exactly as B-22 specifies. This is the B-22 composition the brief asks for.
Build delta is small: (a) one production call site that wraps the compliance pre-gate result with a plan-approval decision, (b) one new SSB action_type `plan_decision_event` (Pattern-2 single-variant) whose payload mirrors the existing `GateDecisionPayload`, (c) one dashboard approval card. Reimplement-from-odysseus prior-art: the DISTILL/REJECT-on-bad-result gate semantics (teacher_escalation.py:621-626 NO_SKILL gate) inform the "reject is fail-closed, redirect must be a valid target" invariant — reimplemented in Rust, not ported.

## REVISED scope (W-10 tiered)
SHIPS NOW (WAVE 4):
- A `PlanApprovalGate` decision computed at the live PLANNING/FEASIBILITY_PROBE -> TESTING_FIRST FSM transition. In INTERACTIVE gate_mode it calls the already-installed `RuntimeWiring.interactive_gate` (`CliInteractiveGate`) via `run_interactive_gate`; the human sees the plan summary and answers approve/redirect/reject. In AUTONOMOUS gate_mode it routes through `AutonomousGate::decide`: a LOW-risk plan auto-approves (decision recorded as auto_advance), a MEDIUM/HIGH plan emits `RequestHuman` and surfaces to the dashboard card (compose B-22).
- The decision lands as ONE new SSB row `plan_decision_event` (Pattern-2 single-variant; payload `PlanDecisionPayload` mirrors `GateDecisionPayload`: decision {approve|redirect|reject|auto_advance}, target_state, risk_level, reason, plan_session_id). Append-only; the human did NOT author this row (it is emitted by the runtime at the transition) -> off-agent artifact per W-1.
- REJECT blocks the transition: the FSM stays at PLANNING (returns an outcome the transition driver treats as refusal, analogous to `FsmError::ComplianceBlocked` at fsm.rs:965); REDIRECT to a different valid target is validated against the transition matrix before it is honored (reuse `run_interactive_gate`'s REDIRECT validation, gate.rs:227).
- Dashboard plan-approval card (frontend_pair) surfaces the pending plan + approve/redirect/reject buttons in interactive mode and renders the recorded decision in autonomous mode.

DEFERRED (W-10): the MODIFY re-plan loop beyond a single round (gate.rs already caps MODIFY at 3 re-evals — we expose only approve/redirect/reject in the first cut, MODIFY routes to redirect-back-to-PLANNING); a learned-from-rejection memory write (would compose H-31/H-32 but is a separate plan); installing a real `ComplianceProvider` (orthogonal — H-37 works with or without it).

Local-token discipline: the plan summary surfaced to the human/gate is the EvidenceSummary (gate.rs:50), bounded by gate_results count — NOT the full plan text. No always-injected block; the summary is built on-demand at the transition only. No user-memory is injected into this gate (the gate decision is a steering control, not a personalization surface) — consistent with the auditor-objectivity firewall.
Staleness: the plan_decision_event row is bi-temporal-free (it is an immutable decision-at-an-instant, like the existing gate_decision rows); no supersession needed. A later REDIRECT emits a NEW row; the dashboard shows newest-wins by created_at, never narrating superseded decisions.
