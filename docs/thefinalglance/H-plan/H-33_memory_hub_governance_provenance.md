# H-33 -- memory hub, governance, and provenance surface
- Track 4 (UX + USER-MEMORY) | lever STEERING/TRUST | grounding STRONG | nature ACTIVATION | effort M | WAVE 4 | depends H-31
- Premise: the user can see, edit, forget, and pin every decision ELAI has stored about their work, see which of those stored decisions are about to influence a run BEFORE it acts, and on /continue get a resume-summary that flags any SUPERSEDED decision so a stale preference cannot silently steer the resumed run. Strictly "your saved decisions (editable)", never "remembers you" -- the surface reads the SSB journal + FactStore directly and injects ZERO tokens into any model prompt (personal_agent_risk: low; the panel is a ledger viewer, not a persona).

## Steal/build
ACTIVATION-dominant. The CLI verb surface, the bi-temporal supersession chain, soft_close, the trust-aware retrieval filter, the decay scheduler, and a read-only Tauri memory drawer ALL EXIST in ELAI today (see Existing ground truth). H-33 does NOT build a memory store -- the research bundle and Letta "filesystem is all you need" explicitly warn against a parallel store. H-33 lights up the already-parsed-but-unrouted `elai memory` dispatch, adds the one missing governance verb (`pin`), and adds two pure-read surfaces (provenance + resume-summary). The only NET-NEW persisted artifact is a single append-only SSB beacon for the two governance mutations (forget, pin/unpin). odysseus is MIT prior-art for the governance/context-budget algorithms (src/context_compactor.py, src/context_budget.py) -- reimplement the headroom-clamp math in Rust against the local ceiling, never port Python.

## REVISED scope (W-10 tiered)
SHIP NOW (effort M):
1. ROUTE THE STUB (the activation). Replace the main.rs:1019-1024 hard-error with a real dispatch into a new sync driver `crates/cli/src/memory_cmd.rs::run_memory_subcommand(action)` (mirrors github_pr_cmd::run_pr_subcommand main.rs:1042 and incident-record pattern). `List` -> `FactStore::list_current` printed as a table (date=ingested_at_ms, fact_type, key, value-summary, trust_score, scope, source-session=first evidence_pointer, status=active|superseded->id). `Inspect`/`show` -> `FactStore::get` full row incl. evidence_pointers + superseded_by + the supersession CHAIN (walk superseded_by backward AND forward by querying older/newer rows of the same (project_id,scope,key)). `Delete`/`forget` -> `FactStore::soft_close` THEN emit one governance beacon (below). `Insert` stays as the existing manual-T0 path (already specified args.rs:1315-1318; route it but it is not H-33's focus). `--json` honored (args_memory.rs:135) for machine output.
2. ADD `pin`/`unpin` WITHOUT a sqlite migration. MemoryFact has no `pinned` column and adding one would force a memory-db migration touching fact.rs:138 struct + every SELECT column list (list_current:155, iter_current:323) + the row decoder -- that is a BUILD, out of scope for effort M and it churns a frozen schema. INSTEAD pin = an append-only governance beacon (the SSB is the source of truth, no memory-db change): `elai memory pin --fact-id <id>` emits `MemoryGovernanceEvent::Pinned{fact_id}`; `unpin` emits `::Unpinned{fact_id}`. The decay scheduler reads the current pin-set (latest beacon per fact_id wins) and HARD-SKIPS pinned fact_ids in `decay_tick` (decay.rs:88) so a pinned decision is decay-exempt. CSQ (mcp_think counterfactual): if the pin-set read fails at decay time, decay STILL runs on all rows (fail-toward-decay) -- a pinned row would age rather than be silently frozen forever; acceptable because the user can re-pin and nothing is deleted. This keeps the memory sqlite schema frozen and makes pin status reconstructable from the journal alone (RRA-replayable).
3. PROVENANCE "which preferences fired" READ surface (zero tokens). `elai memory provenance [--task <hint>]` prints the set of currently-valid decisions that PASS the H-31 trust-floor + non-empty-evidence predicate (retrieval.rs:62-78,97 semantics, computed read-only -- NOT a call into the wire-dark get_relevant_facts), each annotated active|superseded. This answers "what is eligible to steer the next run" before the run acts. It is a READ of the FactStore + a recompute of the same gate, never an injection.
4. /continue RESUME-SUMMARY-AS-CONFIRMATION. On a resumed run (the /continue path), before the resumed run acts, surface a resume-summary that lists which stored decisions will influence the run and FLAGS any whose status is superseded (valid_to_ms IS NOT NULL OR superseded_by IS Some) -- defusing intent-drift (the async-layer worry: a stale preference silently steering the resumed work). The summary is presented to the human as a confirmation gate output; it does NOT auto-act.
