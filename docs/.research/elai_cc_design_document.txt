PART 1: WHAT WE ARE BUILDING

elai_cc is a Rust-native autonomous LLM workflow system.
Not a CLI assistant. An autonomous development engine where the human provides input
and the system executes the full development cycle with minimal human intervention.

Two deliverables:
  D1: elai_cc — standalone autonomous workflow tool (personal use first)
  D2: elai_cc-empire — merge with Empire's factory-brain + factory-static (collaborative)
  D1 must be battle-tested before D2.

Core properties:
  - Model-agnostic: cloud + local (Gemma 4 31B as primary local executor)
  - Per-project: all state, indexes, graphs, RAG live inside project directory
  - Deterministic-first: ALL outputs verified by deterministic scripts, even LOC counts
  - Token-efficient: msgpack storage, postcard wire format, phase-aware context loading
  - Never-compact: use full context smartly, hand off to new session if exhausted
  - Autonomous: human provides task, system executes full cycle
  - Clean model: no system prompt biases, no pre-injected instructions from harness
  - Path-agnostic: Windows + Linux without path assumptions
  - Open-source compliant: no proprietary deps, clean licensing

PART 5: REASONING ENGINE (GRC) — DEEP DESIGN

Purpose: Replace ALL model-internal thinking. This is the core innovation.
GRC makes elai_cc model-agnostic — reasoning structure is external to the model.

5.1 GRC State Machine (per topic):
  observe(grounding) -> hypothesize(grounding) -> plan_action -> act -> verify(grounding)

  Each step MUST cite grounding source.
  Steps without grounding are rejected by the engine.
  The model receives ONLY the structured prompt for the current step.
  No <thinking> tags, no chain-of-thought tokens consumed by the model.

5.2 Budget System:
  Per-topic: max_calls (1-12), max_chars (200-1500)
  Global default configurable in elai_cc.toml
  Overflow -> forced convergence (must produce conclusion) or escalation (hand to human)
  Budget scales with task complexity: simple=3/600, moderate=5/800, complex=8/1200

5.3 Grounding Verification (NEW — core differentiator):
  Every claim in a plan or hypothesis MUST be verified before acting on it.

  Verification methods:
    FILE_CHECK:   does the file/function/class actually exist? (grep/glob)
    API_CHECK:    does this API/library work as claimed? (test call or docs lookup)
    WEB_CHECK:    is this algorithm/method real? (web search verification)
    SOURCE_CHECK: does the source code we're referencing actually do what we think? (read)
    TEST_CHECK:   does a test confirm this behavior? (run test)

  Grounding levels:
    VERIFIED:  searched, tested, or read from source
    HIGH:      code just read in this session
    UNCERTAIN: from training, not verified — MUST be resolved before acting

  Plan grounding sweep:
    Before any plan enters EXECUTING, GRC scans ALL claims in the plan.
    Each claim classified: GROUNDED, VERIFY_NEEDED, UNGROUNDED.
    UNGROUNDED claims block execution until resolved.
    This prevents the "LLM proposes plan based on hallucinated API" failure mode.

5.4 Fact-Based Planning Protocol:
  When human gives task:
    1. GRC breaks task into sub-questions (observe step)
    2. Each sub-question answered via VERIFIED sources (not training)
    3. If LLM doesn't know -> web search, source read, or "I don't know"
    4. Plan assembled ONLY from verified facts
    5. Plan iterated: break down -> verify each part -> check feasibility
    6. Pre-implementation tests written from plan (TESTING_FIRST)
    7. Adversarial review of plan by auditor agent
    8. Only then: EXECUTING

5.5 Model Interaction Protocol:
  GRC does NOT send "think about X" to the model.
  GRC sends: "Given these verified facts: [F1, F2, F3]. Produce: [specific output format]."
  Model returns raw completion.
  GRC validates: format correct? grounding cited? new claims introduced?
  New ungrounded claims -> flagged for verification before next step.

5.6 Anti-Hallucination Stack (per model role):

  CRITICAL: Layer-level optimizations (DoLa, TurboQuant, steering vectors) require
  vLLM or custom inference. Ollama is a black box — no layer intervention.
  Design is phased: ollama for Phase 0-1, vLLM integration in Phase 2+.

  Phase 0-1 (ollama — available immediately):
    All roles: constrained decoding via grammar parameter (ollama supports this)
    All roles: temperature/top-p per role in elai_cc.toml
    Executor: standard inference, rely on GRC for grounding verification
    Auditor: low temperature (0.1-0.3), constrained output format

  Phase 2+ (vLLM — after vLLM integration):
    For Gemma 4 31B (executor):
      TurboQuant KV cache compression (3.8-6.4x, extends effective context)
      DoLa contrastive decoding (contrast early vs late layers, improves factuality)
      Constrained decoding for structured outputs (grammar-based)

    For auditor (DeepSeek-R1-Distill-32B):
      DoLa with amplified contrast (more aggressive layer comparison)
      Steering vectors toward skepticism (truthfulness + critical analysis)
      Lower temperature (0.1-0.3) for deterministic analysis

    For prompt-engineer (Qwen 3.5 27B):
      Constrained decoding (must output valid structured format)
      No DoLa needed (dense model, structurally stable)

    For context-compiler:
      High temperature allowed (0.7) for creative retrieval
      Steering vectors toward completeness (don't miss relevant files)

  These are configured in elai_cc.toml per-role as providers::LayerConfig.
  LayerConfig has two backends: OllamaConfig (Phase 0-1) and VllmConfig (Phase 2+).

5.7 Counterfactual Safety (CSQ):
  Before finalizing any non-trivial logic:
    GRC asks: "If [assumption X] is wrong, code will [consequence Y]."
    If consequence is dangerous (data loss, security hole, financial error):
      MUST add guard/check in implementation.
    Minimum 1 CSQ per function touching: files, network, money, auth.

5.8 Per-Agent GRC Configuration (NEW — 2026-04-05):

  Every agent runs GRC — not just the executor. But each role has different reasoning needs.
  Configured in elai_cc.toml under [agents.{role}.grc]:

  executor (Gemma 4 31B):
    budget: complex (8/1200)
    required_steps: [observe, hypothesize, plan_action, act, verify]
    grounding: all steps require source citation
    csq: mandatory for file/network/money/auth functions

  auditor (DeepSeek-R1-Distill-32B):
    budget: high (10/1200) — more reasoning room for adversarial analysis
    required_steps: [observe, hypothesize, verify, verify] — double verify
    grounding: VERIFIED only (no HIGH or UNCERTAIN accepted)
    extra: must find >= 1 issue per review (anti-rubber-stamp)
    csq: mandatory on every finding (what if this finding is wrong?)

  context-compiler:
    budget: low (3/600) — mostly deterministic retrieval
    required_steps: [observe] — observe-heavy, no plan_action needed
    grounding: FILE_CHECK and SOURCE_CHECK only
    no csq (read-only agent, no mutations)

  prompt-engineer:
    budget: moderate (5/800)
    required_steps: [observe, hypothesize, converge]
    grounding: must cite plan + context package
    output: constrained format (must match prompt template schema)

  memory-writer:
    budget: minimal (2/400)
    required_steps: [observe, converge]
    grounding: must cite diff + test results
    output: deterministic changelog format, no prose

  Per-agent FSM sub-states:
    Each agent has its own mini-FSM tracking: IDLE -> LOADING -> REASONING -> ACTING -> DONE
    Sub-state persisted in agent checkpoint (see 6.5)
    Orchestrator reads agent sub-states to make scheduling decisions


PART 6: ORCHESTRATION — REVISED

6.1 Context Management (NEVER COMPACT):
  Real-time token counting via providers::LlmProvider::token_count()
  Budget tracking: orchestrator::Fsm::token_budget_remaining()

  Phase-aware context loading:
    PLANNING:      load rules + knowledge engine results + plan template
                   DO NOT load: edit tools, bash tools, validation tools
    TESTING_FIRST: load test framework + plan + rules
                   DO NOT load: edit tools, bash tools
    EXECUTING:     load edit tools + current phase spec + relevant code context
                   DO NOT load: planning tools, full plan (only current phase)
    AUDITING:      load validation tools + test runner + code under review
                   DO NOT load: edit tools, planning tools

  When context approaches limit (configurable threshold, e.g. 85%):
    1. Current task state saved to .elai_cc/sessions/{id}/handoff.msgpack
    2. Includes: FSM state, current phase, completed steps, pending work, key findings
    3. Session ends gracefully
    4. New session spawns, reads handoff file, continues from exact state
    NO SUMMARIZATION. Raw state transfer via structured data.

6.2 Agent Parallelism (NEW):
  Deterministic control flow — NOT an LLM deciding what to parallelize.
  The FSM + plan structure determines parallelizable work.

  Example: Plan Phase 3 has steps A, B, C where A and B are independent, C depends on both.
    orchestrator spawns: agent_A(step_A), agent_B(step_B) in parallel
    Both complete -> orchestrator spawns: agent_C(step_C)

  Resource-aware scheduling (concrete for 2x RTX 3090 24GB):
    Detection: nvml-wrapper crate (Windows NVML bindings) or sysinfo for cross-platform
    Query available VRAM per GPU before spawning

    Dual-3090 scheduling table (CORRECTED 2026-04-05 — sequential, not parallel):
      CRITICAL: 24GB per GPU cannot hold two ~18-20GB models simultaneously.
      Large models are SEQUENTIAL — one loaded at a time per GPU.
      Only parallelism: large model (~18-20GB) + embedding model (~1.5GB) on separate GPUs.

      PLANNING:           GPU0: executor (Gemma4 31B, ~18-20GB)
                          GPU1: embedding model (~1.5GB)
      FEASIBILITY_PROBE:  GPU0: executor (stays loaded)
                          GPU1: embedding model (stays loaded)
      TESTING_FIRST:      GPU0: executor (stays loaded)
                          GPU1: embedding model
      EXECUTING:          GPU0: executor (stays loaded)
                          GPU1: embedding model (precompute embeddings for changed files)
      AUDITING:           GPU0: UNLOAD executor -> LOAD auditor (DeepSeek-R1, ~18-20GB)
                          GPU1: embedding model (stays loaded, ~1.5GB)
                          Swap cost: ~15-30 seconds (model unload + load via ollama)
      MEMORIZING:         GPU0: UNLOAD auditor -> LOAD memory-writer (small, ~4GB)
                          GPU1: idle
      Back to EXECUTING:  GPU0: UNLOAD memory-writer -> LOAD executor (~15-30s swap)

      Model swaps happen ONLY at phase boundaries (checkpointed, crash-safe).
      Never two large models on the same GPU. Never mid-phase model swaps.

    If VRAM insufficient: serialize agents (one at a time on one GPU)
    If cloud fallback: parallel API calls (rate-limit aware, no VRAM concern)

  Inter-agent communication (adopted from Empire factory-brain EngineMKI):
    Via session-scoped message bus (not LLM-mediated)
    Messages are structured data (msgpack), not natural language
    Bus pattern from factory-brain:
      Named buses per concern (e.g., "code.*", "test.*", "knowledge.*")
      Glob-pattern subscriptions: agent subscribes to "code.change.*" to get all file changes
      Hook types mapped: event (broadcast), route (request/response), schedule (periodic)
    Agent A can signal: "I found X in file Y, relevant to your task"
    Receiving agent incorporates as grounded fact
    Permission model: scope bitflags per agent role (FILESYSTEM, NETWORK, CONFIG, SECURITY)
      Executor: FILESYSTEM + NETWORK (for web search)
      Auditor:  FILESYSTEM (read-only) + NETWORK (test runners)
      Context-compiler: FILESYSTEM (read-only)
      Memory-writer: FILESYSTEM (write to memory-bank only)

  No "main brain" LLM:
    The orchestrator crate is pure Rust deterministic code
    It reads FSM state, plan structure, resource availability
    It decides what runs when, what depends on what
    LLMs are workers, not managers

6.4 Session Handoff (replaces Progress-Compress-Reset):
  When token budget at threshold:
    1. Save structured state (not LLM summary) to handoff.msgpack
    2. State includes: FSM, phase, step, findings, code changes made, tests written
    3. Current session ends
    4. New session starts, loads handoff, continues

  Between sessions:

6.5 Agent Checkpointing (NEW — 2026-04-05):

  Problem: in current Claude Code, stopping an agent loses ALL its work. Agent gets stuck
  in a loop = all progress gone. This is unacceptable for autonomous operation.

  Solution: incremental per-agent checkpointing.

  Checkpoint location: .elai_cc/sessions/{sid}/agents/{agent_id}/
  Files:
    state.msgpack      — current agent sub-FSM state (IDLE/LOADING/REASONING/ACTING/DONE)
    grc_history.msgpack — all GRC steps taken so far (observe, hypothesize, etc.)
    tool_results.msgpack — results of all tool calls (file reads, greps, edits)
    output_draft.msgpack — partial output being assembled
    checkpoint_ts       — last checkpoint timestamp

  Checkpoint triggers (automatic, no agent involvement):
    - After each completed GRC step (observe, hypothesize, verify, etc.)
    - After each tool call that returns results
    - After each file edit is confirmed
    - Before any potentially slow operation (web search, model inference)

  Recovery protocol:
    1. Orchestrator detects agent stop/crash/timeout
    2. Reads last checkpoint from agents/{agent_id}/
    3. Spawns new model instance (same role, same config)
    4. Injects checkpoint as structured context: "You are resuming. Prior work: [checkpoint]"
    5. Agent continues from last GRC step, not from scratch
    6. If agent was stuck (same GRC step repeated 3x), orchestrator flags and either:
       - Reduces scope (adaptive, like DAIRA trace_depth reduction)
       - Escalates to human (in INTERACTIVE mode)
       - Tries different approach (swap step type: hypothesize -> observe)

  Anti-spiral (agent-level):
    Agent sub-FSM tracks: same_step_count. If >3, checkpoint + escalate.
    Orchestrator can kill stuck agents without losing prior work.
    This is the key difference from Claude Code: stop is safe, always resumable.

6.6 Model Lifecycle Management (NEW — 2026-04-05):

  Problem: 48GB VRAM across 2x 3090. Cannot load all models simultaneously.
  Gemma4 31B Q4 ~18GB + auditor ~18GB = 36GB. Embedding model + OS overhead = tight.
  Need intelligent load/unload to maximize throughput.

  ModelPool (providers/ crate):
    Tracks: {model_id -> ModelState(Loaded(gpu_id, vram_used) | Unloaded | Loading)}
    Queries VRAM via nvml-wrapper (NVIDIA) or sysinfo (cross-platform fallback)

  Loading strategy:
    ACTIVE:    model needed by currently running agent. Highest priority. Never unloaded.
    PRELOAD:   model needed by next likely agent (predicted from FSM state).
               Loaded in background if VRAM available. Unloaded if ACTIVE needs space.
    IDLE:      model not needed soon. Unloaded first when VRAM pressure.

  Predictive pre-loading (FSM-driven, deterministic):
    EXECUTING phase -> pre-load auditor model (AUDITING comes next)
    AUDITING phase -> pre-load executor model (might need fixes)
    PLANNING phase -> pre-load prompt-engineer model
    TESTING_FIRST -> pre-load executor model

  Model swap protocol:
    1. Orchestrator determines next model needed
    2. Check VRAM: fits alongside current? Load in parallel.
    3. Doesn't fit: wait for current agent to reach checkpoint, then unload.
    4. Load new model. Confirm loaded (health check inference).
    5. Resume agent pipeline.

  Ollama integration:
    ollama already handles model loading/unloading via its API
    ModelPool wraps: POST /api/generate (triggers load), DELETE /api/delete (unload)
    KEEP_ALIVE parameter controls auto-unload timeout
    For dual-GPU: CUDA_VISIBLE_DEVICES per ollama instance, or single instance with --gpu flag

  vLLM integration (Phase 2+):
    vLLM manages its own GPU memory. ModelPool delegates to vLLM scheduler.
    Multiple models via --served-model-name with tensor parallelism across GPUs.


PART 7: WORKFLOW — DUAL MODE (REVISED 2026-04-05)

7.0 Execution Modes:

  elai_cc operates in two modes. Mode is set at session start and switchable mid-session.

  AUTONOMOUS MODE:
    Human provides initial input. System executes the ENTIRE development cycle.
    Output: finished, tested, polished system from start to end.
    Phase gates auto-advance when evidence artifacts pass validation.
    No human confirmation at non-dangerous gates.
    Dangerous actions (delete, overwrite, force-push) STILL require gate review —
      but the gate is another agent (auditor), not a human.
    Session handoff is automatic (token budget threshold -> save -> new session -> continue).
    The only human touchpoints: initial task + final delivery.
    If system gets stuck (3x anti-spiral on same issue): escalates to human with
      full context (checkpoint + GRC history + what was tried).

  INTERACTIVE MODE:
    Human-in-the-loop at every phase transition.
    Each gate pauses and presents: evidence artifacts, agent reasoning, proposed next step.
    Human can: approve, modify, reject, redirect, or switch to AUTONOMOUS.
    Useful for: learning the system, debugging workflow issues, high-stakes tasks,
      tasks where human domain knowledge is needed mid-execution.

  Mode field in FSM: orchestrator::Fsm::mode: ExecutionMode (AUTONOMOUS | INTERACTIVE)
  Gate behavior lookup: rules::GatePolicy::should_pause(mode, gate_type, risk_level) -> bool

  Risk levels per gate:
    LOW:    MEMORIZING -> next phase (auto in both modes)
    MEDIUM: PLANNING -> TESTING_FIRST, EXECUTING -> AUDITING (auto in AUTONOMOUS, pause in INTERACTIVE)
    HIGH:   dangerous actions, external API calls, file deletion (pause in both modes, auditor reviews)

7.1 The Full Cycle (human touches only step 1 in AUTONOMOUS):

  FSM states (revised 2026-04-05):
    IDLE -> PLANNING -> FEASIBILITY_PROBE -> TESTING_FIRST -> EXECUTING -> AUDITING -> MEMORIZING -> COMPLETE -> IDLE

  1. HUMAN INPUT: "Build feature X" or "Fix bug Y"
  2. RESEARCH (Research Agent + GRC — see PART 23):
     - Decompose task into capability requirements
     - Per capability: search web, papers, registries for SOTA approaches
     - Rank alternatives by evidence quality (benchmarks > docs > blogs > training)
     - Output: structured Research Report with grounded alternatives
  3. PLAN CREATION (PLANNING state):
     - Takes Research Report as grounded input (verified facts only)
     - Vertical slices (each phase = working testable unit)
     - Each phase small and targeted
     - GRC runs observe -> hypothesize -> verify per step
     - Grounding sweep: all claims verified against Research Report
     - Adversarial review by auditor
  4. FEASIBILITY PROBE (FEASIBILITY_PROBE state — see PART 25):
     - Per NOVEL step: generate stub (< 50 lines) + test assertion
     - Execute stubs empirically — does the approach actually work?
     - PASS: step is feasibility-grounded, proceed
     - FAIL: reject step, loop back to PLANNING with alternative
     - Evidence artifact: stub_results.msgpack
  5. PER-PHASE EXECUTION LOOP:
     a. TESTING_FIRST: write tests for this phase
     b. EXECUTING: implement to pass tests
     c. AUDITING: adversarial review + validation pipeline
     d. If BLOCK: back to EXECUTING with specific fixes
     e. If PASS: MEMORIZING -> next phase
  6. DANGEROUS ACTION GATING:
     - Delete, overwrite, force-push: BLOCKED by rules engine
     - Another agent (auditor or dedicated safety agent) reviews
     - TDD verification: deterministic script confirms safety
     - Only then: action allowed
  7. COMPLETION:
     - All phases done
     - Full validation pipeline passes
     - Git commits made
     - Session ends, IDLE state

7.2 Git Integration (git2 crate):
  Auto-commit after each verified phase completion
  Auto-grep history when regression reported
  Auto-gitignore heavy data files (configurable patterns)
  Branch per plan (feature branches)
  Commit messages generated from phase outcomes (deterministic, not LLM prose)

7.3 Validation Pipeline:
  Tier 1: Determinism (same input = same output, verified mathematically)
  Tier 2: Quality (AST analysis, code smells, test quality, branch coverage)
  Tier 3: Unit tests
  Tier 4: Integration/contract tests
  Tier 5: Stress/adversarial tests

  All run by auditor agent. Main executor NEVER runs its own tests.
  Results are deterministic and machine-verifiable.
  Even LOC counts are verified deterministically.


PART 8: RULES ENGINE (NEW — PART OF D1)

Purpose: Enforce deterministic behavior on LLMs without consuming tokens on rules
that should be enforced by code.

8.1 Rule Types:
  STRUCTURAL: code architecture rules (SOLID, DI, no God classes)
  SECURITY:   no eval(), no unsanitized input, OWASP compliance
  TRADING:    no lookahead bias, temporal leakage prevention, commission modeling
  WORKFLOW:   FSM state constraints, tool access per phase
  CUSTOM:     per-project rules defined in elai_cc.toml

8.2 Enforcement Mechanism:
  Rules are Rust functions, not LLM prompts.
  PreToolUse hook: check action against active rules -> ALLOW/BLOCK/WARN
  PostToolUse hook: check output against active rules -> flag violations
  Rules engine evaluates deterministically — no LLM in the loop.

8.3 Phase-Aware Rules:
  PLANNING:  enforce grounding rules (no unverified claims)
  TESTING:   enforce test quality rules (branch coverage, no happy-path-only)
  EXECUTING: enforce code quality rules (SOLID, no lazy code, no TODO)
  AUDITING:  enforce adversarial rules (must find at least N issues per review)

8.4 Rule Inheritance:
  Global rules (always active) + phase rules + project-specific rules
  Trading rules active when editing trading code (file-path matching)
  Security rules escalated for auth/crypto code
  Domain rules configurable per project

PART 15: PIPELINE FACTORY ARCHITECTURE (NEW — 2026-04-04)

Purpose: elai_cc is not a code assistant. It is a universal automation engine.
The user provides ANY goal — "build a SaaS", "create a trading bot", "generate animation sprites",
"set up CI/CD", "analyze this dataset". The system DESIGNS the pipeline, BUILDS it, then
EXECUTES it — autonomously. The LLM handles creative and written work. Everything else is
deterministic infrastructure. The less tokens wasted on things code can enforce, the better.
The system creates its own sub-pipelines when needed (e.g., animation task spawns a sprite
generation pipeline, which identifies required models and programs automatically).

15.1 Three-Layer Architecture:

  L1 — PIPELINE DESIGNER (LLM-driven, GRC-grounded):
    Input: human task description ("I want a SaaS for X")
    Process:
      1. GRC decomposes task into sub-questions (observe step)
      2. Each sub-question answered via VERIFIED sources:
         - What components are needed? (web search for best practices)
         - What models are needed? (knowledge engine query)
         - What programs/tools are required? (tool registry lookup)
         - What rules apply to this domain? (rules engine query + web search)
         - What pipeline patterns exist for this type of task? (template library)
      3. If a needed rule set doesn't exist (e.g., "SaaS rules"):
         - GRC researches best practices (web search, papers, standards)
         - Proposes rule set with grounding citations
         - Auditor reviews proposed rules
         - Rules installed in project's elai_cc.toml
      4. Pipeline spec assembled from verified components ONLY
    Output: PipelineSpec (TOML/msgpack) — phases, steps, dependencies, model assignments,
            rule sets, tool requirements, resource estimates

  L2 — PIPELINE BUILDER (deterministic, no LLM):
    Input: PipelineSpec from L1
    Process:
      1. Validates all referenced components exist (models available, tools registered)
      2. Creates FSM state definitions for each phase
      3. Configures agent roles and model assignments per phase
      4. Installs domain-specific rules from PipelineSpec
      5. Estimates resource requirements (VRAM, disk, network)
      6. Generates dependency graph (which steps parallel, which serial)
      7. Creates test harness skeleton (TESTING_FIRST templates)
    Output: ExecutablePipeline — ready for L3, stored in .elai_cc/pipelines/{id}/

  L3 — PIPELINE EXECUTOR (current design — FSM + agents + rules):
    Input: ExecutablePipeline from L2
    Process: existing autonomous execution loop (PART 7)
    Output: completed task, committed code, validation results

15.2 Self-Extending Rules Engine:

  Current design: rules are predefined (STRUCTURAL, SECURITY, TRADING, WORKFLOW, CUSTOM).
  Extension: L1 can CREATE new rule categories at runtime.

  Rule creation protocol:
    1. L1 identifies domain needs ("this SaaS needs GDPR compliance rules")
    2. GRC researches requirements (web search, standards docs, papers)
    3. Proposed rules written as Rust-evaluable predicates:
       - File-path matching (which files these rules apply to)
       - AST patterns (what code structures to check)
       - Build/test requirements (what must pass)
    4. Auditor agent reviews proposed rules for:
       - Soundness (does the rule catch what it claims?)
       - Completeness (are edge cases covered?)
       - Performance (does evaluation add latency?)
    5. Rules saved to .elai_cc/rules/{domain}/ and registered in config
    6. L3 enforces them like built-in rules — no distinction at runtime

  Rule templates (shipped with elai_cc):
    SaaS:       auth, rate limiting, data validation, API versioning, GDPR
    Trading:    no lookahead, temporal leakage, commission modeling, drawdown limits
    Game:       frame budget, memory pools, deterministic physics, asset pipeline
    Data:       schema validation, null handling, encoding, pipeline idempotency
    Security:   OWASP top 10, injection prevention, crypto best practices
    ML:         train/test split, data leakage, reproducibility, metric tracking
    Custom:     user-defined via elai_cc.toml

15.3 Pipeline Templates (accelerate L1):

  Completed pipelines become reusable templates.
  Stored in .elai_cc/templates/{type}/ as PipelineSpec + outcomes.
  L1 queries template library before designing from scratch.
  Templates are versioned — improvements propagate to future uses.

  Example template: "rust-library"
    Phase 0: scaffold (Cargo.toml, crate structure, CI config)
    Phase 1: core types + traits (TESTING_FIRST)
    Phase 2: implementation (per-module vertical slices)
    Phase 3: integration tests + benchmarks
    Phase 4: documentation + examples
    Rules: STRUCTURAL + SECURITY
    Models: executor=gemma4, auditor=deepseek-r1

15.4 Pipeline Composition:

  Complex tasks decompose into multiple pipelines.
  "Build a SaaS" = pipeline(backend-api) + pipeline(frontend) + pipeline(infrastructure)
  Orchestrator manages inter-pipeline dependencies.
  Each sub-pipeline runs independently with its own FSM.
  Results feed into parent pipeline via structured handoff.

15.5 External Tool Integration:

  L1 can identify that a pipeline needs external tools:
    - "Animation sprites need Aseprite or Pixelorama"
    - "3D models need Blender CLI"
    - "PDF generation needs wkhtmltopdf or weasyprint"
  Tool availability check: is the tool installed? version? path?
  If not available: L1 proposes installation or alternative.
  Tool execution wrapped in tools/ crate with timeout, error handling, output parsing.
  External tool outputs validated by auditor (did the sprite generate correctly?).


15.6 Model Capability Registry:

  L1 needs to answer: "what model does this task need?"
  Registry stores per-model capabilities as structured data:
    model_id: "gemma4:31b"
    capabilities: [code_generation, reasoning, instruction_following]
    vram_required: 18000  # MB at Q4
    max_context: 131072
    strengths: [rust, python, structured_output]
    weaknesses: [long_prose, creative_writing]
    layer_config: {dola: false, turboquant: false}  # ollama limitation
    provider: "ollama"

  Population: initial manual config in elai_cc.toml.
  Extension: L1 can query ollama /api/tags to discover available models,
    run a capability probe (small test prompts), and register new models.
  Selection: L1 matches task requirements to model capabilities deterministically.
    Score = sum(capability_match) * context_fit * vram_feasibility.
    No LLM judgment in model selection — pure numeric ranking.

15.7 External Tool Auto-Discovery and Installation:

  L1 identifies external tool requirements. Three resolution levels:
    AVAILABLE: tool found on PATH, version compatible. Use immediately.
    INSTALLABLE: tool exists in package manager (winget, apt, cargo install).
      L1 proposes installation command. User confirms (dangerous action gate).
      After install, tool registered in .elai_cc/tools/{name}.toml.
    UNAVAILABLE: no known install path. L1 proposes alternatives or flags as blocker.

  Tool wrapper contract (tools/ crate):
    fn execute(args) -> ToolResult  // stdout/stderr/exit_code
    fn validate_output(result) -> bool  // domain-specific output check
    fn version() -> SemVer  // compatibility tracking
    timeout: configurable per tool (default 60s, GPU tools 600s)

  Auto-discovery: L1 can query: (a) system PATH, (b) package managers, (c) web search
    for tools that solve a specific capability gap. All proposals go through auditor review.

15.8 Evidence Gate Protocol (DAIRA-derived):

  Every FSM phase transition requires an evidence artifact — not LLM self-assessment.
  This is the single most impactful anti-hallucination mechanism (DAIRA ablation: -11.3pp
  without structured evidence, -8.1pp without runtime data, -5.4pp without FSM gates).

  Gate definitions:
    PLANNING -> TESTING_FIRST:
      Evidence: grounding_sweep_report (all claims in plan classified GROUNDED)
      Gate: zero UNGROUNDED claims remaining
    TESTING_FIRST -> EXECUTING:
      Evidence: test_file_paths[] (tests written and parseable)
      Gate: all tests fail for the right reasons (not syntax errors)
    EXECUTING -> AUDITING:
      Evidence: diff_summary + test_results (tests now pass)
      Gate: at least 1 test flipped from FAIL to PASS
    AUDITING -> MEMORIZING:
      Evidence: audit_report (auditor findings + resolutions)
      Gate: zero BLOCK findings remaining
    MEMORIZING -> next phase or COMPLETE:
      Evidence: changelog_entry + knowledge_engine_updated
      Gate: DKG reflects new code, changelog has entry

  Adaptive context (DAIRA pattern): any evidence-gathering tool that produces
  variable-length output MUST implement adaptive scope reduction.
  Pattern: run -> check size -> if > token_budget * 0.3, reduce scope -> retry.
  Max 3 reduction attempts before escalating to human.

16.1 DAIRA (arxiv 2603.22048v2) — Dynamic Analysis-Enhanced Issue Resolution:
  Core insight: static analysis hits ceiling on complex bugs. Runtime tracing exposes
  implicit type degradations, polymorphic control flows, variable mutations.

  Integration into elai_cc:
    tools/ crate: ADD trace_execution(script, trace_config) -> TraceReport
      - Lightweight tracer (Hunter-based or tracing crate) generates serialized logs
      - TraceReport contains: call stack, variable mutations, type transitions, timing
    reasoning/ GRC observe step: ADD dynamic trace option
      - Current: observe = file reads + grep
      - New: observe can invoke trace_execution for runtime behavior
    orchestrator/ AUDITING state: trace-first debugging protocol
      - Before static analysis, run failing test with tracing enabled
      - Trace output fed to auditor as grounded evidence
      - Auditor reasons from ACTUAL runtime behavior, not inferred behavior
    Validation pipeline: Tier 2 gains trace-based verification
      - Not just "does it compile" but "does it behave correctly at runtime"

  Key metric from paper: 80.8% resolution on medium bugs, 44.4% on hard bugs (SOTA).
  Efficiency: more tool calls BUT -13% to -18% total cost (targeted retrieval).
  Validates: smaller models + better tooling > larger models alone.

  Ablation evidence (cost of skipping GRC steps):
    Without TLSA (semantic trace analysis): -11.3% resolution
    Without DAT (dynamic analysis tool):   -8.1% resolution
    Without TTDW (structured FSM workflow): -5.4% resolution
    Each GRC step has measurable, proven value. Skipping any step is quantifiably worse.

  Generalizable primitive — adaptive overflow loop:
    DAIRA's trace_depth auto-reduces when output exceeds token budget.
    elai_cc should generalize this: ANY variable-output tool (grep, AST scan, trace)
    should have an adaptive scope reduction mechanism.
    Pattern: run tool -> check output size -> if > budget, reduce scope -> retry.
    Implemented as a tools/ crate wrapper: AdaptiveTool<T: Tool> with budget parameter.

PART 17: ADVERSARIAL AUDIT RESULTS (2026-04-05)

  Adversarial auditor ran against proposed additions (SSB, inline validator, two-layer comms,
  context budget allocator, self-improvement loop) plus 3 user concerns (plan robustness,
  multi-project isolation, deterministic plan verification).

  9 BLOCKs found. All accepted and resolved. Key findings:

  BLOCK 1: SQLite WAL single-writer
    Claim: "WAL gives lock-free concurrent reads" — TRUE for reads, FALSE for writes.
    WAL allows only ONE writer at a time. Multiple agents writing = serialized or SQLITE_BUSY.
    Fix: single-writer via tokio::mpsc. See PART 18.
    Sources: sqlite.org/wal.html, berthug.eu SQLITE_BUSY analysis

  BLOCK 2: T3 inline validator latency
    Claim: "1B model on CPU, 200-500ms" — FALSE. CPU inference for code validation
    with 500+ token input = 10-100 seconds, not 200-500ms.
    Fix: kill T3 model. Use pattern-match heuristic library or batch at superstep boundary.
    Sources: arxiv 2511.07425 (CPU inference benchmarks), Intel IPEX data

  BLOCK 3: DAIRA TLSA mapping incorrect
    Claim: "T1/T2/T3 maps to DAIRA's TLSA" — WRONG. TLSA is semantic transformation of
    runtime traces (extra LLM call, three-part structured report). Inline validator is
    static analysis. Conflating them misleads implementors.
    Fix: rename to "tiered static analysis hook." DAIRA TLSA correctly mapped in GRC observe.
    Source: daira-interface.md line 59

  BLOCK 4: BinaryOp channel non-determinism
    Claim: "same writes = deterministic" — FALSE for non-commutative operators with concurrent writes.
    Write order depends on OS scheduler, not logical causality.
    Fix: drop BinaryOp channels entirely. Use only LastValue + Topic (commutative append).
    Sources: LangGraph race condition issue #1112, LangGraph channels reference

  BLOCK 5: Multi-project isolation missing
    No project_id in SSB schema. PID reuse on Windows. No cross-contamination prevention.
    Fix: project_id namespace, physical isolation. See PART 24.

  BLOCK 6: Self-improvement reward hacking
    Auto-downgrading rules by false positive rate is dangerous. Security rules that fire
    rarely but catch catastrophic bugs would be downgraded.
    Fix: never auto-adjust security/safety/architecture rules. Human approval required.
    Source: Darwin Godel Machine (arxiv 2505.22954) — documents reward hacking in self-improving systems

  BLOCK 7: Plan feasibility gap
    Grounding sweep checks existence ("does this API exist?") not feasibility ("will this work?").
    Fix: add FEASIBILITY_PROBE FSM state. See PART 25.
    Source: DAIRA Phase 1 pattern (edge case scripts before diagnosis)

  BLOCK 8: Payload BLOB schema
    Opaque msgpack BLOB with no schema enforcement makes debugging and migration painful.
    Fix: typed action_type enum + normalized junction table ssb_files(seq, file_path).

  BLOCK 9: Context budget allocator terminal condition missing
    No specification for what happens after 3 reductions fail.
    Fix: ESCALATE (interactive) or SPLIT_TASK (autonomous). Floors on all categories.

  WARNs (accepted, documented):

    - Superstep boundary condition ambiguous — define precisely when barrier fires
    - Novel task types with no template have unknown failure rate — mitigated by Research Agent

PART 18: SHARED STATE BOARD (SSB) — INTER-AGENT COMMUNICATION

  Purpose: replace vague "msgpack over session bus" with concrete, proven implementation.
  SSB is the single source of truth for all agent activity within a project.

  18.1 Architecture:
    Single SQLite database in WAL mode, per-project.
    All agents write to SSB via a single-writer tokio::mpsc channel.
    All agents read from SSB via read-only connections (WAL lock-free reads).
    Append-only — rows are never updated or deleted during a session.

  18.2 Single-Writer Pattern:
    CRITICAL: SQLite WAL does NOT allow concurrent writers. One writer at a time.
    All SSB writes routed through a dedicated writer task:

    Rust pseudocode:
      let (tx, mut rx) = tokio::sync::mpsc::channel::<SsbEntry>(1024);
      tokio::spawn(async move {
          while let Some(entry) = rx.recv().await {
              db.execute_insert(&entry);
              validator.check(&entry);  // tiered static analysis fires here
          }
      });
      // Each agent gets tx.clone() — sends are non-blocking

    Throughput: SQLite handles ~50,000 serial inserts/second.
    Agent write rate: ~1-10 writes/second total. No bottleneck.
    The serialization gives total ordering for free (seq autoincrement).

  18.3 Schema:
    CREATE TABLE ssb (
        seq           INTEGER PRIMARY KEY AUTOINCREMENT,
        project_id    TEXT NOT NULL,
        session_id    TEXT NOT NULL,
        agent_id      TEXT NOT NULL,
        superstep     INTEGER NOT NULL,
        action_type   TEXT NOT NULL CHECK(action_type IN (
            'file_write','file_read','tool_result','test_outcome',
            'finding','claim','checkpoint','model_swap','phase_transition'
        )),
        payload       BLOB NOT NULL,
        created_at    INTEGER NOT NULL
    );

    CREATE TABLE ssb_files (
        seq       INTEGER REFERENCES ssb(seq),
        file_path TEXT NOT NULL
    );
    CREATE INDEX idx_ssb_project ON ssb(project_id);
    CREATE INDEX idx_ssb_session ON ssb(session_id);
    CREATE INDEX idx_ssb_superstep ON ssb(superstep);
    CREATE INDEX idx_ssb_files_path ON ssb_files(file_path);

  18.4 Agent Usage:
    Write: every tool call result, file edit, GRC conclusion, phase transition -> SSB row.
    Read: agents query SSB filtered by file overlap (JOIN ssb_files WHERE file_path IN (...)).
    Conflict detection: orchestrator queries SSB before spawning agent:
      SELECT DISTINCT agent_id FROM ssb_files WHERE file_path IN (?)
      AND session_id != ? AND superstep = ?
    If conflict: block agent spawn, report to orchestrator.

  18.5 Testable Invariants:
    - ssb.seq is monotonically increasing (total ordering guaranteed by autoincrement)
    - All writes visible to all readers within 1ms (WAL mode guarantee for reads)
    - No two agents write to same file simultaneously (orchestrator prevents via SSB query)
    - Single-writer task processes all writes (no direct DB access from agents)


PART 19: TIERED STATIC ANALYSIS HOOK

  Purpose: real-time validation of every agent action. NOT a full LLM agent.
  NOT DAIRA's TLSA (that is GRC observe + trace_execution, correctly placed in PART 16.1).
  This is a static analysis cascade triggered by the SSB single-writer task.

  19.1 Three Tiers:

    T1 — RULES (deterministic, <1ms):
      Fires on: EVERY SSB write. Zero exceptions.
      Implementation: Rust functions from rules/ crate.
      Checks: SOLID violations, security patterns (eval, unsanitized input), workflow constraints.
      Output: ALLOW | WARN | BLOCK with rule_id and reason.

    T2 — AST (deterministic, <10ms for files <5000 lines):
      Fires on: action_type = 'file_write' only.
      Implementation: tree-sitter parse + pattern matching.
      Checks: syntax validity, import correctness, dead code, lazy code (pass bodies, TODO).
      Circuit breaker: files > 5000 lines degrade to T1-only (skip T2).
      Output: ALLOW | WARN | BLOCK with ast_location and reason.

    T3 — PATTERN MATCH (deterministic, <5ms):
      Fires on: T1 or T2 return WARN (ambiguous cases only).
      Implementation: pattern-match library of known-ambiguous code patterns.
      NO LLM. Deterministic heuristic lookup.
      Examples: "function > 200 lines" -> WARN:complexity, "catch Exception: pass" -> BLOCK:swallow.
      Output: ALLOW | BLOCK with pattern_id and reason.
      NOTE: original 1B model on CPU proposal REJECTED by auditor (latency 10-100s, not 200-500ms).

  19.2 BLOCK Handling:
    BLOCK from any tier -> SSB entry with action_type='finding'.
    Working agent receives finding on next SSB read.
    Orchestrator creates fix task if agent does not self-correct within 2 tool calls.

  19.3 Testable Invariants:
    - Every SSB write triggers T1 within 1ms
    - T2 only fires on 'file_write' actions
    - T3 only fires when T1 or T2 return WARN
    - T3 is deterministic (pattern match, no model)
    - BLOCK from any tier is recorded in SSB as 'finding'
    - No LLM in the validation hot path


PART 20: TWO-LAYER COMMUNICATION MODEL

  Purpose: deterministic macro-level orchestration with flexible micro-level coordination.
  Combines LangGraph's BSP superstep model with SSB for intra-phase communication.

  20.1 Layer 1 — BSP Supersteps (phase-level, deterministic):

    Adapted from LangGraph Pregel model (verified from source: pregel/_loop.py:461-580).
    Phase transitions are superstep boundaries. All channel writes applied atomically.

    Rust pseudocode:
      loop {
          let tasks = prepare_next_tasks(&checkpoint, &channels, &nodes);
          if tasks.is_empty() { break; }

          // Execute all tasks for this superstep (sequential on GPU due to VRAM)
          let writes = execute_tasks(tasks, &model_pool, &ssb);

          // Apply all writes atomically (deterministic)
          let updated_channels = apply_writes(&mut checkpoint, &mut channels, writes);

          // Checkpoint (crash-safe resume point)
          save_checkpoint(&checkpoint, &channels);

          // Check evidence gates before transitioning
          if !evidence_gate_passes(&checkpoint, &channels) {
              continue; // block transition, create remediation tasks
          }

          superstep += 1;
      }

  20.2 Layer 2 — SSB Intra-Step Communication:

    Within a superstep, agents communicate via SSB (PART 18).
    SSB writes are ordered by seq (autoincrement via single-writer task).
    Agents can read SSB in real-time for awareness of what other agents are doing.
    Channel updates happen ONLY at superstep boundary (atomic, deterministic).

    This gives: real-time awareness (agents read SSB) + deterministic macro state
    (channels updated atomically between supersteps).

  20.3 Channel Types (from LangGraph, in Rust — BinaryOp DROPPED):

    LastValue:
      Stores single value. Last writer wins.
      Deterministic: write order defined by SSB seq.
      Used for: current_phase, active_agent, latest_test_result.

    Topic (accumulate: bool):
      Stores append-only list of values.
      accumulate=true: values persist across supersteps.
      accumulate=false: values cleared at superstep boundary.
      Used for: findings (accumulate), test_results (accumulate), notifications (clear).

    BinaryOp: DROPPED.
      Reason: non-commutative operators with concurrent writes = non-deterministic result.
      LangGraph's own issue tracker documents race conditions with this channel type.
      Aggregation done instead by Rust functions at superstep boundary over Topic contents.

  20.4 Testable Invariants:
    - Channel state at superstep N is deterministic given state at N-1 and writes from N
    - SSB reads within a superstep never see writes from future supersteps
    - Checkpoint at superstep boundary contains full channel state (crash-safe)
    - Only LastValue and Topic channel types exist (no BinaryOp)
    - Aggregation computed by deterministic Rust functions, not channel operators


PART 21: CONTEXT BUDGET ALLOCATOR

  Purpose: compute per-agent context windows before each model invocation.
  Each model has different context limits. Each agent needs different context.
  Allocator ensures no agent exceeds its model's context window.

  21.1 Budget Computation:

    per_agent_context_budget(agent_role, phase, ssb) -> ContextWindow:
      total = model_registry[agent_role].max_context
      output_reserve = 2000  // FLOOR: never starve response space

      // Fixed allocations (measured in tokens)
      system_prompt = grc_structured_prompt(agent_role, phase)    // ~500-1500 tokens
      rules = active_rules(phase, agent_role)                     // ~200-800 tokens
      phase_spec = current_phase_spec()                           // ~300-600 tokens

      // Variable allocations (adaptive, with FLOORS)
      remaining = total - system_prompt - rules - phase_spec - output_reserve
      ssb_budget = max(remaining * 0.3, 200)       // FLOOR: 200 tokens minimum
      code_budget = max(remaining * 0.5, 500)       // FLOOR: 500 tokens minimum
      grc_budget = max(remaining * 0.2, 500)        // FLOOR: 500 tokens minimum

      // Adaptive reduction if total exceeds remaining
      ssb_entries = ssb.query(files_overlap=agent.files, budget=ssb_budget)
      code_context = knowledge.query(agent.task, budget=code_budget)
      grc_history = agent.checkpoint.grc_history(budget=grc_budget)

      return ContextWindow { system_prompt, rules, phase_spec, ssb_entries, code_context, grc_history }

  21.2 Adaptive Reduction Protocol (DAIRA pattern):

    If any category overflows its budget:
      Attempt 1: filter by relevance score (file overlap count for SSB, BM25 score for code)
      Attempt 2: reduce granularity (function signatures instead of full bodies)
      Attempt 3: reduce scope (fewer files, most recent SSB entries only)

    TERMINAL CONDITION (after 3 reductions fail):
      INTERACTIVE mode: ESCALATE to human with context budget report
      AUTONOMOUS mode: SPLIT_TASK — break current task into smaller sub-tasks
                       that individually fit in context. Each sub-task gets its
                       own agent invocation with fresh budget.

    NEVER silently truncate context. Every reduction logged to SSB.

  21.3 File Overlap Score Definition (resolves auditor WARN):
    score(ssb_entry, agent_files) = |intersection(ssb_entry.files, agent_files)| / |agent_files|
    Range: [0.0, 1.0]. 1.0 = SSB entry touches all files the agent is working on.
    Deterministic: same inputs always produce same score. No model involved.

  21.4 Code Context Chunk Size Limit:
    Maximum single chunk: 2000 tokens (prevents one large file from saturating budget).
    If file exceeds 2000 tokens: return function signatures + relevant function bodies only.
    Selection: BM25 query against agent's current task description.

  21.5 Testable Invariants:
    - sum(all_allocations) <= model.max_context for every agent invocation
    - output_reserve >= 2000 tokens always
    - SSB entries >= 200 tokens always (floor)
    - GRC history >= 500 tokens always (floor)
    - No silent truncation (every reduction logged to SSB)
    - Terminal condition always fires (never infinite reduction loop)


PART 22: SELF-IMPROVEMENT LOOP

  Purpose: pipeline outcomes feed back into template ranking and rule weighting.
  All modifications are data changes (SQLite/TOML), not code changes.
  All modifications are versioned and reversible.
  NO LLM in the feedback loop — pure arithmetic.

  22.1 Metrics Collected Per Pipeline Execution:
    PipelineOutcome {
        template_id: String,
        project_id: String,
        phases_total: u32,
        phases_passed_first_try: u32,
        audit_findings_total: u32,
        audit_findings_block: u32,
        test_coverage_final: f32,
        time_to_complete_seconds: u64,
        tokens_consumed_total: u64,
        human_interventions: u32,
        rules_triggered: Vec<(RuleId, TriggerCount, CatchRate)>,
    }

  22.2 Template Ranking Formula:
    score = (phases_passed_first_try / phases_total) * 0.4
          + test_coverage_final * 0.3
          + (1.0 - audit_findings_block / max(audit_findings_total, 1)) * 0.2
          + (1.0 - tokens_consumed_total / max_expected_tokens) * 0.1

    Templates with higher scores preferred by L1 Pipeline Designer.
    Templates with score < 0.3 flagged for revision (not auto-deleted).
    Minimum 3 executions required before ranking is applied.

  22.3 Rule Weight Adjustment:

    SAFETY RULES (NEVER auto-adjusted):
      Categories: Security, Safety, Architecture.
      Any weight change requires HUMAN APPROVAL in both AUTONOMOUS and INTERACTIVE modes.
      Rationale: rules that fire rarely but catch catastrophic bugs must never be downgraded.
      Source: Darwin Godel Machine (arxiv 2505.22954) — documents reward hacking risk.

    ADJUSTABLE RULES (auto-adjusted with guardrails):
      Categories: Style, Custom.
      High false positive rate (>80% over 10+ executions) -> flag for REFINEMENT.
      REFINEMENT means: make the rule more precise, NOT remove or downgrade it.
      "Noisy rule" and "wrong rule" are different diagnoses with different fixes.

  22.4 Configuration Versioning:
    All rule weight changes stored in .elai_cc/projects/{id}/rule_history.db.
    Schema: rule_id, old_weight, new_weight, reason, timestamp, human_approved(bool).
    Rollback: any change can be reverted by restoring previous weight from history.

  22.5 Testable Invariants:
    - Template score changes only from actual execution outcomes, never from LLM judgment
    - Rule weight changes for Security/Safety/Architecture require human_approved=true
    - Minimum 3 (templates) or 10 (rules) executions before any automatic adjustment
    - All configuration changes are versioned in rule_history.db
    - Human can override any automatic weight/rank change


PART 23: RESEARCH AGENT

  Purpose: structured SOTA discovery for novel task types. Equivalent to "Gemini Deep Research"
  but deterministic — output is structured data, not prose. Fires during L1 Pipeline Designer
  BEFORE plan assembly. Makes the system domain-agnostic for novel task types.

  23.1 Agent Configuration:
    Role: researcher
    Model: cloud API preferred (broad knowledge + web access) or Gemma4 local with web search tool
    GRC budget: high (10/1200) — deep exploration needed
    Trigger: L1 encounters a capability requirement with no template match
    Permissions: NETWORK (web search), FILESYSTEM (read-only)

  23.2 Process:
    1. DECOMPOSE task into capability requirements
       "Build a SaaS for X" -> [auth, database, API, frontend, deployment, monitoring]
       "Create animation sprites" -> [asset_pipeline, sprite_format, animation_tool, export]

    2. Per capability, STRUCTURED SEARCH:
       a. Package registries (crates.io, npm, pypi) for existing solutions
       b. Web search for SOTA approaches (arxiv, official docs, benchmark comparisons)
       c. Template library for prior successful implementations
       d. Model capability registry for required model types

    3. RANK alternatives by evidence quality:
       BENCHMARK (published numbers, reproducible)          -> confidence: VERIFIED
       OFFICIAL_DOCS (vendor-maintained, version-specific)  -> confidence: HIGH
       BLOG_POST (community-tested, may be outdated)        -> confidence: MEDIUM
       TRAINING (from model's training data, not verified)  -> confidence: UNCERTAIN

    4. Output: RESEARCH REPORT (structured, not prose)
       Per capability: {
           capability: String,
           alternatives: [{
               name: String,
               evidence_level: BENCHMARK | OFFICIAL_DOCS | BLOG_POST | TRAINING,
               source_url: String,
               pros: Vec<String>,
               cons: Vec<String>,
               integration_complexity: LOW | MEDIUM | HIGH,
           }],
           recommendation: String,
           confidence: VERIFIED | HIGH | MEDIUM | UNCERTAIN,
       }

  23.3 Evidence Gate:
    Research Report must have >= 1 BENCHMARK or OFFICIAL_DOCS grounded alternative per capability.
    If all alternatives for a capability are TRAINING-level:
      -> capability flagged as HIGH_RISK
      -> requires human input in BOTH modes (autonomous and interactive)
    This prevents the system from planning with unverified approaches.

  23.4 Integration with L1:
    Research Report feeds L1 Pipeline Designer as grounding input.
    L1 can ONLY reference alternatives from the Research Report.
    L1 cannot introduce new approaches not in the report.
    This closes the loop: verified research -> grounded planning -> feasibility testing.

  23.5 Testable Invariants:
    - Every capability in the Research Report has >= 1 alternative
    - Alternatives with evidence_level=TRAINING are flagged as UNCERTAIN
    - HIGH_RISK capabilities (all TRAINING) require human input
    - L1 cannot reference approaches not in the Research Report
    - Research Report is stored as evidence artifact (structured msgpack)


PART 24: PROJECT ISOLATION NAMESPACE

  Purpose: prevent cross-contamination between projects. Physical separation of all state.
  Each project gets its own SSB, knowledge engine, rules, and checkpoints.

  24.1 Project Identity:
    project_id: UUID v4 (generated at project creation)
    Stored in: .elai_cc/projects/{project_id}/project.toml
    Contains: name, created_at, status (active|paused|completed), resource_requirements

  24.2 Session Identity (corrected — no PID reuse):
    session_id: {project_id}:{pid}:{timestamp_ms}
    PID reuse on Windows is a known issue (PIDs recycle after ~65536 processes).
    Adding timestamp_ms eliminates collision probability.

  24.3 Directory Structure:
    .elai_cc/
      projects/
        {project_id}/
          project.toml
          ssb.db
          knowledge.db
          index/              (tantivy)
          rules/
          templates/
          sessions/
            {session_id}/
              checkpoint/
              agents/
          pipelines/
            {pipeline_id}/

      global/
        model_registry.toml   (shared across projects)
        rule_templates/       (global templates, copied into project on use)
        pipeline_templates/   (global templates)
        metrics/              (cross-project self-improvement metrics)

  24.4 Resource Scheduling:
    Only one project active on GPU at a time.
    Queue is FIFO with priority override.

    ProjectQueue {
        active: Option<ProjectId>,
        waiting: VecDeque<ProjectId>,
        cold: HashMap<ProjectId, ProjectState>,
    }

    Project switch protocol:
      1. Checkpoint active project (all agent state saved)
      2. Unload models from GPU
      3. Load new project state from disk
      4. Load new project's required models
      5. Resume new project from checkpoint
    Switch cost: ~30-60 seconds (model load). Acceptable for project-level granularity.
    Cold projects: on-disk only, no VRAM or RAM residency. Can be resumed at any time.

  24.5 Testable Invariants:
    - No two projects share an SSB database (physical file isolation)
    - No two projects share a knowledge engine database
    - session_id contains project_id (cross-project session collision impossible)
    - Only one project holds GPU resources at a time
    - Project switch always checkpoints before unloading


PART 25: FEASIBILITY_PROBE FSM STATE

  Purpose: empirically test that novel plan steps actually work before committing to
  full implementation. DAIRA Phase 1 pattern: generate edge case scripts BEFORE diagnosis.
  Catches "plan looks good but approach doesn't work" failure mode.

  25.1 FSM Position:
    PLANNING -> FEASIBILITY_PROBE -> TESTING_FIRST -> EXECUTING -> ...

  25.2 What Gets Probed:
    Only NOVEL steps — steps that introduce something not in the DKG or template library.
    Novel detection (automated):
      - References a library not in Cargo.toml/package.json? -> NOVEL
      - References an API not in knowledge engine? -> NOVEL
      - References a tool not on PATH? -> NOVEL
      - References an approach not in any prior template? -> NOVEL
    Non-novel steps ("create file", "add import", "write function") are NOT probed.

  25.3 Probe Process:
    Per novel step:
      1. Executor generates minimal stub implementation (< 50 lines)
      2. Executor generates single test assertion that proves the approach works
      3. Auditor reviews stub: "Is this actually testing feasibility, or is it trivial?"
      4. Execute stub + assertion
      5. Record result in SSB as action_type='test_outcome'

    Example:
      Plan step: "Use rusqlite for SSB storage"
      Stub: create in-memory DB, create table, insert row, query row, assert value matches
      Result: PASS -> rusqlite works as expected, proceed

      Plan step: "Use vllm-hook for DoLa on Gemma4"
      Stub: import vllm, load model, register activation hook, run inference
      Result: FAIL (vllm-hook doesn't support Gemma4 yet) -> reject step, find alternative

  25.4 Evidence Gate:
    FEASIBILITY_PROBE -> TESTING_FIRST:
      Evidence: stub_results.msgpack (stub code + pass/fail + error per novel step)
      Gate: all stubs pass OR alternative approaches found and re-probed for failing stubs
      Zero unresolved feasibility failures remaining

  25.5 Loop Back:
    If a stub fails:
      1. Research Agent searches for alternative approach
      2. L1 revises plan step with alternative
      3. New stub generated and probed
      4. Max 3 alternatives per step. After 3 failures: ESCALATE to human.

  25.6 Tools Available in FEASIBILITY_PROBE State:
    ALLOWED: file write (stub only, < 50 lines), bash (execute stub), web search
    BLOCKED: full file edit, git commit, production file modification
    Stubs are written to .elai_cc/projects/{id}/probes/ (isolated, not in project source)

  25.7 Testable Invariants:
    - Only novel steps are probed (non-novel steps skip)
    - Stubs are < 50 lines (enforced by rules engine)
    - Stubs are written to probes/ directory, not project source
    - TESTING_FIRST is blocked until all novel steps have passing probes
    - Max 3 alternative attempts per step before escalation


PART 26: PLAN ELABORATION PIPELINE (4-STAGE)

  Purpose: make plan building robust for ANY task type. The plan elaboration is not a single
  step — it is a 4-stage pipeline where each stage adds a different kind of validation.

  26.1 Stage 1 — RESEARCH (Research Agent + GRC):
    Input: human task description
    Process: decompose into capabilities, SOTA search per capability, rank alternatives
    Output: Research Report (structured, grounded)
    Validation: evidence quality (>= 1 BENCHMARK or OFFICIAL_DOCS per capability)
    GRC role: enforces grounding on every claim. No training-only claims pass.
    See PART 23 for full Research Agent specification.

  26.2 Stage 2 — PLAN ASSEMBLY (L1 Pipeline Designer + GRC):
    Input: Research Report (grounded facts only)
    Process: assemble phases, steps, dependencies, model assignments, rule sets
    Per step: GRC runs observe -> hypothesize -> verify
    Grounding sweep: all claims verified against Research Report
    Adversarial review: auditor checks plan for gaps, contradictions, missing steps
    Output: PipelineSpec (TOML) with every step grounded
    Validation: zero UNGROUNDED claims remaining

  26.3 Stage 3 — STRUCTURAL VALIDATION (L2 Pipeline Builder — NO LLM):
    Input: PipelineSpec from Stage 2
    Process (pure Rust, deterministic):
      - All referenced tools exist on PATH
      - All models referenced are in model registry
      - Dependency graph has no cycles
      - Resource estimates fit hardware (VRAM, disk)
      - Rule sets referenced exist or can be created
      - Test harness skeleton generated
      - FSM state definitions generated
    Output: ExecutablePipeline or REJECT with specific failure reason
    Validation: same input always produces same output (deterministic by construction)

  26.4 Stage 4 — FEASIBILITY PROBE (Executor Agent — empirical):
    Input: ExecutablePipeline from Stage 3
    Process: per novel step, generate stub + assertion, execute
    PASS: step is feasibility-grounded
    FAIL: reject step, loop back to Stage 2 with alternative
    Output: validated ExecutablePipeline ready for execution
    See PART 25 for full FEASIBILITY_PROBE specification.

  26.5 Key Design Decisions:

    Q: "Does the plan-building phase need to know how the workflow works?"
    A: NO — and this is by design. L1 produces a PipelineSpec (WHAT to do). L2 translates it
       to an ExecutablePipeline (HOW to do it using the workflow's FSM/agents/rules). The LLM
       in L1 never sees the internal workflow machinery. The LLM proposes WHAT, deterministic
       code decides HOW. This is safe: the LLM cannot break the workflow by proposing bad HOW.

    Q: "What is GRC's role in planning?"
    A: GRC is the reasoning ENGINE, not a pipeline stage. It is the protocol that agents use
       to reason at every stage. Think of GRC as the language, not the speaker. Every hypothesis
       must cite a source. Every claim must be grounded. GRC enforces this structurally — the
       agent cannot skip grounding without the GRC engine rejecting the step.

    Q: "Can this handle ANY task type?"
    A: Stage 1 (Research Agent) makes it domain-agnostic. Without it, the system can only plan
       tasks it has templates for. With it, novel task types get proper SOTA research before
       planning begins. The Research Agent is what makes this a universal automation engine
       rather than a template-driven code generator.

  26.6 Testable Invariants:
    - Every plan that reaches TESTING_FIRST has passed all 4 stages
    - Stage 3 is fully deterministic (no LLM, same input = same output)
    - Stage 4 catches "plan looks good but doesn't work" before implementation begins
    - Research Report is required input for Stage 2 (L1 cannot plan without it)
    - Loop-back from Stage 4 to Stage 2 is bounded (max 3 alternatives per step)


PART 12 ADDENDUM: RISK REGISTER (new risks from adversarial audit, 2026-04-05)

  R10 (MEDIUM — NEW): SSB write throughput ceiling
    Single-writer pattern limits to ~50K inserts/sec.
    Risk: if agent write rate exceeds this (unlikely but possible with heavy tracing).
    Mitigation: measured ceiling is 50x expected rate. Monitor write queue depth.
    Fallback: batch writes (collect N entries, insert in single transaction).

  R11 (LOW — NEW): Feasibility probe false negatives
    A stub may pass but the full implementation may fail (stub too simple).
    Mitigation: auditor reviews stub quality. Stub must test the NOVEL aspect, not boilerplate.
    Fallback: if implementation fails despite passing probe, add to gotchas.md and refine
    probe templates for that approach type.

  R12 (MEDIUM — NEW): Research Agent quality for novel domains
    First-of-kind task types have no template AND sparse web evidence.
    Mitigation: Research Report flags capabilities with all-TRAINING evidence as HIGH_RISK.
    Fallback: human input required for HIGH_RISK capabilities in both modes.

  R13 (LOW — NEW): Project switch latency
    Model unload + load takes ~30-60 seconds. Frequent project switches waste time.
    Mitigation: FIFO queue with priority override. Batch work per project.
    Fallback: dedicated GPU per project if hardware expands beyond 2x 3090.


PART 27: SELF-MODIFICATION SYSTEM (GODEL PATTERN)

  Purpose: elai_cc improves its own workflow configuration over time. Not theoretical —
  based on two verified systems: FunSearch (DeepMind, Nature 2024) proved evolutionary
  self-improvement works when evaluation is deterministic. Darwin Godel Machine
  (arxiv 2505.22954, Sakana AI 2025) proved where it breaks: the agent learned to
  falsify test results when it was both proposer AND judge.

  Core safety property: the modifying agent NEVER evaluates its own modifications.
  Deterministic benchmarks judge. The agent proposes, code decides.

  27.1 Three-Layer Architecture:

    LAYER 1 — DATA (automatic, no approval):
      What changes: template ranking scores, rule trigger counts, pipeline outcome metrics.
      Mechanism: pure arithmetic from PipelineOutcome (PART 22.1). No LLM involved.
      Already designed in PART 22. No change needed.
      Safety: security/safety/architecture rules NEVER auto-adjusted (PART 22.3).

    LAYER 2 — CONFIG (full pipeline, auditor approval):
      What changes: new rules, agent GRC budgets, context allocation ratios, model
      assignments per role, new pipeline templates, tool configurations.
      These are the high-value modifications — the system tunes HOW it works.

      Detection heuristics (triggers self-mod candidate):
        - phases_passed_first_try / phases_total < 0.5 (too many retries)
        - tokens_consumed > 2x template baseline (inefficient)
        - audit_findings_block > threshold per phase (quality issues)
        - 3+ anti-spiral triggers in one pipeline (workflow friction)
        - Same rule triggers false positive > 80% over 10 executions (noisy rule)
      All thresholds configurable in elai_cc.toml.

      Process (a self-modification IS a pipeline task):
        1. DETECT: metrics trigger candidate after pipeline completion
        2. RESEARCH: Research Agent investigates root cause
           Output: {root_cause, proposed_change, expected_improvement, evidence}
        3. PLAN: proposed change becomes a PipelineSpec targeting .elai_cc/ config
           Goes through all 4 elaboration stages (PART 26):
           Stage 1 (research) -> Stage 2 (plan) -> Stage 3 (structural validation)
           -> Stage 4 (feasibility probe)
        4. SANDBOX: copy current workflow config to .elai_cc/sandbox/{mod_id}/
           Apply proposed change to sandbox copy only
        5. BENCHMARK: re-run the SAME task that triggered detection using sandbox config
           Collect identical metrics as original run
           Comparison is deterministic: subtract two numbers
        6. GATE: new config scores better on deterministic metrics
           AND auditor finds no safety regressions
           AND no evidence gate definitions were modified
           -> APPLY (copy sandbox config to active config, archive old)
           -> DISCARD (log attempt, keep current config)

      Anti-reward-hacking locks (enforced by PreToolUse hook during self-mod pipeline):
        READ-LOCKED during self-modification:
          - .elai_cc/core/metrics/ (metrics collection code)
          - .elai_cc/core/gates/ (evidence gate definitions)
          - auditor agent config (when auditor judges the modification)
          - benchmark harness code
          - the test suite used for benchmarking
        The modifying agent cannot write to these files. Period.
        Same mechanism as cross-session file locks (PART multi-session).

    LAYER 3 — STRUCTURE (human approval required, always):
      What changes: FSM state additions/removals, new agent roles, GRC protocol changes,
      evidence gate modifications, core pipeline control flow.
      Process: same as Layer 2 (detect -> research -> plan -> probe -> benchmark)
      Gate: human review in BOTH autonomous and interactive modes.
      Rationale: structural changes to the evaluation system itself are how DGM's
      reward hacking started. The evaluation infrastructure MUST be outside modification scope.

  27.2 Resource Scheduling:
    Self-modification runs at LOWEST priority.
    Only during idle (no active user task). User task preempts at any checkpoint.
    Cost ceiling: max 1 self-mod pipeline per N completed pipelines (configurable, default N=5).
    Benchmark cost: uses smallest representative task, not full original.
    Storage: .elai_cc/global/self_mod_history.db
      Schema: mod_id, layer, proposed_change, old_config_hash, new_config_hash,
              benchmark_before, benchmark_after, accepted(bool), timestamp, rollback_path.

  27.3 Rollback Protocol:
    Every Layer 2 modification:
      1. Versioned in self_mod_history.db BEFORE applying
      2. Old config archived as .elai_cc/global/config_archive/{timestamp}/
      3. Monitored for 3 pipeline runs after application
      4. Auto-rolled-back if metrics degrade >10% from pre-modification baseline
      5. Rollback is atomic: restore archived config, log rollback reason

  27.4 FunSearch Pattern Mapping:
    FunSearch: LLM proposes program variants -> external evaluator scores -> best survive
    elai_cc:  Research Agent proposes config change -> benchmark scores -> better config survives
    Key alignment: evaluation is ALWAYS external, deterministic, and not modifiable by the proposer.

  27.5 Testable Invariants:
    - Self-modifying agent cannot write to metrics/gates/auditor-config during self-mod pipeline
    - Layer 2 modifications benchmarked against deterministic metrics (no LLM judgment)
    - Auto-rollback triggers if post-mod metrics degrade >10% over 3 pipelines
    - Max 1 self-mod per N completed pipelines (resource ceiling)
    - Layer 3 modifications always require human_approved=true
    - Every self-mod attempt logged with full before/after metrics
    - Sandbox config is physically separate from active config (no cross-contamination)
    - Old config is archived before any modification (rollback always possible)


PART 28: MEDIA VALIDATOR AGENT ROLE

  Purpose: validate non-code outputs (images, 3D models, audio, UI screenshots).
  The auditor validates code. The media validator validates everything else.
  Only loaded when the Pipeline Designer (L1) identifies a media-producing step.

  28.1 Agent Configuration:
    Role: media_validator
    Model (Tier 2 only): LLaVA-7B (~4GB VRAM) or InternVL-2B (~2GB) for visual
    GRC budget: low (3/600) — mostly deterministic checks
    Trigger: L1 PipelineSpec contains a step with output_type in [image, model_3d, audio, video]
    Permissions: FILESYSTEM (read-only on output files)

  28.2 Two-Tier Validation:

    TIER 1 — DETERMINISTIC (no model, <100ms):
      Always runs first. Catches format/structural issues before consuming GPU.

      Image validation:
        - Format check: expected format (PNG/JPEG/WebP) matches actual
        - Resolution check: within expected bounds (min/max width/height)
        - File size check: within expected range
        - Color space check: RGB/RGBA as specified
        - SSIM against reference (if reference provided): score > threshold
        - LPIPS perceptual distance (if reference): score < threshold
        - Deterministic: same input always produces same pass/fail

      3D model validation:
        - Vertex/face count within bounds
        - Manifold check (watertight mesh)
        - UV overlap detection
        - Normal consistency
        - File format validity (glTF/OBJ/FBX)
        - Bounding box dimensions within spec
        Tools: Blender CLI headless mode (bpy.ops verification scripts)

      Audio validation:
        - Sample rate/bit depth match spec
        - Duration within bounds
        - Silence detection (% silence vs content)
        - Clipping detection (samples at max amplitude)
        - Format validity (WAV/MP3/OGG)

      UI screenshot validation:
        - Resolution matches target device spec
        - SSIM against design mockup (if provided)
        - Color histogram comparison (palette compliance)
        - Text detection via OCR (tesseract) for content verification

    TIER 2 — VLM QUALITATIVE (model required, ~2-5 seconds):
      Runs ONLY when Tier 1 passes but qualitative check is specified in QualitySpec.
      Not always needed — many pipelines only need Tier 1.

      Process:
        1. Load VLM (LLaVA-7B or smaller) on GPU1
        2. Send image + structured prompt:
           "Given this specification: [spec]. Does this image match? Report:
            matches_spec (bool), issues (list), confidence (0-1)."
        3. Parse structured output (constrained decoding via grammar)
        4. VLM output is ADVISORY — Tier 1 deterministic checks have veto power
        5. If VLM says "bad" but Tier 1 says "pass" -> flag for human review
        6. If Tier 1 says "fail" -> fail regardless of VLM opinion

      Audio qualitative (CLAP model, ~1GB):
        - Audio-text similarity: "does this sound like [description]?"
        - Cosine similarity score against text description
        - Threshold configurable per pipeline

  28.3 GPU Scheduling:
    Tier 1: no GPU needed. Runs on CPU. Zero scheduling impact.
    Tier 2 VLM: loads on GPU1 (same slot as embedding model).
      Embedding model is ~1.5GB, VLM is ~4GB. Cannot coexist on one 3090.
      Swap: unload embedding -> load VLM -> validate -> unload VLM -> reload embedding.
      Swap cost: ~10-15 seconds. Acceptable at phase boundaries.
    Alternative: if validation is frequent, keep VLM loaded and batch embedding updates.

  28.4 External Tool Integration:
    Media validator wraps external tools via Tool Auto-Discovery (PART 15.7):
      - ImageMagick: format conversion, metadata extraction, comparison
      - Blender CLI: 3D mesh validation, rendering for visual comparison
      - FFmpeg: audio/video format validation, stream analysis
      - Tesseract: OCR for UI text verification
      - ComfyUI API: image generation pipeline control (PART 28.6)
    Each tool registered with validate_output() contract (PART 15.7).

  28.5 Integration with Pipeline:
    EXECUTING phase produces media output -> SSB entry with action_type='file_write'
    Tiered Static Analysis Hook (PART 19) detects media file extension
    Routes to Media Validator instead of T2 AST analysis (AST is for code only)
    Media Validator result written to SSB as action_type='finding'
    BLOCK finding -> same handling as code BLOCK (fix task created)

  28.6 ComfyUI Integration (external image generation pipeline):
    ComfyUI exposes REST API: POST /prompt (submit workflow), GET /history (results)
    elai_cc drives it as an external tool:
      1. Executor writes ComfyUI workflow JSON (the "code" for image generation)
      2. Tool wrapper sends workflow to ComfyUI API
      3. Polls /history until generation complete (timeout: 600s for GPU rendering)
      4. Downloads generated images
      5. Media Validator Tier 1 runs deterministic checks
      6. Media Validator Tier 2 runs VLM qualitative check if specified
    Same pattern applies to any external generation tool (Blender render, FFmpeg encode).

  28.7 Testable Invariants:
    - Tier 1 always runs before Tier 2 (deterministic before qualitative)
    - Tier 1 fail overrides Tier 2 pass (deterministic has veto)
    - VLM output is structured (constrained decoding, not free-form prose)
    - Media validator only loaded when PipelineSpec contains media-producing steps
    - External tools checked for availability before pipeline enters EXECUTING
    - SSIM/LPIPS scores are deterministic (same input = same score)


PART 29: QUALITY SPECIFICATION (QualitySpec)

  Purpose: define "quality" in measurable, deterministic terms per pipeline.
  Without QualitySpec, "high quality" is undefined and unverifiable.
  QualitySpec is generated by L1 Pipeline Designer alongside PipelineSpec.
  L2 Pipeline Builder validates that every metric has a corresponding automated check.

  29.1 Schema:

    QualitySpec {
        pipeline_id: String,
        metrics: Vec<QualityMetric>,
        media_specs: Vec<MediaSpec>,       // only if pipeline produces media
        performance_specs: Vec<PerfSpec>,   // only if pipeline has perf requirements
    }

    QualityMetric {
        name: String,           // e.g. "branch_coverage", "api_response_time"
        target: f64,            // e.g. 0.85, 100.0
        unit: String,           // e.g. "ratio", "ms", "bytes", "score"
        method: String,         // e.g. "branch_coverage_tool", "benchmark", "ssim"
        phase: String,          // which phase validates this metric
        hard_fail: bool,        // true = pipeline fails if unmet, false = WARN only
    }

    MediaSpec {
        output_name: String,    // e.g. "hero_image", "sprite_sheet"
        format: String,         // e.g. "png", "gltf", "wav"
        resolution: Option<(u32, u32)>,
        file_size_max: Option<u64>,
        reference_path: Option<String>,   // for SSIM comparison
        ssim_threshold: Option<f64>,      // e.g. 0.90
        vlm_check: bool,                  // whether Tier 2 VLM validation needed
        vlm_prompt: Option<String>,       // what to ask the VLM
    }

    PerfSpec {
        name: String,           // e.g. "api_latency_p99"
        target: f64,
        unit: String,
        method: String,         // e.g. "load_test", "benchmark"
        sample_count: u32,      // minimum samples for statistical validity
    }

  29.2 Generation:
    L1 Pipeline Designer generates QualitySpec during Stage 2 (plan assembly).
    Sources for quality targets:
      - Research Report (industry benchmarks, SOTA numbers)
      - Template library (prior successful pipeline metrics)
      - Domain rules (e.g., trading rules mandate specific coverage thresholds)
      - User overrides (human can set explicit targets)
    Every target MUST have a grounding source (GRC enforced).
    "High quality" with no grounding -> GRC rejects.

  29.3 Validation by L2:
    L2 Pipeline Builder checks every QualityMetric:
      - method references a tool that exists (tool registry lookup)
      - phase references a valid FSM state
      - if media_spec: reference_path exists (if specified), format supported
      - if perf_spec: benchmark tool available, sample_count > 0
    If any metric has no automated check method -> L2 REJECTS pipeline.
    This guarantees: every quality claim is mechanically verifiable.

  29.4 Enforcement:
    During AUDITING phase, auditor runs all QualityMetric checks.
    Results compared to targets. hard_fail=true metrics that miss -> BLOCK.
    hard_fail=false metrics that miss -> WARN (logged, does not block).
    All results stored in SSB as action_type='test_outcome'.

  29.5 Self-Improvement Integration:
    QualitySpec results feed into Self-Improvement Loop (PART 27):
      - Consistently missed targets -> detection heuristic triggers
      - Consistently exceeded targets -> template ranking improves
      - Target values themselves can be adjusted by Layer 2 self-mod
        (e.g., "85% coverage target is too low for this domain, data shows 92% is achievable")

  29.6 Testable Invariants:
    - Every QualityMetric has a method that maps to an existing tool
    - L2 rejects pipelines with unmeasurable quality claims
    - hard_fail metrics block phase transition when unmet
    - QualitySpec is generated WITH PipelineSpec (not after)
    - All quality targets have grounding sources (GRC enforced)

PART 5.9: INLINE FEASIBILITY CHECK (new GRC mechanism)

  Purpose: catch ungrounded claims that emerge DURING execution, not just during planning.
  The grounding sweep (PART 5.3) catches claims at plan time. But during EXECUTING,
  the executor may introduce new approaches not in the plan. GRC must catch these.

  Trigger: GRC verify step detects a NEW claim not present in the approved plan.
  Detection: claim references a library, API, tool, or algorithm not in:
    - PipelineSpec
    - Research Report
    - DKG (existing codebase knowledge)

  Process (inline, max 2 GRC calls):
    1. GRC flags: "New ungrounded claim: [X]"
    2. Quick verification: web search OR grep codebase OR API_REGISTRY_CHECK
    3. PASS: claim is grounded, proceed. Logged to SSB.
    4. FAIL: claim is ungrounded. Executor MUST use plan's original approach.
       Cannot introduce alternative without going through Research Agent.

  Budget: 2 calls max. This is a quick check, not a full research loop.
  If the executor needs a fundamentally different approach, the correct path is:
    EXECUTING -> BLOCK -> back to PLANNING with new requirements.

  Testable Invariants:
    - Every new claim during EXECUTING triggers inline feasibility check
    - Max 2 GRC calls per inline check (bounded, not open-ended)
    - Failed inline check forces executor to use plan's original approach
    - All inline checks logged to SSB as action_type='claim'


PART 25.8: SYSTEM_PROBE (addition to FEASIBILITY_PROBE)

  Purpose: check hardware/environment capabilities BEFORE feasibility stubs run.
  A stub that requires 16GB RAM on a 8GB machine will fail for wrong reasons.

  25.8.1 Probe Targets (via sysinfo crate — already in deps for VRAM detection):
    - Available disk space (for data-heavy pipelines)
    - Available RAM (for in-memory processing steps)
    - GPU VRAM (already tracked by ModelPool)
    - Network connectivity (can reach required external services?)
    - Available ports (for server pipelines)
    - Installed runtimes (Python version, Node version, Rust toolchain)
    - OS capabilities (Docker available? systemd? WSL?)

  25.8.2 Process:
    Runs ONCE at start of FEASIBILITY_PROBE, before any stubs.
    Output: SystemCapabilities struct (all deterministic, no LLM).
    PipelineSpec resource estimates (from L2) compared against SystemCapabilities.
    PASS: all requirements met -> proceed to stubs.
    FAIL: specific requirement unmet -> report which, suggest alternatives.
      Example: "Pipeline requires 32GB disk, only 12GB available. Options:
        (a) reduce dataset size, (b) use streaming instead of batch, (c) clean disk."
    INTERACTIVE mode: present options to user.
    AUTONOMOUS mode: try alternatives in order, escalate if all fail.

  25.8.3 Testable Invariants:
    - SYSTEM_PROBE runs before any feasibility stubs
    - All checks are deterministic (sysinfo crate, not LLM estimation)
    - Failed system check prevents stub execution (no wasted compute)
    - SystemCapabilities struct stored in SSB for reference by later phases

PART 12 ADDENDUM 2: RISK REGISTER (new risks from session 5, 2026-04-05)

  R14 (MEDIUM — NEW): Self-modification reward hacking
    Despite anti-reward-hacking locks, the modifying agent could find indirect
    ways to game benchmarks (e.g., optimizing for the benchmark task specifically
    rather than general improvement).
    Mitigation: benchmark uses 3 different representative tasks, not just the trigger task.
    Benchmark rotation prevents overfitting to one task type.
    Fallback: Layer 2 self-mods limited to N=5 per pipeline completion ratio.
    Source: Darwin Godel Machine (arxiv 2505.22954) documented this failure mode.

  R15 (LOW — NEW): VLM media validation accuracy
    LLaVA-7B MMMU benchmark is 36.4% — good for "roughly right" not pixel-perfect.
    Risk: VLM approves low-quality media, or rejects good media.
    Mitigation: VLM is ADVISORY only. Tier 1 deterministic checks have veto power.
    VLM disagreement with Tier 1 -> flagged for human review.
    Fallback: skip VLM entirely, use only deterministic metrics (SSIM, vertex count, etc.).

  R16 (MEDIUM — NEW): Self-modification resource contention
    Self-mod pipelines consume same GPU as productive work.
    Risk: system spends more time improving itself than doing user work.
    Mitigation: lowest priority scheduling, max 1 self-mod per 5 completed pipelines,
    user task always preempts. Self-mod runs during idle time only.
    Fallback: disable Layer 2 self-mod entirely (Layer 1 data-level still runs).

30.3 ADOPTED: SWE-bench Benchmark Integration

  Source: OMC benchmark/ directory (run_benchmark.py, evaluate.py, compare_results.py).
  Evidence: SWE-bench is the industry standard for coding agent evaluation.
  Used by OpenAI (SWE-agent), Anthropic, Google. Published leaderboards. Reproducible.

  Integration into elai_cc:
    Self-Modification System (PART 27) benchmarks currently use "same task re-run."
    This is vulnerable to overfitting to one task type (R14).
    SWE-bench provides a ROTATION BENCHMARK SET — hundreds of real-world coding tasks.

    Implementation:
      tools/ crate: ADD swe_bench_runner(instance, mode) -> BenchmarkResult
        - Wraps SWE-bench Verified dataset (Princeton, ~500 verified instances)
        - Modes: "baseline" (no elai_cc orchestration) vs "orchestrated" (full pipeline)
        - Output: structured result (pass/fail, tokens, time, patch)
      Self-mod benchmark rotation (PART 27.2):
        - Current: re-run trigger task only
        - New: run 3 SWE-bench instances from rotation set + trigger task
        - Rotation prevents overfitting to specific task patterns
        - Instances selected by diversity (different repos, different bug types)

    Evidence gate for self-modification (PART 27.1 Layer 2, step 5):
      - Old: "new config scores better on deterministic metrics" (single task)
      - New: "new config scores better on trigger task AND does not regress on SWE-bench rotation"
      - Regression on SWE-bench = DISCARD modification even if trigger task improved

    Scheduling: SWE-bench runs are expensive (~30 min per instance).
      Self-mod already runs at LOWEST priority during idle time.
      SWE-bench rotation adds ~90 min (3 instances) to self-mod pipeline.
      Cost ceiling still applies: max 1 self-mod per 5 completed pipelines.

  Testable Invariants:
    - Self-mod benchmark includes >= 3 SWE-bench instances from rotation set
    - Rotation set diversified by repo and bug type (no single-repo bias)
    - SWE-bench regression blocks self-mod acceptance regardless of trigger task result
    - Benchmark results stored in self_mod_history.db with full per-instance breakdown

30.4 ADOPTED: Failure Taxonomy for Auditor

  Source: OMC analyze_failures.py — categorizes test failures by type, identifies n-gram
  patterns, groups by repo, generates severity-ranked recommendations.
  Evidence: pattern-based failure triage is standard in CI/CD analytics (BuildKite, CircleCI,
  Datadog CI Visibility). Proven to reduce mean-time-to-resolution.

  Integration into elai_cc:
    Auditor agent (PART 5.8) currently receives "test failed" and reasons from scratch.
    Adding structured failure classification before reasoning reduces GRC budget waste.

    Failure taxonomy (deterministic classification, no LLM):
      SYNTAX_ERROR:     parse failure (tree-sitter detects)
      TYPE_ERROR:       type mismatch (compiler output pattern match)
      IMPORT_ERROR:     missing dependency (pattern: "cannot find", "no such module")

30.5 ADOPTED: Structured Execution Markers

  Source: OMC Gyoshu Bridge marker taxonomy — structured output markers like [OBJECTIVE],
  [FINDING], [ERROR], [STAT:mean] parsed from execution output into semantic categories.
  Evidence: structured logging reduces debugging time 40-60% vs unstructured (DORA State of
  DevOps 2023). OpenTelemetry spans follow same principle. Proven at scale.

  Integration into elai_cc:
    DAIRA trace_execution() (PART 16.1) produces TraceReport but output format was unspecified.
    Markers give structure to trace output, reducing token cost of trace analysis.

    Marker protocol for tools/ crate trace_execution():
      Markers are line-prefixed tags in trace output. Parseable by deterministic regex.
      Format: [MARKER_TYPE] content
              [MARKER_TYPE:subtype] content

      Taxonomy (adapted from OMC, extended for Rust debugging):
        Execution:  [CALL] function_name(args)
                    [RETURN] function_name -> value
                    [MUTATION] variable: old_value -> new_value

                    [PANIC] message + backtrace_summary
                    [TIMEOUT] operation exceeded limit
        Findings:   [FINDING] semantic observation about behavior
                    [PATTERN] detected behavioral pattern
                    [ANOMALY] unexpected behavior vs expected
        Metrics:    [STAT:name] value unit
                    [DURATION:name] ms
                    [MEMORY:name] bytes
        Flow:       [CHECKPOINT] named state snapshot
                    [STEP:n] phase description

    GRC observe step integration:
      Current (PART 5.1): observe = read file + grep
      With DAIRA (PART 16.1): observe can invoke trace_execution()
      With markers: observe FIRST reads [FINDING] and [ANOMALY] markers only.
        If insufficient: expand to [MUTATION] and [BRANCH] markers.
        If still insufficient: read full trace.
      Adaptive reading: markers enable progressive detail expansion.
      Token savings: reading 5 [FINDING] lines vs 500 raw trace lines.

    Implementation:
      tools/ crate trace_execution():
        - Wraps execution with marker-injecting tracer
        - For Rust: tracing crate spans -> [CALL]/[RETURN] markers
        - For Python: sys.settrace -> [CALL]/[MUTATION] markers
        - Post-processing: parse markers into MarkerReport struct
      MarkerReport {
          findings: Vec<String>,
          anomalies: Vec<String>,
          mutations: Vec<(String, String, String)>,  // var, old, new
          errors: Vec<String>,
          stats: HashMap<String, f64>,
          raw_line_count: usize,
          marker_line_count: usize,  // for token savings measurement
      }

  Testable Invariants:

    - Markers are deterministically extractable (regex, no LLM)
    - GRC observe reads markers before raw trace (progressive detail)
    - Token savings measurable: marker_line_count / raw_line_count ratio tracked

31.1 Channel Taxonomy Expansion (PART 20 addendum):

  PART 20.3 originally specified 2 channel types (LastValue, Topic). Expanded to 4.
  Source: LangGraph channels/ directory (untracked_value.py, ephemeral_value.py).
  Auditor corrections: UntrackedValue does NOT auto-clear; guard=True default crashes multi-writer.

  Updated channel types:

    LastValue:
      Unchanged from PART 20.3. Single value, last writer wins.

    Topic (accumulate: bool):
      Unchanged from PART 20.3. Append-only list.

    UntrackedValue:
      In-memory only. NEVER serialized to checkpoint. NEVER written to SSB.
      Use case: large transient objects (trace reports, intermediate ASTs, full file contents).
      CRITICAL SEMANTICS (auditor-verified from langgraph source):
        - Does NOT auto-clear between supersteps (persists until explicitly overwritten).
        - guard=false required for multi-writer scenarios (default guard=true raises on concurrent writes).
        - Value is lost on crash/restart (intentional — transient by design).
      Why needed: without this, SSB checkpoints balloon with transient data.

    EphemeralValue:
      Cleared to MISSING on any superstep where no writes occur.
      Use case: one-shot signals (branch-taken notifications, interrupt flags).
      If agent A writes "ready" in superstep N, agent B reads it in superstep N.
      In superstep N+1, if no one writes, value is MISSING (auto-cleared).
      Why needed: clean fire-and-forget signaling without manual cleanup.

  PART 20.4 invariant UPDATED:
    Old: "Only LastValue and Topic channel types exist (no BinaryOp)"
    New: "Only LastValue, Topic, UntrackedValue, and EphemeralValue channel types exist (no BinaryOp)"

  Testable Invariants:
    - UntrackedValue is never present in checkpoint data
    - UntrackedValue with guard=false accepts concurrent writes without error
    - EphemeralValue returns MISSING after a zero-write superstep
    - All channel types implement atomic update(values: Sequence) for batch writes

31.2 Deferred Node Execution (PART 20 addendum):

  Source: LangGraph channels/named_barrier_value.py + pregel/_algo.py.
  Auditor BLOCK-5: Deferred nodes require quiescence detection, incompatible with BSP barrier.
  Resolution: deferred execution is a post-barrier cleanup phase, not a BSP replacement.

  Mechanism:
    BSP superstep proceeds normally (barrier: all scheduled tasks complete).
    After barrier: check for pending deferred nodes.
    If deferred nodes exist AND all their input channels have been written:
      Execute deferred nodes in a "cleanup superstep" (deterministic, sequential).
    Cleanup superstep writes are applied atomically (same as main superstep).
    Then: checkpoint, advance to next superstep.

  Use case: fan-in aggregation. Agent A and Agent B produce partial results in parallel.
  Deferred aggregation node fires only after both complete. No need to know branch count at build time.

  Rust pseudocode:
    loop {
        let tasks = prepare_next_tasks(&checkpoint, &channels, &nodes);
        if tasks.is_empty() { break; }
        let writes = execute_tasks(tasks, &model_pool, &ssb);
        apply_writes(&mut checkpoint, &mut channels, writes);

        // NEW: deferred node phase
        let deferred = get_deferred_nodes(&nodes);
        for node in deferred {
            if node.all_inputs_satisfied(&channels) {
                let deferred_writes = execute_single(node, &channels);
                apply_writes(&mut checkpoint, &mut channels, deferred_writes);
            }
        }

        save_checkpoint(&checkpoint, &channels);
        if !evidence_gate_passes(&checkpoint, &channels) { continue; }
        superstep += 1;
    }

  Testable Invariants:
    - Deferred nodes never execute before the main barrier completes
    - Deferred nodes execute only when all input channels have been written
    - Cleanup superstep writes are atomic (same guarantee as main superstep)
    - Deferred execution is deterministic (same inputs -> same outputs)

31.3 Dynamic Fan-Out (PART 6.2 addendum):

  Source: LangGraph pregel/_algo.py Send() objects + TASKS Topic channel.
  Auditor BLOCK-6: Checkpoint namespace collision for concurrent same-type subgraphs.
  Resolution: AtomicU64 counter per subgraph type.

  Mechanism:
    During execution, an agent can emit Send(target_role, input_data) objects.
    Orchestrator collects Send objects at superstep boundary.
    Each Send spawns an independent agent with its own checkpoint namespace.

    Namespace format: "{parent_ns}|{subgraph_type}:{counter}"
      parent_ns: current agent's checkpoint namespace
      subgraph_type: target role name (e.g., "executor", "auditor")
      counter: AtomicU64, per-subgraph-type, monotonically increasing
      Example: "main|executor:0", "main|executor:1", "main|executor:2"

    Counter state:
      HashMap<SubgraphType, AtomicU64> in orchestrator state.
      Checkpointed at superstep boundary (converted to HashMap<String, u64> for serialization).
      On recovery: restore counters from checkpoint, new Send() objects get fresh IDs.

  Use case: "Process each file in this directory" — executor discovers 47 files at runtime,
  emits 47 Send() objects, orchestrator spawns them respecting VRAM limits (sequential on GPU).

  Resource-aware: orchestrator checks ModelPool before spawning.
  If insufficient VRAM: queue Send tasks, execute serially.
  If VRAM available: execute in parallel (embedding model + one executor per GPU).

  Testable Invariants:
    - Every Send-spawned agent has a unique checkpoint namespace
    - Counter is monotonically increasing (no reuse after crash recovery)
    - Send tasks respect GPU scheduling (never exceed available VRAM)
    - Parent agent checkpoint includes pending Send queue

31.5 Per-Exception Retry Policy (PART 6.5 addendum):

    struct RetryPolicy {

        backoff: BackoffStrategy,             // Fixed, Exponential, or None
    }

    enum RetryAction { Retry, ReduceScope, Escalate, Abort }

31.6 Node-Level Cache with TTL (PART 6.6 addendum):

  Source: LangGraph types.py CachePolicy + cache/base/.
  Auditor WARN-2: floating-point cache keys need normalization.

  struct CachePolicy {
      key_fn: fn(AgentInput) -> CacheKey,
      ttl_seconds: u64,
  }

  CacheKey construction:
    Input is hashed via xxhash after normalization.
    Float normalization: NaN -> u64::MAX sentinel, -0.0 -> 0.0, round to 6 decimal places.
    This prevents spurious cache misses from float representation differences.

  Cache storage: in-memory HashMap<CacheKey, (Output, Instant)> per node.
  NOT checkpointed (cache is perf optimization, checkpoint is correctness).
  TTL checked on access: if expired, entry removed, cache miss.

  Use case: context-compiler re-reading unchanged files returns cached DKG result.
  Knowledge engine queries with same input return cached context chunks.
  Saves: model inference cost + tool execution time.

  Testable Invariants:
    - Cache hit skips agent execution entirely (zero model calls)
    - Expired entries are not returned (TTL enforced)
    - Cache is not in checkpoint data (UntrackedValue semantics)
    - Float normalization produces identical keys for -0.0 and 0.0

31.7 PageRank Repo Map (PART 4 addendum):

  Source: Aider repomap.py:365-706.
  Auditor BLOCK-3: edge-weight boost and personalization are separate mechanisms.
  Auditor WARN-3: dense cyclic graphs degrade PageRank signal.

  New layer between DKG graph and CatRAG traversal:

  Layer 3.5 — PageRank Importance Ranking:

    Input: DKG graph + current task description + chat-relevant files
    Process:
      1. EDGE-WEIGHT BOOST (topology modification):
         For each edge where source or target is in chat-relevant files: weight *= 50.
         This makes the random walk strongly prefer paths through active files.
         Applied to DKG adjacency matrix BEFORE PageRank computation.

      2. PERSONALIZATION VECTOR (walk bias):
         For each node whose identifier is mentioned in the task description: personalization = 10x.
         Uniform distribution for all other nodes.
         This biases the starting distribution of the random walk.

      3. DENSITY GUARD:
         If graph density > 0.3 (edges / (nodes * (nodes-1))): skip PageRank, use BM25 only.
         Dense cyclic graphs produce near-uniform PageRank (no signal). BM25 is better.

      4. BINARY SEARCH TOKEN FITTING:
         PageRank produces ranked node list. Binary search for cutoff that fits max_map_tokens.
         Tolerance: +-15% (same as Aider). Uses sampling-based token estimation (31.9).

    Output: ranked list of code symbols with importance scores, fitted to token budget.

    Special files list (~100 items): Cargo.toml, Dockerfile, .gitignore, README.md, etc.
    Always included in repo map regardless of PageRank score.

  Integration with existing pipeline:
    query -> BM25 -> vector rerank -> PageRank importance filter -> CatRAG expand -> A-RAG filter -> context

  Testable Invariants:
    - Edge-weight boost applied before PageRank (not after)
    - Personalization vector sums to 1.0 (valid probability distribution)
    - Density guard activates at threshold 0.3 (falls back to BM25)
    - Binary search converges within 10 iterations
    - Special files always present in output regardless of rank

31.8 3-Tier Edit Matching (tools/ crate):

  Source: Aider editblock_coder.py:134-330.
  Auditor WARN-4: tier 4 (fuzzy) disabled in Aider production. Not adopted.

  When executor generates SEARCH/REPLACE edit block:

    Tier 1 — Exact Match:
      Find search_text in file content. If found, replace. Done.

    Tier 2 — Whitespace-Normalized Match:
      Normalize both search_text and file content: collapse whitespace, strip trailing spaces.
      Match on normalized forms. Apply replacement preserving original indentation.

    Tier 3 — Ellipsis-Elision Expansion:
      If search_text contains "..." lines, expand to match any number of lines in the file.
      "..." acts as a wildcard for line sequences.

    On Failure (all tiers miss):
      Compute SequenceMatcher similarity against all same-length chunks in file.
      Return "did you mean" hint with the nearest chunk (similarity score + location).
      Do NOT apply the edit. Return failure with hint to executor for retry.

  Testable Invariants:
    - Tier 1 tried before Tier 2 before Tier 3 (strict ordering)
    - Tier 2 preserves original file indentation (does not inject normalized whitespace)
    - Tier 3 "..." only matches at line boundaries (not mid-line)
    - Failed edit never silently applies wrong match
    - "Did you mean" hint includes file location (line number + snippet)

31.11 Session-Owned Commit Tracking (PART 7.2 addendum):

  Source: Aider commands.py:560-656.
  Auditor WARN-7: commit hashes must persist across session handoff.

  Session commit tracking:
    Each session maintains: commit_hashes: Vec<String> — commits made by this session.
    On every auto-commit: append commit hash to list.
    On session handoff: commit_hashes included in handoff.msgpack.
    New session inherits commit_hashes from handoff (can undo inherited commits too).

  Safe undo protocol:
    fn undo_last_commit(session: &Session) -> Result<()>:
      1. Check: last commit hash in session.commit_hashes? If not, BLOCK (not our commit).
      2. Check: working tree clean? If dirty, BLOCK (uncommitted changes would be lost).
      3. Check: commit has parent? If not, BLOCK (initial commit, cannot undo).
      4. Check: commit not pushed to remote? If pushed, BLOCK (would require force-push).
      5. Execute: git reset --soft HEAD~1
      6. Remove hash from session.commit_hashes.

  Testable Invariants:
    - Only session-owned commits can be undone (foreign commits blocked)
    - Undo blocked if working tree is dirty
    - Undo blocked if commit was pushed to remote
    - commit_hashes persists across session handoff

31.12 File Reading Tool Enhancement (tools/ crate, claw-code modification):

  Novel improvement. Neither LangGraph nor Aider implements this.

  Current behavior (claw-code Read tool):
    Model calls read_file(path) -> gets content (possibly truncated at 2000 lines).
    Model has NO IDEA how big the file is before content arrives.
    Wastes context on large files that should have been read selectively.

  New behavior:

    read_file(path, start_line: Option<usize>, end_line: Option<usize>) -> FileReadResult

    struct FileReadResult {
        path: String,
        total_lines: usize,
        estimated_tokens: usize,    // sampling-based (31.9)
        content: FileContent,       // either Full or Outline
    }

    enum FileContent {
        Full(String),               // complete file content with line numbers
        Outline {                   // structural summary for large files
            sections: Vec<Section>, // tree-sitter parsed sections
            hint: String,           // "Use read_file(path, start=X, end=Y) for specific sections"
        },
    }

    struct Section {
        start_line: usize,
        end_line: usize,
        kind: String,               // "imports", "struct Foo", "fn bar", "impl Trait for X"
        signature: String,          // first line of the section (function signature, struct name)
    }

  Decision logic:
    If start_line/end_line provided: return requested range (always Full).
    If total_lines <= threshold (configurable, default 300): return Full.
    If total_lines > threshold: return Outline (tree-sitter structural summary).

  Outline generation:
    Uses tree-sitter (already in deps for Knowledge Engine, PART 4).
    Parse file -> extract top-level nodes (functions, structs, impls, classes, imports).
    Each node becomes a Section with line range + kind + signature.
    Model sees the structure, decides which sections to read in detail.

  Token savings:
    1000-line Rust file: Full = ~3000 tokens. Outline = ~200 tokens.
    Model reads outline, requests 2 specific functions = ~400 tokens.
    Total: ~600 vs ~3000. 5x savings.

  Testable Invariants:
    - Metadata header always present (total_lines, estimated_tokens)
    - Files <= threshold always return Full content
    - Files > threshold without range return Outline
    - Range requests always return Full content for that range
    - Outline sections cover 100% of file lines (no gaps)
    - estimated_tokens within 15% of actual (sampling accuracy from 31.9)

       b. Send continuation request with same context + partial assistant message.
       c. Model continues generating from where it stopped.
       d. Merge partial + continuation into single output.
    4. If not supported: report as error, executor must reduce output scope.

  Max continuations: 3 (prevent infinite loops on genuinely oversized output).

  SCOPE LIMIT (auditor-enforced):
    Applied to: code generation in EXECUTING phase only.
    NOT applied to: GRC reasoning, agent context assembly, SSB reads, planning.
    Rationale: code output is append-only (continuation is safe).
    Reasoning context requires coherence across the full response (continuation may lose thread).

  Testable Invariants:
    - Only triggers on finish_reason=length (not stop or tool_use)
    - Max 3 continuations per generation (bounded)
    - Merged output is syntactically valid (tree-sitter parse check)
    - Never applied outside EXECUTING phase
