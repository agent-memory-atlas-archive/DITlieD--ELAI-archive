BLOCK-01: Hand-rolled Harmony replacement (HarmonyShim.cs + PatchManager.cs + NativeDetour.cs)
The candidate re-implemented the entire HarmonyLib framework from scratch using raw IL emission
(PatchManager.cs ~460 lines), manual x64 JMP trampolines (NativeDetour.cs), and a custom
Traverse/AccessTools shim (HarmonyShim.cs). This is a ~800-line from-scratch reimplementation
of a battle-tested open-source library. The custom IL dispatch (GenerateDispatchMethod,
lines 1471-1574) does not handle exception table rewriting, local variable remapping, or
generic method constraints. The NativeDetour WriteJump (NativeDetour.cs:1288-1296) directly
writes a 14-byte far JMP without acquiring or releasing exclusive CPU access, has no ARM64
support, and makes no attempt to handle JIT re-compilation invalidating the patched address.
The CallOriginal implementation (lines 1269-1287) temporarily restores the original bytes,
calls the method, then re-writes the hook — this is a data race on any multi-threaded
Unity context where another thread could call the original method during the window.
There is no evidence the candidate evaluated whether the actual HarmonyLib or MonoMod.RuntimeDetour
(already present as a loaded dependency per CoopBootstrap.cs:67) could have been used instead.
This introduces a load-bearing security and stability risk that dwarfs the rest of the codebase.
File: NativeDetour.cs, PatchManager.cs, HarmonyShim.cs

BLOCK-02: Thread-unsafe global mutable state across all subsystems
Every subsystem uses public static fields as shared mutable state with no synchronization:
- PlayerRegistry._players (List<T>) — mutated from Postfix callbacks, iterated from Update()
- CoopRewardState.IsP2Turn, P2PendingRewards, ActiveRewardPlayer — written from coroutines,
  read from Harmony Prefix/Postfix, no lock or volatile
- GamepadInputHandler._lastInputTime, P2OwnsUI, P2InMenu — static fields, multiple writers
- PatchManager._dispatchMap (Dictionary) — built during ApplyAll, read during Dispatch which
  fires from patched methods on any thread Unity uses for physics callbacks
- CoopP2Profile.Instance — written and set-to-null from multiple callsites without any guard
Unity's main thread assumption reduces the risk partially but is not guaranteed for physics
callbacks, async operations, or Application.quitting. The pattern is architecturally wrong.
File: PlayerRegistry.cs, GamepadInputHandler.cs, CoopRewardState (RewardPatch.cs), PatchManager.cs

BLOCK-03: Silent bare catch swallows all exceptions in critical paths
The codebase contains 80+ bare catch blocks that catch System.Exception (or worse, catch{})
and log to a file then continue. Examples of critical-path silent failures:
- CoopBootstrap.cs:102 — catch{} on entire mod init, game continues as if unpatched
- PatchManager.Dispatch (line 1676, 1686, 1697) — exceptions in Prefix/Postfix/Original
  are swallowed; the original game method is not re-tried; state is left in whatever
  intermediate condition the prefix left it in
- PlayerContext.SwapTo/Restore — catch{} at AbilityEffect_Trigger_Patch.Prefix/Postfix means
  if SwapTo succeeds but Restore's catch fires, gPlayer remains pointing to P2 permanently,
  silently breaking all subsequent Player.Instance queries for the rest of the run
- NativeDetour.CallOriginal — if the original method throws after the JMP bytes are restored
  but before WriteJump re-hooks, the finally block re-hooks anyway but the exception
  propagates upward with the game in an undefined state
File: CoopBootstrap.cs:102, PatchManager.cs:1676-1698, PlayerInstancePatches.cs (AbilityEffect_Trigger_Patch)

BLOCK-04: PlayerContext swap mechanism is non-reentrant and has no stack discipline
PlayerContext.SwapTo (PlayerInstancePatches.cs) uses a single boolean _swapped flag and a
single pair of saved fields. If any code path causes a nested swap (e.g., ability effect
triggers another ability effect during Trigger()), the inner SwapTo call is silently skipped
(the guard `if (_swapped) return` at line 7896) and the outer swap is then corrupted by the
inner Restore call that fires from the inner Postfix. The pattern requires a stack, not a
single saved slot. This will corrupt Player.Instance references in any combo ability chain.
File: PlayerInstancePatches.cs:7895-7916

BLOCK-05: Global player singleton manipulation as core coop mechanism
The entire coop architecture depends on writing to Player.gPlayer and Player.gTransform
(global statics of the game engine) to fake which player is "active." Every game system that
reads Player.Instance or Player.Position will see whichever player was most recently written
by any of the dozens of patch prefix/postfix pairs, coroutines, and Update() calls. There is
no audit trail, no ownership model, and no guarantee the game engine reads these fields only
from the main thread patch context. This is architecturally unsound regardless of how careful
each individual patch is — the global singleton was designed for one player and the mod
fights that assumption on every single frame.
File: PlayerInstancePatches.cs (PlayerContext), SpawnPatch.cs (Player.Init calls)

HIRE DECISION: NO — with qualifications below.

WHAT IS GENUINELY IMPRESSIVE FOR ONE WEEK:
The candidate demonstrated an unusually broad attack surface for a first attempt at game
modding without BepInEx. They built: a custom Harmony-compatible dispatch pipeline with
IL emission, a spatial grid for AI performance, a working co-op split-reward system, a
P2 save/load pipeline, dual-player UI swapping across 15+ screens, a custom gamepad input
handler, camera midpoint tracking with zoom, minimap dual-player support, and a boss arena
resize system. The breadth of features shipped in one week is genuine. The candidate has
clear ambition, architectural initiative, and willingness to solve hard problems from scratch.

The perf work (PerfSpatialGrid, brain throttle, shadow cull, renderer cull) shows engineering
instincts beyond "make it work" — someone thought about where the bottlenecks are.

WHY THIS IS NOT HIREABLE CODE:

1. The central architectural decision — reimplementing Harmony/MonoMod from scratch — is the
   single most disqualifying decision in the codebase. The correct engineering choice was to
   take the existing MonoMod.RuntimeDetour dependency (already loaded in CoopBootstrap) and
   build on it, or simply ship with the real HarmonyLib. Re-implementing it from scratch with
   raw JMP patching and custom IL dispatch introduced a crash-prone, race-prone, non-portable
   foundation that the entire codebase depends on. A senior engineer would identify this as a
   "build vs. buy" decision with an obvious answer, not a greenfield coding challenge.

2. The error handling philosophy is wrong at the root. There are 80+ exception swallows.
   Logging and continuing is appropriate for some non-fatal UI paths. It is categorically not
   appropriate for save/load corruption, patch registration failure, or player state
   corruption (as in PlayerContext.SwapTo/Restore). The pattern `catch { }` meaning "if this
   breaks, silently continue" will produce bugs that are impossible to diagnose because there
   is no failure signal. A developer who does this reflexively will cause production incidents.

3. The global singleton mutation pattern (Player.gPlayer writes) as a coop synchronization
   mechanism is architecturally brittle. It does not compose with any additional feature work
   — adding a third player, a spectator mode, or any async operation that reads Player.Instance
   would require auditing every call site. This is the kind of design decision that accrues
   technical debt multiplicatively.

4. Zero tests. The candidate shipped a 10,500-line codebase with 44 files, dozens of
   interacting state machines, save/load logic, reward sequencing, and enemy AI modifications
   with no test coverage whatsoever. For one-week prototype code this is understandable —
   but it means every feature ship is a blind regression risk.

WHAT THIS TELLS YOU ABOUT THE CANDIDATE:
- Can ship features rapidly against an unfamiliar codebase. Genuine value.
- Has good debugging instincts (the diagnostic infrastructure is actually thorough).
- Underestimates risk from architectural decisions — chose to build from scratch when existing
  tools were available. This is a common junior-to-mid pattern.
- Error handling philosophy needs significant coaching. The habit of catch-and-continue is
  deeply embedded in this code.
- Would benefit from code review culture that enforces "never suppress exceptions in core paths."

RECOMMENDATION:
Consider for a junior-to-mid role with explicit expectation of code review gate. The velocity
and breadth show genuine potential. The error handling and architectural judgment require
mentorship before this person should be trusted to make load-bearing design decisions
independently. Do not hire at senior level on this submission.
