RECURSIVE DECOMPOSITION EXTENSION (Fractal Research Pipeline)

  The base 4D steps (4D.1-4D.6) produce a flat ResearchTree for a single task.
  This extension makes FlashResearch recursive: it operates at all 4 levels of the
  decomposition tree (Concept -> Phase -> Step -> BabyStep), with grounded research
  at every node. The LLM never controls flow. The orchestrator drives traversal.

  DESIGN PRINCIPLE
    The system is a PIPELINE, not a session. Each agent is a tool. The orchestrator
    (Rust code) drives everything deterministically. The LLM does not decide what to
    research next — the TreeNavigator does. The LLM does not choose frameworks — it
    receives grounded options from research and either picks (autonomous) or presents
    (interactive). The LLM cannot implement something unverified.

  DECOMPOSITION LEVELS
    Level 0 — IDEA: user input. System runs top-level FlashResearch.
      Output: ConceptDecomposition (list of N concepts with feasibility scores).
      Research scope: profitability, usefulness, tech stack feasibility, language choice.
      Gate: all concepts must have grounded feasibility > threshold or be dropped.

    Level 1 — CONCEPT: e.g. "Database Schema & RLS", "Core API Backend".
      Each concept gets its own research cycle via FlashResearch.
      Output: PhaseDecomposition per concept (frameworks, packages, approach).
      Research scope: which framework, which packages, API compatibility, version constraints.
      Gate: each phase must reference grounded package/framework (verified exists + compatible).

    Level 2 — PHASE: e.g. "concept1_phase1: JWT Auth with Axum".
      Each phase gets research on specific implementation approach.
      Output: StepDecomposition per phase (ordered implementation steps).
      Research scope: exact API usage, version-specific behavior, edge cases.
      Gate: each step must have a grounded implementation path (not training-derived).

    Level 3 — STEP -> BABY STEPS: e.g. "concept1_phase1_stepA: Argon2 hashing".
      Each step decomposed into atomic baby steps (<2K token context each).
      Output: Vec<BabyStepSpec> per step. Each BabyStepSpec has full 8-block structure.
      Research scope: exact function signatures, error handling, test patterns.
      Gate: each baby step must be independently executable and testable.

  NEW TYPES (added to orchestrator crate alongside existing ResearchTree types)

    struct ConceptDecomposition {
        idea: String,
        concepts: Vec<ConceptNode>,
        research: ResearchReport,              // top-level research findings
        feasibility_scores: Vec<(String, f64)>, // per concept, [0.0, 1.0]
    }

    struct ConceptNode {
        concept_id: ConceptId,
        name: String,                          // e.g. "Database Schema & RLS"
        description: String,
        research: Option<ResearchReport>,      // populated at Level 1
        phases: Vec<PhaseNode>,                // populated at Level 2
        feasibility: f64,                      // from research, [0.0, 1.0]
        tech_stack: Option<TechStackDecision>, // framework + language + packages
    }

    struct PhaseNode {
        phase_id: PhaseId,
        concept_id: ConceptId,                 // parent
        name: String,                          // e.g. "JWT Auth with Axum"
        research: Option<ResearchReport>,      // populated at Level 2
        steps: Vec<StepNode>,                  // populated at Level 3
        framework: Option<String>,
        packages: Vec<PackageRef>,
        depends_on: Vec<PhaseId>,              // cross-concept dependencies
    }

    struct StepNode {
        step_id: StepId,
        phase_id: PhaseId,                     // parent
        name: String,                          // e.g. "Argon2 password hashing"
        research: Option<ResearchReport>,      // populated at Level 3
        baby_steps: Vec<BabyStepSpec>,
    }

    struct BabyStepSpec {
        baby_step_id: BabyStepId,
        step_id: StepId,                       // parent
        grounding: BabyStepGrounding,
        pre_gate: Vec<PreGateCondition>,
        task: TaskSpec,
        tdd: TddSpec,
        deterministic_check: Vec<DeterministicCheck>,
        acceptance: AcceptanceCriteria,
        integration: IntegrationSpec,
        exit_criteria: Vec<ExitCriterion>,
    }

    struct BabyStepGrounding {
        research_findings: Vec<SourceCitation>, // relevant findings for THIS baby step
        overall_context_summary: String,        // max 500 tokens, compressed from parent chain
        required_types: Vec<String>,            // types this baby step must know about
        required_imports: Vec<String>,           // packages/modules needed
    }

    struct PreGateCondition {
        description: String,
        check_command: String,                  // deterministic shell command
        expected_exit_code: i32,
    }

    struct TaskSpec {
        description: String,                    // what to implement
        max_lines: u32,                         // budget for this baby step
        target_file: String,                    // which file to edit/create
        entry_point: Option<String>,            // function/struct to connect to
    }

    struct TddSpec {
        test_file: String,                      // where tests go
        test_count: u32,                        // minimum tests to write
        test_framework: String,                 // e.g. "cargo test", "pytest"
        write_before_code: bool,                // always true — TDD
    }

    struct DeterministicCheck {
        description: String,
        command: String,                        // runnable by auditor
        expected_output: Option<String>,
    }

    struct AcceptanceCriteria {

  RECURSIVE RESEARCH PROTOCOL

    The orchestrator drives this loop. No LLM decides what happens next.

    fn research_decompose(idea: &str, mode: ExecutionMode) -> DecompositionTree {
        // Level 0: top-level research
        let top_research = flash_research(idea, complexity=Complex);
        let concepts = extract_concepts(top_research);  // deterministic extraction

        for concept in concepts {
            // Level 1: per-concept research
            let cache_key = normalize_query(&concept.name);
            let concept_research = research_cache.get_or_research(cache_key, || {
                flash_research(&concept.name, complexity=Moderate)
            });

            if mode == Interactive {
                present_options(concept_research.alternatives);  // user picks
            } else {
                auto_select(concept_research, by=evidence_level);  // highest-grounded wins
            }

            let phases = extract_phases(concept_research);

            for phase in phases {
                // Level 2: per-phase research
                let phase_research = research_cache.get_or_research(
                    normalize_query(&phase.name), || {
                        flash_research(&phase.name, complexity=Simple)
                    }
                );
                verify_packages(&phase_research);  // API_REGISTRY_CHECK each package

                let steps = extract_steps(phase_research);

                for step in steps {
                    // Level 3: per-step -> baby steps
                    let step_research = research_cache.get_or_research(
                        normalize_query(&step.name), || {
                            flash_research(&step.name, complexity=Simple)
                        }
                    );
                    let baby_steps = decompose_to_baby_steps(step, step_research);
                    // Each baby_step gets compressed grounding from parent chain
                }
            }
        }
    }

    Research cache prevents redundant calls. Siblings researching similar topics
    (e.g. two phases both need "Axum routing") hit the cache. Cache keyed by
    normalized query string. TTL prevents stale research across sessions.

    Package verification: every PackageRef gets API_REGISTRY_CHECK (reasoning.txt S4).
    If package doesn't exist or version is wrong, research agent retries with corrected info.
    This is the anti-hallucination gate for dependencies. The LLM cannot invent a package.

  Steps 4D.1-4D.10 design the Research Agent and tree-structured research protocol.

  DESIGN PRINCIPLES (from surveyed papers):
    1. API-based retrieval, not browser automation (2506.18096: browser = 2-3x resource
       cost, prohibitive below 8GB VRAM). SearXNG self-hosted = zero API cost.
    2. ManuSearch-style deterministic orchestration (2508.12752: no RL needed for
       rule-based planner + search + extraction agents). LLM does not control flow.
    3. Progressive disclosure from A-RAG (2602.03442): snippets first, selective full
       read. 90% token savings vs naive full-chunk retrieval.
    4. Evidence grows monotonically (2508.12752 invariant). Pruning is separate from
       evidence collection — prune at synthesis, not at retrieval.
    5. Hybrid tree-based search strategy preferred in tuning-free settings (2508.05668).
       Our FlashResearch tree + per-node research loop matches this.
    6. Source quality is deterministic domain lookup, never LLM-scored (4D spec, sec 7).

      - Per-node research loop (implements 4D.5 FORMULATE-SEARCH-EXTRACT-REFLECT-CONVERGE):
          1. FORMULATE: LLM generates search query from sub-question + prior findings
             (via IPC to sidecar, existing SidecarClient)
          2. SEARCH: SearxClient.search(query) -> Vec<SearchResult>
          3. QUALITY GATE: SourceQualityTable.lookup(domain) -> sort by tier
             Tier1-3 fetched first. Tier4-5 only if budget allows.
          4. FETCH + EXTRACT: WebFetcher.fetch(url) -> ContentExtractor.extract(html)
             Parallel fetches up to max_concurrent_fetches (from tier config)
          5. INDEX: add extracted content to WebContentIndex (chunk + embed)
          6. RETRIEVE: A-RAG progressive disclosure on WebContentIndex
             keyword_search for entities, semantic_search for concepts
             Budget manager decides which chunks to read in full
          7. REFLECT: LLM evaluates phi (goal satisfaction), psi (quality),
             contradictions, new sub-questions, information gain
             (via IPC to sidecar)
          8. CONVERGE or EXPAND: based on thresholds from tier config
      - FlashResearch tree integration:
          WebResearchOrchestrator drives the ResearchTree traversal.
          Each ResearchNode runs the per-node loop above.
          Tree invariants (acyclic, bounded depth/breadth) enforced by existing 4D types.
      - IPC proxy wiring:
          Research Agent (Tier C process) sends:
            SearchRequest -> orchestrator -> SearxClient -> SearXNG
            FetchRequest -> orchestrator -> WebFetcher -> target URL
            EmbedRequest -> orchestrator -> sidecar /v1/embed
            InferenceRequest -> orchestrator -> sidecar /v1/completions
