PHASE 2C: PER-AGENT GRC CONFIGURATION
Prerequisites: Phase 2B complete (grounding verification methods implemented, plan sweep blocks ungrounded claims)

SCOPE: see docs/specs/guide/implementation-guide.txt


GOAL
Different agent roles get different GRC budgets, step sequences, grounding constraints,
and allowed verification methods. The GRC engine routes configuration by role at spawn
time. Auditor gets double-verify with VERIFIED-only grounding. Context-compiler gets
observe-only with FILE_CHECK/SOURCE_CHECK only. Config is layered: global defaults in
elai_cc.toml, per-role overrides in [agents.{role}.grc] tables, validated at load time.

DESIGN DECISIONS (grounded)

  D1. Per-agent transition maps extending GrcState::allowed_next().
      The auditor requires [observe, hypothesize, verify, verify] — double verify.
      Phase 2A's allowed_next() defines the default chain: observe->hypothesize->
      plan_action->act->verify. It does NOT permit verify->verify. Without extension,
      the auditor's required_steps would trigger GrcError::InvalidTransition on the
      second verify step. Solution: AgentGrcConfig carries an optional
      transition_overrides: HashMap<GrcState, Vec<GrcState>> that the engine merges
      with the default allowed_next() for that agent's session. Auditor's override:
      {Verify: [Verify, Observe]}. This is additive (cannot remove default transitions,
      only add new ones) to prevent misconfiguration from breaking valid chains.
      Grounding: reasoning.txt section 7 line 97 specifies auditor required_steps
      includes double-verify. Phase 2A's GrcState::allowed_next() has no Verify->Verify
      path. Without this, the spec is unimplementable.

  D2. Config validation at load time (fail-fast).
      AgentGrcConfig is validated when parsed from elai_cc.toml, not at first GRC call.
      Validation rules: (a) required_steps is non-empty, (b) required_steps forms a
      valid chain through default + overridden transitions, (c) budget.max_calls >=
      required_steps.len() (budget must allow completing the chain), (d) if csq_required
      is true, required_steps must include at least one Verify step, (e) allowed_methods
      is a subset of all known VerificationMethod variants.
      Grounding: standard fail-fast config validation (common engineering practice).
      Provable benefit: catches impossible configs (e.g., budget=1 with 5 required_steps)
      before any work starts. Without validation, these fail at runtime with confusing
      BudgetExhausted errors mid-reasoning.

  D3. TOML layering: global defaults + per-role overrides.
      Global GRC defaults defined in [grc.defaults] table. Per-role overrides in
      [agents.{role}.grc] table. Merge strategy: per-role values override globals
      field-by-field (not deep merge). Missing per-role fields inherit from global.
      This matches the existing TOML pattern: [agents.{role}.supervision] (orchestrator),
      [agents.{role}.slo_tier] (providers), [agents.{role}.sandbox] (tools),
      [agents.{role}.role_prompt] (prompt-architecture).
      Grounding: reasoning.txt section 3 line 38 says "Global default configurable in
      elai_cc.toml." Five existing specs use [agents.{role}.X] pattern (grep confirmed).
      NOTE: existing TOML keys use underscores (e.g., [agents.context_compiler],
      [agents.prompt_engineer]) per prompt-architecture.txt lines 74-82. Phase 2C MUST
      follow this convention: [agents.context_compiler.grc], NOT [agents.context-compiler.grc].
      Hyphenated keys would be valid TOML but silently mismatched with existing tables.

  D4. Allowed verification methods per role (policy layer).
      AgentGrcConfig gains an allowed_methods: Vec<VerificationMethod> field. This is a
      POLICY restriction: it limits which grounding methods an agent is permitted to
      request, independent of what the infrastructure makes available.
      Distinction from reasoning.txt section 9 (CAPABILITY layer): section 9 lines
      140-146 describe IPC proxy capabilities — what the orchestrator CAN provide to
      each role (e.g., "WEB_CHECK: Available to all" via IPC proxy). The allowed_methods
      field is what the role's GRC config PERMITS it to request. Policy <= Capability.
      Context-compiler policy: [FILE_CHECK, SOURCE_CHECK] only (reasoning.txt section 7
      lines 105-106), even though the orchestrator could proxy WEB_CHECK for it.
      Executor/auditor policy: all methods (matching full capability set).
      In phase 2C, the policy is enforced in-process (GRC engine rejects disallowed
      method requests before they reach the orchestrator). In phase 4A, the orchestrator
      adds a second enforcement layer on GroundingRequest IPC messages.
      SPEC UPDATE NEEDED: reasoning.txt line 186 AgentGrcConfig should add
      allowed_methods: Vec<VerificationMethod> and transition_overrides: HashMap<GrcState, Vec<GrcState>>.
      (Cannot edit reasoning.txt — owned by session s-1003192. Flag for reconciliation.)

  D5. Anti-rubber-stamp enforcement for auditor.
      The auditor "must find >= 1 issue per review" (reasoning.txt line 99). This is
      not just a prompt instruction — it is enforced in GRC. When the auditor's GRC
      session reaches Converge, the engine checks that at least one ThinkStep in the
      session's history has step_type=Verify with a finding (content contains a
      structured finding marker, e.g., "FINDING:" prefix). If no finding exists, the
      Converge step is rejected with a new GrcError variant: InsufficientFindings.
      Grounding: reasoning.txt section 7 line 99.
      Provable benefit: without enforcement, the anti-rubber-stamp rule is advisory-only
      and the auditor model can skip verification with no consequence. The auditor is the
      last line of defense before code is accepted — a rubber-stamp auditor defeats the
      entire adversarial review architecture.

          Returns Err(GrcError::ConfigValidation) on first failure with specific reason.

      I2. Transition override merging + step whitelist (engine.rs):
          When AgentGrcConfig is set via with_agent_config(), the engine stores the config.
          On each think() call, effective_allowed_next(state) computes:
            base: GrcState::allowed_next(state)
            plus: config.transition_overrides.get(state).unwrap_or_default()
            merged: base.union(overrides) — additive only, never removes base transitions.
          THEN: if config.required_steps is non-empty, filter merged set to only include
          states that appear in required_steps (plus Status and Converge, which are always
          allowed). This is the step whitelist: it restricts the agent to only the step
          types its role permits. Without this filter, context-compiler's required_steps=
          [Observe] would have no effect — default allowed_next(Observe)=[Hypothesize]
          would still allow Hypothesize. The filter ensures only Observe (and the always-
          allowed Status/Converge) remain reachable.
          Whitelist: reachable_states = required_steps + [Status, Converge].
          effective_allowed = merged.intersect(reachable_states).

      I3. Grounding level enforcement (engine.rs):
          On think() with grounding, classify the GroundingLevel.
          If level < config.grounding_level (e.g., Uncertain < Verified), reject step.
          New error variant or extend UngroundedStep with a "level_insufficient" reason.
          Ordering: Verified > High > Uncertain. Implement PartialOrd on GroundingLevel.
          CRITICAL: enum variant order MUST be { Uncertain=0, High=1, Verified=2 } so that
          derived PartialOrd gives Uncertain < High < Verified. If declared as
          { Verified, High, Uncertain } (phase 2A default), derived Ord inverts:
          Verified=0 < Uncertain=2, and the `level < config.grounding_level` check passes
          when it should reject. Phase 2A's GroundingLevel enum order must be corrected
          or an explicit PartialOrd impl must be provided (not derived).
          Test: assert!(GroundingLevel::Verified > GroundingLevel::Uncertain) — add to T8.

      I4. Anti-rubber-stamp (engine.rs):
          On think(Converge) when agent config role == "auditor":
            scan session history for Verify steps with "FINDING:" prefix in content.
            if count < 1: return Err(InsufficientFindings { role, expected_min: 1 }).
          The finding marker is a const FINDING_PREFIX: &str = "FINDING:".
          Contract: a finding is any Verify step whose content starts with FINDING_PREFIX
          (case-sensitive, after trimming leading whitespace). This is an internal protocol
          between the GRC engine and auditor prompt — not natural language parsing.
          Tests must cover: exact prefix, leading whitespace, content without prefix.

      I5. Config loading from TOML (config.rs):
          TomlConfigLoader::load_config(role, defaults):
            reads from core::Config (already parsed from elai_cc.toml)
            merges [grc.defaults] with [agents.{role}.grc] per D3
            calls validate_config() before returning
          If role not found in config: use defaults only (no error — allows dynamic roles).
          If role found but validation fails: return error (misconfiguration).

      I6. Per-role routing (engine.rs):
          with_agent_config() stores the config and resets topic state.
          All subsequent think() calls use the config's budget, transitions, grounding level.
          get_agent_config() returns the current config (for orchestrator inspection).
          If no agent config set, engine uses global defaults (backward-compatible with 2A).

          authority to the orchestrator and demotes agent-side to advisory. This phase
          does NOT need to anticipate that demotion — phase 4A handles the transition.
          The same GrcBudget struct is used in both modes; only who enforces changes.
