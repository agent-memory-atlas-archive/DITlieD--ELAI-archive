PHASE 3G: HIERARCHICAL PLAN MANAGEMENT
Prerequisites: Phase 3D complete (BSP supersteps + channels operational),
  Phase 3E complete (context budget allocator, needed for Slot 3 sizing in step 3G.4)
Depends on: orchestrator::SSB (action_type='plan_update'), orchestrator::ContextBudget (Slot 3),
  providers::token_count, providers::token_count_estimate
NOTE: implementation-guide.txt dependency graph shows 3E and 3G as parallel siblings from 3D.
  This is incorrect — 3G.4 requires 3E's Slot 3 allocator. Graph should show 3D -> 3E -> 3G.
  Alternatively, steps 3G.1-3G.3 and 3G.5-3G.6 can proceed without 3E; only 3G.4 blocks on it.
  Recommended: keep parallel start but gate 3G.4 on 3E completion (partial parallelism).

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
Two-artifact plan representation: skeleton (fits 2-4k tokens, always in Slot 3) + per-phase
elaboration (loaded on demand). Contract extraction propagates interface changes to dependent
phases. Coherence enforcement prevents elaboration drift from skeleton intent.

RISKS TO WATCH
  R23: Plan skeleton may exceed 4k on very large plans. One-liner per phase enforcement.
  R24: Contract extraction may miss implicit dependencies (e.g. shared constraints not in
    inputs/outputs). Mitigation: explicit constraints field per phase entry.
  R25: Coherence check false positives if auditor interprets contracts too strictly.
    Mitigation: auditor checks structural contract match, not semantic equivalence.
  R26: Version counter monotonicity lost on concurrent skeleton edits from parallel sessions.
    Mitigation: SSB single-writer guarantees sequential writes; version read-modify-write
    is atomic within a session (single-writer tokio::mpsc, orchestrator.txt Section 3).


TYPES (from orchestrator.txt section 9, design PART 26)

  struct PlanSkeleton {
      pipeline_id: PipelineId,
      phases: IndexMap<PhaseId, PhaseEntry>,  // ordered, preserves insertion order
      global_constraints: Vec<String>,        // cross-cutting invariants — grounded: orchestrator.txt L237 "Shared constraints"
      version: u32,                           // skeleton-level version — grounded: orchestrator.txt L245 "Version number in skeleton incremented"
      created_at: u64,                        // via ClockProvider — UNGROUNDED (standard practice, not in spec)
      updated_at: u64,                        // via ClockProvider — UNGROUNDED (standard practice, not in spec)
  }

  struct PhaseEntry {
      phase_id: PhaseId,
      goal: String,                           // one-liner, max 120 chars
      inputs: Vec<ContractRef>,               // what this phase receives from dependencies
      outputs: Vec<ContractRef>,              // what dependents expect from this phase
      constraints: Vec<String>,               // phase-specific invariants
      depends_on: Vec<PhaseId>,
      depended_by: Vec<PhaseId>,
      version: u32,                           // per-phase version, independent of skeleton version
      output_type: Option<OutputType>,        // media output type (None for non-visual phases)
      visual_check: bool,                     // trigger render-capture-evaluate loop (default false)
  }
  // output_type + visual_check: see media-validator.txt section 7 (Render-Capture-Evaluate).
  // When visual_check=true, L2 validates that a MediaRenderAdapter exists for output_type.
  // When output_type=None, visual_check must be false (enforced at validation time).

  struct ContractRef {
      name: String,                           // e.g. "AgentPool::write(action)"
      type_signature: String,                 // e.g. "fn(SsbAction) -> Result<SsbSeq>"
      invariants: Vec<String>,                // e.g. ["append-only within session"]
  }

  struct PhaseDetail {
      phase_id: PhaseId,
      skeleton_version: u32,                  // skeleton version at time of elaboration — UNGROUNDED (implied by orchestrator.txt L245, not explicit)
      contracts: ExtractedContracts,          // prepended to detail (see contract extraction)
      implemented_contracts: Vec<ContractRef>,// contracts this phase actually implements (structured, for coherence check 1)
      declared_interfaces: Vec<ContractRef>,  // all pub interfaces this phase introduces (structured, for coherence check 2)
      content: String,                        // full elaboration text
      token_count: usize,                     // exact count via providers::token_count
  }

  struct ExtractedContracts {
      input_contracts: Vec<ContractRef>,      // from dependency phases' outputs
      output_contracts: Vec<ContractRef>,     // from dependent phases' inputs
      shared_constraints: Vec<String>,        // cross-cutting invariants from skeleton
  }

  Storage (dual-path, TOML authoritative):
    Skeleton:     .elai_cc/pipelines/{id}/skeleton.toml (authoritative, TOML file on disk)
    Phase detail: .elai_cc/pipelines/{id}/phases/{phase_id}.toml (authoritative, TOML file on disk)
    SSB audit:    action_type='plan_update' (every write also recorded in SSB for audit trail)
    NOTE: orchestrator.txt L250 references SQL query "SELECT * FROM plan_phases WHERE ...".
    This is conceptual shorthand — there is no plan_phases table in SSB schema (which only has
    ssb + ssb_files). Implementation: query SSB with action_type='plan_update' filter +
    JSON payload extraction for phase_id/dependency lookups. Or: introduce a plan_phases
    view/table as a spec amendment (requires user confirmation per CLAUDE.md).

TOKEN COUNTING STRATEGY (from providers.txt, same as Phase 3E)

  Skeleton token budget: use token_count_estimate for allocation checks during editing,
  token_count (exact) for final validation on write. If exact count exceeds 4096 tokens,
  reject the write with SkeletonBudgetExceeded error. The 4096 limit is a hard cap;
  well-formed skeletons with one-liner goals should fit in ~1-2k tokens for 20-phase plans.
  Phase detail token count: measured on write, stored in PhaseDetail.token_count.
  Slot 3 loading: skeleton_tokens + active_phase_detail_tokens must fit within
  SlotAllocation for ContextSlot::PhaseSpec (see Phase 3E context budget allocator).


CONTRACT EXTRACTION ALGORITHM (from orchestrator.txt L234-239)

  Before elaborating Phase X, extract contracts in 3 steps:
  1. Input contracts: for each dep in X.depends_on, collect dep.outputs.
     These are what Phase X receives — the elaboration must consume them.
  2. Output contracts: for each dep in X.depended_by, collect dep.inputs.
     These are what Phase X must produce — the elaboration must provide them.
  3. Shared constraints: collect skeleton.global_constraints + X.constraints.
     These are invariants the elaboration must respect.
  Result: ExtractedContracts struct prepended to phase detail before elaboration.
  The model elaborates AGAINST contracts, not against full plan text.


COHERENCE ENFORCEMENT (from orchestrator.txt L241-246)

  After elaboration, auditor checks 3 things:
  1. Phase detail satisfies all input/output contracts from skeleton.
     Check: every ContractRef in ExtractedContracts has a corresponding
     implementation reference in the elaboration text.
  2. No new interfaces introduced that skeleton does not declare.
     Check: parse elaboration for function signatures / type definitions
     not present in skeleton's inputs/outputs/constraints.
  3. Version number in skeleton incremented if contracts changed.
     Check: if elaboration modifies any ContractRef, skeleton.phases[X].version
     must be > previous value, AND skeleton.version must be > previous value.
  Violation -> auditor emits BLOCK finding. Elaboration rejected until fixed.


STUB REFERENCES (from orchestrator.txt L62, action_type='stub_reference')

  When a skeleton references a phase that has not yet been elaborated, it holds a stub:
  the PhaseEntry exists in the skeleton (with goal, contracts, dependencies) but the
  corresponding PhaseDetail file does not exist yet. On skeleton write, for each phase
  without a PhaseDetail file, emit SSB action_type='stub_reference' with payload
  { phase_id, skeleton_version }. This allows the orchestrator to track which phases
  need elaboration and prioritize them. When a PhaseDetail is written for a stub phase,
  the stub_reference is superseded (no deletion needed — SSB is append-only).


DEPENDENCY PROPAGATION (topological traversal)

  When a phase's contracts change (detected by version increment):
  1. Build directed graph from depends_on / depended_by edges.
  2. Starting from changed phase, BFS/topological traversal of depended_by edges.
  3. For each reached phase: set needs_review = true in SSB (action_type='plan_update',
     payload includes { phase_id, reason: "dependency_contract_changed", source_phase }).
  4. Phases flagged needs_review must be re-elaborated before execution.
  Cycle detection: DAG property enforced on skeleton write (reject if cycle detected).
  Algorithm: Kahn's algorithm for topological sort — O(V+E), standard for DAGs.
  Rationale: Kahn's detects cycles as a side effect (remaining nodes after sort = cycle members).

  3G.6 DEPENDENCY PROPAGATION AND VERSION TRACKING
    PRE_GATE:
      - 3G.1 types exist (depends_on/depended_by fields)

    TASK:
      - Implement PlanSkeleton::propagate_changes(changed_phase_id)
      - Build directed graph from depended_by edges
      - BFS from changed_phase_id through depended_by: flag each reached phase needs_review=true
      - Record each flagged phase in SSB: action_type='plan_update',
        payload { phase_id, reason: "dependency_contract_changed", source_phase }
      - Cycle detection on skeleton write using Kahn's algorithm
      - Version tracking: phase.version += 1 on any contract field change,
        skeleton.version += 1 on any phase version change
      - Skeleton split operation: PlanSkeleton::split_phase(phase_id, split_points) must
        carry a preserve_contracts: bool flag (default true). When true, the split operation:
        (a) copies input contracts to the first sub-phase, (b) copies output contracts to the
        last sub-phase, (c) creates internal contracts between adjacent sub-phases.
        This ensures L2 Phase Sizing (pipeline-factory.txt Stage 3.5) can split large phases
        without breaking contract propagation. Max split depth: 2 (matches Phase 4G SPLIT_TASK).
        Source: technical-analysis-v3.txt Concern 4 (Layer 2 Phase Sizing), orchestrator.txt §9.
    DETERMINISTIC_CHECK:
      - Chain A -> B -> C -> D: change A's contracts -> B, C, D all flagged needs_review
      - Diamond A -> B, A -> C, B -> D, C -> D: change A -> B, C, D flagged (D flagged once)
      - Isolated phase E (no depended_by): change E -> no propagation
      - Cycle detection: A -> B -> C -> A in depends_on -> Err(CycleDetected { phases: [A,B,C] })
      - Version: change A.outputs -> A.version += 1 -> skeleton.version += 1
      - Split with preserve_contracts=true: phase B (inputs from A, outputs to C) split into
        B1, B2 -> B1 gets A's inputs, B2 gets C's outputs, B1->B2 has internal contract
      - Split with preserve_contracts=false: sub-phases get empty contracts (caller responsible)
    ADVERSARIAL:
      - If BFS visits already-flagged phases redundantly (diamond case), SSB gets duplicate entries.
        Test: visited set prevents re-flagging. SSB entries for same phase_id + source_phase deduplicated.
      - If version increment overflows u32 on extremely long-lived plans (2^32 edits), UB.
        Test: version uses checked_add, returns Err on overflow. Practically unreachable
        but defensive coding.
    ACCEPTANCE:
      - Transitive propagation works for chains, diamonds, and forests
      - Cycle detection rejects invalid dependency graphs
      - Version tracking is monotonic and correct
      - SSB records all propagation events
