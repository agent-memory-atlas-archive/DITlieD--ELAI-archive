PHASE 3I: DETERMINISTIC SIMULATION TESTING (DST)
Prerequisites: Phase 0.8 (entropy quarantine) + Phase 3A-3D (FSM, SSB, agents, BSP)

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
Prove FSM+SSB+BSP correctness via deterministic simulation.
Reference model (digital sibling) serves as infallible oracle.
Same seed = same output, guaranteed.

NOTE: this sub-phase is NOT optional. The FSM+SSB+BSP architecture IS a deterministic
state machine. Testing with non-deterministic tools misses entire classes of bugs.


DST INFRASTRUCTURE REQUIREMENTS

  VCR (Video Cassette Recorder) pattern for LLM determinism:
    Problem: temperature=0 + fixed seed does NOT guarantee LLM determinism (GPU
    float divergence, MoE routing, ollama caching anomalies). madsim alone cannot
    make LLM inference deterministic.
    Source: deterministic-simulation-testing.md section 7

    During initial non-DST run against live ollama:
      1. Intercept all HTTP requests/responses at transport layer.
      2. Compute blake2s hash of full HTTP request body (prompt + config + model).
      3. Store (hash, response) pairs as cassette file (msgpack).

    During DST runs:
      1. HTTP transport layer intercepted (reqwest middleware or madsim
         network mock), NOT at LlmProvider trait level. This captures
         ollama-specific caching behavior and HTTP-level anomalies.
      2. Compute blake2s hash of full HTTP request body (prompt + config + model).
      3. Look up in cassette. Return recorded HTTP response with
         deterministic simulated latency from madsim timer.
      4. If hash not in cassette: test fails (flags prompt drift).

    Note: trait-level interception (mocking LlmProvider::complete()) is
    a separate, complementary pattern for unit testing the orchestrator
    without any transport concerns. VCR operates at transport level to
    catch ollama caching anomalies that trait mocking would miss.

    TraceOps layer (for complex multi-step agent interactions):
      Record entire agent execution trajectory (GRC steps, tool calls,
      branching decisions) as structured trace. During DST, feed
      deterministic trajectory instead of live LLM. Tests FSM/SSB logic
      without any LLM inference.

    Evidence:
      "Live LLM inference in a 10,000-step DST sequence will inevitably
       cause state divergence." (DST section 7.1)
      "VCR cassettes transform probabilistic AI responses into pure
       deterministic data payloads mapped to prompt hashes." (DST section 7.2)

  Custom SQLite VFS (Virtual File System) for DST:
    Trap write()/fsync() syscalls, redirect to in-memory byte buffer
    managed by simulation. Simulator's deterministic PRNG dictates
    exact latency of read/write operations. When SQLite requests flush,
    VFS yields to simulation's timer queue.

    Enables:
      - Torn write simulation (truncate WAL at arbitrary byte boundary)
      - Deterministic I/O latency (no OS jitter)
      - WAL recovery testing (simulated crash + reboot + recovery)

    Implementation: ~200-400 LOC Rust implementing sqlite3_vfs struct.
    Requires unsafe Rust for C FFI (sqlite3_vfs callback interface).
    Coordination with madsim: madsim patches libc time syscalls. Custom VFS
    must use madsim's timer queue for I/O latency, not its own independent
    source. Single deterministic time source required.
    Reference: Limbo project (async SQLite rewrite, NOT a VFS plugin —
    reference for API patterns only, not architecture).
    Source: deterministic-simulation-testing.md section 6.1

    SPIKE REQUIRED: evaluate whether madsim's existing libc I/O hooks
    are sufficient for SQLite determinism before implementing custom VFS.
    If madsim hooks cover write/fsync interception: VFS may be unnecessary.


RISKS
  R1: madsim Windows compatibility is UNVERIFIED. No platform-specific code in madsim
      (pure userspace network simulation), but no confirmed Windows CI either.
      Mitigation: spike test in step 3I.1 before any madsim-dependent work.
  R2: madsim is NOT a drop-in tokio replacement. Requires cfg(madsim) compile flag
      and Cargo.toml dependency swaps (madsim-tokio instead of tokio).
      Mitigation: conditional compilation setup in step 3I.2.
  R3: proptest-state-machine crate (v0.8.0, same repo as proptest) is the correct tool
      for stateful PBT with auto-shrinking. Phase must use its ReferenceStateMachine
      and StateMachineTest traits, not hand-rolled Vec<FsmEvent> generation.
  R4: RUSTFLAGS="--cfg madsim" triggers full workspace rebuild, invalidating normal
      cargo cache. IPC tests should be isolated (separate test binary or documented
      recompile expectation) to avoid surprising compile-time deltas in multi-session CI.
  R5: PROPTEST_CASES=10000 with up to 200 transitions/case can generate 2M+ apply() calls.
      Requires timeout budget (10 min hard limit) or reduced local case count.
