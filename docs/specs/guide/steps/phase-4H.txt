PHASE 4H: SELF-MODIFICATION (DGM/CEL/DarwinNet-derived) -- REVISED 2026-04-15
Prerequisites: Phase 4A complete (process isolation operational)
Dependency: Phase 4A provides Tier C isolation used for self-mod agent sandboxing.

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
System improves its own configs, rules, and data tables from pipeline outcome data.
Layer 1 (automatic metrics, no LLM) + Layer 1A (automatic data-table growth, no LLM) +
Layer 2 (config parameter proposals with staged eval) +
Layer 3 (structural changes, human-only, stubs in this phase).
The modifying agent NEVER evaluates its own modifications.

Paper references:

    proposals, staged evaluation (10/50/200), parent selection, self-referential alignment.
  DarwinNet (arxiv 2604.01236): Protocol Solidification Index (PSI) inspired our MSI.
    PSI formula: M(t) = 1 - (N_agent/N_total). Our MSI uses weighted moving avg of

  SWE-World (arxiv 2602.03419): TestOutcomeReport 4-category grading (FAIL_TO_PASS etc.),
    SWR reward model (accuracy 0.754-0.770 on 32B-72B) for optional pre-screening.

ARCHITECTURAL NOTE (audit INFO-13):
  DGM self-modification modifies AGENT CODE (Python files). 4H self-modification targets
  CONFIG KEYS and DATA TABLES only. This is a deliberate safety divergence: modifying
  Rust source files and recompiling in a production orchestrator is unsafe. The DGM
  principle (self-referential improvement from empirical evidence) is preserved;
  the mechanism (config/data vs code) is adapted for safety.

SELF-MODIFICATION CLASSES (audit BLOCK-3, new in this revision):
  Class A — DATA-TABLE UPDATES (additive, low-risk, Layer 1A):
    New rows in deprecated_patterns, new FailureTaxonomy categories,
    new lazy-code regex patterns, new source-tier entries.
    Validation: false-positive rate < threshold over last N pipelines.
    No staged benchmark evaluation required.
    Grounding: DarwinNet Gene Pool (section IV-A2) stores successful protocol
    patterns for reuse. Same principle: pipeline finds pattern -> stores it ->
    future pipelines benefit. DGM archive accumulates all valid variants.
  Class B — PARAMETER CHANGES (systemic effects, Layer 2):
    ETC threshold, baby step LOC limits, AB-MCTS temperatures, context slot
    weights, freshness decay half-life, retry budgets, steering vector coefficients.
    Validation: staged evaluation (10/50/200 tasks) because changes have
    non-local effects across the entire pipeline.

    - Score normalization (audit BLOCK-1):
        score: f32 = weighted_sum(metrics) / max_possible
        score is ALWAYS in [0.0, 1.0]. Never a raw count.
        Metric weights defined in elai_cc.toml [self_mod.score_weights]:
          first_try_rate_weight = 0.3   (phases_passed_first_try / phases_total)
          coverage_weight = 0.2         (test_coverage_final, already in [0,1])
          efficiency_weight = 0.2       (1.0 - tokens_consumed / token_budget)
          intervention_weight = 0.15    (1.0 - human_interventions / max_interventions)
          findings_weight = 0.15        (1.0 - audit_findings_block / phases_total)
        All component metrics are fractions in [0,1]. Weighted sum is in [0,1].

    - MSI (Modification Solidification Index):
        Weighted moving average of delta_score over last N variants (default N=10).
        delta_score = variant.score - parent.score. Since score in [0,1],
        delta_score in [-1, 1]. MSI in [-1, 1].
        Weight function: EXPONENTIAL DECAY (audit WARN-5).
          w_i = exp(-lambda * (N - i)) where lambda = 0.3, i = position (newest = N).
          Recency-weighted: recent variants matter more than old ones.
          With lambda=0.3 and N=10: oldest weight = 0.07, newest weight = 1.0.
        Our design, inspired by DarwinNet PSI concept but different formula.
        DarwinNet PSI measures agent-intervention frequency; our MSI measures
        improvement trajectory. Both track convergence.

    - Parent selection (DGM-derived, NOT UCB):
        performance score: s_i = sigmoid(lambda * (alpha_i - alpha_0))
        exploration bonus: h_i = 1 / (1 + n_i)  where n_i = children count
        weight: w_i = s_i * h_i
        probability: p_i = w_i / sum(w_j)
        Parameters: lambda=10, alpha_0=0.5 (per DGM paper section 2.3)
        All variants have non-zero selection probability.
        MODE FILTER: parent selection pools are per-PipelineMode.
        A SURGICAL config variant is never selected as parent for GREENFIELD eval.

    - ConfigVariantSimilarity struct (4H.7B):
        key_overlap: f32,                      // |keys(curr) ∩ keys(prev)| / |union|
        type_match: f32,                       // shared keys with same value type / shared
        exact_match: f32,                      // shared keys with identical value / shared
        similarity: f32,                       // 0.5*key_overlap + 0.3*type_match + 0.2*exact_match
      compute(curr: &ConfigBlob, prev: &ConfigBlob) -> ConfigVariantSimilarity
      Range: [0.0, 1.0]. Threshold for STAGNANT: similarity >= 0.95 over
      stagnation_window=3 consecutive variants.

    - OscVerdict enum (4H.7B):
        Stagnant { window: usize, similarity: f32 },        // >=3 consecutive >= 0.95
        Oscillating { period: usize },                       // A->B->A->B detected
        Evolving,                                            // genuine evolution
        Inconclusive { reason: String },                     // need more data

    - AcRegression struct (4H.7C):
        ac_index: usize,
        ac_text: String,
        passed_in_pipeline: PipelineId,        // last pipeline where AC passed
        failed_in_pipeline: PipelineId,        // current pipeline (regression detected)
        consecutive_failures: usize,           // count from latest backward

    - RegressionReport struct (4H.7C):
        regressions: Vec<AcRegression>,
        has_regressions: bool,
        regressed_ac_indices: Vec<usize>,
      detect(history: &[PipelineOutcome]) -> RegressionReport
      Algorithm (port of ouroboros regression.py):
        For each AC in latest pipeline.test_outcomes:
          if NOT passed AND passed in any prior pipeline:
            REGRESSION (record last_passed, count consecutive failures from latest)
          if NEVER passed: skip (persistent failure, not a regression)
      Distinct from TestOutcomeReport.pass_to_fail (single-pipeline view).
      RegressionReport spans the entire pipeline history. Used as additional
      gate in 4H.5 (block promotion) and 4H.6 (trigger auto-revert).

    - EvolutionGateResult enum (4H.7D):
        Allow { evolved_count: usize },                     // >=1 genuine mutation
        Withhold { reason: String, identical_streak: usize },  // never evolved
      compute(window: &[ConfigVariant]) -> EvolutionGateResult
      evolved_count = number of (curr, prev) pairs with similarity < 0.95.
      If evolved_count == 0 AND latest_similarity >= 0.95:
        -> Withhold (Reflect-equivalent conservatively preserved config,
           or Wonder/Reflect errors prevented mutation; not real convergence).
      Distinct from OscVerdict::Stagnant: stagnation can be a valid stop state
      (system is good); evolution gate catches "system never even tried."

4H.7B TEST (OSC -- Ontology-Similarity Convergence)  -- NEW (ouroboros port)
  PRE_GATE:
    - 4H.7 passes (MSI operational)
    - At least 5 ConfigVariant entries in archive (per mode tested)
  TASK:
    Catches "score jiggle": variants whose nominal score moves but whose
    config_blob is structurally identical or alternates between two states.
    MSI alone misses this — MSI tracks delta_score, not delta_structure.
    A config that flips between two equivalent shapes can produce non-zero
    delta_score (noise) while having near-1.0 structural similarity.

    Source: github.com/Q00/ouroboros (MIT). Ports:
      src/ouroboros/core/lineage.py OntologyDelta.compute (line range
        roughly 110-180 in repo at 0.36.x).
      src/ouroboros/evolution/convergence.py _check_oscillation (323-346)
      and _check_stagnation (306-321).

    Similarity formula (over ConfigVariant.config_blob deserialized to
    flat key->value map):
      similarity = 0.5*key_overlap + 0.3*type_match + 0.2*exact_match
      where:
        key_overlap = |keys(curr) ∩ keys(prev)| / |keys(curr) ∪ keys(prev)|
        type_match  = (shared keys with same value type) / |shared keys|
        exact_match = (shared keys with identical value) / |shared keys|
      Range [0.0, 1.0]. If |shared keys| == 0: type_match = exact_match = 0.

    Verdict logic (per PipelineMode):
      - Stagnant: similarity >= 0.95 for stagnation_window=3 consecutive
        variants (window slides over the archive, latest 3 measured).
      - Oscillating: PERIOD-2 FULL VERIFICATION (audit-grade, ouroboros
        convergence.py:328-336). Requires >= 4 variants. Check:
          sim(N, N-2) >= 0.95  AND  sim(N-1, N-3) >= 0.95
        Both half-periods must pass — single half-period is inconclusive
        (could be coincidental). With only 3 variants: check sim(N, N-2)
        only and emit Inconclusive on a single half-period match.
      - Evolving: at least one consecutive pair has similarity < 0.95.
      - Inconclusive: < min_history (default 3 variants).

    Effects:
      Stagnant -> emit ConvergenceStagnant SSB row, boost exploration_bonus
        h_i in next parent_selection (multiply by 2.0 for stagnant mode's
        next 3 selections). Does NOT block promotion — stagnation can be
        a valid stop state.
      Oscillating -> emit ConfigOscillation SSB row, FREEZE the keys that
        differ between the two oscillating states (mark them in
        AllowedConfigKey runtime exclusion list for next 5 pipelines).
        Prevents the agent from re-proposing the same flip.
      Evolving / Inconclusive -> no action.

    PER-MODE: OSC computed per PipelineMode independently, identical
    treatment to MSI per-mode.

  DETERMINISTIC_CHECK:
    - cargo test -p elai_self_mod -- osc (all OSC tests pass)
    - Test: 5 identical ConfigBlob entries -> Stagnant{window:3}
    - Test: A->B->A->B->A->B (4+ variants) -> Oscillating{period:2}
    - Test: A->B->A (3 variants only) -> Inconclusive (cannot verify
      both half-periods)
    - Test: monotonically diverging configs -> Evolving
    - Test: Stagnant in SURGICAL mode does NOT trigger exploration boost
      in GREENFIELD parent_selection
  ADVERSARIAL:
    - If only single-snapshot similarity >= 0.95 triggers Stagnant, noise
      causes false positives. Test: 1 high-similarity step -> Inconclusive
      (need 3 consecutive).
    - If oscillation only checks half-period sim(N, N-2) without checking
      sim(N-1, N-3), genuine periodic systems misclassified. Test: with
      only 3 variants where sim(N, N-2) >= 0.95, emit Inconclusive
      (NOT Oscillating).
    - If frozen keys are not actually excluded, the agent re-proposes the

      to a frozen key -> rejected at routing.
    - If exploration boost decays to 1.0 immediately, stagnation never

  ACCEPTANCE:

4H.7C TEST (REG -- Cross-Pipeline AC Regression Detector)  -- NEW

    failed at gen 5) that single-eval comparison misses.

      src/ouroboros/evolution/regression.py RegressionDetector.detect (39-112).

      For each AC in latest TestOutcomeReport:

          if last_passed_pipeline exists:
            count consecutive failures from latest backward
            record AcRegression { ac_index, last_passed, current, consecutive }
          else:
            skip (persistent failure, not a regression)
      Return RegressionReport(regressions: Vec<AcRegression>)

        even if score improved. Distinct from same-eval PASS_TO_FAIL check.
      4H.6 auto-revert trigger: if active variant's pipelines accumulate
        regressions over 3 consecutive runs -> auto-revert.

    Persistent failures (AC NEVER passed in any pipeline) are NOT regressions.
    They are open issues that should surface separately in audit findings.

    PER-MODE: RegressionDetector runs per PipelineMode. SURGICAL pipeline
    history compared against SURGICAL ACs only.

  DETERMINISTIC_CHECK:

      -> regression detected, last_passed=1, consecutive=1
    - Test: AC fail at all pipelines -> NOT a regression (persistent failure)
    - Test: AC pass at 1, fail at 3, fail at 4, fail at 5 (latest)
      -> regression with consecutive_failures=3
    - Test: regressed variant cannot promote in 4H.5 even if score improved
    - Test: 3 consecutive regressed pipelines on active variant
      -> 4H.6 auto-revert fires
  ADVERSARIAL:

    evolved. Distinct from OSC.Stagnant (3 consecutive identical = system
    is stable) and from MSI.STABILIZING (low improvement = system is
    refining): EVO catches the case where consecutive ConfigVariants
    are byte-identical despite differing scores. This signals one of:
      (a) Reflect-equivalent (the proposer module) conservatively preserved
          a well-performing config without mutating it
      (b) The proposer or evaluator hit errors silently and produced no
          mutation, only a re-evaluation
      (c) Score noise produced delta_score != 0 on identical configs
    Without EVO, MSI can read IMPROVING from pure noise on a frozen config.

    Source: github.com/Q00/ouroboros (MIT). Port:
      src/ouroboros/evolution/convergence.py:156-171
      _count_evolved_generations and the withholding clause around 161-171.

    Compute (per PipelineMode):
      window = last N=10 ConfigVariants in mode
      evolved_count = count of (window[i], window[i-1]) pairs where
        ConfigVariantSimilarity::compute(...).similarity < 0.95
      latest_similarity = ConfigVariantSimilarity::compute(
        window.last(), window[-2]).similarity

      if evolved_count == 0 AND latest_similarity >= 0.95:
        Withhold { reason: "ontology never evolved", identical_streak: N }
      else:
        Allow { evolved_count }

    Effects:
      Withhold -> emit EvolutionWithheld SSB row, MSI verdict for the mode
        is FORCED to STABILIZING (NOT IMPROVING) regardless of computed
        delta_score moving average. Prevents fake-convergence from
        hiding behind score noise.
      Allow -> no override; MSI verdict stands.
