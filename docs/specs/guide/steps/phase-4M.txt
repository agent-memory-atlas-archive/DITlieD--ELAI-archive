PHASE 4M: MULTI-RUNTIME BACKEND ABSTRACTION (ouroboros-derived) -- NEW 2026-05-10
Prerequisites: Phase 3J complete (sidecar + AgentDispatchConfig + backend
mode = local|api|hybrid|auto), Phase 4A complete (Tier C process isolation
+ IpcGateway types). Phase 4G recommended (mode switch lifecycle).

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
  Today ELAI binds the orchestrator to two control planes: the local sidecar
  speaking the Anthropic /v1/messages protocol, and the cloud Anthropic API.
  Phase 3J added [backend] mode = "local" | "api" | "hybrid" | "auto" but
  the dispatch shape is bespoke per backend (ANTHROPIC_BASE_URL switching).

  Ouroboros (github.com/Q00/ouroboros, MIT) demonstrates a cleaner pattern:
  ONE workflow specification drives multiple runtime backends interchangeably
  -- Claude Code, Codex CLI, OpenCode, Hermes, Gemini CLI, Kiro CLI, GitHub
  Copilot CLI -- via a single AgentRuntime trait + per-backend adapter +
  resolve_runtime_backend_name dispatch.

  Phase 4M ports that abstraction to ELAI: a single AgentRuntime trait,
  one adapter per backend, runtime selection via elai_cc.toml or CLI
  flag. The orchestrator writes Anthropic-shaped messages once; adapters
  translate to whatever the underlying runtime expects (or stay native
  Anthropic for the existing sidecar/cloud paths).

  Why now: ELAI's value proposition is "the intelligence is in the
  infrastructure, not the model." The infrastructure should not be
  locked to one inference protocol. Multi-runtime support also unlocks
  hybrid topologies (e.g., Designer in cloud Codex, Executor in local
  sidecar, Auditor in Claude Code) without forking the orchestrator.

NON-GOALS
  - Building new agent runtimes from scratch. We only adapt to existing
    third-party CLIs / APIs that the user has installed.
  - Ouroboros's "skills" magic-keyword routing. ELAI uses FSM + Designer
    pipelines, not keyword triggers; we keep that shape.
  - LiteLLM dependency. Ouroboros uses litellm for cloud providers; ELAI's
    existing providers crate already has a LlmProvider trait. We extend
    LlmProvider, not adopt litellm.

TYPES (new -- to be propagated to providers.txt + orchestrator.txt after approval)

  enum RuntimeBackend {
      Sidecar,        // existing: local Anthropic-protocol sidecar
      AnthropicApi,   // existing: cloud Anthropic /v1/messages
      ClaudeCode,     // new: spawn `claude` CLI (Claude Code) as subprocess
      CodexCli,       // new: spawn `codex` (Codex CLI)
      OpenCode,       // new: spawn `opencode run` subprocess
      Hermes,         // new: Hermes CLI
      GeminiCli,      // new: `gemini` CLI
      KiroCli,        // new: Kiro CLI
      CopilotCli,     // new: GitHub `copilot` CLI
      Ollama,         // new: native Ollama HTTP (ELAI-specific addition)
      Vllm,           // new: native vLLM HTTP (ELAI-specific addition)
  }

  trait RuntimeAdapter: Send + Sync {
      async fn complete(
          &self,
          messages: Vec<Message>,
          config: CompletionConfig,
      ) -> Result<CompletionResponse, RuntimeError>;

      async fn stream(
          &self,
          messages: Vec<Message>,
          config: CompletionConfig,
      ) -> Result<BoxStream<'static, StreamChunk>, RuntimeError>;

      fn capabilities(&self) -> RuntimeCapabilities;
      // Reports: supports_tools, supports_streaming, supports_vision,
      // max_context, max_output, json_schema_mode, supports_prefill,
      // supports_caching, native_thinking_budget.

      async fn health_check(&self) -> RuntimeHealth;
  }

  // Existing LlmProvider trait (providers.txt S1) BECOMES the dyn-dispatched
  // generalization of RuntimeAdapter. Phase 4M makes RuntimeAdapter the
  // canonical name for the role; LlmProvider remains as the same vtable.

  struct RuntimeFactoryConfig {
      backend: RuntimeBackend,                // selected backend
      cli_path: Option<PathBuf>,              // for CLI-spawning backends
      base_url: Option<String>,               // for HTTP backends
      api_key: Option<SecretString>,          // for cloud backends
      model: Option<String>,                  // backend-specific model id
      permission_mode: PermissionMode,        // ouroboros parity
      runtime_profile: Option<String>,        // ouroboros parity (Codex)
      cwd: Option<PathBuf>,
      startup_output_timeout_seconds: Option<f64>,
      stdout_idle_timeout_seconds: Option<f64>,
  }

  enum PermissionMode {
      AcceptEdits,                            // Claude Code's accept-edits mode
      Plan,                                   // plan-only, no writes
      DangerouslySkipPermissions,             // bypass (for sandbox runs)
      Default,                                // backend default
  }

  struct ResolveBackendError {
      candidate: String,
      supported: Vec<String>,
  }

  struct PerRoleRuntime {
      role: AgentRole,
      backend: RuntimeBackend,
      fallback_chain: Vec<RuntimeBackend>,    // ordered alternatives
  }
  // Hybrid topology lives here: each AgentRole gets its own backend.
  // Example config:
  //   [agents.designer.runtime] backend = "anthropic_api"
  //   [agents.executor.runtime] backend = "sidecar"
  //   [agents.auditor.runtime]  backend = "claude_code"

  "Single AgentRuntime trait + per-backend adapter + resolve_backend
  dispatch" -> GROUNDED: ouroboros src/ouroboros/orchestrator/
  runtime_factory.py + adapter.py. MIT-licensed source.

  "7 CLI backends list (claude/codex/opencode/hermes/gemini/kiro/copilot)"
  -> GROUNDED: ouroboros backends/__init__.py runtime_backend_choices()
  + per-backend runtime files in src/ouroboros/orchestrator/.

  "Per-role hybrid topology" -> PARTIALLY GROUNDED: ouroboros has
  per-role agent registration (AgentSpec) but their hybrid is per-CALL
  not per-ROLE. ELAI extends to per-role because our FSM is role-aware.

  "Runtime-fallback chain (orthogonal to model fallback)" -> OUR DESIGN:
  ouroboros has no runtime-fallback. Need is ELAI-specific because we
  support local sidecar that may genuinely go down (remote 3090 is
  not always available).

  "Tier C isolation for CLI subprocesses" -> GROUNDED in ELAI's own
  architecture (Phase 4A): all subprocess outputs must pass through
  IPC sanitization. Ouroboros runs CLIs without process isolation
  (Python parent process holds CLI subprocess directly); ELAI
  hardens this.

  "Native Ollama + vLLM adapters" -> ELAI-SPECIFIC ADDITION: ouroboros
  uses litellm for these. ELAI already has direct Ollama + vLLM
  providers (Phase 3J), so we port directly.

  "PermissionMode enum" -> GROUNDED: ouroboros src/ouroboros/
  claude_permissions.py + codex_permissions.py + copilot_permissions.py.


RISKS TO WATCH
  R1: CLI version drift. Each backend's CLI evolves independently.
    Adapter must report capability accurately even on older CLI versions.
    Mitigation: capabilities() runs probe at startup, caches result.
  R2: Permission-mode bypass. If Claude Code adapter runs with
    --dangerously-skip-permissions in production, sandbox is meaningless.
    Mitigation: default permission_mode=AcceptEdits; require explicit
    user override (config + CLI flag) to use DangerouslySkipPermissions.
  R3: Subprocess prompt injection. Malicious CLI stdout could inject
    into orchestrator context. Mitigation: all stdout sanitized via
    existing 4A IPC sanitizer before reaching prompt context.
  R4: Runtime fallback masking real outage. If sidecar fails and
    AnthropicApi succeeds, user pays cloud cost they didn't intend.
    Mitigation: runtime_fallback SSB emits warning event; dashboard
    surfaces it as a yellow indicator; cost-tracker integrates with
    4G CloudSpendTracker.
