GROUP D: CLOUD MODE
========================================================================

Cloud mode elevates API-backed execution to first-class. The deterministic
harness (rules, AST, tests, evidence gates) still runs locally. Cloud is
"use Claude INSIDE ELAI's validation pipeline."

ORDERING RATIONALE: config + routing (D-1) first because everything else
depends on provider selection working. Context budget (D-2) next because
baby step sizing affects the entire pipeline. Privacy (D-3) before
escalation (D-4) because HYBRID mode sends code to cloud and privacy
controls must exist first. Cost estimation (D-5) last — it's a display
feature, not a functional requirement.

GROUP E: FOCUS TUNNEL
========================================================================

Zero-overhead LLM execution. The model outputs ONLY code. The system
handles file routing, writes, validation, dependency installation.

ORDERING RATIONALE: FIM assembly (E-1) is the core mechanism — everything
else builds on it. Diff parser (E-2) is the second generation mode.
Mode selection (E-3) ties them together. Streaming validation (E-4) and
pipeline parallelism (E-5) are optimizations that require the base modes
working. Dependency resolution (E-6) and file routing (E-7) are
convenience features that enhance focus tunnel but aren't required.


STEP E-1: FIM PROMPT ASSEMBLY + MODEL CAPABILITY DETECTION [FT]
  READ: docs/specs/guide/focus-tunnel-design.txt
    -> MODE 1: FILL-IN-MIDDLE section (FULL: prompt structure with
       <|fim_prefix|>/<|fim_suffix|>/<|fim_middle|> tokens, context
       assembly for prefix/suffix, token savings calculation)
    -> Model support section (Qwen2.5-Coder native FIM, StarCoder,
       DeepSeek-Coder support. Cloud models do NOT support FIM.)
  READ: docs/specs/crates/providers.txt
    -> S1 (LlmProvider trait — add supports_fim() capability query)
  What: implement FIM generation mode.
    (1) ModelCapabilities: add supports_fim: bool field. Set true for
        Qwen2.5-Coder, StarCoder, DeepSeek-Coder. False for cloud models.
        Queried from model metadata at registration.
    (2) FimPromptAssembler: takes (file_content, start_line, end_line,
        task_description, dependencies) and produces FIM prompt.
        PREFIX: file header comment + imports + referenced symbols +

        SUFFIX: code from end_line to EOF (or next 50 lines if large).
        Token budget: prefix + suffix + max_gen must fit context window.
    (3) FIM output handler: model output is raw code. Orchestrator inserts
        at edit region. PostToolUse hooks validate (rules, AST, linter).
    (4) Fallback: if model doesn't support FIM, fall back to STRUCTURED.
  Touches: providers/ (ModelCapabilities), orchestrator/ (FimPromptAssembler,
    output handler)
  Prerequisites: Phase 4 complete (providers, tools, orchestrator exist)
  Estimated scope: ~300-400 LOC


STEP E-2: DIFF OUTPUT PARSER + EDIT MATCHING INTEGRATION [FT]

STEP E-3: GENERATION MODE SELECTION LOGIC [FT]
  READ: docs/specs/guide/focus-tunnel-design.txt
    -> Selection logic section (deterministic rules: edit_existing +
       single region = FIM, edit_existing + multi region = DIFF,
       create_file = STRUCTURED, else STRUCTURED)
    -> INTERACTION WITH OTHER DESIGNS section (cloud mode uses STRUCTURED,
       pipeline factory specifies preferred mode per step)
  What: deterministic mode selector per baby step.
    (1) ModeSelector function: takes (step_spec, model_capabilities,
        execution_mode) -> GenerationMode (FIM | DIFF | STRUCTURED).
    (2) Rules:
        - execution_mode == CLOUD -> STRUCTURED (always)
        - step.type == "create_file" -> STRUCTURED
        - step.type == "edit_existing" AND step.edit_region.is_some()
          AND model.supports_fim -> FIM
        - step.type == "edit_existing" AND step.changes > 1 -> DIFF
        - else -> STRUCTURED
    (3) PipelineSpec step gains optional preferred_mode: Option<GenerationMode>
        field. Designer can suggest mode, orchestrator has final say.
    (4) Metrics: track mode_distribution per task in SSB. Report FIM/DIFF/
        STRUCTURED percentages.
  Touches: orchestrator/ (mode selector), pipeline types (preferred_mode field)
  Prerequisites: E-1 (FIM exists), E-2 (DIFF exists)
  Estimated scope: ~150-200 LOC


STEP E-4: STREAMING VALIDATION FRAMEWORK [FT]
  READ: docs/specs/guide/focus-tunnel-design.txt
    -> STREAMING VALIDATION section (FULL: token-level checks during
       generation, chunk-level AST parse every ~50 tokens, early
       termination savings calculation)
  READ: docs/specs/guide/code-completeness-enforcement-design.txt
    -> section 3.1 (lazy code patterns — used for token-level detection)
  READ: docs/specs/guide/anti-staleness-enforcement.txt
    -> section 2.3 (import validation during generation)
  What: validate model output AS it streams, not just after.
    (1) Token-level checks (during generation):
        - Import validation: as use/import statements stream in, check
          against VERSION_GATE deprecated_patterns. Block if deprecated.
        - Lazy code detection: detect todo!(), pass, unimplemented!(),
          "// TODO" in code positions (not comments/strings — use
          tree-sitter partial parse to distinguish).
        - On detection: stop generation, inject constraint, re-prompt.
    (2) Chunk-level checks (every ~50 tokens):
        - Running tree-sitter parse attempt. If AST shows structural
          impossibility (unclosed brace count growing unbounded),
          early-terminate and retry.
        - Token budget tracking: if output exceeds expected length by 2x,
          stop (likely degenerate generation).
    (3) Early termination: catching bad generation at token 50 instead of
        500 saves ~90% of generation time for that attempt.
    (4) Metrics: early_termination_rate, tokens_saved_by_early_term.
  Touches: providers/ (streaming callback hooks), orchestrator/ (validation
    pipeline integration), rules/ (deprecated_patterns lookup)
  Prerequisites: E-3 (mode selection determines when streaming validation runs)
  Estimated scope: ~350-450 LOC


STEP E-5: PIPELINE PARALLELISM FOR CONTEXT PRE-ASSEMBLY [FT]
  READ: docs/specs/guide/focus-tunnel-design.txt
    -> PIPELINE PARALLELISM section (FULL: while step N validates,
       pre-assemble context for step N+1. Depth limited to 1. Discard
       on validation failure. Adaptive depth control.)
  READ: docs/specs/crates/orchestrator.txt
    -> S4 (BSP supersteps — pipeline parallelism must respect superstep
       boundaries)
  What: overlap context assembly with validation.
    (1) While step N runs post-generation validation (rules, AST, linter):
        read plan for step N+1, query knowledge engine, assemble
        FIM/DIFF/STRUCTURED prompt for N+1.
    (2) If step N passes: step N+1 generation starts immediately with
        pre-assembled context. Saves 100-500ms per step.
    (3) If step N fails: discard pre-assembled N+1 context (it may depend
        on N's output). Cost: ~10-50ms wasted context assembly.
    (4) Adaptive depth: start with depth=1. If validation pass rate drops
        below 80%, disable pre-assembly until rate recovers.
    (5) NOT speculative execution of LLM. Only context assembly is pipelined.
  Touches: orchestrator/ (superstep loop, context pre-assembly)
  Prerequisites: E-3 (mode selection working), Phase 3D (BSP supersteps)
  Estimated scope: ~200-300 LOC


STEP E-6: AUTOMATED DEPENDENCY DETECTION + RESOLUTION [FT]
  READ: docs/specs/guide/focus-tunnel-design.txt
    -> DEPENDENCY MANAGEMENT section (FULL: detection per language,
       resolution pipeline 7-step, approval gate, auto-approve conditions)
  READ: docs/specs/guide/anti-staleness-enforcement.txt
    -> section 1.2 (deprecated_patterns for dependency substitution)
  What: when model writes code with new imports, system handles deps.
    (1) Detection (deterministic): compare import statements in new code
        against manifest file (Cargo.toml / pyproject.toml / package.json).
        Missing package = dependency needed. Per-language import parser.
    (2) Resolution pipeline: identify dep name -> check deprecated_patterns
        for substitution -> query registry for latest compatible version ->
        conflict check -> add to manifest -> install.
    (3) Approval gate: new deps require user confirmation (existing rule).
        In autonomous mode: auto-approve if dep is in pre-approved
