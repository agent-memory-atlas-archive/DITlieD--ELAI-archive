MEASUREMENT 1 DETAIL: ATTENTION QUALITY CURVE (attention.rs)

  For each context_size in config:
    1. Build prompt:
       - System: "You are a code generator. Output ONLY the function body."
       - Padding: random code snippets from fixtures/padding.txt, totaling
         (context_size - task_tokens - system_tokens) tokens.
         Padding inserted BEFORE the task (simulates "lost in the middle").
       - Task: one of 5 simple tasks, rotated:
         a. "Write fn reverse(s: &str) -> String"
         b. "Write fn fibonacci(n: u32) -> u32"
         c. "Write fn is_palindrome(s: &str) -> bool"
         d. "Write fn max_element(v: &[i32]) -> Option<i32>"
         e. "Write fn count_words(s: &str) -> usize"
    2. Send to model endpoint. Collect output.
    3. Validate: extract code, attempt to parse with tree-sitter.
       If parses AND passes a simple correctness check (hardcoded
       test cases per task): PASS. Else: FAIL.
    4. Repeat task_repeats times per context_size.
    5. Record: context_size -> pass_rate (0.0 to 1.0)

  Output to report:
    [attention_curve]
    # context_tokens = pass_rate
    1024 = 1.0
    2048 = 1.0
    4096 = 0.95
    8192 = 0.6
    12288 = 0.3
    16384 = 0.1
    24576 = 0.0
    attention_ceiling = 4096   # last size with pass_rate >= threshold

  The attention_ceiling value feeds directly into ModelCapabilityProfile.


MEASUREMENT 2 DETAIL: RETRY SUCCESS RATE (retry.rs)

  Load 50 tasks from fixtures/tasks.json.
  Each task is a baby-step-sized coding problem:
    {
      "id": "task_01",
      "description": "Add a validate_email function...",
      "file_context": "// existing code in the file...",
      "expected_signature": "fn validate_email(email: &str) -> bool",
      "test_cases": [
        {"input": "\"user@example.com\"", "expected": "true"},
        {"input": "\"not-an-email\"", "expected": "false"}
      ],
      "language": "rust"
    }

  For each task:
    attempt = 0
    error_history = []
    while attempt < max_retries:
      1. Build prompt with retry-appropriate modifications:
         - attempt 0: base prompt (task + file_context)
         - attempt 1: base + lower temperature
         - attempt 2: base + "Previous error: {last_error}. Fix this."
         - attempt 3+: base + error history + "Try a different approach."
      2. Send to model. Collect output.
      3. Validate: tree-sitter parse + test case execution.
         If ALL test cases pass: record (task_id, attempt, PASS). Break.
         Else: record error, increment attempt.
    Record: (task_id, attempts_needed, final_status)

  Output to report:
    [retry_curve]
    # after_N_attempts = cumulative_pass_rate
    1 = 0.62
    2 = 0.74
    3 = 0.82
    4 = 0.86
    5 = 0.88
    6 = 0.89
    7 = 0.89
    optimal_retries = 4        # point of diminishing returns (delta < 2%)
    futility_same_error = 3    # if same error class 3x, model is stuck


MEASUREMENT 3 DETAIL: FEW-SHOT VS ZERO-SHOT (few_shot.rs)

  Same 50 tasks, run TWICE:
    Run A: zero-shot (task + context only)
    Run B: few-shot (task + context + 1 solved example from same domain)

  Few-shot examples: hand-crafted, one per task category:
    - String manipulation: reverse() example
    - Numeric: factorial() example
    - Data structure: stack push/pop example
    - Validation: is_valid_url() example
    - I/O: read_config_file() example

  Each run uses attempt 1 only (no retries). Measures raw capability delta.

  Output to report:
    [few_shot]
    zero_shot_pass_rate = 0.58
    few_shot_pass_rate = 0.76
    delta = 0.18
    few_shot_token_cost = 280    # avg tokens per example
    verdict = "ADOPT"            # ADOPT if delta > 0.10, SKIP if <= 0.05


MEASUREMENT 4 DETAIL: STRUCTURED VS FREE-FORM (structured.rs)

  Same 50 tasks, run TWICE:
    Run A: free-form ("Write the function. Output code only.")
    Run B: structured (JSON schema enforced via vLLM guided decoding):
      {
        "type": "object",
        "properties": {
          "code": { "type": "string" },
          "reasoning": { "type": "string", "maxLength": 100 }
        },
        "required": ["code"]
      }

  Measures:
    - Valid output rate (can we extract code from the response?)
    - Correctness rate (extracted code passes test cases)
    - Latency delta (structured decoding overhead)

  Output to report:
    [structured_output]
    freeform_valid_rate = 0.72      # produced parseable code
    freeform_correct_rate = 0.58    # code also passes tests
    structured_valid_rate = 0.98    # always valid JSON
    structured_correct_rate = 0.68  # code passes tests
    latency_overhead_pct = 8.5      # % slower generation
    verdict = "ADOPT"               # ADOPT if correct_rate delta > 0.05

MEASUREMENT 7 DETAIL: MODEL SWAP LATENCY (swap.rs)

  Requires: at least 2 models available (e.g., Qwen2.5-Coder-7B + Qwen2.5-Coder-3B).

  Protocol per swap measurement:
    1. Ensure model A is loaded and warm (run one inference)
    2. Record timestamp T0
    3. Unload model A (ollama stop / vLLM unload)
    4. Record timestamp T1 (unload_time = T1 - T0)
    5. Load model B (ollama run / vLLM load)
    6. Record timestamp T2 (load_time = T2 - T1)
    7. Run one inference to measure warmup
    8. Record timestamp T3 (warmup_time = T3 - T2)
    9. Total swap time = T3 - T0

  Run 5 times per direction (A->B, B->A). Report mean + p95.
  Also run: cold swap (model not in OS page cache, after clearing cache)
  vs warm swap (model was loaded within last 5 minutes, in page cache).

  Output to report:
    [swap_latency]
    cold_swap_mean_ms = 6200
    cold_swap_p95_ms = 7800
    warm_swap_mean_ms = 1400
    warm_swap_p95_ms = 2100
    unload_mean_ms = 350
    load_cold_mean_ms = 4500
    load_warm_mean_ms = 800
    warmup_mean_ms = 1350

EXECUTIVE SUMMARY

elai_cc has two equal objectives:
  1. TRUST: make LLM output verifiable via deterministic enforcement
  2. EFFICIENCY: make a 12GB VRAM local model produce frontier-model-quality artifacts

This document designs objective 2. The core economic insight:

  CLOUD MODEL: 1 attempt x $0.03 x high accuracy = paid quality
  LOCAL MODEL: N attempts x $0.00 x low accuracy + system compensation = FREE quality

  Time replaces parameters. The system is the intelligence, not the model.

This is not about making the model smarter. It is about making the model's
job so small, so well-defined, and so thoroughly verified that even a 3B
parameter model produces correct output — eventually.


========================================================================
1. THREE CEILINGS (the real constraints)
========================================================================

A local model on consumer hardware hits three distinct ceilings.
Confusing them leads to wrong design decisions.

CEILING 1 — VRAM (hardware limit)
  What fits in GPU memory. Model weights + KV cache + FFN activation scratch.
  RTX 3060 12GB: ~10GB usable (Windows + display driver eat ~2GB).
  MEASURED (2026-04-14, baseline_findings_and_actions.md):
    Qwen2.5-Coder-3B NF4: 1.92GB weights, ~8GB free for KV+compute
    Qwen2.5-Coder-7B NF4: 5.18GB weights, ~4.8GB free for KV+compute
  KV cache per token: 3B = 1 KB, 7B = 56 KB (56x difference).
  FFN activation scratch is the hidden VRAM consumer at long contexts:
    7B at 25K tokens: peak FFN = 1.9GB per layer (mitigated by chunked prefill).
  This ceiling determines WHAT CAN BE LOADED, not what works well.

CEILING 2 — CONTEXT WINDOW (in-VRAM KV cache limit)
  How many tokens fit in GPU memory with the model loaded.
  MEASURED (2026-04-14):
    3B NF4+FA2 on 12GB: ~40K tokens in-VRAM, ~81K with CPU overflow
    7B NF4+FA2 on 12GB: ~25K tokens in-VRAM, ~35K projected with 8-bit KV
  Bottleneck differs by model:
    3B: FFN activation scratch (1 KB/token KV is trivial)
    7B: KV cache (56 KB/token dominates), chunked prefill helps marginally
  8-bit KIVI KV compression: 1.78x savings, lossless for code, ~25% speed cost.
  Only worthwhile for 7B+ (3B KV is already trivial).
  This ceiling determines THE HARD TOKEN BUDGET.

CEILING 3 — ATTENTION QUALITY (model capability limit)
  How many tokens the model can attend to EFFECTIVELY.
  MEASURED (2026-04-14, 100% pass rate at all tested sizes):
    3B NF4+FA2: 16K+ context tokens (25K real) — 100% pass through highest test
    7B NF4+FA2: 16K+ context tokens (25K real) — 100% pass through highest test
    3B NF4+SDPA: 4K context (6.2K real) — drops to 0% at 8K (timeout)
    7B bf16+SDPA: ~1K context — not viable on 12GB
  FA2 is the critical factor: 4x ceiling improvement over SDPA.
  FA2 requires: head_dim <= 256, uniform architecture (no mixed head_dim).
  Gemma 4 E2B REJECTED: mixed head_dim (256+512) blocks FA2 on 7/35 layers.
  This ceiling determines THE REAL PROMPT BUDGET.

  CRITICAL: with FA2, ceiling 3 is NOT the binding constraint on 12GB.
  Ceiling 2 (in-VRAM KV) is binding for 7B. Ceiling 3 exceeds ceiling 2.
  For 3B, neither ceiling 2 nor 3 binds until ~40K tokens.
  DESIGN PRINCIPLE: the context budget allocator (Phase 3E) must enforce
  min(ceiling 2, ceiling 3) per model. On 12GB with FA2, that's ceiling 2.


========================================================================
2. EFFECTIVE CONTEXT BUDGET (tuned per model tier)
========================================================================

Different models on different VRAM budgets have different effective ceilings.
The context budget must ADAPT to the loaded model, not use fixed allocations.

VRAM TIER TABLE (grounded by measurement where marked, projected otherwise):

  VRAM   Model                      Weights   KV/tok   In-VRAM Ctx    Prompt Budget   Features                Status
  8GB    Qwen2.5-Coder-3B NF4+FA2   1.92GB    1 KB     ~25K (proj)    20K             no DoLa, no steering    PROJECTED
  12GB   Qwen2.5-Coder-3B NF4+FA2   1.92GB    1 KB     ~40K           35K             no DoLa, no steering    MEASURED
  12GB   Qwen2.5-Coder-7B NF4+FA2   5.18GB    56 KB    ~25K (35K TQ8) 20K (30K TQ8)   TQ8 default             MEASURED
  16GB   Qwen2.5-Coder-7B NF4+FA2   5.18GB    56 KB    ~50K (proj)    45K             TQ8 default             PROJECTED
  24GB   Qwen2.5-Coder-14B NF4+FA2  ~10GB     ~112 KB  ~40K (proj)    35K             TQ8, test DoLa          PROJECTED
  48GB   Qwen2.5-Coder-32B NF4+FA2  ~20GB     256 KB   ~35K (proj)    30K             TQ4, DoLa, steering     PROJECTED
  any    Cloud frontier              0         0        128K+          per-provider    per-provider             N/A

  PROJECTED rows must be measured on real hardware before shipping.
  All local models require FA2 (flash-attn). Without FA2, ceiling drops 4x.
  Output reserve: 512 tokens (measured: real code outputs rarely exceed 256).

  Model family: Qwen2.5-Coder-Instruct (dense, uniform layers, head_dim=128).
  Gemma 4: REJECTED (mixed head_dim blocks FA2, 18x larger KV, dead end).
  MoE models (Qwen3-Coder-30B-A3B, DeepSeek): REJECTED for DoLa/steering
    (expert routing breaks layer contrasting and activation addition).

  12GB DEFAULT: 7B NF4+FA2+TQ8.
    Rationale: 7B has 90% code pass rate vs 3B's 72%. TQ8 pushes ceiling
    from 25K to ~35K. 3B available as --long-context fallback (40K ceiling).
  48GB DEFAULT: 32B NF4+FA2+TQ4.
    Rationale: 64 dense layers enable DoLa. 256 KB/token KV needs TQ4.
    HumanEval 92.7%, MBPP 90.2% (highest among local models).

  FA2 requirement: Python env elai-fa2 (Python 3.12, flash-attn 2.7.4).
    Python 3.13: no FA2 wheel available (Windows). Falls back to SDPA.
    SDPA ceiling: ~4K tokens (not viable for production use).

  DoLa status by model size (measured/projected):
    3B:  not tested, likely harmful (too few layers)
    7B:  HARMFUL (measured: -15% code quality, -6% factuality, 4.7x slower)
    14B: untested, likely harmful (similar layer count to 7B)
    32B: untested, projected viable (64 layers, sufficient early/late contrast)

  Steering status: NEUTRAL on 7B (infrastructure works, generic contrast pairs
    have zero effect). Needs domain-specific pairs (anti-staleness design).

========================================================================
3. TASK GRANULARITY CALIBRATION (decompose to model capability)
========================================================================

Core principle: decomposition depth is a FUNCTION of model capability.
Bigger model = fewer, larger baby steps. Smaller model = more, tinier steps.

BABY STEP SIZING RULES (revised with measured attention ceilings):

  VRAM     Model   Max LOC/Step   Max Files   Max Symbols   Rationale
  8GB      3B      25 lines       1 file      2 functions   72% pass@1, 20K budget
  12GB     7B      40 lines       2 files     3 functions   90% pass@1, 20K budget
  12GB     3B      25 lines       1 file      2 functions   72% pass@1, 35K budget (more context, same quality)
  16GB     7B      50 lines       2-3 files   4 functions   90% pass@1, 45K budget
  24GB     14B     60 lines       2-3 files   4 functions   projected higher pass rate
  48GB     32B     100 lines      3-5 files   5+ functions  92.7% HumanEval, 30K budget
  cloud    API     100 lines      3-5 files   5+ functions  frontier quality

  Previous MICRO tier assumed 15 LOC / 1 file because attention ceiling was
  guessed at 4K. Measured ceiling is 16K+ with FA2. Baby step sizing is
  driven by CODE QUALITY (pass rate), not context capacity.
  7B at 90% pass rate handles 40 LOC reliably. 3B at 72% needs smaller steps.

  PER-FILE LIMITS: unchanged. Each file touched by a baby step must stay
  within language-specific file size limits (code-completeness-enforcement-design.txt).

DECOMPOSITION DEPTH ADAPTATION (revised):

  For a MEDIUM complexity surgical task (5-15 files, multi-module):

  Model   Decomposition Depth    Approximate Baby Steps
  3B      3 levels               30-50 baby steps
  7B      2-3 levels             15-30 baby steps
  14B     2 levels               10-20 baby steps
  32B     2 levels               5-15 baby steps

  More baby steps = more wall clock time, but each succeeds more reliably.
  The tradeoff is explicit: 3B tasks take 3-5x longer but cost $0.

COMPLEXITY THRESHOLDS (per model, for surgical mode):

  Classification    7B/14B/32B Criteria      3B Override
  TRIVIAL           1 file, <50 LOC          1 file, <25 LOC
  SMALL             2-5 files, <200 LOC      1-3 files, <100 LOC
  MEDIUM            5-15 files               3-10 files
  LARGE             >15 files                >10 files

  3B classifies more tasks as MEDIUM/LARGE, triggering deeper decomposition.
  7B handles SMALL tasks without deeper decomposition (90% pass rate).


========================================================================
4. PROMPT STRATEGY FOR SMALL MODELS
========================================================================

Small models need fundamentally different prompting than frontier models.
This is not about "dumbing down" — it is about PRECISION.
Model family: Qwen2.5-Coder-Instruct (all sizes). Not Gemma.

PRINCIPLE 1: LITERAL OVER ABSTRACT
  BAD (any language):
    "Implement authentication middleware following the project's patterns."
  GOOD (language-specific, from FILE_PLAN + ProjectProfile):
    Rust:       "Write function validate_jwt(token: &str) -> Result<Claims, AuthError>
                 in file src/middleware/auth.rs. Use the jsonwebtoken crate already in
                 Cargo.toml. Return Claims { sub, exp, iat }. See reference:
                 src/middleware/cors.rs:validate_origin() for similar pattern."
    Python:     "Write function validate_jwt(token: str) -> Claims in file
                 src/middleware/auth.py. Use the pyjwt package already in
                 pyproject.toml. Return Claims(sub, exp, iat). See reference:
                 src/middleware/cors.py:validate_origin() for similar pattern."
    TypeScript: "Write function validateJwt(token: string): Claims in file
                 src/middleware/auth.ts. Use the jose package already in
                 package.json. Return { sub, exp, iat }. See reference:
                 src/middleware/cors.ts:validateOrigin() for similar pattern."
    Go:         "Write function ValidateJWT(token string) (*Claims, error) in file
                 middleware/auth.go. Use the golang-jwt/jwt/v5 module already in
                 go.mod. Return &Claims{Sub, Exp, Iat}. See reference:
                 middleware/cors.go:ValidateOrigin() for similar pattern."

  The literal prompt is assembled from: FILE_PLAN (target file, function signature),
  ProjectProfile (dependencies, naming conventions), and DKG (reference patterns).
  Language-specific formatting is automatic — the prompt assembler uses the
  project's detected language to format signatures, imports, and references.

  The bad prompt requires the model to: find patterns, identify the right
  library, choose a return type, pick a file location. Each is a failure
  point for small models. The good prompt eliminates ALL ambiguity.

PRINCIPLE 2: SHOW, DON'T TELL (few-shot is mandatory for MICRO/SMALL)
  Every baby step prompt includes 1-2 CONCRETE examples from the same
  codebase. Retrieved via DKG (find similar function signatures) or BM25
  (find similar implementations). The examples show:
  - How THIS codebase handles error types
  - What naming conventions THIS project uses
  - How THIS project structures tests

  Cost: ~200-400 tokens per example. Worth it: reduces retry count by ~50%
  for small models (based on SWE-bench few-shot ablation studies).

PRINCIPLE 3: FILL-IN-THE-BLANK OVER OPEN-ENDED
  Instead of: "Write a function that validates user input"
  Generate a TEMPLATE with blanks (language-specific skeleton from
  code-completeness-enforcement-design.txt section 2.1):

  Rust:

  Python:

        ___BLANK_2___

        // CHECK 1: email format

  The model fills blanks. The structure is guaranteed correct.
  Skeleton template generated from: FILE_PLAN (signatures) + DKG type info
  + LanguageTemplateRegistry (language-specific patterns). See
  code-completeness-enforcement-design.txt section 2.1 for fill protocol.

  Template generation cost: deterministic (tree-sitter + type info). No LLM.
  Template fill: LLM generates ONLY the blank contents. Much shorter output.
  Orchestrator patches blanks into the skeleton buffer and writes once.

PRINCIPLE 4: STRUCTURED OUTPUT WITH ADAPTIVE CONSTRAINTS
  Small models hallucinate more when generating free-form text.
  ALL model outputs must be structured:

  For code:    grammar-guided generation (vLLM supports EBNF grammars)
  For plans:   JSON schema constrained (vLLM json_schema parameter)
  For GRC:     structured ThinkStep format (already designed in Phase 2A)
  For edits:   diff format only (unified diff, not full file rewrite)

  Grammar-guided generation prevents entire categories of errors:
  - Unclosed brackets/braces
  - Invalid syntax
  - Mixed code + natural language in code blocks
  - Runaway generation (grammar has explicit end markers)

  ADAPTIVE CONSTRAINED DECODING (research-grounded):
  Research (LLM-Code-Generation-Summary.txt section 4e):
    "Alignment tax: forcing grammar constraints degrades semantic/analytical
    capability in instruction-tuned models."
    "CRANE algorithm: augments grammar with transitional rules; +10pp accuracy
    over unconstrained/rigid baselines on symbolic reasoning."
    "AdapTrack: unconstrained 61.58% -> constrained+AdapTrack 66.11% EM@1."
    "CodeFast (training-free token-level early stopping): +34% to +452%
    inference speed, zero Pass@1 degradation."

  Implementation:
    - Use CRANE-style adaptive constraints: relax grammar at semantic decision
      points (algorithm choice, variable naming), enforce strictly at structural
      points (brackets, function boundaries, return types). This avoids the
      alignment tax of rigid grammars while preventing structural errors.
    - Use CodeFast early stopping: detect when the model enters repetition
      loops (excess token phenomenon) and terminate generation cleanly.
      This prevents runaway generation without hard max_tokens truncation
      (which causes avg 19.45% Pass@1 drop per section 3c).
    - vLLM: implement via custom LogitsProcessor chain:
      [CRANE_grammar, CodeFast_early_stop, language_syntax_enforcer]
    - ollama fallback: JSON schema mode only (no custom LogitsProcessor).
      Compensate with stronger T2 AST validation post-generation.


========================================================================
5. RETRY ECONOMICS (time is the currency)
========================================================================

On a cloud API: each retry costs money. Minimize retries.
On a local model: each retry costs ONLY wall-clock time. Maximize quality.

MEASURED RETRY DATA (2026-04-14, Qwen2.5-Coder-7B NF4+FA2):
  Pass@1: 90% (18/20 tasks). Optimal retries: 1.
  Two tasks (task_06, task_15) fail consistently across all configs.
  Retry 1 recovers the remaining ~2% (72% -> 76% for 3B, 90% -> ~92% for 7B).
  Beyond retry 1: diminishing returns. Structural retry (decompose) is better.

RETRY BUDGET PER LEVEL (revised with measured data):

  Level          Max Retries    Wall-Clock Budget    Escalation Target
  Baby Step      3              3 minutes            Step (redecompose)
  Step           2              20 minutes           Phase (replan)
  Phase          2              2 hours              Concept (research)
  Concept        1              4 hours              Human / cloud fallback

  Reduced from 5 to 3 baby step retries: measured data shows retry 2+
  rarely succeeds if retry 1 failed. Structural change (decompose/template)
  is more effective than repeated attempts at the same granularity.
  Total worst case for a MEDIUM task: ~6 hours.
  Compared to: same task on cloud API = 5-15 minutes, $0.50-$5.00.
  The user gets: privacy, zero cost, full control. Tradeoff: time.

RETRY STRATEGY (structural only — research proves instructional retries fail):

  Research (LLM-Code-Generation-Summary.txt section 1): "Prompt engineering
  ('emotional appeals', tips, threats) empirically worsened scores."
  "Inhibition adaptation = 17.6%." Models cannot be instructed out of failure.
  ALL retries must change the STRUCTURE, not the instruction.

  Each retry is a STRUCTURAL modification:

  Retry 1: DECOMPOSE — split the baby step, each function gets its own step
           Research: MoTCoder-7B +5.9% Pass@1 via decomposition.
  Retry 2: TEMPLATE — generate skeleton with blanks, model fills only blanks
           Research: Interleaved generation +6% Pass@1, -60% latency.
  Retry 3: FEW-SHOT — add a WORKING example from same codebase (DKG lookup)
           Research: TDP +6.09% avg improvement across 8 models.
  Retry 4: simplify the task further (split baby step into 2 sub-steps)
  Retry 5: BEST-OF-3 — generate 3 candidates, pick the one that passes

  After retry 5: BubbleUp. The task is too hard for this model at this
  granularity. The step must be redecomposed or the model must be swapped.

REASONING PIPELINE INTEGRATION (reasoning-architecture-design.txt):

  The 6-layer reasoning pipeline runs BEFORE structural retries above.
  When a baby step fails, the sequence is:

  1. Layer 1 (deterministic, 0 tokens, <100ms): classify error, localize via
     DKG/compiler, generate fix template. If resolved: no retry needed.
  2. Layer 2 (micro-reflection, ~600 tokens, 2-5s): one focused JSON question.
     If diagnosis resolves: inject fix instruction into next attempt.
  3. Layer 3 (interrogation, ~2K tokens, 10-30s): system-guided Q&A tree.
  4. Layer 4 (AB-MCTS, 3-18K tokens, 30-90s): branch at failure point.
     GG intrinsic signals (token confidence + novelty) score branches.
  5. Layers 5-6 (cloud, $0.002-$2.00): diagnosis then generation.

  Only AFTER the reasoning pipeline is exhausted (Layer 4 fails, or cloud
  budget depleted) do the STRUCTURAL retries above activate:
  Retry 1 (decompose) -> Retry 2 (template) -> etc.

  This means most errors are resolved WITHOUT consuming retry budget.
  Projected: ~85-90% of errors resolve at Layers 1-4 (zero cloud cost).
  Structural retries handle the remaining ~10-15%.

  REPAIR CONTEXT PROFILE:
  Retries triggered by the reasoning pipeline use Compressed Context Replay
  (reasoning-architecture-design.txt): fresh 1400-token context per attempt.
  This is a NEW SlotWeights profile (REPAIR_CONTEXT) in the context budget
  allocator (Phase 3E). Different from first-attempt allocation:
    System prompt:        50 tokens
    Baby step spec:       200 tokens
    MistakeBook:          150 tokens (forbidden diffs + constraints)
    Relevant code (DKG):  500 tokens
    Working example:      300 tokens
    Fix instruction:      100 tokens
    Output reserve:       100 tokens
    TOTAL:                ~1400 tokens (fits ANY model tier)

  GENERATION PARAMETERS FOR REPAIR (FixAudit, arXiv:2604.05560):
  First attempt: temperature 0.3, top-p 0.9 (focused).
  Repair retries: temperature 1.0, top-p 1.0 (prevents cyclic traps).
  AB-MCTS branches: [0.7, 1.0, 0.3] (diversity + exploration + focus).
  See reasoning-architecture-design.txt GENERATION PARAMETERS section.

FUTILITY DETECTION (stop grinding early):

  Same-error-class detection: if 3 consecutive retries produce the SAME
  FailureTaxonomy category (e.g., MISSING_IMPORT three times), stop.
  The model doesn't know how to fix it. BubbleUp immediately.

  Regression detection: if retry N breaks tests that retry N-1 passed,
  the model is thrashing. Stop at retry N, revert to best previous state.

  Output stagnation: if retry N produces >90% identical output to retry N-1
  (measured by diff size), the model is stuck in a loop. BubbleUp.

BEST-OF-N SELECTION (ensemble at system level):

  For critical baby steps (marked in decomposition tree): generate N=3
  independent completions with different seeds/temperatures. Score each:

  Score = compile_success * 100
        + tests_passed * 50
        + token_confidence_mean * 20  // GG intrinsic signal (free from sidecar)
        + novelty_vs_previous * 10   // GG: divergence from failed attempts
        + zero_warnings * 10
        + code_length_penalty (shorter = better, within bounds)

  GG INTRINSIC VERIFICATION (reasoning-architecture-design.txt):
  token_confidence (mean logprob) and generation_novelty (cosine divergence
  from last failed output) are extracted from the sidecar at zero cost during
  generation. They replace external PRM verifiers, saving VRAM.
  See reasoning-architecture-design.txt GG INTRINSIC VERIFICATION section.

  Pick highest score. Cost: 3x wall-clock, but dramatically higher
  success rate for tricky implementations.

  When to use best-of-N:
  - Baby steps marked CRITICAL by decomposer
  - Baby steps touching auth/security/financial code
  - First baby step of a new concept (sets the pattern for siblings)
  - Never for TRIVIAL steps (waste of time)


========================================================================
6. OUTPUT CONSTRAINTS (structured generation)
========================================================================

Small models waste tokens on:
  - Natural language explanations mixed with code
  - Verbose variable names and excessive comments
  - Repeating the prompt back before answering
  - Generating code that already exists (failing to use the provided context)

CONSTRAINT 1: OUTPUT FORMAT ENFORCEMENT
  Every LLM call specifies an output schema. The model MUST produce:

  For EXECUTING (code generation):
    {
      "edits": [
        { "file": "path", "old": "existing code", "new": "replacement" }
      ],
      "reasoning": "one sentence max"
    }

  For TESTING_FIRST (test generation):
    {
      "test_file": "path",
      "test_code": "full test function",
      "expected_behavior": "one sentence"
    }

  For PLANNING (decomposition):
    TOML structure matching BabyStepSpec schema.

  Enforced via vLLM json_schema or grammar-guided generation.
  If the model fails to match the schema: automatic retry (does NOT
  count toward the baby step retry budget — this is an output format
  issue, not a capability issue).

CONSTRAINT 2: DIFF-ONLY EDITS
  The model NEVER outputs a full file. Only unified diffs.
  Benefits:
  - 5-10x fewer output tokens (function body vs entire file)
  - Forces the model to reference existing code (it must specify "old")
  - Prevents "rewrite the world" tendencies of small models
  - Edit application is deterministic (patch, not overwrite)

  Implementation: the baby step prompt includes the target code section
  (from CodeContext slot) and instructs: "Output ONLY the edit diff."

CONSTRAINT 3: ONE FUNCTION PER TURN
  For MICRO tier: each LLM call generates AT MOST one function/method.
  If a baby step requires 3 functions, it takes 3 LLM calls.
  Each call gets fresh context assembly (updated with previous edits).

  Benefits:
  - Shorter output = fewer errors per call
  - Immediate T1/T2/T3 verification after each function
  - If function 2 fails, function 1 is already committed and correct
  - The model sees its own previous output via DKG incremental update

  Cost: 3 context assemblies instead of 1. ~50ms * 3 = 150ms overhead.
  Token cost: 3 * 3K (MICRO budget) = 9K total input. But each individual
  call is within the attention ceiling. Quality >> speed here.


========================================================================
7. MODEL SWAPPING STRATEGY (one model at a time on 12GB)
========================================================================

On 12GB VRAM, only one model fits. Agent roles must share.

SINGLE-MODEL STRATEGY (12GB / default):
  All roles use the SAME model (Qwen2.5-Coder-7B NF4+FA2). No swapping needed.
  Roles differentiated by: system prompt + rules + context, not model.
  This is the simplest and most VRAM-efficient approach.

  Role-specific behavior via prompt prefix:
    Executor: "You are writing code. Output JSON edits only."
    Auditor:  "You are reviewing code. Output findings as JSON."
    Designer: "You are decomposing a task. Output TOML plan structure."

  GRC budgets already differ per role (Phase 2C). Same model, different
  behavior. This works because the SYSTEM is the intelligence, not the model.

DUAL-MODEL STRATEGY (24GB VRAM):
  Keep two models resident: primary (larger, executor/designer) +
  secondary (smaller, auditor/memory-writer).
  Predictive loading: orchestrator knows FSM transitions, pre-loads
  the next model while current model finishes last tokens.
  Swap latency: <2s (model already in VRAM when needed).

MULTI-MODEL STRATEGY (48GB+ VRAM):
  All role-specific models resident simultaneously.
  Zero swap latency. Maximum quality per role.
  This is the PRODUCTION target for teams/companies.

MODEL SWAP PROTOCOL:
  1. Current model finishes generation (do not interrupt mid-token)
  2. All pending output written to SSB (artifacts persisted)
  3. Model unloaded from VRAM (vLLM handles this, or ollama stop)
  4. Next model loaded (vLLM from disk, or ollama run)
  5. New model receives fresh context assembly from budget allocator
  6. Context is assembled from SSB + DKG + knowledge engine (no state
     transfer between models — all state is in infrastructure)

  Swap time: ~5-10s cold, ~1-2s warm (see benchmark measurement 7).
  This happens between FSM states (EXECUTING -> AUDITING), so it
  overlaps with test execution and auditing preparation.


7B. MODEL SWAP OPTIMIZATION (minimizing swap latency)

  Swap latency breakdown (cold, 7GB model, NVMe SSD):
    Unload from VRAM:     ~100-500ms   (CUDA buffer deallocation)
    Read from disk:       ~1-2.3s      (NVMe sequential ~3-7 GB/s)
    PCIe transfer to GPU: ~220-500ms   (PCIe 4.0 x16 ~32 GB/s)
    Driver/CUDA overhead: ~300-800ms   (kernel compilation, memory mapping)
    Warmup (first pass):  ~1-3s        (KV cache allocation, CUDA graph capture)
    Total cold swap:      ~3-7s

  Six strategies to eliminate or hide this cost:

  STRATEGY 1: AVOID SWAPPING (12GB default)
    On 12GB: ALL roles use the SAME model. Zero swap. Ever.
    Role differentiation via system prompt + rules + constrained decoding.
    Executor prompt: "Output JSON edits only. No explanation."
    Auditor prompt: "Output findings as JSON. Must cite line numbers."
    The model doesn't change. The instructions change. The GRC budget changes.
    This is the CORRECT default for <=16GB VRAM.
    Only override if user explicitly provides multiple models.

  STRATEGY 2: PREDICTIVE PRELOADING (hide disk I/O behind useful work)
    When the model WILL change (24GB+ or explicit multi-model config):
    The orchestrator knows the FSM: EXECUTING always -> AUDITING.
    While executor generates its last tokens:
      - Begin loading the auditor model from disk INTO SYSTEM RAM (not VRAM)
      - Use mmap: model file mapped into virtual memory, OS prefetches pages
      - Cost: zero VRAM, uses system RAM (~7GB), happens in background
    When executor finishes:
      - Unload executor from VRAM (~200ms)
      - Transfer pre-loaded model from RAM to VRAM (~500ms-1s)
      - Warmup (~1s with pre-compiled CUDA graphs)
      - Total visible swap: ~1.5-2s (vs 5-7s cold)

    Implementation:
      PredictiveLoader {
        next_model: Option<ModelId>,        // set by FSM lookahead
        preload_state: PreloadState,        // IDLE | LOADING_RAM | READY_IN_RAM
        mmap_handle: Option<MmapHandle>,    // memory-mapped model file
      }

      Trigger: when current agent enters its LAST baby step (or LAST GRC step),
      PredictiveLoader starts mmap preload of the next role's model.
      Detection: orchestrator tracks baby step index within current phase.

  STRATEGY 3: MMAP + OS PAGE CACHE (make repeated loads near-instant)
    OS page cache keeps recently-accessed file pages in RAM.
    First load of a 7GB model: full disk I/O (1-2.3s).
    Second load (within ~5-30 min, depending on RAM pressure): ~200-500ms.
    The model file is ALREADY in RAM from last time.

    Exploitation:
    - On 64GB RAM: ALL models fit in page cache. Every swap after the
      first is warm. Alternating executor/auditor = ~1.5s each swap.
    - On 32GB RAM: the two most recent models fit. Good enough for
      executor/auditor alternation.
    - On 16GB RAM: only current model cached. Cold swaps every time.
      -> Use strategy 1 (single model, no swap).

    Implementation: nothing to do. The OS handles this. But the harness
    (measurement 7) must measure BOTH cold and warm swap times so the
    system knows whether page cache is effective on the user's hardware.

    Config option:
      [performance]
      preload_models_on_startup = true   # touch all model files at startup
                                          # to populate OS page cache.
                                          # Adds ~10-30s to startup but makes
                                          # all subsequent swaps warm.

  STRATEGY 4: OVERLAP SWAP WITH DETERMINISTIC WORK (free latency hiding)
    After executor finishes and before auditor starts, the system runs:
      - T1 rules check: CPU, <1ms
      - T2 tree-sitter parse: CPU, <10ms
      - T3 compilation: CPU, typically 2-15s for incremental
      - Test execution: CPU, typically 1-30s
      - DKG re-indexing: CPU, <1s
      - SSB write: CPU + disk, <10ms

    ALL of these are CPU-only. GPU is idle during this entire window.
    Total deterministic work: 3-45s.
    Model swap: 1.5-7s.

    The swap runs IN PARALLEL with deterministic work.
    In the common case: swap completes before tests finish.
    The auditor model is warm and ready when test results arrive.

    Implementation:
      After executor signals "done":
        tokio::join!(
          async { run_post_edit_checks().await },   // CPU work
          async { swap_model(next_role).await },      // GPU swap
        )
      Both complete before auditor's context is assembled.
      Zero visible swap latency in practice.

  STRATEGY 5: CUDA GRAPH CACHING (eliminate warmup cost)
    The warmup cost (~1-3s) comes from CUDA compiling execution graphs
    for the model's specific shapes (batch size, sequence length, etc.).
    vLLM caches CUDA graphs by default: first inference is slow,
    subsequent inferences with same shapes are fast.

    Optimization: at model load time, immediately run a DUMMY inference
    with a minimal prompt (e.g., "Hello") to trigger CUDA graph compilation.
    This moves warmup INTO the swap window (parallel with CPU work)
    rather than delaying the first real inference.

    Implementation: model loader sends a warmup ping after load completes.
    The warmup result is discarded. Time: ~500ms-1s (single short inference).

  STRATEGY 6: WARM MODEL POOL (24GB+ only)
    Keep multiple models loaded simultaneously:
      24GB: primary (7GB) + secondary (3-4GB) = fits with room for KV
      48GB: primary (14GB) + secondary (7GB) + tertiary (7GB) = luxury

    Model routing: no swap at all. The request goes to the right model.
    vLLM natively supports serving multiple models from one instance.
    ollama keeps recently-used models warm (configurable keep-alive).

    Implementation:
      ModelPool::route(role: AgentRole) -> &ModelEndpoint
      Routing table from elai_cc.toml:
        [agents.executor.backend]
        model = "Qwen2.5-Coder-32B-Instruct"
        [agents.auditor.backend]
        model = "Qwen2.5-Coder-32B-Instruct"

    For 12GB: ModelPool has exactly 1 entry. route() always returns it.
    No overhead. Just a thin abstraction for when more VRAM is available.


  SWAP LATENCY BY HARDWARE TIER (expected, confirmed by benchmark):

    VRAM     Strategy                   Visible Swap Latency
    12GB     Single model, no swap      0ms (no swap ever)
    16GB     Single model preferred     0ms (or ~2s if 2 small models)
    24GB     Predictive + overlap       0-500ms (hidden behind CPU work)
    48GB+    Warm pool, no swap         0ms (all models resident)

  THE BOTTOM LINE: on 12GB, there is NO swap problem because there is
  NO swap. One model, all roles, differentiated by prompt. When the user
  upgrades hardware or uses cloud fallback, the swap infrastructure
  activates automatically. The system ADAPTS to what's available.


7C. STATELESS INFERENCE (why context never grows)

  CRITICAL ARCHITECTURAL PROPERTY: elai_cc does NOT maintain a conversation
  with the model. Every LLM call is an independent, stateless request.

  This is fundamentally different from ChatGPT / Claude Code / any chat UI:

    CHAT UI (Claude Code, ChatGPT):
      Turn 1: [system + user message]          -> KV cache: 2K tokens
      Turn 2: [system + turn 1 + user message] -> KV cache: 5K tokens
      Turn 3: [system + turn 1-2 + user msg]   -> KV cache: 9K tokens
      ...
      Turn N: context grows until limit. Need compaction or summarization.
      PROBLEM: tokens wasted on stale history. Quality degrades as history
      fills the attention window with irrelevant past turns.

    ELAI_CC (stateless per-call):
      Call 1: [fresh prompt assembled from SSB+DKG+knowledge] -> 3K tokens
      (KV cache freed)
      Call 2: [fresh prompt assembled from SSB+DKG+knowledge] -> 3K tokens
      (KV cache freed)
      Call 3: [fresh prompt assembled from SSB+DKG+knowledge] -> 3K tokens
      (KV cache freed)
      ...
      Call N: still 3K tokens. No growth. No degradation. No compaction.

  VRAM LIFECYCLE PER CALL:

    IDLE:       model weights [7.2GB] + empty [3GB free]
    INFERENCE:  model weights [7.2GB] + KV cache [~1-3GB building]
    GENERATING: model weights [7.2GB] + KV cache [~1-3GB peak]
    COMPLETE:   model weights [7.2GB] + KV cache FREED [3GB free again]

    The KV cache is EPHEMERAL. Built from scratch for each prompt.
    Released completely after the response is generated.
    No accumulation. No growth. No reset needed. No OOM risk from context.

  HOW BABY STEPS MAINTAIN CONTINUITY WITHOUT CONVERSATION:

    The model has complete amnesia between calls. All continuity lives in
    deterministic infrastructure:

    1. Baby step N finishes. Its output (code edits) is written to DISK.
    2. SSB records: "step N wrote fn X in file Y. Tests: 3/3 pass." (~50 tokens)
    3. DKG re-indexes the changed files (<1s, CPU). New code is now searchable.
    4. Baby step N+1's prompt is assembled FRESH by the context budget allocator:
       - Queries SSB: "what happened recently?" -> gets step N's summary
       - Queries DKG: "what code exists at the edit target?" -> sees N's code
       - Queries knowledge engine: "what's relevant to this task?" -> retrieval
    5. The model receives a curated 3K-token prompt. No stale history. No bloat.
       Every token is relevant to THIS baby step, not residue from past steps.

    Result: baby step 80 gets the SAME quality context as baby step 1.
    No context window degradation over time. No "lost in the middle" problem.
    The system's understanding of the project IMPROVES over time (DKG gets
    richer, SSB has more records to filter from) while the prompt size
    stays CONSTANT within the attention ceiling.

  PREFIX CACHING (vLLM optimization, not context growth):

    vLLM and some ollama backends cache the KV computation for common
    prompt prefixes. If Slot 1-3 (system prompt, rules, telescope) are
    identical across consecutive baby steps, the prefix KV cache is REUSED.

    This is pure speedup:
    - Without prefix cache: each call computes KV for all ~1K prefix tokens
    - With prefix cache: prefix KV reused, only new tokens computed
    - Saves ~200-500ms per call on MICRO tier prompts
    - Evicts automatically when the prefix changes (e.g., new phase starts)

    This is NOT context growth. The cached prefix occupies the SAME VRAM
    it would during inference. It just persists between calls to avoid
    redundant computation. If VRAM is needed for a larger prompt, the
    cache evicts. Zero risk.

  WHY THIS MATTERS FOR TOKEN EFFICIENCY:

    In a chat UI, you pay the "context tax" — every turn carries all
    previous turns as dead weight. A 20-turn coding session on Claude Code
    might have 80% of the context window filled with stale conversation.

    In elai_cc, 100% of the context window is active, relevant content.
    The budget allocator has FULL CONTROL over every token. There is no
    "history" competing for space with the actual task.

    This is how a 3K-token MICRO prompt outperforms a 16K-token chat
    prompt: no noise, no history tax, every token selected by code.


========================================================================
8. QUALITY COMPENSATION MECHANISMS
========================================================================

Five strategies that make the SYSTEM compensate for model weakness:

STRATEGY A: NARROWING (decompose until trivial)
  Make each baby step so small that even a weak model succeeds.
  Metric: "Could a first-year CS student implement this given the
  function signature, test, and one example?" If no, decompose further.
  The decomposer is calibrated per model tier (section 3).

STRATEGY B: TEMPLATING (reduce generation to slot-filling)
  For common patterns (CRUD, REST handlers, tests, config loading),
  maintain per-project and per-language code templates.
  Sources:
  - DKG: extract patterns from existing codebase (surgical mode)
  - Rules engine: language-specific idiom templates (greenfield)
  - FlashResearch: best-practice templates from official docs

  Template application:
  1. Identify pattern match (baby step task matches template category)
  2. Generate template skeleton with blanks
  3. LLM fills only the blanks (domain-specific logic)
  4. Template structure guarantees correctness of everything around blanks

  Template categories (initial set):
  - FUNCTION_IMPL: signature given, fill body
  - TEST_CASE: function under test given, fill assertions
  - ERROR_HANDLER: error type given, fill match arms
  - CONFIG_STRUCT: fields given, fill validation logic
  - API_ENDPOINT: route + types given, fill handler logic

STRATEGY C: VERIFICATION DENSITY (catch errors faster)
  Small model = more errors. Response: check more frequently.

  MICRO tier check frequency:
  - After EVERY line of generated code (not every edit — every LINE)
    via grammar-guided generation that validates syntax incrementally
  - T1 rules check after every edit (same as larger tiers)
  - T2 tree-sitter parse after every edit (same as larger tiers)
  - T3 compilation check after EVERY function (not every baby step)

  This catches errors within seconds, not minutes. The model fixes one
  broken line instead of debugging 15 lines of cascading errors.

STRATEGY D: ENSEMBLE VIA BEST-OF-N (limited use, research-constrained)
  Research (LLM-Code-Generation-Summary.txt section 4c):
    "Requires N > 32 for substantial gains, often N > 100 for complex tasks."
    "Defeats purpose of using small models (efficiency)."
    "Cannot fix fundamental knowledge gaps."
  Best-of-3 is insufficient for statistical recovery on 7B models.
  USE ONLY for: first baby step of each concept (pattern-setting step where
  correctness matters most — siblings copy this pattern).
  For all other steps: decomposition + constrained decoding are cheaper and
  more effective (section 4f: +5.5-6.5% Pass@1 vs best-of-N's diminishing returns).

STRATEGY E: PROGRESSIVE ESCALATION
  Start with the smallest model that MIGHT work. Escalate only on failure.

  Escalation chain (model depends on VRAM tier):
  12GB:
    1. Qwen2.5-Coder-7B NF4+FA2+TQ8 — try first (90% pass@1)
    2. Qwen2.5-Coder-3B NF4+FA2 — on BubbleUp (less quality, more context)
    3. CLOUD fallback (API, costs money) — last resort, user must approve
    4. HUMAN — system shows what it tried, what failed, asks for help
  48GB:
    1. Qwen2.5-Coder-32B NF4+FA2+TQ4 — try first (92.7% HumanEval)
    2. Qwen2.5-Coder-7B NF4+FA2 — on BubbleUp (faster, more context)
    3. CLOUD fallback
    4. HUMAN

  Each level in the chain gets a FRESH context assembly and the full
  retry budget (not the remaining retries from the previous level).
  The higher model gets the benefit of seeing what the lower model
  attempted and why it failed (via SSB records).

  Expected distribution (based on SWE-bench small model data):
  - MICRO handles: ~60-70% of baby steps on first try
  - After 5 retries: ~85-90% of baby steps
  - Needing escalation: ~10-15% of baby steps
  - Needing human: <2% of baby steps (architectural decisions, ambiguous requirements)

9. CONTEXT WINDOW OPTIMIZATION (every token earns its place)
========================================================================

FORMATTING REMOVAL (research-grounded, free token savings):

  Research (LLM-Code-Generation-Summary.txt section 3e):
    "Formatting removal (indentation, whitespace, newlines) before inference:
    avg 24.5% token reduction, virtually zero accuracy degradation."

  On a MICRO tier 3K budget, 24.5% = ~735 tokens saved. That's enough for
  an entire additional function example in context — or 3 more SSB entries.

  Implementation:
    1. CODE CONTEXT (Slot 5) formatting removal:
       - Strip leading/trailing whitespace per line
       - Collapse multiple blank lines to single blank
       - Remove trailing comments that just repeat the code
       - Preserve: string literals, docstrings, significant indentation (Python)
       Language-specific: Python preserves indentation (semantic). All others strip.

    2. OUTPUT FORMATTING RESTORATION:
       After LLM generates code (in diff format), apply tree-sitter pretty-print
       to restore proper indentation before writing to disk.
       The model generates semantically correct but minimally formatted code.
       The system restores formatting deterministically.

    3. SSB ENTRIES (Slot 6) compression:
       SSB summaries already use ~50 tokens per entry. Further compress by
       removing redundant fields (agent_id in every entry when same agent).

    4. GRC HISTORY (Slot 7) compression:
       Keep only the conclusion of each GRC step, not the full reasoning chain.
       Full chain available via SSB lookup if needed.

  This is applied during context budget assembly (Phase 3E).
  Zero model quality impact. Purely mechanical token savings.
  Benchmark harness (Measurement 8, to add): verify accuracy with/without
  formatting removal on the 50 task fixtures.


TOKEN AUDIT CHECKLIST (applied to every slot):

  Slot 1 (SystemPrompt):
  - MICRO: strip to absolute minimum. No explanation of the system.
    Just: role, output format, 3 critical rules.
  - Remove all "you are a helpful assistant" framing (wastes tokens, no value)
  - Remove examples from system prompt (move to few-shot in CodeContext)
  - Target: 200 tokens for MICRO, 330 for LARGE.

  Slot 2 (Rules):
  - MICRO: top 5 rules only, selected by: (1) rules that triggered in last
    3 baby steps, (2) rules for the file being edited, (3) CRITICAL rules.
  - Rules stored as compact DSL, not natural language.
    BAD:  "When writing error handling code, always use the Result type
           instead of panicking with unwrap()."
    GOOD: "RULE: no_unwrap | scope: non-test | action: WARN"
  - Target: 150 tokens for MICRO, 500 for LARGE.

  Slot 3 (Context Telescope):
  - MICRO: skip Layer 1 (project vision) and Layer 2 (concept summary).
    Include only Layer 3 (phase goal) and Layer 4 (step context).
    The model doesn't need the big picture for a 15-line baby step.
  - LARGE: full telescope (all 4 layers).
  - Target: 400 tokens for MICRO, 1000 for LARGE.

  Slot 4 (RepoMap):
  - MICRO: OMITTED. Not worth the tokens. The baby step already names
    the exact file and function. The model doesn't need to know about
    other files it's not touching.
  - SMALL: top 10 symbols only (by PageRank, personalized).
  - MEDIUM+: full personalized repo map.
  - Target: 0 for MICRO, 2000 for LARGE.

  Slot 5 (CodeContext):
  - MICRO: max 3 code snippets. Each snippet: function signature +
    body OR just signature if body not needed.
    Selection priority: (1) the function being edited, (2) one caller,
    (3) one similar function (few-shot example).
  - A-RAG compression: enabled for all tiers, more aggressive for MICRO.
  - ShortCoder (Phase 4B): apply AST simplification to context snippets,
    removing unnecessary details (comments, long string literals, etc.)
  - Target: 1200 tokens for MICRO, 6000 for LARGE.

  Slot 6 (SSB entries):
  - MICRO: last 2 entries only, filtered by file overlap.
    Compressed format: "prev_step: wrote fn X in file Y. Tests: 3/3 pass."
  - Not the full SSB record with all metadata. Just the ARTIFACT summary.
  - Target: 200 tokens for MICRO, 1500 for LARGE.

  Slot 7 (GRC history):
  - MICRO: last CONVERGE step only (the conclusion, not the reasoning chain).
    100 tokens max. If the model needs to reason, it uses its own GRC budget.
  - LARGE: last 3 steps of reasoning chain.
  - Target: 100 tokens for MICRO, 1000 for LARGE.

  Slot 8 (OutputReserve):
  - MICRO: 750 tokens. One function + one test + structured JSON wrapper.
    If the model needs more: the task is too big. Split it.
  - LARGE: 4000 tokens. Room for longer implementations.

TOKEN RECLAMATION TECHNIQUES:
  1. Abbreviate file paths: src/middleware/auth.rs -> middleware/auth.rs
     (model can infer src/ from context)
  2. Strip doc comments from code snippets (comments waste small model attention)
  3. Collapse import blocks: show as "// [12 imports]" with expand-on-request
  4. Use symbol names instead of full signatures when context is clear
  5. Deduplicate: if the same type appears in 3 snippets, define it once

10. CONSTRAINED DECODING (vLLM integration for output quality)
========================================================================

vLLM supports several constrained generation modes that directly improve
small model output quality:

JSON SCHEMA MODE:
  vLLM --guided-decoding-backend=outlines can enforce JSON schemas.
  Every LLM call in elai_cc should specify its output schema.
  This eliminates: mixed code/prose, missing fields, wrong types.
  Cost: minimal latency overhead (~5% slower generation).

GRAMMAR-GUIDED GENERATION:
  For code output: define EBNF grammars per language.
  The model can ONLY generate syntactically valid code.
  This eliminates: unclosed brackets, invalid syntax, runaway generation.
  Pre-built grammars for: Rust, Python, TypeScript, Go (from tree-sitter).
  Cost: moderate latency overhead (~10-15% slower generation).

REGEX CONSTRAINTS:
  For structured fields (file paths, function names, version strings):
  constrain to regex patterns. Prevents hallucinated paths.

STOP SEQUENCES:
  Aggressive stop sequences prevent the model from over-generating:
  - For code: stop at closing brace matching the function level
  - For edits: stop after the "new" field in the diff JSON
  - For plans: stop after the TOML closing bracket

IMPLEMENTATION:
  ConstrainedDecodingConfig {
    mode: DecodingMode,               // JSON_SCHEMA | GRAMMAR | REGEX | NONE
    schema: Option<JsonSchema>,        // for JSON_SCHEMA mode
    grammar: Option<String>,           // for GRAMMAR mode (EBNF)
    regex: Option<String>,             // for REGEX mode
    stop_sequences: Vec<String>,       // always applied
    max_tokens: usize,                 // hard output limit
  }

  Each agent role has a default ConstrainedDecodingConfig.
  Each baby step can override specific fields.
  The orchestrator passes this to the provider (vLLM, ollama) at call time.

OPEN QUESTIONS (for user decision)
========================================================================

1. Should the baseline measurement run automatically on first model use,
   or require explicit /benchmark command?

   RECOMMENDATION: automatic on first use, with progress bar.
   Takes ~5-10 minutes. Results cached forever until model changes.
   User can re-run with /benchmark --model <name>.

2. For MICRO tier, should the Context Telescope skip project vision
   (Layer 1) or include a ULTRA-compressed version (~50 tokens)?

   RECOMMENDATION: ultra-compressed 50-token version.
   Even for tiny tasks, knowing "this is a SaaS app" vs "this is a game
   engine" prevents the model from choosing wrong patterns. 50 tokens
   is cheap insurance.

3. Should template generation be fully deterministic (from DKG + types)
   or use a lightweight LLM pass to generate templates?

   RECOMMENDATION: deterministic from DKG where possible.
   Template STRUCTURE: deterministic (function signature, return type, error types).
   Template BLANK DESCRIPTIONS: can use LLM if helpful, but keep optional.
   Templates are infrastructure, not intelligence.

4. What should the default best-of-N count be?

   RECOMMENDATION: N=1 for TRIVIAL/SMALL baby steps, N=3 for critical.
   N=3 is the sweet spot: 3x wall-clock for ~30% quality improvement.
   N=5 shows diminishing returns for 5x cost (based on OpenAI best-of-N
   research, verified via web search).

5. Should the system expose retry/escalation activity to the user via TUI?

   RECOMMENDATION: yes, always.
   Show: [Attempt 2/5] [Error: MISSING_IMPORT] [Retrying with example...]
   User builds trust by seeing the system WORK through problems, not hide them.
   Zero token cost — this is orchestrator state, not LLM output.
