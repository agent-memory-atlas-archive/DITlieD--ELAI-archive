ELAI_CC IMPLEMENTATION GUIDE
For LLM-driven phase-by-phase implementation.
Date: 2026-04-06


HOW TO USE THIS GUIDE

You are implementing elai_cc, a Rust-native LLM workflow engine (INTERACTIVE-first).
This guide is the entry point. Each phase has its own step file in steps/.

Workflow per session:
  1. Read this file (you are here) for project scope and phase map.
  2. Identify which phase/sub-phase to implement.
  3. Read the step file: steps/phase-{N}.txt (e.g. steps/phase-1A.txt).
  4. The step file lists READ directives — read those spec files for detail.
  5. Follow the cycle: SKELETON -> VERIFY -> TEST -> IMPLEMENT -> MEASURE.
  6. Do not start a phase until its prerequisites are complete.

Setup prerequisite (before any phase):
  ONNX models must be pre-staged at .elai_cc/models/onnx/.
  Run setup script: download models + blake2 hash verify + write index_version.toml.
  Missing models at startup -> DEGRADED mode (BM25_ONLY), not crash.
  See core.txt section 4 (ONNX model storage) for canonical path and details.


PROJECT SCOPE (concise)

elai_cc is a Rust-native LLM workflow engine (INTERACTIVE-first, then AUTONOMOUS).
Human provides task, system executes the development cycle.
Not a CLI assistant — a development engine. INTERACTIVE (HITL) mode validated
end-to-end before AUTONOMOUS auto-advance is enabled (Phases 0-3 = INTERACTIVE,
Phase 4G = AUTONOMOUS enablement).

9 crates: core, providers, knowledge, reasoning, orchestrator, tools, plugins, rules, cli.
Base: claw-code-rust-port fork (61,317 LOC, 69 .rs files, 684 tests, compiles clean).
  Verified 2026-04-06 from local copy at .elai_cc/rust/. Older specs say 59,449/666 (stale).
Target dir: .elai_cc/ (all generated code goes here).

FSM states: IDLE -> PLANNING -> FEASIBILITY_PROBE -> TESTING_FIRST -> EXECUTING
  -> AUDITING -> MEMORIZING -> COMPLETE -> IDLE.
Storage: msgpack (disk), postcard (wire), SQLite WAL (SSB inter-agent state).
Parallelism: BSP supersteps with typed channels (LastValue, Topic, Ephemeral, Untracked).

Hardware: Phase 0 = 1x RTX 3060 12GB. Production = 2x RTX 3090 24GB.
Phase 0 model: Qwen2.5-Coder-7B-Instruct NF4+FA2 (5.18GB, 90% code pass rate).
  Fallback: Qwen2.5-Coder-3B-Instruct NF4+FA2 (1.92GB, 72% pass, longer context).
  Gemma 4 E2B: REJECTED (mixed head_dim blocks FA2, 18x larger KV cache).
Production models: Qwen2.5-Coder-32B NF4+FA2+TQ4 (all roles, 48GB GPU).
  Per-role model routing deferred until multi-model quality comparison done.
  Cloud fallback available.
Model storage: F:\.ELAI_workflow\.elai_cc\models\ (local HF format, not ollama).
Inference: sidecar server (python/elai_inference/server.py), not ollama.
  Ollama is fallback only. Sidecar provides: FA2, DoLa, steering, TQ8/TQ4.
Model-agnostic: all behind LlmProvider trait.

Key properties:
  - Entropy-quarantined: all time/randomness via injectable traits (deterministic testing)
  - Deterministic-first: all outputs verified by deterministic scripts
  - Token-efficient: msgpack, postcard, phase-aware context loading
  - Per-project: all state lives inside project directory
  - Code-driven orchestration: ~330 tokens meta-instructions per turn, not 1600+

Two deliverables: D1 (standalone elai_cc), D2 (Empire integration, deferred).

Full architecture: docs/specs/architecture-overview.txt
All specs index: docs/specs/design_index.txt

EVERY PHASE CYCLE

  0. IMPROVE   — ground all claims, add pre-gates and deterministic checks, inject adversarial tests
  1. SKELETON  — minimal structure, stubs, types
  2. VERIFY    — does it compile? do existing tests still pass?
  3. TEST      — write contract/integration tests (they FAIL — that's the point)
  4. IMPLEMENT — make tests pass
  5. MEASURE   — collect metrics (compile time, test count, LOC, coverage)
  6. DECIDE    — fix issues found, then proceed

  Step 0 (IMPROVE) runs once per phase before implementation begins.
  Trigger: "improve phase {N}" in the workflow. See planning-workflow skill for full protocol.
  Produces: grounded phase file with PRE_GATE, DETERMINISTIC_CHECK, ADVERSARIAL, ACCEPTANCE blocks.
  Grounding log: workflow/reasoning/phase-{N}-grounding.md
  Idempotent: can run multiple times; no-ops if nothing changed.

  No phase starts until previous phase's tests pass.
  Metrics stored in: .elai_cc/metrics/phase_{N}.toml


IMPROVED PHASE STEP FORMAT

  Each step in an improved phase file contains these blocks (added by step 0):

  {N}.{M} [STEP NAME]
    PRE_GATE:
      - [deterministic condition that must hold before this step starts]
      - [command or check, not subjective criteria]
    TASK:
      - [original step content, unchanged]
    DETERMINISTIC_CHECK:
      - [command/assertion that proves step succeeded, runnable by auditor]
    ADVERSARIAL:
      - If [assumption] is wrong, [consequence]. Test: [deterministic check].
    ACCEPTANCE:
      - [binary pass/fail criterion per deliverable, tied to command or metric]
    GROUNDING:
      - "[claim]" -> [GROUNDED|VERIFIED|INGESTED|UNGROUNDED]: [evidence]
