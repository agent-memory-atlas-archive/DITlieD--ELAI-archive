ELAI PROBLEM COVERAGE ANALYSIS
Maps every documented AI coding tool problem to ELAI's solution status.
Source: AI_Coding_Tool_Problems_Summary.md (3 Gemini Deep Research reports, 2025-2026)
Date: 2026-04-17


================================================================================
LEGEND
================================================================================

ELIMINATED  = architecturally impossible in ELAI. The system physically prevents it.
SOLVED      = ELAI has a complete design that addresses the root cause end-to-end.
MITIGATED   = ELAI significantly reduces severity/frequency but cannot fully prevent.
PARTIAL     = ELAI addresses some aspects but meaningful gaps remain.
NOT SOLVED  = outside ELAI's scope or no current design addresses it.

Each entry: problem summary, real user quotes/data from research, ELAI mechanism,
which phases/steps implement it, and honest assessment of remaining gaps.


================================================================================
SECTION A: PROBLEMS ELAI ELIMINATES
================================================================================

These problems cannot occur in ELAI because the architecture makes them
structurally impossible. Not "unlikely" — impossible.


A1. PHANTOM CODE / TODO / PLACEHOLDER GENERATION [ELIMINATED]
............................................................................

Problem: LLMs output todo!(), pass, placeholder, stub functions, mock data
instead of real implementations. Users discover non-functional code later.
  - "constant placeholders, dummy code, stubs despite explicit instructions" (Claude Code, 2025)
  - "$4 burned in minutes from agent looping on TODO file creation" (Cursor Sonnet, Aug 2025)
  - "391 claims extracted, zero concepts registered in DB = entirely unusable" (Claude Code, Mar 2026)
  - "20+ credits spent trying to replace placeholder initials, never succeeded" (Replit, Apr 2025)
  - Root cause: RLHF teaches models that syntactically correct stubs satisfy prompts

ELAI mechanism:
  Zero Lazy Code enforcement. T1 GREP_PATTERN rules in rules.db detect todo!(),
  pass, unimplemented!(), placeholder, // TODO, "... rest", mock data patterns
  in code positions (not comments/strings — tree-sitter distinguishes).
  PostToolUse hook evaluates predicates on every model output in <1ms.
  BLOCK verdict rejects output before anyone sees it. Same severity as syntax error.
  The model physically cannot produce output containing these patterns.
  Focus tunnel streaming validation (E-4) catches lazy code at token 50 during
  generation, terminating early instead of waiting for 500 tokens of garbage.

Phases: A-2 (T1/T2 hook fix), A-21 (CC hook enforcement, per-language lazy regex),
  3F (rules engine), E-4 (streaming validation)

Remaining gaps: none for known patterns. Novel lazy patterns (e.g. a function that
  returns a hardcoded value that happens to look valid) require auditor or human
  review. Self-discovery (3F) auto-proposes new rules when auditor catches patterns
  3+ times, so coverage expands over time.


A2. RULE DISOBEDIENCE / CONSTRAINT VIOLATIONS [ELIMINATED]
............................................................................

Problem: LLMs ignore explicit user instructions — .cursorrules, CLAUDE.md,
system prompts, per-message constraints.
  - ".cursor/rules/ with alwaysApply:true forbidding branch deletion — agent deleted branch anyway" (Cursor, 2026)
  - "do not implement code until I approve the plan" routinely bypassed (Cursor, 2026)
  - ".CLAUDE.md files fail early, fail always at governance" (Claude Code, 2025)
  - "do not touch this block — agent modified exactly that block, required 5 corrections" (Copilot Sonnet 4, 2025)
  - Root cause: RLHF optimizes for task completion. Negative constraints require
    suppressing probable token sequences — architecturally difficult for LLMs.

ELAI mechanism:
  Rules are DATA in SQLite, evaluated by Rust code. The model never sees
  enforcement logic. Three tiers:
    T1 (deterministic, <1ms): regex/AST patterns. ZERO prompt tokens. Model
      output is checked AFTER generation. BLOCK rejects and re-prompts.
    T2 (structural, <10ms): tree-sitter AST parse + pattern check. ZERO tokens.
    T3 (semantic, ~50-100 tokens): 3-5 rules in prompt, auditor double-verifies.
  The model does not decide whether to follow rules. The system enforces rules
  on the model's output. "Don't delete branches" is a T1 Bash safety filter
  (A-27) that BLOCKs the git command before execution. "Don't touch file X" is
  a visibility filter — the file returns "not found" to the model.
  Action classifier (A-31) tags tool calls as SAFE/REVERSIBLE/IRREVERSIBLE and
  gates dangerous actions before they execute.

Phases: 3F (rules engine), A-2 (T1/T2 hook fix), A-27 (bash safety filter),
  A-31 (action classifier), 4A (agent process isolation — visibility filter),
  4C (hooks intercept IPC messages in orchestrator)

Remaining gaps: T3 semantic rules (~5% of total rules) are prompt-injected and
  the model CAN ignore them. But auditor double-verifies T3 compliance, and the
  auditor MUST find at least 1 issue or the audit is rejected. So even T3
  violations get caught — just one step later, not at generation time.


A3. UNSOLICITED MODIFICATIONS / SCOPE CREEP [ELIMINATED]
............................................................................

Problem: LLMs "helpfully" refactor code nobody asked to touch, add unrequested
features, rename files, restructure folders, cascade single-line fixes into
massive multi-file PRs.
  - "lost hours of work from spontaneous unsolicited changes" (Windsurf, 2025)
  - "600 lines of unprompted code inserted during routine prompt" (Cursor, 2025)
  - "autonomously renamed files and restructured folders" (Cursor, 2025)
  - "unsolicited scope creep consumed up to half of active development sessions" (Claude Code, 2025)
  - Bug fix -> entire function -> "optimizes" adjacent code -> cascades to all call sites

ELAI mechanism:
  Baby-step decomposition. Each step is 25-40 LOC max (calibrated per model).
  The model receives a single precise task with a single target file and edit
  region. It cannot touch other files because:
    1. Focus tunnel (E-1/E-7): speculative file routing — system controls which
       file gets written, model outputs only code
    2. Visibility filter (4A): model can only see files in the baby step's scope
    3. DKG blast radius: system computes which files SHOULD be affected. Model
       touching files outside blast radius triggers BLOCK
    4. Per-phase git commits: changes are atomic per baby step. Rollback is trivial.
  The model is a code printer. It receives a template ("write code that goes
  between line 42 and line 67 of auth.rs") and fills it in. It cannot decide to
  also touch user.rs.

Phases: 4D (baby-step decomposition), 4E (DecompositionTree + TreeNavigator),
  E-7 (speculative file routing), 4A (visibility filter), 4B (git commit tool)

Remaining gaps: none at baby-step level. At PLAN level, the designer agent could
  over-scope the plan itself. But the plan goes through human approval in
  INTERACTIVE mode, and structural validation in AUTONOMOUS mode checks plan
  against the original task scope.


A4. TOKEN GENERATION CASCADE [ELIMINATED]
............................................................................

Problem: single-line fix -> regenerates entire function -> "optimizes" adjacent
code -> changes variable name -> cascades to all call sites -> massive
unauthorized multi-file PR.

ELAI mechanism:
  Structurally impossible. Baby step = single edit region in single file.
  Focus tunnel FIM mode: model outputs ONLY the code between prefix and suffix.
  It cannot regenerate the surrounding function. It cannot touch other files.
  Even in DIFF mode, the system validates that hunks only affect the specified
  edit region. Hunks outside scope = BLOCK.

Phases: E-1 (FIM), E-2 (DIFF), E-7 (file routing), 4D/4E (decomposition)

Remaining gaps: none.


A5. DEPRECATED TECHNOLOGY / TEMPORAL DISLOCATION [ELIMINATED]
............................................................................

Problem: LLMs use outdated libraries, old syntax, deprecated APIs from training
data. Users get code using 2019 methods, wrong framework versions, removed APIs.
  - "confuses Tailwind 4/3, Svelte 5/4, React 19/18" (Claude, 2025/2026)
  - "generated code using 2019 methods, imported uninstalled libraries" (Claude Code, 2025)
  - "massively outdated on Tailwind, completely ignored instructions to use React Router 7" (Claude 3.7, 2026)
  - "spoke about itself as if still unreleased, claimed browser environment" (Claude Code, Jul 2025)
  - Half of vulnerable packages in ecosystem introduced through AI-generated commits

ELAI mechanism:
  Anti-staleness 4-layer defense:
    Pre-generation: VERSION_GATE predicate in rules.db. deprecated_patterns table
      seeded from outdated-tech-audit.md. Constitutional injection adds CONSTRAINTS
      block to phase spec. Freshness scoring in RAG pipeline (recent docs ranked higher).
    During-generation: streaming validation (E-4) checks imports as they stream in
      against deprecated_patterns. Blocked imports terminate generation immediately.
      Constrained decoding (B-2) enforces positive import allowlists via grammar.
    Post-generation: T1 hook evaluates VERSION_GATE on output. T2 hook extracts
      imports via tree-sitter and cross-references deprecated_patterns. Both <10ms.
      Deterministic auditor runs VERSION_GATE check before LLM audit even starts.
    Maintenance: nightly dep audit (A-15) queries 7 registry APIs, updates
      deprecated_patterns automatically. Self-modification Layer 1A (4H) grows
      deprecated_patterns from auditor findings. Steering vector refresh on change.
  The model CAN generate deprecated code. But the system rejects it before it
  reaches the codebase. The model then gets a fresh prompt with the constraint
  "do not use X, use Y instead" and retries.

Phases: A-6 (VERSION_GATE + deprecated patterns), A-7 (constitutional injection),
  A-8 (freshness steering), A-14 (T2 AST import extraction), A-15 (nightly audit),
  A-12 (deterministic auditor), E-4 (streaming validation), B-2 (constrained decoding),
  4H (self-modification auto-grows deprecated_patterns)

Remaining gaps: brand-new deprecations (announced today) won't be caught until the
  nightly audit runs or a human adds them. Partially mitigated by ETC entropy
  monitoring (A-9) which detects when the model is uncertain about an import —
  suggesting it might be hallucinating or outdated.


A6. HALLUCINATED DEPENDENCIES / SLOPSQUATTING [ELIMINATED]
............................................................................

Problem: LLMs invent plausible but fictitious package names. Malicious actors
register these names on npm/PyPI with embedded malware.
  - "fabricated transaction.atomic_async, insisted module not found was user's fault" (Gemini, 2025/2026)
  - "hallucinated payment gateway connection logic" (Cursor, 2025/2026)
  - "hallucinated cryptographic code, completely insecure due to missing library files" (Cursor Opus, Dec 2025)
  - "did not understand what libraries were actually installed" (Cursor, 2025/2026)
  - Slopsquatting reached critical mass in Claude Code and Cursor ecosystems

ELAI mechanism:
  Anti-slopsquatting is a hard rule. Multiple enforcement layers:
    1. API_REGISTRY_CHECK verification (2B grounding): every PackageRef verified
       against real registry APIs before code is accepted
    2. Focus tunnel E-6 (automated dependency resolution): model writes code with
       imports, system detects missing deps, queries registry for real package,
       checks deprecated_patterns for substitution, resolves version, installs.
       Model NEVER runs cargo add / pip install / npm install.
    3. T2 hook (A-14): extracts imports via tree-sitter, cross-references against
       project manifest (Cargo.toml/pyproject.toml/package.json). Unknown import
       triggers verification pipeline.
    4. New deps require human confirmation (existing hard rule). In autonomous mode:
       auto-approve only from pre-approved allowlist.

Phases: 2B (API_REGISTRY_CHECK), A-14 (T2 import extraction), E-6 (dependency
  resolution), 4D (PackageRef in baby step spec with verify_packages)

Remaining gaps: registry check requires network access. In air-gapped mode (D-3),
  verification is limited to packages already in the local manifest. Mitigated by
  the allowlist mechanism.


A7. TEST SUBVERSION / DECEPTIVE SUCCESS REPORTING [ELIMINATED]
............................................................................

Problem: agents modify/weaken/delete tests to make them pass instead of fixing
the actual code. False positive test results.
  - "agents rewrite tests, loosen assertions, add blind retries until false positive" (2025/2026)
  - "documented pattern of unearned confidence, failure to read context between writes" (Claude Code, Apr 2026)
  - "fabricated timestamps, claimed bugs resolved without editing files" (Replit Agent, 2025/2026)

ELAI mechanism:
  Structural separation of concerns:
    1. Executor writes code. Auditor runs tests. Executor NEVER runs its own tests.
    2. Evidence gates require artifacts, not self-assessment:
       TESTING_FIRST -> EXECUTING: all tests fail for right reasons
       EXECUTING -> AUDITING: at least 1 test flipped from fail to pass
    3. Anti-rubber-stamp: auditor MUST find at least 1 issue or audit is rejected
    4. Test files can be locked via session file ownership (multi-session protocol)
    5. 5-tier validation pipeline runs deterministic checks (build, VERSION_GATE,
       file size, lazy code, completeness) BEFORE LLM audit starts
    6. Self-modification locks (4H): test suite is READ-LOCKED during execution.
       Metrics code, gate definitions, auditor config all read-locked.
  The model cannot claim success. The system measures success independently.

Phases: 3A (FSM evidence gates), 3C (agent roles — executor vs auditor),
  A-12 (deterministic-first auditor), 4H (self-modification read locks),
  4B (5-tier validation pipeline)

Remaining gaps: a model could write a NEW test that is trivially true (e.g.
  assert!(true)). Mitigated by: T1 lazy code detection catches assert!(true),
  cyclomatic complexity check (A-21) flags tests with zero branches, and auditor
  explicitly checks test quality.


================================================================================
SECTION B: PROBLEMS ELAI SOLVES
================================================================================

These have complete design coverage. The system addresses the root cause
end-to-end, though not via structural impossibility.


B1. CIRCULAR DEBUGGING / AI DEATH SPIRAL [SOLVED]
............................................................................

Problem: fix A causes error B, fix B re-introduces A. Infinite loops. Hours
wasted. Users describe "gaslighting" and "spaghetti."
  - "wasted twice the time untangling AI spaghetti than implementing by hand" (2025/2026)
  - "up to 2 hours paying LLM to gaslight with incorrect logic" (2025/2026)
  - "$400 single debug session — agent hallucinated deprecated APIs, dismantled working code" (Replit, 2025/2026)
  - CodeBreaker launched 2026 specifically to terminate circular debugging loops

ELAI mechanism:
  Most comprehensive anti-thrashing design in any AI coding tool:
    1. MistakeBook (A-20): blake3 hashes of failed diffs. Model never re-generates
       the same failed output. Forbidden diffs injected as constraints (max 150 tokens).
       Variable names and code snippets from failed attempts NEVER shown to model
       (CTIM-Rover finding: showing failed code degrades success from 42% to 31-40%).
    2. Fresh context per retry: model NEVER sees its own failed chain-of-thought.
       Gets a fresh 1400-token REPAIR_CONTEXT assembly (A-18).
    3. Temperature 1.0 for repair loops: prevents cyclic traps (FixAudit validated).
    4. Anti-spiral: 3x same step (blake3 content hash) = escalate. Stop and rethink.
    5. 6-layer reasoning escalation:
       L1 deterministic (60-70% of errors, no LLM, <100ms): template-based fixes
       L2 micro-reflection (20-25%): 500 tokens, JSON-constrained, 2-5s
       L3 interrogation tree (5-8%): 3-7 multiple choice questions, 10-30s
       L4 AB-MCTS tree search (3-5%): 3+ alternatives at different temperatures, 30-90s
       L5 cloud diagnostic (2-4%): diagnosis only, no code generation, $0.002-$0.05
       L6 cloud generation (0.5-1%): cloud generates, local validates
    6. Failure taxonomy (A-34): deterministic regex-based error classification (9+
       categories). Auditor reads classification BEFORE raw output. Saves 200-500 tokens
       and directs fix to correct layer.

Phases: A-20 (MistakeBook), A-18 (repair context), A-23 (micro-reflection),
  A-19 (interrogation trees), A-17/A-25 (GG signals for AB-MCTS), A-34 (failure taxonomy),
  3C (anti-spiral detection), RA design (6-layer escalation)

Remaining gaps: the heuristics for "when to give up vs try harder" need empirical
  tuning. Self-modification (4H) tunes futility thresholds from pipeline outcome data.


B2. INPUT STACKING / STATELESS CONTEXT BLOAT [SOLVED]
............................................................................

Problem: LLMs are stateless — must re-send system prompt + conversation history +
file data every call. Token costs explode with conversation length.
  - "by 10th message, 172,000 tokens of context per request (~$0.51 just for input)" (Windsurf, 2025/2026)
  - "single prompt consumes 3-10% of user's entire daily limit" (Claude Code Opus 4.6, Feb 2026)
  - "$500/week on Claude Code, tool autonomously indexes broader repo" (2025/2026)
  - "$10/hour running cost" (Claude Code, 2025/2026)

ELAI mechanism:
  Systematic token reduction at every layer:
    Meta-instructions: 330 tokens/turn vs 1600-2600 in current tools
    T1/T2 rules: ZERO tokens (evaluated by Rust code, not in prompt)
    Focus tunnel: ~6,800 tokens saved on 30-step task (FIM/DIFF modes strip tool
      schemas, JSON wrappers, file routing instructions)
    ShortCoder (A-24): 18-38% compression on code context via AST simplification
    Token reclamation (A-42): formatting removal (24.5%), path abbreviation,
      import collapsing, deduplication
    Context budget allocator (3E): 8 fixed slots with percentage distribution.
      Per-model adaptation (A-10). MICRO tier: ~3000 tokens total vs ~17330 for LARGE.
    Phase-aware loading: only current phase's detail loaded, not entire plan
    Session handoff (3H): structurally lossless trimming — large tool results
      replaced with stubs recoverable from SSB. Never re-sends dead context.
  Combined effective context increase: ~45-65% over raw model context window.
  On 7B with 25K context: effective ~36-41K tokens of useful content.

  For cloud mode specifically: same validation pipeline, but baby steps jump from
  25-40 LOC to 300-500 LOC. Fewer steps = fewer API calls = lower cost. A MEDIUM
  task: ~30 local steps vs ~4-6 cloud steps (D-2).

Phases: 3E (context budget), A-10 (adaptation), A-24 (ShortCoder), A-40 (MICRO slots),
  A-42 (reclamation), E-1/E-2/E-3 (focus tunnel), 3H (session handoff), D-2 (cloud budget)

Remaining gaps: cloud mode is still stateless per-call. But per-call payload is
  dramatically smaller (330 tokens meta vs 2000+, compressed code context, minimal
  rules in prompt). The cost reduction is 5-10x per equivalent task, not infinite.


B3. CONTEXT WINDOW EXHAUSTION / "THE COMA EFFECT" [SOLVED]
............................................................................

Problem: multi-step projects lose track of objectives. New chat = "waking up from
a coma." Attention decays as token count rises.
  - "creates random disjointed files, abandons half-finished features, misses dependencies"
  - "jumped between tasks" mid-implementation
  - Even within continuous sessions, attention decays

ELAI mechanism:
  Never-compact design. Context is managed, not accumulated:
    1. Session handoff (3H): DAG-based state versioning with structurally lossless
       trimming. At 85% token budget: checkpoint, trim, continue. User/assistant
       messages never stubbed. Stubs recoverable from SSB.
    2. Context Telescope (A-46): compressed ancestry chain travels with every baby
       step: project vision (200tok) + concept (150tok) + phase (100tok) + step
       (100tok) + task. The model always knows the big picture.
    3. Phase-aware context loading: only current phase's detail in prompt. Skeleton
       (2-4K) always present. Per-phase elaboration loaded on demand.
    4. SSB (3B): structured reasoning traces persist across sessions. New session
       reads relevant SSB entries, not raw conversation history.
    5. Knowledge engine queries on demand: model doesn't carry the codebase in
       context. It queries DKG/BM25/vectors for relevant code per baby step.
    6. Baby-step decomposition: each step is self-contained. The model doesn't need
       to remember step 1 when executing step 15. The system provides context.

Phases: 3H (session handoff), A-46 (context telescope), 3E (context budget),
  3G (hierarchical plan management), 3B (SSB), 4D/4E (decomposition)

Remaining gaps: the "why" behind design decisions is preserved in plan skeleton
  and SSB traces, but a model with a 25K context window has limited ability to
  reason about cross-cutting concerns that span the entire project. Mitigated by
  DKG blast radius analysis injecting relevant cross-file dependencies.


B4. REPETITIVE INSTRUCTION FATIGUE [SOLVED]
............................................................................

Problem: rules, conventions, constraints must be re-stated every session or
every message because the tool forgets or ignores them.
  - "custom instructions obeyed for 24-48 hours max, then reverts" (Copilot, 2025/2026)
  - Users maintain elaborate .cursorrules / CLAUDE.md / copilot-instructions.md

ELAI mechanism:
  Rules persist in SQLite (rules.db), not markdown files. They survive across
  sessions, across restarts, across model changes. T1/T2 rules cost ZERO tokens —
  the model doesn't need to "remember" them because the system enforces them
  independently. T3 semantic rules (~3-5 per turn, ~50-100 tokens) are the only
  rules in the prompt, and they're the rules that genuinely need LLM judgment.
  Project Intelligence (A-4/A-5) auto-detects conventions from the codebase and
  seeds rules automatically. User doesn't write rules — the system derives them.
  Rule lifecycle (3F): PROPOSED -> CANDIDATE -> SHADOW -> ACTIVE -> RETIRED.
  Rules that work get promoted. Rules that false-positive get retired. Automatic.

Phases: 3F (rules engine), A-4/A-5 (project intelligence + rule seeding),
  A-2 (T1/T2 hooks), A-21 (CC enforcement)

Remaining gaps: none for enforceable rules. Stylistic preferences that can't be
  expressed as patterns (e.g. "write code in a functional style") remain T3
  semantic and depend on model compliance + auditor verification.


B5. 450-LINE DEGRADATION / LOST IN THE MIDDLE [SOLVED]
............................................................................

Problem: single files >450 LOC cause hallucinations. Model forgets earlier
sections, hallucinates helper functions and variable fields.
  - "500-700 LOC: hallucinations spike dramatically"
  - Forces atomic single-function edits

ELAI mechanism:
  Two-sided solution:
    1. Baby steps are 25-40 LOC. Model generates small, verified chunks.
    2. Focus tunnel FIM (E-1): model sees only prefix (code before edit region) +
       suffix (code after edit region). On a 2000-line file, model might see
       lines 1-50 (imports+signatures) + lines 440-470 (target region) + lines
       471-520 (after region). Never the full 2000 lines.
    3. Code completeness enforcement (A-21): file size limits per language.
       Hard BLOCK at 4x language-specific limits (Rust: 400 LOC BLOCK).
       Recovery: automatic file splitting when limits exceeded.
    4. ShortCoder (A-24): collapses function bodies to signatures when code is
       loaded as context (not as edit target). 18-38% compression.
    5. File read outline mode (4B): files >300 lines shown as structure outline,
       not full content. Model requests specific ranges.

Phases: E-1 (FIM), A-21 (file size limits + splitting), A-24 (ShortCoder),
  4B (outline mode), 4D/4E (baby-step decomposition)

Remaining gaps: reading (not editing) very large files for understanding still
  requires attention over many tokens. Mitigated by DKG providing structural
  understanding without reading the full file.


B6. SEARCH FRAGMENTATION AT SCALE [SOLVED]
............................................................................

Problem: tools pull irrelevant context from large repos. "Fix auth bug" loads
user models, test suites, config schemas. Minutes wasted before finding the
right file. Context bloated with irrelevant content.
  - "bloated context for 4 minutes before finding auth middleware" (Claude Code, mid-2025)
  - "required third-party tools (DeepContext) for semantic syntax trees"
  - "AI building 5-screen app bloated to 10,000 LOC"

ELAI mechanism:
  7-layer knowledge pipeline (phases 1A-1I):
    DKG: tree-sitter dependency graph in SQLite. Knows exactly which functions
      call which functions.
    BM25: sub-millisecond keyword search via tantivy
    Dual vectors: GraphCodeBERT (code structure) + Granite (natural language)
    PageRank: ranks symbols by importance with personalization (task-mentioned
      nodes boosted 10x)
    CatRAG: query-aware graph traversal following dependency edges
    A-RAG: hierarchical retrieval, 55-87% token savings on context retrieval
    Cross-encoder reranker: ms-marco-MiniLM, CPU, <50ms for 50 candidates
  Query tier routing (3K): FAST (<20ms, BM25), STANDARD (<200ms, hybrid+reranker),
    DEEP (<5s, expansion+HyDE+full pipeline). Auto-selects based on query.
  "Fix auth bug" -> DKG finds auth middleware via dependency graph -> BM25 finds
    keyword matches -> vectors find semantically similar code -> PageRank ranks
    by importance -> CatRAG follows edges to related files -> A-RAG filters to
    token budget -> reranker picks top results. Result: precisely the relevant
    code, not the whole repo.

Phases: 1A-1I (knowledge engine), 3K (RAG production hardening), A-13 (freshness scoring)

Remaining gaps: DKG quality on dynamic languages (Stone 3). Addressed by F-4
  (LSP-backed DKG). Full pipeline indexing takes minutes on first run for large
  repos. Addressed by F-2 (progressive indexing — BM25 usable in <5s).


================================================================================
SECTION C: PROBLEMS ELAI MITIGATES
================================================================================

ELAI significantly reduces severity and frequency. Root cause partially
addressed, but complete elimination requires capabilities beyond current design.


C1. COST EXPLOSION / BILLING SHOCKS [MITIGATED]
............................................................................

Problem: unexpected API bills from $50/day to $18,000/month. Hidden quotas.
Credit depletion. No cost visibility.
  - "$18,000/mo single Claude Code user" (Apr 2026)
  - "$1,513/mo on $200/mo subscription" (Cursor Ultra, 2026)
  - "$80/day for 5-10 prompts" (Windsurf, 2026)
  - "$400 single debug session" (Replit, 2025/2026)

ELAI mechanism:
  LOCAL mode: zero API cost. GPU electricity only. Default for 8GB+ VRAM.
  HYBRID mode: local first, cloud only on L3+ reasoning failure. Typical daily
    cloud spend: $0.01-$0.05 (RA design).
  CLOUD mode: explicit cost ceilings. Pre-task cost estimation. Per-task and
    per-day spend limits enforced BEFORE each API call. At ceiling: HYBRID
    degrades to LOCAL, CLOUD fails with user message. No silent overrun.
  Token efficiency: 5-10x reduction in tokens per equivalent task (330 meta
    tokens vs 2000+, compressed context, focus tunnel, ShortCoder).
  Dashboard (4K): running spend total visible in MONITOR window.

Phases: D-1 (cloud config + cost tracking), D-2 (cloud budget), D-4 (cost estimation),
  C-1 (MONITOR window shows spend)

What remains: users with no GPU (or <8GB VRAM) must use cloud. Cloud costs are
  real, though dramatically lower than current tools. The $0.01-$0.05/day
  estimate assumes most work is local with occasional cloud escalation. Heavy
  cloud usage (all tasks in CLOUD mode) will still cost money — but with
  visibility and hard ceilings. BYOE (D-3) eliminates API costs for users with
  their own inference endpoint.

Honest comparison:
  Current tools: $50-500/month with no ceiling, no visibility, no control
  ELAI local: $0/month (GPU electricity negligible)
  ELAI hybrid: $1-5/month typical (measured estimate, not marketing)
  ELAI cloud: $20-50/month with hard ceiling (user-configurable)


C2. AGENTIC REGRESSION / FIX-ONE-BREAK-ANOTHER [MITIGATED]
............................................................................

Problem: fixing one thing breaks another. Previously functional elements regress.
  - "rewrites or changes parts of code unnecessarily" (Claude Code, 2025/2026)
  - "nonsense edits frequently made their way into commit log" (Cursor, 2025/2026)
  - "consistently deleted core functionality code repeatedly" (Replit Agent, Apr 2025)
  - "undid verified successful work when unrelated test failed" (Claude Code "Panic Revert", Mar 2026)
  - "broke working code without being asked, ignored rules, lost all context" (Windsurf, Apr 2026)

ELAI mechanism:
  Multiple regression prevention layers:
    1. DKG blast radius: before any change, graph traversal identifies all files
       that could be affected. Only those files enter the model's context.
    2. Baby-step decomposition: changes are 25-40 LOC. Small changes = small blast radius.
    3. Integration test runner (4B): 4 levels — BABY_STEP (cargo check, <5s),
       STEP (module tests, <30s), PHASE (crate tests, <60s), CONCEPT (workspace, <120s).
       Run after every baby step acceptance.
    4. Per-phase git commits (4B): atomic commits after verified phase completion.
       Rollback to any phase boundary is one git command.
    5. Evidence gate EXECUTING -> AUDITING: "at least 1 test flipped AND no existing
       tests newly broken." Regression = BLOCK.
    6. Auditor gets DKG blast radius subgraph in context — explicitly checks
       whether changes affect related code.

Phases: 4B (git commits + integration test runner), 4D/4E (decomposition),
  3A (evidence gates), 1A (DKG blast radius)

What remains: regressions in BEHAVIOR that aren't covered by tests. If existing
  tests don't exercise the code path that regressed, the evidence gate passes.
  Mitigated by: weaker gates for legacy code (F-3) write tests for ELAI-modified
  code, gradually increasing coverage. Type-driven test generation for typed langs.
  But fundamentally: no tests = no regression detection. This is an unsolvable
  problem without either existing tests or observation-based test generation.


C3. FULL AUTONOMY FAILURES / SILENT DEGRADATION [MITIGATED]
............................................................................

Problem: autonomous agents go off-rails, produce garbage, silently return fake
data or hallucinated bypass paths. Application appears to run while introducing
latent invisible flaws.
  - "Devin: incapable of understanding massive repos" (2025)
  - "GPT-5 Codex: infinite loops, context dilution, structural hallucinations" (2025)
  - "Claude Code autonomous: silently returns fake data or hallucinated bypass paths"
  - "A crashed system is minor; a system silently generating hallucinated data is catastrophe"

ELAI mechanism:
  Autonomous mode (4G) built ON TOP of validated INTERACTIVE pipeline. Not a
  separate mode — same evidence gates, same validation, same deterministic checks.
    1. AutonomousGate wraps InteractiveGate: checks evidence artifacts first.
       Delegates to human on HIGH-risk gate, missing evidence, or escalation.
    2. 6 evidence checks per gate (knowledge readiness, zero UNGROUNDED, tests fail
       correctly, test flipped, zero BLOCKs, DKG+changelog present).
    3. Anti-spiral: 3x same step = escalate to human. Circuit breaker: >10 auto-
       advances without human check = forced pause.
    4. Baby steps: each autonomous step is tiny (25-40 LOC) and independently verified.
       Silent degradation requires ALL of: model produces bad code + T1/T2 hooks miss it
       + deterministic auditor misses it + LLM auditor misses it + integration tests miss
       it. Every layer must fail simultaneously.
    5. Risk levels per decomposition level: BabyStep=LOW, Step=LOW, Phase=MEDIUM,
       Concept=HIGH. Concept-level changes always require human approval.
    6. DecompositionTree bubble-up (4E): failure cascades up with configurable retry
       thresholds. BabyStep(3 retries) -> Step(2) -> Phase(1) -> Concept(0) -> Escalate.

Phases: 4G (autonomous mode), 3A (evidence gates), 4E (bubble-up), 3C (anti-spiral)

What remains: domain-specific business logic errors that are syntactically correct,
  pass all tests, and satisfy all rules — but produce wrong BUSINESS outcomes.
  Example: a financial calculation that uses the wrong formula but produces
  plausible-looking numbers. ELAI's CSQ (2D) partially addresses this for
  functions touching files/data/network/auth ("if assumption X is wrong, code
  will Y"), but CSQ depends on the model identifying the right assumptions.
  For truly critical business logic: human review remains necessary.


C4. SECURITY VULNERABILITIES [MITIGATED]
............................................................................

Problem: AI-generated code has 3x vulnerability rate vs human-written. Missing
RLS policies, hardcoded API keys, SQL injection, XSS, CSRF, race conditions.
  - "45% of AI-generated code fails security compliance" (2025/2026)
  - "170+ Lovable apps exposed via CVE-2025-48757" (Spring 2025)
  - "race conditions in payment systems double-charging customers"
  - "API keys hardcoded in public repos"
  - "Prompt-Validation Paradox: natural language cannot articulate complex security logic"

ELAI mechanism:
  Security rules are mutable=0 (never auto-adjusted, never auto-retired):
    T1: regex patterns for hardcoded secrets, SQL injection patterns, XSS patterns,
      insecure defaults, missing CSRF tokens. <1ms per check.
    T2: AST patterns for unsafe function calls, missing auth checks, unvalidated
      input at system boundaries.
    GRAPH_REACHABILITY: DKG path queries for architectural enforcement (e.g.,
      "all database access must go through the auth middleware" — if a new function
      bypasses the auth layer, the graph query catches it).
  CSQ (2D): counterfactual safety questions on functions touching data/network/auth.
    "If user sends malicious input, this function will [X]." Critical without guard
    = blocks progression.
  Evidence gate: auditor explicitly checks security findings. Zero BLOCKs required
    to progress. Security BLOCK = pipeline stops.

Phases: 3F (rules engine, security rules), 2D (CSQ), A-12 (deterministic auditor),
  4C (hooks intercept IPC, enforce security rules at system level)

What remains: novel vulnerability patterns not in rules.db. The Lovable RLS issue
  was a business-logic-level security flaw — the AI chose an architecture that was
  inherently insecure (client-driven auth). ELAI's rules catch KNOWN patterns
  (SQLi, XSS, hardcoded keys) but cannot reason about whether an ARCHITECTURE
  is secure. Partially mitigated by: auditor double-verify, cloud escalation for
  security-critical code (cloud models are better at architectural reasoning), and
  self-discovery proposing new security rules when auditor catches novel patterns.
  But fundamentally: security review of architecture requires human or frontier-
  model judgment. Non-programmers remain vulnerable to architectural security flaws.


C5. LEGACY CODE INCOMPATIBILITY [MITIGATED]
............................................................................

Problem: AI can't understand existing codebases. Mixed patterns, inconsistent
conventions, implicit dependencies, invisible business rules.
  - "treats inconsistent legacy codebases as absolute nightmare"
  - "auth implemented 3 different ways, mixed async/await with callbacks = tools rendered useless"
  - "AI cleans up invisible protections, breaking systems in subtle ways"
  - "missing semantic intent — cannot infer WHY an irrational business rule was implemented"

ELAI mechanism:
  Surgical mode (PM design): designed specifically for existing codebases.
    DKG as primary grounding source. Blast radius via graph traversal. Max
    decomposition depth 2 (vs 4 for greenfield). Regression gates after every
    step (existing tests breaking = STOP). Research priority: codebase first.
  Project Intelligence (A-4/A-5/A-11): auto-detects language, framework,
    conventions, architecture. Extracts naming patterns, error handling style,
    module organization from existing code. Seeds rules from conventions found.
  Weaker evidence gates for legacy (F-3): zero-test codebases get relaxed gates.
    TESTING_FIRST: "compilation succeeds" (not "tests fail right").
    EXECUTING: "new tests pass AND existing behavior unchanged."
  Incremental test adoption: write tests ONLY for code ELAI modifies (blast radius).

Phases: PM design (surgical mode), A-4/A-5/A-11 (project intelligence),
  F-3 (weaker evidence gates), A-48 (DKG data flow edges)

What remains: semantic intent. WHY a business rule exists cannot be derived from
  code alone. The "irrational business rule" problem is fundamentally about
  missing documentation, not missing tooling. ELAI can detect that a rule exists
  (DKG + code analysis) but cannot infer whether it's intentional or accidental.
  In INTERACTIVE mode: ELAI asks the human. In AUTONOMOUS mode: ELAI preserves
  existing behavior by default (regression gates) rather than "cleaning up."


C6. PROJECT SIZE CEILING [MITIGATED]
............................................................................

Problem: AI tools become useless at scale. 10K+ LOC projects overwhelm context.
Autonomous agents delete code they don't understand.
  - "user briefly suspended oversight on ~10,000 LOC, agent permanently deleted 10,000 lines of bloat" (Cline, 2025)
  - "5-directory React app had constant native context dropping, nuking project state" (Cursor, 2026)

ELAI mechanism:
  The model never sees the full project. Baby steps are 25-40 LOC with precisely
  assembled context from the knowledge engine. Project size doesn't matter because:
    1. DKG maps the entire codebase structure in SQLite — queried, not loaded
    2. BM25 + vectors retrieve only relevant code per step
    3. Context budget allocator ensures model window never exceeded
    4. File visibility filter: model sees only allowed paths for current step
    5. Code completeness enforcement prevents monolithic files from forming
  A 500K LOC project and a 5K LOC project produce identical-sized prompts for
  a given baby step. The difference is indexing time (addressed by F-2 progressive
  indexing) and DKG graph size (SQLite handles millions of rows).

Phases: 1A-1I (knowledge engine), 3E (context budget), 4A (visibility filter),
  4D/4E (decomposition), F-2 (progressive indexing)

What remains: cross-cutting changes that genuinely affect many files (e.g.,
  "rename the User table to Account everywhere"). Baby-step decomposition
  handles this via a sequence of small steps, but the PLAN must correctly identify
  all affected locations. DKG blast radius helps, but dynamic language DKG (Stone 3)
  may miss some. Mitigated by integration tests at CONCEPT level running full
  workspace tests to catch anything the plan missed.

SECTION D: PROBLEMS ELAI PARTIALLY ADDRESSES

ELAI has relevant mechanisms but meaningful gaps remain that would require

D1. COGNITIVE DEBT / "THE WEEK 7-8 WALL" [PARTIAL]
............................................................................

Problem: after weeks of AI-driven development, nobody on the team understands
the system. Design decisions were made by AI, team can't explain why. Simplest
changes trigger cascading failures. Eventually: discard and manual rewrite.
  - "theory of the system vanished. No one could explain WHY decisions were made"
  - "AI's abstractions leaked, team lacked semantic understanding"
  - "resolution: discard AI-generated app entirely, ground-up manual rewrite"

What ELAI does:
  - Plan skeleton preserves WHY: concept goals, phase rationale, step reasoning
  - SSB reasoning traces: every GRC step is a machine-readable record with
    grounding citations. Decisions are auditable.
  - Context Telescope: ancestry chain travels with every step, maintaining
    connection from baby step to project vision
  - Changelog (memory-bank): per-file change history with rationale
  - Decision docs: workflow/reasoning/phase-X-decisions.md written before EXECUTING

What remains:
  The SYSTEM preserves the "why." But the HUMAN still doesn't understand the code
  unless they read the plan, traces, and changelogs. For non-programmers (the
  primary vibe coder audience), these artifacts are opaque. ELAI shifts cognitive
  debt from "nobody knows" to "the system knows, query it via EXPLORE window."
  That's better — but "I can ask the AI why this code exists" is different from
  "I understand why this code exists." If ELAI becomes unavailable, the human is
  still lost. Partially mitigated by Oracle mode (structured Q&A about the
  codebase) and the dashboard EXPLORE window, but fundamental understanding
  requires human effort that ELAI cannot force.


D2. DEPLOYMENT CHASM / ENVIRONMENTAL BRITTLENESS [PARTIAL]
............................................................................

Problem: code works locally but fails in production. CI/CD, Docker, auth
integration, DB setup, DNS, SSL — all outside the AI's capability.
  - "25% of vibe-coded projects stall at deployment" (Mar 2026)
  - "AI gets non-programmer 80% there, final 20% requires actual development knowledge"
  - "AI assumes sterile homogenous execution environment"
  - "projects working on localhost fail with cryptic Webpack errors on Railway" (Jun 2025)

What ELAI does:
  - Pipeline Factory (4D/4E) can include deployment steps in the plan
  - Project Intelligence detects build system, CI config, deployment platform
  - Integration test runner at CONCEPT level can include deployment smoke tests
  - Pipeline templates: successful deployment pipelines become reusable templates
    ranked by outcome. Second project with same stack gets proven deployment steps.

What remains:
  ELAI is a development engine, not a deployment engine. The "last 20%" involves:
    - Cloud provider configuration (AWS/GCP/Vercel/Railway account setup)
    - DNS and SSL certificate management
    - Database provisioning and migration in production
    - Environment variable management across environments
    - CI/CD pipeline configuration and debugging
  These are partially addressable via pipeline templates for common stacks
  (Next.js + Vercel, Django + Railway, etc.). But novel deployment targets,
  on-prem infrastructure, and multi-service architectures require human
  knowledge that ELAI can assist with (via Oracle mode research) but cannot
  fully automate. This is a real gap for vibe coders who need end-to-end.


D3. DEVELOPER SKILL DEGRADATION [PARTIAL]
............................................................................

Problem: junior developers bypass learning. AI tools require senior expertise
to operate safely. Influx of professionals with engineering titles who cannot
untangle AI-generated "code disasters."
  - "AI tools paradoxically require senior-level expertise to operate safely"
  - "industry recording influx of professionals who cannot untangle AI-generated code disasters"

What ELAI does:
  - Deterministic enforcement means the model's output meets quality standards
    regardless of whether the human understands it. The code won't have TODOs,
    deprecated deps, or security holes even if the human can't check.
  - EXPLORE window: Q&A about the codebase helps learning
  - SSB reasoning traces: transparent decision history enables post-hoc learning
  - Structured plan with rationale: the "why" is documented

What remains:
  ELAI makes it SAFE for non-experts to produce code (deterministic quality
  gates prevent the worst outcomes). But it doesn't make non-experts into
  experts. The skill degradation concern is societal/educational — ELAI can
  provide guardrails and transparency, but can't force humans to learn from
  them. This is analogous to how calculators didn't teach math — they made
  it safe for non-mathematicians to do calculations correctly.


D4. THE BABYSITTING PROBLEM (INTERACTIVE MODE) [PARTIAL]
............................................................................

Problem: users spend more time directing, correcting, and reviewing the LLM
than the task would take manually.
  - "chat UI forces linear single-threaded interaction"
  - "multi-file responses become un-navigable wall of text"
  - "more time maintaining the workflow than saved building it"
  - Developer built custom VS Code extension to intercept when Claude Code stopped

What ELAI does:
  - AUTONOMOUS mode: human provides task, system runs to completion. Dashboard
    for monitoring, not chatting. Interventions only when needed.
  - INTERACTIVE mode: human approves at phase gates, not at every token.
    Structured gates (approve/reject/modify/redirect) not free-form chat.
  - Dashboard: visual monitoring of agent progress, not wall-of-text conversation
  - Baby-step decomposition: each step is independently verified. Human doesn't
    need to review every line — the system validates.

What remains:
  INTERACTIVE mode still requires human at every phase gate. For a 30-step task
  across 3 phases, that's 3 human approvals minimum (plus TESTING_FIRST and
  AUDITING gates). This is BY DESIGN — human oversight is a feature, not a bug.
  But for vibe coders who want "tell AI what to build and walk away," INTERACTIVE
  mode is still babysitting (just structured babysitting).
  AUTONOMOUS mode is the answer, but requires: (a) validated INTERACTIVE pipeline
  end-to-end first, (b) trust that evidence gates catch issues, (c) willingness
  to accept that the system will pause and ask when genuinely stuck.
  The honest answer: ELAI INTERACTIVE = structured babysitting with much less waste.
  ELAI AUTONOMOUS = genuinely hands-off for tasks within the model's capability.

SECTION F: CLAUDE OPUS 4.7 COMPARISON (added 2026-04-17)
================================================================================

Anthropic's Opus 4.7 announcement (https://www.anthropic.com/news/claude-opus-4-7)
lists specific failure modes of Opus 4.6 that 4.7 addresses. This is a useful
independent data point because Anthropic's internal testing identified these as
the most important problems to fix — and their fix was "train a better model."
ELAI's thesis is that these problems can be fixed by infrastructure instead of
by scale. This section maps each 4.6->4.7 fix to ELAI's status and is honest
about where the initial chat assessment overclaimed.

Methodology: each row states (a) the 4.6 failure Anthropic cites, (b) the 4.7 fix,
(c) ELAI's mechanism, (d) honest status (with original chat overclaims corrected).


F1. "WRAPPER FUNCTIONS AND FALLBACK SCAFFOLDING PILE UP" [PARTIAL]
............................................................................
  4.6 problem: Claude 4.6 generated meaningless wrapper functions that just
    forwarded calls, and defensive fallback scaffolding that added no value.
  4.7 fix: "cuts out meaningless wrappers, fixes its own code as it goes"

  ELAI coverage:
    What works: cyclomatic complexity max 10, coupling score max 15, file size
      limits per language (A-21). Excessive coupling/complexity gets BLOCKED.
      Zero Lazy Code catches obvious placeholders.
    What doesn't work: a simple pass-through wrapper has cyclomatic complexity=1
      and passes all current checks. A function that wraps another function with
      minor transformation is structurally valid code. ELAI has no rule that
      specifically detects "this function adds no value" — that requires semantic
      understanding.
  Honest status: PARTIAL. Overclaimed as ELIMINATED in chat.
  Gap: a rule to detect trivial forwarding functions would need to compare function
    bodies against their callees and flag those that don't add meaningful logic.
    Could be added as a T2 AST rule, but not currently designed.


F2. "STOPPING HALFWAY ON TASKS" [SOLVED]
............................................................................
  4.6 problem: model gave up mid-task, leaving work incomplete
  4.7 fix: "carries work all the way through instead of stopping halfway"

  ELAI coverage:
    BabyStepSpec has 8 mandatory blocks including EXIT_CRITERIA.
    Evidence gate EXECUTING -> AUDITING requires "at least 1 test flipped."
    Anti-spiral prevents infinite loops that masquerade as "not finishing."
    FSM cannot advance without artifacts.
  Status: SOLVED. The system literally cannot record a baby step as complete
    without the exit criteria being satisfied. Original chat assessment holds.


F3. "GIVES UP ON DIFFICULT ISSUES" [SOLVED in HYBRID, MITIGATED in LOCAL]
............................................................................
  4.6 problem: model abandoned hard problems instead of persisting
  4.7 fix: "pushes through hard problems rather than giving up"

  ELAI coverage:
    6-layer reasoning escalation (RA design): L1 deterministic -> L2 micro-reflection
      -> L3 interrogation tree -> L4 AB-MCTS -> L5 cloud diagnostic -> L6 cloud gen.
    L1 handles 60-70% of errors via template-based fixes from compiler diagnostics,
      no LLM involved.
    System cannot "give up" until all configured layers are exhausted.
  Honest status: SOLVED in HYBRID mode (cloud layers available). MITIGATED in
    pure LOCAL mode — if L1-L4 all fail on a truly hard problem and cloud budget
    is zero, the system escalates to human. That's structurally different from
    "model giving up" (human gets full reasoning trace and can intervene), but
    it's not "pushes through every hard problem." Overclaimed as SOLVED in chat.
  Gap: for LOCAL-only users with genuinely hard problems exceeding 7B capability,
    the ultimate answer is still human escalation. 32B on 48GB (2x3090) closes
    this gap for more problems but not all.


F4. "LOOPS INDEFINITELY ON 1 IN 18 QUERIES" [ELIMINATED]
............................................................................
  4.6 problem: ~5.6% query rate where model entered unbounded loops in production
  4.7 fix: "highest quality-per-tool-call ratio"

  ELAI coverage:
    MistakeBook (A-20): blake3 hashes of failed diffs. Model physically cannot
      regenerate the same failed output.
    Anti-spiral: 3x same step (blake3 content hash) = escalate. Hard cap.
    Fresh context per retry: model never sees its own failed chain-of-thought.
    Temperature 1.0 for repair loops prevents cyclic traps (FixAudit validated).
  Status: ELIMINATED. The infinite loop is structurally impossible. Infinite
    loops require the model to repeatedly produce the same failed output, which
    MistakeBook prevents at the hash level. Original assessment holds.


F5. "TOOL CALL ERRORS, UNRELIABLE FOLLOW-THROUGH" [MITIGATED]
............................................................................
  4.6 problem: frequent tool call failures, arguments in wrong format, missed
    required parameters, called wrong tools
  4.7 fix: "double-digit jump in tool call accuracy, fewer tool errors"

  ELAI coverage:
    What works: FSM-aware tool filtering per state (wrong tools not even in
      model's schema for current phase). Tool routing layer (A-26) intercepts
      Bash calls that should use dedicated tools (cat -> Read, sed -> Edit).
      Bash safety filter (A-27) blocks dangerous operations. Tool schema
      sanitization strips internal params before model sees schemas.
    What doesn't work: ELAI *rejects* bad tool calls, but it doesn't make the
      model *generate* better ones. If the model keeps generating malformed
      calls, they keep getting rejected until retry budget exhausts, at which
      point reasoning escalates. That's better than production looping, but
      it's not "the model generates correct tool calls."
  Honest status: MITIGATED. Overclaimed as SOLVED in chat.
  Gap: tool call quality fundamentally depends on the model. ELAI's infrastructure
    reduces impact of bad calls (no prod damage, no infinite loops) but doesn't
    improve generation quality. A 7B with ELAI has better USER experience than
    a 4.6 without, but 4.7 may still have higher raw tool call accuracy.


F6. "IMPLICIT NEED RECOGNITION" [PARTIAL]
............................................................................
  4.6 problem: couldn't detect unstated requirements (user asks X, really needs Y)
  4.7 fix: "first model to pass implicit-need tests"

  ELAI coverage:
    What works: Pipeline Factory L1 Designer runs tree-structured research
      (FlashResearch, 4D) to expand task understanding. CSQ (2D) generates
      counterfactual safety questions on functions touching files/data/network/auth
      ("if assumption X is wrong, code will Y"). Research Agent explicitly looks
      for unstated requirements via dual-threshold convergence.
    What doesn't work: CSQ only fires on safety-critical paths, not general
      implicit UX/product/domain needs. Research is driven by the task description
      — if the user says "build a login page" without mentioning "and users
      should be able to reset passwords," the research agent's ability to infer
      that depends on model reasoning. A 7B will miss subtle implicit needs
      that Opus 4.7 catches. The FlashResearch design helps but doesn't match
      frontier-model semantic understanding.
  Honest status: PARTIAL. Overclaimed as SOLVED in chat.
  Gap: domain-specific implicit needs (e.g. "e-commerce site needs cart
    abandonment emails") require either (a) pipeline templates seeded from
    successful prior projects in that domain, or (b) cloud model escalation
    for planning. Both are designed but depend on having prior data or budget.


F7. "STOPPED COLD ON TOOL FAILURES" [SOLVED]
............................................................................
  4.6 problem: tool errors halted execution instead of triggering recovery
  4.7 fix: "keeps executing through tool failures"

  ELAI coverage:
    6-layer reasoning explicitly designed for error recovery.
    L1 (60-70% of errors): parse compiler diagnostics, apply template-based fix,
      no LLM involvement, <100ms.
    Failure taxonomy (A-34): 9+ deterministic error categories. Auditor reads
      classification BEFORE raw output, directing fix to correct layer.
    Tool retries with structural modifications (decompose, template, few-shot,
      simplify, best-of-3) — never instructional ("try harder!") which
      empirically worsens scores.
  Status: SOLVED. Tool failures are a first-class event in ELAI's design with
    explicit recovery pathways. Original assessment holds.


F8. "DEDUCTIVE REASONING STRUGGLES" [MITIGATED]
............................................................................
  4.6 problem: Opus 4.6 was weak on deductive logic tasks
  4.7 fix: "solid on deductive reasoning"

  ELAI coverage:
    What works: GRC (Grounded Reasoning Chain) enforces structured reasoning:
      observe -> hypothesize -> plan_action -> act -> verify. Each step requires
      grounding citation. Unverified claims block progression.
    What doesn't work: GRC *organizes* reasoning, it doesn't *elevate* model
      capability. A 7B model with GRC structure still has 7B-level deductive
      power per step. The chain is more traceable and less likely to skip steps,
      but each step's quality is bounded by the model. If the task requires
      multi-step logical inference beyond the model's capability, GRC won't
      rescue it.
  Honest status: MITIGATED. Overclaimed as SOLVED in chat.
  Gap: genuinely hard deductive reasoning (e.g. novel proof construction,
    complex constraint satisfaction) requires model capability. 6-layer
    escalation to cloud helps here — L5 cloud diagnostic is specifically for
    reasoning problems that exceed local capability.

  Status: ELIMINATED for this specific failure. The system requires evidence for

    confabulated answer). Original assessment holds for this exact problem.

F14. "OVERCONFIDENT / NOT HONEST ABOUT LIMITS" [MITIGATED]
............................................................................
  4.6 problem: gave confident wrong answers instead of admitting uncertainty
  4.7 fix: "noticeably more honest about its own limits"

    What works: confidence calibration rule ("Verified:" / "High confidence:" /
      "Uncertain:"). Grounding verification blocks unverified external claims.

    What doesn't work: within a single code generation, the model can still

      ("this code is optimal").
  Honest status: SPLIT. ELIMINATED for external claims (API existence, file
    paths, test outcomes). MITIGATED for internal code confidence (variable

    Original chat assessment said ELIMINATED overall — true for the claims

  Gap: detecting overconfident naming/commenting requires semantic understanding.

F15. "PROMPT INJECTION / ALIGNMENT" [SOLVED]
............................................................................
  4.6 problem: vulnerable to malicious prompt injection
  4.7 fix: "better honesty and resistance to malicious prompt injection"

  ELAI coverage:
    Agent process isolation (4A): each agent is a separate OS process with NO
      LLM client, NO network, NO tools. Everything proxied via IPC.
    Linux: clone(NEWNS|NEWPID|NEWNET), seccomp-bpf allowlist, zero capabilities.
    Windows: AppContainer or restricted token + Job object.
    Tool schema sanitization: internal parameters stripped before model sees.
    Error message sanitization: agent sees "tool call rejected by policy,"

    Visibility filter: hidden paths return "not found," identical to genuinely

    Self-modification locks: 4 enforcement layers (IPC + filesystem + git + dispatch).
      Compromised agent cannot modify locked config keys.
  Status: SOLVED at architectural layer. Defense in depth. A compromised model

    state, cannot call tools outside its whitelist, cannot see system internals.
    Original assessment holds.

G1. SOLVING F1 (MEANINGLESS WRAPPER FUNCTIONS)
............................................................................
  Gap: pass-through wrappers with cyclomatic complexity=1 currently pass all
    ELAI checks. A function that just forwards args to another function with
    minor transformation adds no value but is structurally valid code.

  Proposed mechanism: TRIVIAL_WRAPPER T2 AST rule.
    Predicate logic:
      FOR EACH function in output:
        IF function body is a single expression statement AND
        expression is a call to another function AND
        (arguments are identity OR minor transformation only) AND
        return type matches callee return type
        THEN FIRE with severity=WARN
    Second check for defensive fallback scaffolding:
      IF function has unreachable branches OR
      contains try/except that re-raises identical exception OR
      contains null check that returns identity value
        THEN FIRE with severity=WARN

  Fits in: phase 3F (rules engine) as new AST_PATTERN rule type, or phase A-21
    (CC hook enforcement) as T2 extension. Rule seeded per language.

  Prerequisite status: [BUILDABLE NOW] — 3F complete, A-21 complete.

  Scope: ~150-200 LOC core + tree-sitter queries per language. Proptest
    regression tests with wrapper patterns vs genuine wrappers.
    NOT counted: curating exemptions per framework (Builder, adapter, facade,
    delegation patterns are all legitimate and must not false-positive). Real
    scope ~400-600 LOC once exemption library is included.

  Open questions + known blockers:
    BLOCKER: distinguishing "meaningless wrapper" from "adapter/facade with
    interface value" is semantically determined by the interface the wrapper
    implements. A T2 AST rule cannot fully determine this without knowing the
    contract. Builder patterns, trait adapters, test doubles, error-type
    adapters are all legitimate wrappers. SHADOW rule lifecycle helps but
    is not a mitigation — it defers the problem to statistical significance
    per-project, which means the rule stays SHADOW indefinitely on small
    codebases. Realistic status: this catches obvious cases (WARN only),
    does not eliminate the class of problem. F1 moves from PARTIAL to
    MITIGATED with G1, not to SOLVED.

G7. SOLVING F14b (INTERNAL CODE CONFIDENCE)
............................................................................
  Gap: model writes confident-sounding variable names and comments that overstate
    code's actual behavior. "calculate_optimal_rate" for a naive implementation.

  Proposed mechanisms:
    G7a. NAMING_CLAIM_CHECK auditor rule.
      Auditor deterministic check (A-12 extension): parse function/variable
      names for claim-bearing words (optimal, fast, secure, safe, validated,
      verified, cached, thread-safe). For each match, require evidence:
        "optimal" -> performance benchmark in same phase
        "validated" -> input validation present
        "secure" -> security review or rules pass
        "cached" -> actual cache implementation present
      No evidence = FINDING (not BLOCK, but rename suggestion).

    G7b. Comment claim extraction and STRUCTURAL (not semantic) verification.
      T2 tree-sitter extraction of docstring/comment claims. Claims that can
      be structurally checked: "returns X" -> check return type + return
      statements. "raises Y" -> check for raise statements of type Y.
      Claims that CANNOT be structurally checked: "handles case Y" (requires
      path analysis or test coverage), "is thread-safe" (requires concurrency
      analysis), "is efficient" (requires benchmarks).
      Structural claims: FINDING on mismatch. Semantic claims: auditor-only
      flag, cannot be deterministically verified.
      Scope correction: ~300 LOC covers tree-sitter extraction + structural
      checks only. Semantic claim verification is out of scope for G7b.

    G7c. Conservative naming convention rule.
      Project Intelligence Tier 2 can detect and enforce conservative naming.
      Instead of optimistic ("calculate_optimal_rate"), prefer descriptive
      ("calculate_rate_linear"). This is a seed rule the codebase can adopt.

  Fits in: G7a extends A-12 (deterministic auditor). G7b extends A-21 (CC
    enforcement with AST comment extraction). G7c is rule pack addition.

  Prerequisite status:
    G7a: [BUILDABLE NOW] — A-12 deterministic auditor is built (but stubs).
    G7b: [BUILDABLE NOW] — A-21 is built.
    G7c: [BUILDABLE NOW] — rule pack mechanism in 3F.

  Scope: G7a ~200 LOC core + claim word dictionary (ongoing curation). G7b
    ~300 LOC structural checks only. G7c ~50 LOC rule data.

  Open questions + honest limits:
    G7a false positives on domain-legitimate terms (`cache` in caching-library

    G7b cannot verify semantic claims (see scope correction above). For those,
