B-29.5 decisions doc
Phase: B-29.5 (symbol_graph_scale_benchmark)
Session: s-22200
Date: 2026-05-16

(a) No criterion crate
The plan's claim "criterion (already a workspace dev-dep per Phase 0)" is FALSE.
grep Cargo.toml for "criterion" returns zero matches workspace-wide.
Decision: use std::hint::black_box + std::time::Instant pattern from
crates/reasoning/benches/grc_bench.rs (harness=false, fn main()).
This avoids a new external dep entirely. p50/p95/p99/mean computed manually
over SAMPLE_COUNT=20 sorted samples per target per tool.
Tradeoff: no criterion-style warmup detection or variance bounds. Mitigated
by running 20 samples (criterion's minimum) and noting variance in the raw JSON.

(b) No new external deps
CLAUDE.md anti-dep rule is absolute. The plan mentions procfs and jemalloc-ctl
as potential deps. Decision: neither added.
RSS on Linux: /proc/self/status VmRSS (stdlib read_to_string; no procfs crate).
RSS on Windows: wmic process where ProcessId=N get WorkingSetSize (std::process::Command).
RSS on other platforms: returns 0 (compile-time cfg gate; not a test failure).
Heap granularity: not measured (jemalloc not used as global allocator; adding it
would be a new dep and change allocator semantics for all benches).

(c) Auto-skip without fixtures
Every bench binary checks ELAI_SCALE_FIXTURE_ROOT. If unset or DB absent, that
tier is skipped via eprintln! + continue — not a panic.
The ELAI workspace itself (elai_self) is always attempted as fallback, resolved
via CARGO_MANIFEST_DIR ancestors().nth(2).join("indexes/dkg.db").
This lets `cargo bench -p elai-knowledge` be meaningful without cloning 70+ GB.

(d) Hardware target
Official measurement run: any developer workstation with 8+ cores, 16+ GB RAM,
NVMe SSD. The p99 budget (500 ms) and RSS ceiling (2048 MB) are set for this tier.
Runs on different hardware produce a sibling file phase_b29_5_scale_<hostname>.toml
rather than overwriting the reference file.
Current development hardware (2026-05-16): Windows 11, consumer CPU, no measured
run yet (fixtures not cloned; ELAI self index not yet built to indexes/dkg.db).

(e) Gate on Linux + VS Code minimum
Decision per plan L420: B-29 release is gated on Linux kernel + VS Code tiers both
passing p99 budget. Rationale: Linux = C-scale proof, VS Code = direct SocratiCode
parity comparison (SocratiCode's largest published test is 200K symbols / ~10K files,
approx VS Code scale; ELAI must match or beat that).
Chromium and Postgres are bonus tiers: failing them triggers a B-29 investigation doc
but does not block release (they cover C++ template-heavy + SQL/Tcl edge cases that
may expose extractor gaps, not cache correctness issues).

(f) Criterion variance bounds replaced by "median + p50/p95/p99 over 20-sample runs"
Criterion detects JIT warmup variance via statistical outlier rejection (Tukey fences).
The std-only harness cannot do this. Mitigation:
- 20 samples per tool per target (not 1 or 5)
- First call always slower (cold LRU); included in samples intentionally since production
  queries will have cold-start cache hits too
- "Determinism" is checked by the #[ignore] test (5 runs, byte-identical files_by_depth)
- Variance > 10% across 2 bench runs of the same tier = flag for investigation (manual
  check; not automated in this harness)
- Future work: if variance is a CI concern, add a running-median filter over 100 samples
  (no external dep needed)

(g) p99 budget rationale
500 ms chosen to match B-29's observable_effect claim. User-facing translation:
the Auditor PostToolUse hook calls symbol_impact, symbol_flow, or symbol_context
once per agent Edit. At p99=500 ms, an Edit round-trip adds at most 500 ms of
latency. This is within the "perceptible but tolerable under interactive use"
threshold (Nielsen: <1000 ms keeps user's flow of thought uninterrupted).
If the measured p99 exceeds 500 ms on Linux or VS Code, B-29 is reopened and
the cache's lazy-load strategy is revisited before release.

(h) scale_p99_budget_contract.rs skip-vs-fail design
The contract file ships in the repo as a schema-only scaffold (populated_at = "null").
The contract test reads this field and returns early with eprintln if null.
This allows the test to be in CI immediately without false failures.
The test only asserts after a human operator sets populated_at to a real timestamp
following a measurement run. This is intentional: a stub metrics file is not a
contract violation; it is just incomplete evidence.
