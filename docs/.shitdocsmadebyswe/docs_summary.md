### `Claude Code Leak Technical Discoveries.txt`

This document details a major security incident on March 31, 2026, where a source map file (`cli.js.map`) for Anthropic's Claude Code CLI was inadvertently published to the npm registry. This leak exposed approximately 512,000 lines of TypeScript source code, revealing the "agentic harness" that orchestrates the AI models. While the leak did not expose model weights or user data, it provided a deep look into the application's architecture, including context memory management, runtime memory leaks, and anti-distillation security measures. The text also discusses a specific patch to fix a caching failure and a separate bug in a custom Bun runtime fork. Finally, it covers severe memory leaks traced to the application's context buffering implementation, which caused operating system lockups during extended sessions.

This file provides a technical analysis of the Claude Code source code leak (version 2.1.88). The root cause was identified as a build configuration failure in the Bun runtime environment, which allowed the source map to be published. The document emphasizes that the incident revealed the crucial client-side mechanisms required to enforce deterministic behaviors upon probabilistic Large Language Models (LLMs), a significant insight for a product reportedly generating $2.5 billion in annualized recurring revenue.

### `Backtest Overfitting and Data Leakage.txt`

This document addresses the severe credibility crisis in quantitative finance stemming from backtest overfitting, target leakage, and lookahead bias. It argues that while generating backtests with impressive Sharpe ratios is now trivial, these strategies frequently fail in live trading. The primary cause is not changing market conditions but models exploiting structural flaws in the data pipeline (e.g., using post-dictive data or retroactively adjusted pricing) and memorizing the future rather than learning tradable alpha. The text promises an exhaustive analysis of these issues to restore rigor to financial machine learning.

### `chat 3 no slop ideas.txt`

This is a transcript of a talk by "Dex" about the evolution of their AI coding methodology from "RPI" (Research, Plan, Implement) to "CRISPY." The central theme is avoiding "slop" code generated by AI without proper human oversight. Key principles include:
-   **Read the code:** Do not blindly trust AI-generated code.
-   **Small, focused prompts:** Break monolithic prompts into a series of smaller ones to respect the LLM's limited "instruction budget" (~150-200 instructions).
-   **Structured alignment:** Use a multi-phase process (Questions, Research, Design, Structure, Plan) to align the human and agent *before* code is written. This provides high-leverage opportunities to steer the agent and significantly reduces time spent on rework and code reviews.

### `chat.txt`

This chat log details a developer's (olscore) highly effective "post-control" workflow for managing a massive 280k-line-of-code quantitative trading system built with an LLM. Instead of complex prompt engineering ("pre-control"), the developer lets the LLM write code freely. This code is then rigorously validated by a comprehensive, automated testing pipeline (using Jest). The pipeline includes quality scans, determinism checks, and conformance tests. The core principle is that code *must* pass these tests to be committed via Git hooks, making the system self-policing. The conversation contrasts this with a "vibe coder's" pre-control approach and concludes that Test-Driven Development (TDD) and a hybrid approach are most effective.

### `LLM Adherence to SOLID Principles.txt`

This document highlights the challenge of maintaining architectural quality when using autonomous LLM agents like Claude Code. It observes that LLMs, to optimize for token efficiency, naturally gravitate towards generating generic, tightly coupled, and monolithic code structures. This tendency violates foundational software engineering paradigms like SOLID, Dependency Injection (DI), and Interface-Driven Design (IDD). The proposed solution is to move beyond simple conversational prompting and implement a multi-layered governance framework within the IDE (VS Code), using `CLAUDE.md` memory rules, deterministic lifecycle hooks, and the Model Context Protocol (MCP) to enforce strict architectural standards.

### `LLM SOLID Principles with Claude.txt`

Similar to the previous document, this text focuses on the architectural decay caused by LLM coding agents. It notes that LLMs are mathematically biased toward consolidating logic into large "God Classes" to conserve their limited context window. This behavior, while token-efficient, leads to unmaintainable codebases requiring "shotgun surgery" for simple changes. The document argues that to counteract this, architects must enforce strict, deterministic guardrails—specifically the SOLID principles—to guide the agent's behavior and ensure the production of robust, scalable applications.

### `Rare Code Flaws in ML.txt`

This document explores subtle and highly technical failure modes in machine learning that cause overfitting and data leakage. It argues that beyond common mistakes, these flaws arise from insidious interactions within complex systems like deep learning frameworks, OS process management, and distributed computing clusters (e.g., hardware-level nondeterminism). These issues are difficult to detect with standard validation methods, leading to models that show inflated performance in-sample but fail catastrophically in production environments.

### `Realistic Paper Trading Executor Research.txt`

This analysis examines "implementation risk" in algorithmic trading—the performance gap between paper trading simulators and live market execution. It argues this gap is not merely "slippage" but is rooted in mechanical, mathematical, and architectural flaws within the simulation engines themselves. The report notes that different simulators can produce significantly different results for the exact same strategy, especially for high-turnover algorithms. The goal of the analysis is to deconstruct the specific code flaws and computational hazards that cause these critical discrepancies.

### `SOTA Codebase Understanding for LLMs.txt`

This document critiques the current limitations of LLMs in understanding large, complex, real-world codebases. It argues that models trained on public code from before 2024 are unaware of modern architectural patterns and proprietary enterprise conventions, causing a significant drop in accuracy on repository-level tasks. The text posits that human engineers comprehend code structurally and topologically, not just linearly. It calls for a new methodology that transcends simple vector retrieval or syntax trees to provide LLMs with a token-efficient, structural, and topological understanding of a codebase, which is essential for advanced software engineering.
