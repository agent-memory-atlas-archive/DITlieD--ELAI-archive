DESIGN DECISIONS (grounded)

  D1. CSQ trigger detection via function signature analysis.
      CSQ must fire on functions touching files/network/money/auth (reasoning.txt s6).
      Detection method: pattern match on function parameters and return types.
      Functions receiving Path/File/TcpStream/Money/AuthToken or calling std::fs/std::net
      APIs are classified as CSQ-required. Phase 1A DKG provides call-graph data, but
      CSQ detection must work WITHOUT DKG (reasoning crate depends on core+providers+tools,
      not knowledge). Standalone pattern: accept a list of "sensitive function signatures"
      from the caller (orchestrator passes DKG results at runtime).
      Grounding: reasoning.txt s6 mandates "minimum 1 CSQ per function touching:
      files, network, money, auth." Detection via call-graph analysis is standard
      static analysis practice (ast-grep uses tree-sitter for structural matching,
      github.com/ast-grep/ast-grep).
      Dependency note: reasoning/ depends on core/, providers/, tools/ (crate map in
      implementation-guide.txt). It does NOT depend on knowledge/. DKG queries are
      injected by orchestrator at call time, not imported directly.

  D2. CSQ severity classification determines guard enforcement.
      Not all CSQ consequences are equal. "Code writes wrong comment" vs "code deletes
      user data" require different responses. Classification:
        CRITICAL (guard MANDATORY): data_loss, security_breach, financial_error, auth_bypass
        WARNING (guard RECOMMENDED): incorrect_output, performance_degradation, stale_cache
      CRITICAL consequences with no guard added = CSQ failure (blocks AUDITING).
      WARNING consequences with no guard = CSQ warning (logged, does not block).
      Grounding: reasoning.txt s6: "Dangerous consequence (data loss, security, financial)
      -> MUST add guard." This maps directly to CRITICAL. VeriGuard (OpenReview 2025)
      co-generates verification with code; CSQ is the lightweight version of this
      principle applied at the reasoning level.

  D3. Inline feasibility uses GRC budget counter, not separate mechanism.
      Inline feasibility (reasoning.txt s8) fires when GRC verify detects a NEW claim
      not in PipelineSpec, Research Report, or DKG. The max-2-call limit is enforced
      by a dedicated counter in InlineFeasibilityState, separate from the per-topic GRC
      budget. Rationale: inline checks are cross-topic (a claim in topic A might need
      verification via topic B's context), so per-topic budget is wrong scope.
      Methods: web_search, grep, api_registry_check (reasoning.txt s8).
      Grounding: reasoning.txt s8 specifies "Quick check (max 2 GRC calls)."
      AgentSpec (arxiv:2503.18666) validates runtime enforcement with bounded checks;
      our approach is simpler (fixed counter vs probabilistic reachability).
      Receiver note: check_inline_feasibility takes &mut self (mutates counter).
      Prior GrcEngine methods (think, set_budget) already use &mut self, so this is
      consistent. verify_claim/ground_plan (2B) use &self since they are read-only.
      Callers already hold &mut GrcEngine for think(); no new API burden.

  D4. Inline feasibility failure signals replan via ReplanRequest.
      On PASS: claim is grounded, proceed with EXECUTING.
      On FAIL: executor must use plan's original approach (no deviation).
      On BLOCKED (fundamentally different approach detected): executor emits
      ReplanRequest(MAJOR) which triggers EXECUTING->PLANNING transition requiring
      human approval (orchestrator.txt s8: "EXECUTING -> PLANNING (major replan):
      requires human approval in both AUTONOMOUS and INTERACTIVE modes").
      Grounding: reasoning.txt s8: "Fundamentally different approach requires
      EXECUTING -> BLOCK -> PLANNING." orchestrator.txt confirms MAJOR replan path.

  D5. CSQ and inline feasibility types extend reasoning/src/types.rs.
      New types (not yet in reasoning.txt s10, will be added):
        CsqCheck { assumption: String, consequence: String,
                    severity: CsqSeverity, guard_added: bool }
        CsqSeverity enum { Critical, Warning }
        CsqResult { function_id: String, checks: Vec<CsqCheck> }
          fn passed(&self) -> bool — true iff all CRITICAL checks have guard_added == true.
          No stored passed field; computed method ensures consistency when checks are mutated.
        FeasibilityMethod enum { SourceMatch }
          Typed enum following the established VerificationMethod pattern (reasoning.txt s10).
          Extensible: future phases add WebSearch, Grep, ApiRegistryCheck variants.
        InlineFeasibilityResult { claim: String, method: FeasibilityMethod,
                                   outcome: FeasibilityOutcome }
        FeasibilityOutcome enum { Pass, Fail, Blocked }
          Pass: claim verified, Fail: use original plan, Blocked: emit ReplanRequest(MAJOR).
        InlineFeasibilityState { checks_used: u32, max_checks: u32 }
          max_checks = 2 (hardcoded from spec). is_exhausted() = checks_used >= max_checks.
          reset() sets checks_used = 0 (orchestrator calls between phases).
          When exhausted, no more inline checks possible; treat new claims as Fail.
      Grounding: type fields derived directly from reasoning.txt s6/s8. CsqSeverity
      maps to the "dangerous consequence" distinction in s6.

      I1. CSQ generation (generate_csq):
          Input: function_id (name of function being analyzed),
                 sensitive_ops (list of sensitive API calls found by caller).
          Logic:
            - If sensitive_ops is empty, return CsqResult { function_id, checks: vec![] }.
              (passed() will return true since no Critical checks exist.)
            - For each sensitive_op, generate a CsqCheck:
              - Classify severity: ops matching file/network/money/auth patterns -> Critical,
                others -> Warning.
              - Pattern matching for classification (case-insensitive: lowercase both
                sensitive_op and pattern before comparison):
                CRITICAL patterns: "fs::", "file", "write", "delete", "remove", "net::",
                  "tcpstream", "money", "payment", "auth", "token", "credential", "password"
                WARNING patterns: everything else in sensitive_ops.
              - assumption: "The call to {sensitive_op} in {function_id} behaves as expected"
              - consequence: severity-dependent template:
                Critical: "data loss/security breach/financial error possible if {sensitive_op} fails"
                Warning: "incorrect output possible if {sensitive_op} fails"
              - guard_added: false (caller must set to true after adding guard code)
            - Return CsqResult { function_id, checks }. The passed() method computes
              correctness dynamically: checks.iter().all(|c| c.severity != Critical || c.guard_added)

      I2. Inline feasibility check (check_inline_feasibility):
          Input: claim (the new claim detected during EXECUTING),
                 sources (list of known sources: PipelineSpec entries, DKG entries, etc.).
          Logic:
            - Check InlineFeasibilityState.is_exhausted(). If yes, return
              Err(GrcError::BudgetExhausted) with topic="inline_feasibility".
            - Check if claim appears in any source (substring match or exact match).
              If found: outcome = Pass.
            - If not found in sources: outcome = Fail (use plan's original approach).
            - Blocked detection: if claim contains negation of a plan assumption
              (heuristic: claim and a source share >50% tokens but have contradicting
              verb/predicate), outcome = Blocked.
              Note: this heuristic is intentionally simple for phase 2D. Phase 4F
              (FEASIBILITY_PROBE) adds full semantic analysis. For now, Blocked is
              only returned when explicitly signaled by the caller via a claim prefixed
              with "CONTRADICTS_PLAN:".
            - Record check: self.inline_feasibility_state.record_check().
            - Return InlineFeasibilityResult { claim, method: FeasibilityMethod::SourceMatch, outcome }.

      I3. CsqResult.passed() method:
          Implement fn passed(&self) -> bool on CsqResult struct (not a stored field).
          fn passed(&self) -> bool { self.checks.iter().all(|c| c.severity != Critical || c.guard_added) }
          This ensures passed is always consistent with current check state.
          The struct has no stored passed field — it is always computed.
