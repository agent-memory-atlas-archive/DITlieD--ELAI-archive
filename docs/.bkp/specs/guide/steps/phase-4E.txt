PHASE 4E: PIPELINE FACTORY L2 (builder + AutoB2G-derived DAG repair)
Prerequisites: Phase 4D complete (PipelineSpec, QualitySpec, ResearchReport types operational)
Status: IMPROVED 2026-04-06

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
Deterministic pipeline assembly from PipelineSpec. No LLM needed. No agent process.
L2 runs entirely in orchestrator crate. Pure Rust, deterministic validation and assembly.
DAG repair loop (AutoB2G-derived pattern) fixes structural issues automatically using
deterministic strategies only (reorder, substitute).
Paper reference: arxiv 2603.26005 (AutoB2G — adopted pattern: bounded DAG validation
  + iterative repair loop. NOT adopted: SOCIA LLM-driven repair. Our repair is deterministic.)

DERIVATION NOTE (AutoB2G)
  AutoB2G uses G=(V,E) DAG of callable functions with topological ordering enforcement.
  Validator returns structured feedback Delta_t; LLM generates S_{t+1} = Phi_LLM(U, S_t, Delta_t).
  We adopt: DAG structure, bounded repair rounds (T_DAG), structured validator feedback.
  We diverge: repair strategies are deterministic (no LLM). Two adopted strategies:
    1. REORDER: topological sort detects back-edges -> break by removing weakest dependency
    2. SUBSTITUTE: missing tool -> find equivalent in ToolRegistry (same category, compatible IO)
  Grounding: external-analysis.txt L173 adopts "reorder, substitute" as the two repair strategies.
  If neither applies or T_DAG exhausted -> escalate to L1 (re-design) or human.
  Non-repairable conditions (escalate immediately, no repair attempt):
    - Resource overflow: detected by validation check #4, not a structural DAG issue
    - Missing transitive dependencies with ambiguous resolution
  Justification for deterministic-only: pipeline-factory.txt sec 2 ("no LLM"),
    external-analysis.txt L176 ("SOCIA iterative optimization NOT ADOPTED").

TYPES (new in this phase)

  Newtypes (all newtype wrappers over primitives):
    struct PipelineId(u64);
    struct StepId(u64);
    struct NodeIndex(usize);    // index into DependencyGraph.nodes
    struct StateId(u64);
    struct DataRef(String);     // named data channel between pipeline steps

  struct ExecutablePipeline {
      pipeline_id: PipelineId,
      spec: PipelineSpec,                       // input, preserved for traceability
      fsm_states: Vec<PipelineFsmState>,         // generated FSM state sequence
      dependency_graph: DependencyGraph,          // validated DAG (no cycles)
      novel_step_ids: Vec<StepId>,               // steps with tool/approach not in capability registry
      agent_configs: Vec<AgentPhaseConfig>,       // per-phase agent assignments
      rule_configs: Vec<RuleBinding>,             // per-phase rule installations
      resource_estimate: ResourceEstimate,        // VRAM, disk, time per phase
      test_harness: TestHarnessSkeleton,          // generated from QualitySpec
      repair_log: Vec<RepairAction>,              // empty if no repair needed
      output_dir: PathBuf,                        // .elai_cc/pipelines/{id}/
  }
  Grounding: pipeline-factory.txt sec 2 lists deliverables: "validates components exist,
    creates FSM states, configures agents, installs rules, estimates resources,
    generates dependency graph, creates test harness skeleton."
    Each field maps to one deliverable.
  novel_step_ids: consumed by phase-4F (phase-4F.txt L99-100: "L2 structural validator marks
    steps as novel when tool/approach not in capability registry"). Populated during structural
    validation: any step whose tool_id is not in ToolRegistry.available_tools = novel.

  struct AgentPhaseConfig {
      phase_id: StepId,
      agent_role: String,           // role name from orchestrator agent pool
      grc_budget: (u32, u32),       // (max_calls, max_chars) per AgentGrcConfig (orchestrator.txt L486)
      model_preference: Option<String>,
  }
  Grounding: pipeline-factory.txt sec 2 "configures agents" + orchestrator.txt L486 AgentGrcConfig.

  struct RuleBinding {
      phase_id: StepId,
      rule_ids: Vec<RuleId>,        // from rules::RuleEngine.get_active_rules(context)
      install_order: u32,           // evaluation priority within phase
  }
  Grounding: pipeline-factory.txt sec 2 "installs rules" + rules.txt L34 (rule schema).

  struct DependencyGraph {
      nodes: Vec<DagNode>,                        // pipeline steps as nodes
      edges: Vec<(NodeIndex, NodeIndex)>,          // dependency edges (from -> to)
  }
  Invariant: topological_sort(&self) always succeeds (no cycles after validation/repair).

  struct DagNode {
      step_id: StepId,
      tool_id: ToolId,                            // must exist in ToolRegistry
      inputs: Vec<DataRef>,                        // outputs of predecessor nodes
      outputs: Vec<DataRef>,
      resource_req: ResourceReq,                   // model, VRAM, disk
      optional: bool,                              // can be removed during repair
  }

  struct PipelineFsmState {
      state_id: StateId,
      phase_name: String,
      allowed_tools: Vec<ToolId>,
      allowed_rules: Vec<RuleId>,
      entry_gate: Option<Predicate>,                // compiled predicate DSL (rules.txt sec 3)
      exit_gate: Predicate,                         // compiled predicate DSL (rules.txt sec 3)
      is_terminal: bool,                            // true for last phase (no outgoing transition)
  }
  Grounding: rules.txt L161 "compile_predicate" validates predicates at insertion time.
    Using compiled Predicate (not raw String) ensures syntactic validity at construction.
    is_terminal: single-phase pipelines have one terminal state with no outgoing transitions.

  struct ResourceEstimate {
      total_vram_mb: u64,
      peak_vram_mb: u64,                           // max across concurrent phases
      estimated_disk_mb: u64,
      estimated_duration_secs: u64,                // sum of sequential phases
      fits_hardware: bool,                         // compared against ModelPool.available_vram
  }

  struct TestHarnessSkeleton {
      test_cases: Vec<TestCase>,                   // one per QualityMetric + PerfSpec
      fixture_stubs: Vec<FixtureStub>,
  }
  Invariant: test_cases.len() >= quality_spec.metrics.len() + quality_spec.perf_specs.len()
  Grounding: pipeline-factory.txt L192 "L2 validates every metric has automated check method."

  enum RepairAction {
      Reorder { from: NodeIndex, to: NodeIndex, reason: String },
      Substitute { old_tool: ToolId, new_tool: ToolId, reason: String },
  }
  Grounding: external-analysis.txt L173 adopts exactly "reorder, substitute" from AutoB2G.

  enum RepairOutcome {
      Repaired { rounds: u32, actions: Vec<RepairAction> },
      Escalated { rounds: u32, remaining_issues: Vec<ValidationError> },
  }

  struct ValidationError {
      kind: ValidationErrorKind,
      node: Option<NodeIndex>,
      message: String,
  }

  enum ValidationErrorKind {
      CycleDetected,
      MissingTool,
      MissingDependency,
      ResourceOverflow,
      UnmeasurableMetric,
      InvalidPredicate,
      MissingAdapter,
      InvalidVisualCheck,
  }

  STRUCTURAL VALIDATION CHECKLIST (8 checks, all deterministic)
    1. Tools referenced in PipelineSpec exist in ToolRegistry
    2. Models referenced exist in ModelPool or are installable
    3. No dependency cycles in pipeline graph (topological sort succeeds)
    4. Resource requirements fit hardware (ModelPool.available_vram query)
    5. Every QualityMetric has automated check method (unmeasurable -> REJECT)
    6. FSM state predicates are syntactically valid (rules::compile_predicate succeeds — rules.txt L161)
    7. Novel step detection: steps with tool_id not in ToolRegistry marked as novel (phase-4F dependency)
    8. Visual check adapter validation: for each phase with visual_check=true,
       a MediaRenderAdapter must exist for the phase's output_type.
       Missing adapter -> ValidationError::MissingAdapter. visual_check=true with
       output_type=None -> ValidationError::InvalidVisualCheck.
       (See media-validator.txt section 7, phase-4I Render-Capture-Evaluate)

          Split by contract boundaries, then directory proximity.
          Max split depth: 2 (matches Phase 4G SPLIT_TASK max depth).
          Merge: adjacent phases only, no external dependents between them.
          Phase Sizing uses PlanSkeleton::split_phase with preserve_contracts=true (Phase 3G).
          Source: technical-analysis-v3.txt Concern 4 (Layer 2), pipeline-factory.txt S3.

DECOMPOSITION TREE EXTENSION (Fractal Pipeline Builder)

  The base 4E steps (4E.1-4E.6) build a flat ExecutablePipeline from PipelineSpec.
  This extension builds a DecompositionTree from ConceptDecomposition (4D recursive output).
  The tree is the primary execution artifact. The orchestrator traverses it deterministically.
  Each leaf (baby step) cycles through FSM: TESTING_FIRST -> EXECUTING -> AUDITING.
  No LLM controls the traversal. The TreeNavigator is pure Rust.

  DESIGN PRINCIPLE
    The DecompositionTree is DATA, not a prompt. It is a typed Rust struct that the
    orchestrator reads to determine what happens next. The LLM fills in content
    (code, tests) but never decides flow. Flow is: TreeNavigator picks next baby step ->
    orchestrator assembles context from BabyStepGrounding -> FSM cycles -> result recorded ->
    TreeNavigator picks next. If baby step fails acceptance, BubbleUpHandler decides what
    to re-research. All decisions are deterministic given the tree state.

  NEW TYPES

    struct DecompositionTree {
        tree_id: PipelineId,
        root: ConceptDecomposition,              // from 4D recursive research
        navigator: TreeNavigatorState,           // traversal state (serializable)
        execution_log: Vec<BabyStepResult>,      // completed baby steps
        bubble_up_log: Vec<BubbleUpEvent>,       // failure escalations
        integration_checkpoints: Vec<IntegrationCheckpoint>,
        created_at: u64,
    }
    Invariant: tree is always a valid DAG (no cycles, verified at construction).

    struct TreeNavigatorState {
        current_concept: Option<ConceptId>,
        current_phase: Option<PhaseId>,
        current_step: Option<StepId>,
        current_baby_step: Option<BabyStepId>,
        completed: BTreeSet<BabyStepId>,         // deterministic iteration
        failed: BTreeMap<BabyStepId, FailureRecord>,
        blocked: BTreeSet<BabyStepId>,           // waiting on dependencies
        traversal_order: Vec<BabyStepId>,        // pre-computed, deterministic
    }
    Serialized to msgpack at every baby step completion for crash recovery.

    struct FailureRecord {
        baby_step_id: BabyStepId,
        attempts: u32,
        alternatives_tried: Vec<String>,         // framework/approach tried
        last_error: String,
        bubbled_up: bool,                        // true if escalated to parent
    }

    struct BabyStepResult {
        baby_step_id: BabyStepId,
        outcome: BabyStepOutcome,
        tests_written: u32,
        tests_passing: u32,
        files_modified: Vec<String>,
        commit_hash: Option<String>,             // WIP commit if code was written
        elapsed_ms: u64,
        auditor_findings: Vec<String>,           // BLOCK/WARN from auditor
    }

    enum BabyStepOutcome {
        Pass,                                    // all acceptance criteria met
        FailRetry { attempt: u32 },             // will retry with alternative
        FailBubbleUp,                           // max retries exhausted, escalating
        Skipped { reason: String },             // dependency not met or deferred
        Deferred,                                // integration deferred (siblings incomplete)
    }

    struct BubbleUpEvent {
        source: BabyStepId,                      // where failure originated
        target_level: DecompositionLevel,         // where it escalated to
        target_id: String,                       // step_id or phase_id or concept_id
        action: BubbleUpAction,
        research_report: Option<ResearchReport>, // new research if alternative found
    }

    enum DecompositionLevel { Concept, Phase, Step, BabyStep }

    enum BubbleUpAction {
        ResearchAlternative,                     // try different framework/approach
        RedecomposeStep,                         // re-break step into different baby steps
        ReplanPhase,                             // re-plan entire phase
        ReplanConcept,                           // re-plan entire concept
        Escalate,                                // give up, ask human (INTERACTIVE) or MAJOR replan
    }

    struct BubbleUpPolicy {
        max_retries_per_baby_step: u32,          // default 3
        max_retries_per_step: u32,               // default 2
        max_retries_per_phase: u32,              // default 1
        max_retries_per_concept: u32,            // default 1
        on_concept_fail: BubbleUpAction,         // default Escalate
    }

    struct IntegrationCheckpoint {
        level: DecompositionLevel,
        id: String,                              // baby_step_id, step_id, phase_id, or concept_id
        test_command: String,
        test_passed: bool,
        connects_to: Vec<String>,                // what main entry points were verified
        timestamp: u64,
    }

    trait TreeNavigator {
        fn next_baby_step(&self, state: &TreeNavigatorState, tree: &DecompositionTree)
            -> Option<BabyStepId>;
        fn record_result(&mut self, result: BabyStepResult);
        fn handle_failure(&mut self, baby_step_id: BabyStepId, policy: &BubbleUpPolicy)
            -> BubbleUpAction;
        fn is_complete(&self) -> bool;
        fn integration_ready(&self, baby_step_id: BabyStepId) -> bool;
    }
    Implementation: DepthFirstNavigator (default).
    Traversal: depth-first within concept, concepts in dependency order.
    Baby steps within a step: sequential (order matters for incremental building).
    Steps within a phase: sequential (dependency order).
    Phases within a concept: topological order (from depends_on edges).
    Concepts: topological order (from cross-concept dependencies).

  TREE NAVIGATOR ALGORITHM

    fn next_baby_step(state, tree) -> Option<BabyStepId> {
        for baby_step_id in &state.traversal_order {
            if state.completed.contains(baby_step_id) { continue; }
            if state.blocked.contains(baby_step_id) { continue; }
            // Check pre_gate: all PreGateConditions must pass
            let spec = tree.get_baby_step(*baby_step_id);
            if !all_pre_gates_pass(&spec.pre_gate) { continue; }
            // Check dependencies: all depends_on baby steps completed
            if !dependencies_met(*baby_step_id, &state.completed, tree) { continue; }
            return Some(*baby_step_id);
        }
        None  // all done or all blocked
    }

    Traversal order pre-computed at tree construction:
      1. Topological sort concepts by cross-concept deps
      2. Within each concept, topological sort phases by depends_on
      3. Within each phase, steps in declared order
      4. Within each step, baby steps in declared order
      5. Flatten to Vec<BabyStepId>

    This is deterministic. Same tree -> same traversal order -> same execution sequence.

  BABY STEP EXECUTION CYCLE (orchestrator-driven, per baby step)

    For each baby_step returned by TreeNavigator::next_baby_step():

    1. CONTEXT ASSEMBLY (orchestrator, pure Rust, <5ms)
       Load BabyStepGrounding into context budget Slot 3 (phase_spec slot).
       Baby step context is tiny (~500 tokens grounding + ~200 tokens task).
       This is how cheap local models produce quality code: narrow, grounded context.

    2. PRE_GATE CHECK (orchestrator, deterministic)
       Run each PreGateCondition.check_command via bash.
       All must return expected_exit_code. Any failure -> baby step BLOCKED.

    3. TESTING_FIRST (FSM state)
       Executor agent writes tests per TddSpec.
       Tests must reference grounded types/APIs from BabyStepGrounding.
       Evidence gate: tests compile but fail (right reasons, not syntax errors).
       Auditor validates test quality (do tests actually test the task?).

    4. EXECUTING (FSM state)
       Executor agent writes code per TaskSpec.
       Context: ONLY BabyStepGrounding + task + test file. No full project context.
       Every edit triggers T1/T2/T3 static analysis hooks (Phase 4C).
       Incremental compilation feedback (Phase 4B) after each file write.
       Max lines enforced: TaskSpec.max_lines.

    5. AUDITING (FSM state)
       Auditor runs DeterministicCheck commands.
       Auditor runs adversarial tests on baby step code.
       If BLOCK findings: executor re-enters EXECUTING (existing AUDITING->EXECUTING cycle).
       Max audit retries: 3 per baby step (matches existing anti-spiral).

    6. ACCEPTANCE CHECK (orchestrator, deterministic)
       Check AcceptanceCriteria: min_tests_passing met?
       If FAIL and attempts < max_retry_alternatives:
         Go back to research for this step (ResearchAlternative).
         FlashResearch runs with failure context: "X failed because Y, find alternative".
         New baby steps generated. Retry.
       If FAIL and attempts >= max_retry_alternatives:
         BubbleUpHandler activates (see below).

    7. INTEGRATION (orchestrator + executor)
       If IntegrationSpec.deferred == false AND all sibling baby steps complete:
         Run IntegrationSpec.integration_test_command.
         If pass: record IntegrationCheckpoint.
         If fail: this is a cross-baby-step issue. BubbleUp to step level.
       If deferred: skip, will run at step completion.

    8. EXIT CRITERIA (orchestrator, deterministic)
       Run each ExitCriterion.check.
       All pass -> baby step COMPLETE. Navigator moves to next.
       Any fail -> treat as ACCEPTANCE failure.

  BUBBLE-UP FAILURE HANDLING

    fn handle_failure(baby_step_id, policy) -> BubbleUpAction {
        let record = state.failed.get(baby_step_id);
        if record.attempts < policy.max_retries_per_baby_step {
            return ResearchAlternative;  // try different approach at baby step level
        }
        // Bubble up to step
        let step = tree.parent_step(baby_step_id);
        let step_failures = count_failures_in_step(step);
        if step_failures < policy.max_retries_per_step {
            return RedecomposeStep;  // re-break the step differently
        }
        // Bubble up to phase
        let phase = tree.parent_phase(step);
        let phase_failures = count_failures_in_phase(phase);
        if phase_failures < policy.max_retries_per_phase {
            return ReplanPhase;  // different framework/approach for whole phase
        }
        // Bubble up to concept
        let concept = tree.parent_concept(phase);
        let concept_failures = count_failures_in_concept(concept);
        if concept_failures < policy.max_retries_per_concept {
            return ReplanConcept;
        }
        // Nothing left
        return policy.on_concept_fail;  // default: Escalate
    }

    Each BubbleUp action triggers re-research at the appropriate level:
      ResearchAlternative: FlashResearch on baby step with failure context
      RedecomposeStep: FlashResearch on step, regenerate baby steps
      ReplanPhase: FlashResearch on phase, regenerate steps + baby steps
      ReplanConcept: FlashResearch on concept, regenerate phases + steps + baby steps
      Escalate: INTERACTIVE -> human decides. AUTONOMOUS -> ReplanRequest(MAJOR).

    All bubble-up events logged in SSB as action_type='replan_request' with tree context.

  INTEGRATION CHECKPOINTS (at every granularity level)

    After each BABY STEP completion (if not deferred):
      Run integration test connecting baby step output to target entry point.
      E.g., after implementing Argon2 hashing, verify it compiles with AppState struct.
      Quick: cargo check on affected files. <5s.

    After each STEP completion (all baby steps in step done):
      Run step-level integration test.
      E.g., after all auth baby steps, verify auth module integrates with router.
      Medium: cargo test on the step's module. <30s.

    After each PHASE completion (all steps in phase done):
      Run phase-level integration test.
      E.g., after entire API backend phase, verify it starts and responds to health check.
      Full: cargo test -p affected_crate. <60s.

    After each CONCEPT completion (all phases in concept done):
      Run concept-level end-to-end test.
      E.g., after entire "Core API" concept, run full API test suite.
      Full: cargo test --workspace -- concept_integration. <120s.

    Integration test generation: L2 builder generates test stubs from IntegrationSpec.
    Executor fills in test bodies during TESTING_FIRST of the first baby step that has
    integration tests. Tests initially fail (TDD). They pass as baby steps complete.
