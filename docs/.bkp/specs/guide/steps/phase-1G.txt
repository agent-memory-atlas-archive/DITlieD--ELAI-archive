DECISION: ort vs fastembed-rs
  Phase 1G uses raw ort + tokenizers crate (not fastembed-rs) because:
  - Other ONNX models in the knowledge crate (GraphCodeBERT, Granite) already use ort directly
  - Raw ort allows ORT_ENABLE_ALL, enable_deterministic_compute, and int8 model loading directly
  - fastembed-rs adds abstraction that limits control over session threading and graph optimization
  - Decision revisitable at Phase 1I if consistency becomes a concern

DECISION: fp32 vs int8 model
  Start with fp32 model. Measure latency. If <50ms target met with fp32 + ORT_ENABLE_ALL + configured threads: stop. If not: export int8 dynamically quantized model, re-measure. Accept int8 only if NDCG@10 delta < 0.5 points on benchmark fixture. Data-driven decision made during step 1G.5, not upfront.
  Evidence: Microsoft Azure blog — BERT int8 on AVX2: ~2.9x speedup, VNNI: up to 6x. Accuracy loss negligible on GLUE.
  INT8 trigger: evaluate if baseline p50 > 30ms. Ungrounded conjecture: 30ms chosen as 60% of 50ms spec budget, leaving 20ms headroom for queue wait latency under concurrent load (<4 agents per knowledge.txt L222).

DECISION: skip threshold
  Default 10 (from spec). Configurable via RerankerConfig. Threshold sweep in 1G.5 uses NDCG@10 (aligning with spec invariant format and academic benchmarks) at thresholds 5, 10, 15, 20, 30. Spec value updated if sweep shows different optimum for code search.

DECISION: batching mechanism
  Use tokio::sync::mpsc bounded channel (capacity 4) for request aggregation. Chosen over tokio::sync::Notify because bounded channel provides atomic drain-and-batch semantics via try_recv loop, avoiding lost-wakeup races inherent in Notify polling patterns. The reranker task drains all pending requests from the channel before acquiring the ONNX session semaphore, merges candidate sets, runs single inference, then splits results back via oneshot channels per caller.

    PRE_GATE:
