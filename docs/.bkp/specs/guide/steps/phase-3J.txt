PHASE 3J: vLLM INTEGRATION + ADVANCED PROVIDERS + PLUGINS + ORCHESTRATOR HARDENING
Prerequisites: Phase 3I complete (DST infrastructure), Phase 1F (speculative decoding eval)

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
Integrate vLLM as the production inference backend. Enable layer-level optimizations
(DoLa, TurboQuant KV cache, steering vectors) that require vLLM's internal access.
Build advanced ModelPool features (GPU multiplexing, predictive pre-loading, workload
profiling). Implement MCP bridge, tiered static analysis hooks, AppContainer isolation,
advanced SSB action types, and MILP scheduling evaluation.

All model-specific steps (DoLa, steering vectors, EAGLE-3, TurboQuant) are developed
and tested on Gemma4 E2B (~2B params, fits on RTX 3060 12GB) as the primary test model.
Final step (3J.14) applies everything to Gemma4 31B via CPU offload on 64GB RAM (slow
but validates artifacts for the 48GB GPU setup).

This phase bridges the gap between the ollama-based Phase 0-3 and the production-grade
Phase 4 by delivering the inference substrate that all subsequent phases depend on.

RISKS
  R1: vLLM Rust client does not exist as a published crate. Must use HTTP/gRPC to the
      vLLM Python server. Latency overhead from HTTP vs in-process ollama needs measurement.
      Mitigation: benchmark HTTP latency in step 3J.1 spike. Accept if <10ms overhead.
  R2: DoLa requires access to intermediate layer logits during inference. vLLM's OpenAI-
      compatible API does NOT expose per-layer logits. Requires either (a) custom vLLM
      plugin/extension, (b) vLLM's internal Python API, or (c) a custom sampling hook.
      Mitigation: spike in step 3J.3. If vLLM plugin API is insufficient, DoLa is deferred.
  R3: TurboQuant for KV cache requires modifying vLLM's attention backend. This is deep
      integration, not API-level. May require forking vLLM or contributing upstream.
      Mitigation: evaluate complexity in step 3J.4. If >2 weeks effort, defer to Phase 4+.
  R4: Steering vectors (ActAdd) require writing to the residual stream at a specific layer
      during forward pass. Same access issue as DoLa (R2). Coupled risk.
      Mitigation: if DoLa plugin works, steering vectors reuse the same hook.
  R5: MILP solver (coin-or/cbc or highs) Rust bindings may have build complexity on Windows.
      Mitigation: spike in step 3J.8. Windows build failure -> defer MILP to Linux-only.
  R6: MCP bridge is 1751 LOC from claw-code (mcp_tool_bridge.rs + mcp_lifecycle_hardened.rs).
      Porting requires understanding the existing protocol. Risk of subtle protocol bugs.
      Mitigation: port incrementally with contract tests per message type.
  R7: AppContainer (Windows) has known weaknesses (NTFS junctions, reparse points). This is
      documented as weaker-than-Linux. Not a blocker but must be documented clearly.
  R8: GPU multiplexing requires accurate VRAM accounting for colocated models. Overcommit
      causes OOM. Safety margin (1GB) may be insufficient for some model combinations.
      Mitigation: conservative accounting + health check after colocation.
  R9: Gemma4 E2B (~2B) is smaller than any model tested in DoLa/EAGLE-3 papers. Results
      may not transfer to 31B. Mitigation: E2B validates code paths and integration, not
      production quality. Quality validation happens on 31B in step 3J.14 and on 48GB hardware.
  R10: Gemma4 31B on CPU offload is extremely slow (~0.5-2 tok/sec). EAGLE-3 draft training
      requires thousands of forward passes — infeasible on CPU. Mitigation: step 3J.14 tests
      everything EXCEPT EAGLE-3 draft training on 31B. Draft training deferred to 48GB hardware.
  R11: vLLM CPU offload may not support layer-level hooks needed for DoLa/steering. If vLLM
      only supports GPU execution for custom hooks, 31B DoLa/steering must wait for 48GB.
      Mitigation: test hook availability in CPU offload mode in step 3J.14. Fall back to
      transformers + PyTorch for artifact generation if vLLM CPU hooks unavailable.

  3J.3 DOLA LAYER-CONTRAST DECODING
    PRE_GATE:
      - Step 3J.1 passed (VllmProvider works with Gemma4 E2B)
      - vLLM exposes per-layer logits or has plugin/hook API for custom sampling
        If NOT: this step produces a SPIKE evaluating access methods, then DEFER
    TASK:
      - Implement DolaDecoder in providers/src/layer_config/dola.rs
      - DoLa algorithm (arxiv 2309.03883, ICLR 2024):
        1. Forward pass to compute hidden states at all candidate layers J and final layer N
        2. Compute early-exit distributions q_j = softmax(phi(h_t^(j))) for j in J
        3. Select premature layer: M = argmax_{j in J} JSD(q_N || q_j)
        4. Adaptive plausibility constraint: V_head = {x : q_N(x) >= alpha * max q_N}
        5. Contrastive logits: log(q_N / q_M) for tokens in V_head, -inf otherwise
        6. Sample from softmax of contrastive logits
      - Candidate layer buckets (model-specific, from DoLa paper Table):
        ~2B (Gemma4 E2B, ~18-26 layers): J = even layers in [0, N/2) or [N/2, N)
          NOTE: 2B is in untested range. Bucket boundaries derived by analogy with 7B.
          Evaluate empirically. Log factuality vs baseline on 20 test prompts.
        7B  (32 layers): J = even layers in [0,16) or [16,32)
        13B (40 layers): J = even layers in [0,20) or [20,40)
        >30B (60+ layers): 3-4 buckets of 20 layers each
      - Hyperparameters: alpha=0.1 (plausibility), theta=1.2 (repetition penalty)
      - DolaConfig struct: enabled (bool), alpha (f64), candidate_buckets (Vec<Range<usize>>),
        repetition_penalty (f64)
      - Per-role application (from providers.txt S3):
        Executor (Gemma 4 31B): DoLa enabled (factuality improvement)
        Auditor (DeepSeek-R1-32B): DoLa amplified (stronger factual grounding)
        Prompt-engineer (Qwen 3.5 27B): DoLa disabled (constrained decoding only)
      - E2B testing: run DoLa on Gemma4 E2B via vLLM on RTX 3060.
        Compare 20 factuality prompts: baseline vs DoLa. Log results.
        If DoLa improves or is neutral on E2B: code validated, ready for 31B.
        If DoLa degrades on E2B: document as expected for small models, code still valid.
      - Latency budget: DoLa adds ~5-8% latency overhead (DoLa paper Section 7: 1.01-1.08x)
      - Memory overhead: stores intermediate layer distributions (DoLa paper: +0.6-1.1% of total)
      - vLLM integration path: either custom SamplingParams hook or vLLM plugin mechanism
        If vLLM does not support custom sampling hooks: implement as post-processing on
        logprobs output (vLLM /v1/completions with logprobs=N returns top-N logprobs per token)
        DEGRADED path: if only top-N logprobs available (not full distribution), DoLa accuracy
        is reduced. Document degradation and measure empirically.
      - CAUTION: DoLa degrades on 335M models (DoLa paper Section 6.7, GPT2-Medium).
        Paper tested 7B+ (improved) and 335M (degraded). 1-7B range is UNTESTED.
        Guard: if model_params < 1B, log WARNING and disable DoLa automatically.
        For 1-7B models (including Gemma4 E2B ~2B): EVALUATE empirically.
        Log DoLa vs baseline factuality metrics. Disable if degradation detected.
    DETERMINISTIC_CHECK:
      - cargo check --workspace --features vllm exits 0
      - grep -r "DolaDecoder" .elai_cc/crates/providers/src/ returns hits
      - grep -r "DolaConfig" .elai_cc/crates/providers/src/ returns hits
      - grep -r "candidate_buckets" .elai_cc/crates/providers/src/ returns hits

  3J.4 TURBOQUANT KV CACHE COMPRESSION (EVALUATION)
    PRE_GATE:
      - Step 3J.1 passed (VllmProvider works)
      - TurboQuant paper ingested: workflow/papers/turboquant-interface.md exists
    TASK:
      - EVALUATE feasibility of TurboQuant KV cache integration with vLLM
      - TurboQuant (arxiv 2504.19874, ICLR 2026):
        Step 1: random rotation matrix Pi (QR of Gaussian, d x d, fixed per instance)
        Step 2: coordinates follow Beta distribution, converge to N(0,1/d) at high d
        Step 3: Lloyd-Max scalar quantizer per coordinate independently
        Expected compression: 3.5-bit matches full-precision (score 0.997 on NIAH)
        2.5-bit gives marginal degradation (49.44 vs 50.06 on LongBench)
      - Evaluation criteria:
        a. Does vLLM's attention backend allow custom KV cache quantization?
           Check: vLLM KVCacheConfig, CacheEngine, attention backends (FlashAttention, PagedAttention)
        b. If custom KV cache: estimate LOC and complexity for TurboQuant integration
        c. If not: can TurboQuant run as external quantizer on KV cache tensors?
        d. Minimum dimension d >= 64 (TurboQuant paper: low-d fails Beta approximation)
      - Implementation sketch (if feasible):
        TurboQuantConfig { bit_width: u8 (1-4), rotation_seed: u64 }
        TurboQuantizer struct: precomputed Pi matrix + Lloyd-Max codebook per (d, b) pair
        quant_kv(key_or_value: &Tensor) -> QuantizedKV (b-bit indices per coordinate)
        dequant_kv(qkv: &QuantizedKV) -> Tensor
      - Critical invariants (from turboquant-interface.md):
        Input must be unit norm (store L2 norm separately, rescale after dequant)
        Pi must be orthogonal rotation matrix
        Codebook size must equal 2^b
        Codebook centroids must be ascending sorted
      - Implementation pitfalls (from paper):
        Do NOT reuse Pi across instances without resetting
        Do NOT skip norm rescaling for non-unit inputs
        Do NOT approximate rotation with Hadamard (full QR required for theoretical guarantees)
        Do NOT use MSE variant for inner product queries (biased)
      - E2B testing: pre-compute Lloyd-Max codebooks for E2B's head dimension (d).
        Codebooks are dimension-specific, not model-specific (data-oblivious algorithm).
        Verify: quant -> dequant roundtrip on random unit-norm vectors within expected MSE.
        Codebooks reusable for any model with same d (including 31B if same head dim).
      - Output: FEASIBLE/DEFER decision with complexity estimate
      - If FEASIBLE and complexity < 1 week: implement TurboQuantizer struct, test on E2B
      - If DEFER: document reason, preserve evaluation in workflow/reasoning/phase-3J-turboquant.md
    DETERMINISTIC_CHECK:
      - Decision file exists: workflow/reasoning/phase-3J-turboquant.md
      - If FEASIBLE: grep -r "TurboQuantizer" .elai_cc/crates/providers/src/ returns hits
    ADVERSARIAL:
      - If TurboQuant quantizes KV cache but vLLM's PagedAttention assumes full-precision,
        attention computation silently produces wrong results.
        Test: if implemented, verify attention output matches full-precision within tolerance.
      - If KV cache compression saves VRAM but adds latency exceeding the VRAM savings benefit,
        net effect is negative. Test: measure tokens/sec with and without compression.
    ACCEPTANCE:
      - FEASIBLE/DEFER decision documented with evidence
      - If FEASIBLE: TurboQuantizer struct compiles, codebook precomputation verified
      - If DEFER: reasoning documented, no dead code left behind

  3J.5 STEERING VECTORS (ActAdd)
    PRE_GATE:
      - Step 3J.3 completed (DoLa layer access path established)
      - ActAdd paper ingested: workflow/papers/actadd-2308.10248/summary.md exists
    TASK:
      - Implement SteeringVectorEngine in providers/src/layer_config/steering.rs
      - ActAdd algorithm (arxiv 2308.10248):
        1. Compute steering vector: h_A^l = h+^l - h-^l from contrast prompt pair
        2. At inference, add c * h_A^l to residual stream at target layer l
        3. Continue forward pass with modified residual
      - Steering vector computation is one-time per contrast pair (amortized):
        Forward model on p+, record activations at layer l -> h+
        Forward model on p-, record activations at layer l -> h-
        Steering vector = h+ - h-
        Store as SteeringVector { layer: usize, vector: Vec<f32>, coefficient: f64 }
      - Pre-computed vectors for agent roles (from providers.txt S3 L102-104):
        Auditor: skepticism steering vector (contrast pair TBD at implementation)
        Context-compiler: completeness steering vector (high temperature 0.7 + steering)
      - SteeringConfig: vectors: Vec<SteeringVectorSpec>, enabled: bool
        SteeringVectorSpec: name (String), layer (usize), coefficient (f64),
          positive_prompt (String), negative_prompt (String)
      - Configurable in elai_cc.toml [agents.{role}.layer_config.steering]
      - Layer selection guidance (from ActAdd paper Section 6.3):
        Early layers (0-5): minimal effect
        Mid layers (6-20): peak effectiveness
        Late layers (25+): declining
        Default: layer = model_layers / 3 (early-mid)
      - Coefficient guidance (from paper Section 6.4):
        Typical range: c in [3, 20]
        Start conservative (c=5), tune per vector
      - vLLM integration: same layer-access hook as DoLa (step 3J.3)
        If DoLa hook works: steering vectors reuse the same mechanism
        If DoLa was deferred: steering vectors also deferred (coupled dependency)
      - Composability: multiple steering vectors can be added simultaneously
        (ActAdd paper confirms composability, Section 9 advantages)
      - CRITICAL: steering vectors require access to intermediate activations.
        API-only models (Anthropic, OpenAI) cannot use this. Local models only.
      - E2B testing: compute steering vectors on Gemma4 E2B (RTX 3060).
        ActAdd paper validated on GPT2-XL (1.5B), so E2B (~2B) is within tested range.
        Compute at least 2 contrast pairs (skepticism, completeness).
        Evaluate steering effect: 5 prompts per vector, compare steered vs baseline output.
        Store computed vectors as .safetensors or .npz for reuse.
    DETERMINISTIC_CHECK:

      - grep -r "SteeringVectorEngine" .elai_cc/crates/providers/src/ returns hits
      - grep -r "SteeringConfig" .elai_cc/crates/providers/src/ returns hits
    ADVERSARIAL:
      - If steering coefficient is too high, output degrades to incoherent text.
        Test: sweep c from 1 to 30, verify coherence does not drop below baseline at c <= 15.
      - If wrong layer is selected, steering has no effect or causes harm.
        Test: sweep layers, verify at least one layer produces measurable steering effect.
      - Not all contrast pairs produce meaningful vectors (ActAdd paper Table 7).
        Test: validate each pre-computed vector with 5 test prompts before deployment.
    ACCEPTANCE:

  3J.6 GPU MULTIPLEXING + PREDICTIVE PRE-LOADING
    PRE_GATE:
      - Step 3J.2 passed (ModelPool supports vLLM backend)
      - Dual-GPU hardware available OR single-GPU with test-mode multiplexing simulation
    TASK:
      - GPU multiplexing (from providers.txt S4 L130-136, Murakkab-derived):
        Small models (<4GB) can colocate on same GPU with large model's idle headroom.
        Embedding model (~1.5GB) + cross-encoder (~130MB) on GPU1 while executor on GPU0.
        Memory-writer (~4GB) can share GPU1 with embedding model during MEMORIZING.
        Constraint: sum(colocated_vram) <= GPU_VRAM - safety_margin (1GB)
        Phase 0-1 (single GPU): no multiplexing, sequential loading only.
        Phase 2+ (dual GPU): multiplexing enabled on GPU1 for small models.
      - MultiplexingPolicy struct:
        safety_margin_bytes: u64 (default 1GB = 1_073_741_824)
        max_colocated: usize (default 3)
        min_model_size_for_dedicated_gpu: u64 (default 4GB)
      - ModelPool.can_colocate(model_id, target_gpu) -> Result<bool>:
        Check: current_vram_used(target_gpu) + model_vram + safety_margin <= gpu_total_vram
      - Predictive pre-loading (from providers.txt S4 L138-140, FSM-driven):
        EXECUTING -> pre-load auditor model
        AUDITING -> pre-load executor model
        PLANNING -> pre-load prompt-engineer model
        TESTING_FIRST -> pre-load executor model
        Pre-load triggers on FSM state entry (not exit). Background tokio::spawn.
        Pre-load blocked if VRAM insufficient (falls back to sequential load at boundary).
      - PreloadPolicy: map from FsmState to Vec<ModelId>
        Configurable in elai_cc.toml [providers.preload]
      - SLO quality tiers (from providers.txt S4 L120-128, Murakkab-derived):
        BEST (auditor, researcher): highest precision model, full VRAM
        GOOD (executor, context-compiler): standard model, standard allocation
        FAIR (prompt-engineer): can use smaller/quantized variant
        BASIC (memory-writer): smallest capable model, minimal resources
        Tier stored in elai_cc.toml [agents.{role}.slo_tier]
        ModelPool uses tier for: model variant selection, GPU assignment, VRAM allocation
        Tier mismatch (BEST role + BASIC model) -> WARNING log
    DETERMINISTIC_CHECK:
      - cargo check --workspace exits 0
      - grep -r "MultiplexingPolicy" .elai_cc/crates/providers/src/ returns hits
      - grep -r "PreloadPolicy" .elai_cc/crates/providers/src/ returns hits
      - grep -r "SloTier" .elai_cc/crates/providers/src/ returns hits
      - grep -r "can_colocate" .elai_cc/crates/providers/src/ returns hits
    ADVERSARIAL:
      - If VRAM accounting is wrong, colocated models cause GPU OOM.
        Test: simulate colocation where sum > GPU_VRAM - margin, verify can_colocate returns false.
      - If pre-load races with current model's inference, VRAM contention.
        Test: verify pre-load waits until current agent is between inference calls (phase boundary).
      - If safety margin (1GB) is too small for a specific model, OOM despite passing check.
        Test: health check after colocation, if OOM -> increase margin and retry.
    ACCEPTANCE:
      - Multiplexing policy enforced with VRAM safety margin
      - Predictive pre-loading triggers on FSM state transitions
      - SLO tiers configurable per agent role
      - Single-GPU mode correctly disables multiplexing

      - MILP problem formulation (Murakkab-derived):
        Decision variables: model_assignment[model, gpu] in {0,1}
        Objective: minimize total phase transition latency (model swap time)
        Constraints:
          sum(vram[model] * assignment[model, gpu]) <= gpu_vram[gpu] - safety_margin for each gpu
          sum(assignment[model, gpu] for gpu) == 1 for each model (each model on exactly 1 GPU)
          models_needed_concurrently assigned to different GPUs or colocated within VRAM
        Reoptimize at phase boundaries, not per-request
      - Evaluate Rust MILP solvers:
        a. good_lp crate (v1.10+): abstraction over CBC, HiGHS, CPLEX
           HiGHS backend: MIT-licensed, actively maintained, no external C++ dependency if using highs crate
           CBC backend: EPL-licensed, coin-or ecosystem
        b. Check Windows build compatibility (R5 risk)
        c. Measure: time to solve 5-model 2-GPU assignment problem
      - Decision criteria:
        If heuristic (greedy: assign largest model first, pack small models) achieves
        <5% worse swap latency than MILP optimal: DROP MILP (complexity not justified)
        If MILP gives >10% improvement: ADOPT with good_lp + HiGHS backend
        If 5-10% improvement: EVALUATE further in Phase 4
      - Heuristic baseline implementation (always needed, even if MILP adopted):
        GreedyModelPlacer: sort models by VRAM desc, assign to GPU with most free space
        Respects multiplexing policy from step 3J.6
