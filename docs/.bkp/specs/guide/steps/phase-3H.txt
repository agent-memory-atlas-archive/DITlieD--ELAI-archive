PHASE 3H: SESSION HANDOFF (CMV-derived DAG state management)
Prerequisites: Phase 3G complete (hierarchical plan management — PlanSkeleton in snapshots),
  Phase 3B complete (SSB operational — stub recovery reads SSB seq entries),
  Phase 3E complete (context budget allocator — trimming target derived from slot allocation),
  providers::token_count callable (stub_threshold measured in tokens)
Depends on: orchestrator::SSB (stub recovery via ssb.query(seq)),
  orchestrator::ContextBudget (trimming target = model_window - allocated_slots - output_reserve),
  orchestrator::PlanSkeleton (persisted in snapshot.findings as plan state),
  providers::token_count (measuring stub_threshold, trimmed context size)

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
DAG-based session state versioning with structurally lossless trimming.
Sessions can branch, explore alternatives, and merge.
Checkpoint triggers: after every GRC step, tool call, phase transition.
Handoff triggers: at token budget threshold (configurable, default 85%).
Paper reference: arxiv 2602.22402 (CMV). Interface map: workflow/papers/cmv-interface.md.

SPEC AMENDMENTS REQUIRED (resolve before implementing):
  1. snapshot_context schema: this phase expands orchestrator.txt L293-294 from a BLOB-per-snapshot
     design (role TEXT, trimmed_messages BLOB, stub_count INTEGER) to a per-message row design
     (seq, role, content, is_stubbed, stub_ssb_seq). Rationale: per-message rows enable selective
     stub recovery without deserializing entire context BLOB. Update orchestrator.txt Section 10
     to reflect the adopted schema before implementing.
  2. SSB action_type for branch operations: orchestrator.txt L57-63 lists 16 action_types.
     Branch abandonment needs either: (a) a new action_type 'branch_abandon' added to the spec,
     or (b) reuse existing 'checkpoint' action_type with branch metadata in payload.
     Decision required before implementing 3H.4.
  3. SSB cleanup on branch merge: orchestrator.txt L312 says "Only winning branch's SSB entries
     kept." This is ambiguous — SSB is append-only (L47). Clarify: does "kept" mean
     (a) physical deletion of losing branch entries, or (b) logical exclusion via query filter?
     This phase assumes (b) — query exclusion, no physical deletes. Confirm or override.


TYPES (expanded from orchestrator.txt L286-325 — see SPEC AMENDMENTS above for divergences)

  SQLite schema (session_dag.db, one per session):

    CREATE TABLE snapshots (
        snap_id     TEXT PRIMARY KEY,       -- UUID v4 via EntropyProvider
        parent_id   TEXT REFERENCES snapshots(snap_id),  -- NULL for root
        session_id  TEXT NOT NULL,
        fsm_state   TEXT NOT NULL,          -- FSM state at snapshot time
        phase       TEXT,                   -- current plan phase (e.g. "3H")
        step        TEXT,                   -- current step within phase (e.g. "3H.2")
        findings    BLOB,                   -- msgpack: Vec<AuditFinding> (from auditor)
        code_changes BLOB,                  -- msgpack: Vec<FileChange> (files touched)
        tests_written BLOB,                 -- msgpack: Vec<TestRef> (tests added/modified)
        commit_hashes TEXT,                 -- comma-separated git commit SHAs owned by session
        created_at  INTEGER NOT NULL,       -- unix millis via ClockProvider
        tag         TEXT                    -- "handoff", "branch:{name}", or NULL
    );

    CREATE TABLE snapshot_context (
        snap_id     TEXT NOT NULL REFERENCES snapshots(snap_id),
        seq         INTEGER NOT NULL,       -- message ordering within conversation
        role        TEXT NOT NULL CHECK(role IN ('system','user','assistant','tool')),
        content     BLOB NOT NULL,          -- msgpack: original or stubbed message content
        is_stubbed  INTEGER NOT NULL DEFAULT 0,  -- 1 if this message was stubbed by trimming
        stub_ssb_seq INTEGER,               -- SSB seq for recovery (NULL if not stubbed)
        PRIMARY KEY (snap_id, seq)
    );

    CREATE INDEX idx_snapshots_session ON snapshots(session_id);
    CREATE INDEX idx_snapshots_tag ON snapshots(tag) WHERE tag IS NOT NULL;
    CREATE INDEX idx_context_stubbed ON snapshot_context(snap_id) WHERE is_stubbed = 1;

RISKS TO WATCH
  R-3H-1: DAG cycle formation during branching. CMV paper lists this as failure mode #3.
    Mitigation: parent_id is always the snapshot being branched FROM (existing, immutable).
    New snapshots append only. Verify acyclicity: parent chain walk terminates at root (NULL).
  R-3H-2: Orphan stub references — stub points to SSB seq that was pruned or corrupted.
    CMV paper failure mode #2. Mitigation: Pass 3 validates every stub against SSB before
    committing trimmed context. If SSB seq missing, keep original content (don't stub).
  R-3H-3: Token counting inaccuracy in trimming — stubbed context still exceeds model window.
    CMV paper failure mode #4. Mitigation: measure trimmed context with exact token_count
    (not estimate) before writing to snapshot_context. Reject if exceeds budget.
  R-3H-4: Branch explosion — more than 3 active branches consume excessive SQLite storage.
    Mitigation: hard limit of 3 active branches enforced on branch creation (orchestrator.txt L314).
    Must close/merge a branch before opening a new one.
  R-3H-5: Prompt cache invalidation during trimming — if trimming changes Slots 1-3 prefix,
    cache miss on next invocation wastes tokens. Mitigation: trimming only operates on
    Slot 6+ content (SSB entries, GRC history). Slots 1-3 (system prompt, rules, phase spec)
    are never stubbed. Slot 4-5 (repo map, code context) are regenerated per invocation anyway.
  R-3H-6: Compaction boundary detection failure (CMV failure mode #1). If handoff trigger
    (85% token budget) is miscalculated, trimming fires too early (wastes context) or too late
    (context overflow before handoff). Mitigation: handoff trigger checks actual token usage
    via exact token_count, not estimate. Test: inject context at exactly 85% -> handoff triggers;
    inject at 84.9% -> no handoff.
  R-3H-7: Session file corruption (CMV failure mode #5). If session_dag.db is partially written
    (crash during transaction), the file may be corrupted. Mitigation: SQLite transactions
    ensure atomicity (DELETE journal mode). On open, run PRAGMA integrity_check. If it fails,
    return Err(DatabaseCorrupted) — caller decides whether to start fresh or abort.
  R-3H-8: TrimConfig.allocated_slots_tokens coupling to Phase 3E. The trimming target formula
    (model_window - allocated_slots - output_reserve) requires Phase 3E to expose a method
    returning total allocated tokens for Slots 1-7. If 3E does not expose this, TrimConfig
    cannot be populated. PRE_GATE in 3H.3 should verify this interface exists.

  3H.3 STRUCTURALLY LOSSLESS 3-PASS TRIMMING
    PRE_GATE:
      - 3H.2 snapshot save/load works
      - providers::token_count callable (needed for stub_threshold measurement)
      - SSB operational (Pass 3 validates stubs against SSB)
      - Phase 3E context budget allocator exposes total_allocated_tokens() or equivalent
        (needed for TrimConfig.allocated_slots_tokens). Verify: grep for method in 3E code.
    TASK:
      - Implement SessionDag::trim_context(messages, config) -> Result<Vec<TrimmedMessage>>
        config: TrimConfig { stub_threshold: usize, model_context_window: usize,
          allocated_slots_tokens: usize, output_reserve: usize }
        target_tokens = model_context_window - allocated_slots_tokens - output_reserve
      - Pass 1 (identify): stream through messages. For each tool-result message, measure
        token count via providers::token_count. If > stub_threshold, mark for stubbing.
        User and assistant messages: NEVER marked (structurally lossless invariant).
      - Pass 2 (stub): for marked messages, replace content with Stub struct (msgpack).
        Stub contains: original_type, original_tokens, summary_hash (blake3 of original),
        ssb_seq (the SSB seq where this tool result was recorded).
        Set is_stubbed=true, stub_ssb_seq=ssb_seq on the TrimmedMessage.
      - Pass 3 (validate): for each stubbed message, verify ssb_seq exists in SSB
        (ssb.query_seq(seq) returns Some). If SSB seq missing: UNSTUB — restore original
        content (cannot recover later, so keep it now). Measure total trimmed token count.
        If total > target_tokens: return Err(TrimBudgetExceeded { actual, target }).
      - Prompt cache awareness: messages in Slots 1-3 positions (system prompt, rules,
        phase spec) are never candidates for stubbing. Only Slot 6+ content (SSB entries,
        GRC history, tool results) eligible.
    DETERMINISTIC_CHECK:
      - 10 messages, 3 tool results >500 tokens each -> 3 stubbed, 7 unchanged
      - All user/assistant messages preserved verbatim (byte comparison)
      - Stub.summary_hash matches blake3(original_content) for each stub
      - Stub.ssb_seq is valid (SSB lookup returns original content)
      - SSB seq missing for one stub -> that message unstubbed (original preserved)
      - Total trimmed tokens < target_tokens for valid input
      - Input with all messages < stub_threshold -> 0 stubs, output identical to input
      - token_reduction = sum(original_tokens) - sum(trimmed_tokens) >= 0 (invariant from CMV)
      - Same input + same seed -> identical output (determinism)
    ADVERSARIAL:
      - If token_count is slow (~10ms per call) and context has 500 messages, Pass 1 takes 5s.
        Acceptable for handoff (infrequent). But test: measure Pass 1 wall time with 500 messages,
        verify < 10s. If too slow, batch token counting (concatenate then count once) as fallback.
      - If blake3 hash collision occurs (astronomically unlikely), stub recovery returns wrong
        content. Test: this is not testable probabilistically. Mitigation: ssb_seq is the primary
        recovery key, hash is integrity check only. Verify: recovered content hash matches stub hash.
      - If stub_threshold is set very low (e.g. 10 tokens), nearly everything gets stubbed,
        including small tool results that are cheap to keep. Test: minimum stub_threshold enforced
        at 100 tokens (CMV paper hyperparameter range [100, 1000]).
      - If trimming runs AFTER prompt cache prefix is computed, stubs in Slots 1-3 break cache.
        Test: assert no message with seq <= slot_3_boundary is ever stubbed.
    ACCEPTANCE:
      - All user/assistant messages preserved (zero content changes)
      - Token reduction >= 0
      - Every stub recoverable from SSB (or unstubbed if SSB missing)
      - Trimmed output fits within target_tokens
      - stub_threshold enforced in [100, 1000] range
    GROUNDING:
      - "3 streaming passes" -> GROUNDED: orchestrator.txt L300-304, CMV paper (O(3*N))
      - "stub_threshold default 500" -> GROUNDED: orchestrator.txt L301, CMV hyperparameters
      - "structurally lossless" -> GROUNDED: orchestrator.txt L630 ("preserves ALL user and assistant messages")
      - "every stub references valid SSB seq" -> GROUNDED: orchestrator.txt L631
      - "prompt cache prefix Slots 1-3" -> GROUNDED: orchestrator.txt L635, context budget L143
      - "stub_threshold range [100, 1000]" -> GROUNDED: CMV interface map hyperparameters
      - "blake3 for hashing" -> UNGROUNDED: orchestrator.txt does not specify hash algorithm.
        Assumed because: blake3 is fast (3.5 GB/s) and already common in Rust ecosystem.
        Alternative: sha256. Decision deferred to implementation.
