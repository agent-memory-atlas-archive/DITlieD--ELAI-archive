PHASE 1B: BM25 (tantivy full-text search)
Canonical path: .elai_cc/crates/knowledge/ (same as Phase 1A)
Prerequisites: Phase 1A complete (knowledge/ crate exists, DKG tests pass, KnowledgeEngine trait defined)

SCOPE: see docs/specs/guide/implementation-guide.txt

GOAL
Full-text search over codebase via tantivy BM25 index.
Per-project index isolation. Sub-10ms queries for indexes under 100K documents.
Zero orphan files: every text file in the project appears in the BM25 index, even if
tree-sitter cannot parse it (unsupported language, syntax errors). Binary files (null bytes
in first 8KB) are the sole exception.

      matches expectations (tantivy uses a u32 constant, not a string label).

  R2: Index corruption on crash. tantivy uses directory-based indexes — need atomic commit.
  R3: Windows path handling. tantivy index paths must use valid Windows paths.
  R4: Memory usage on large repos. tantivy loads segments into memory.
  R5: Binary file indexing. Must not panic on non-UTF8 content — skip, log warning.
  R6: Chunking strategy mismatch. BM25 chunks must align with how later layers (vectors, reranker) chunk.
  R7: path field schema. The path field used for delete_term MUST be STRING (untokenized),
      not TEXT (tokenized). Tantivy tokenizes TEXT fields, splitting paths on / . - which
      makes exact-match deletion impossible. Verified from tantivy examples.

    TASK:
      - Create bm25.rs module in .elai_cc/crates/knowledge/src/
      - Define BM25 chunk type owned by this module:
          pub struct BM25Chunk {
              pub path: PathBuf,
              pub content: String,
              pub line_start: u32,
              pub line_end: u32,
              pub kind: ChunkKind,
          }
          pub enum ChunkKind { Function, LineBlock, File }
        NOTE: Phase 1A's DKG exports DkgNode (AST metadata: kind, name, start/end lines) but NOT
        file content. BM25Chunk includes content because BM25 must index text. The conversion from
        DKG nodes to BM25Chunks requires reading file content at the line ranges DKG provides.
        This conversion is BM25's responsibility, not DKG's.
      - Define Bm25Index struct:
          new(project_root: &Path, project_id: &str) -> Result<Self>
          project_id is passed explicitly (not derived) — matches knowledge.txt L274 which requires
          project_id as a first-class input. The caller (KnowledgeEngine) manages project_id assignment.
      - Index path: {project_root}/.elai_cc/projects/{project_id}/bm25/
      - Tantivy schema:
          path:       STRING | STORED  (untokenized — required for exact-match delete_term)
          content:    TEXT | STORED    (tokenized — this is what BM25 searches)
          line_start: u64 STORED
          line_end:   u64 STORED
          chunk_kind: STRING | STORED  (serialized from ChunkKind enum, not free-form text)
        CRITICAL: path MUST be STRING, not TEXT. Tantivy tokenizes TEXT fields (splits on /, ., -).
        delete_term on a tokenized path field will not produce exact-match deletion, causing silent
        data corruption (orphaned documents or wrong deletions). Verified from tantivy's
        deleting_updating_documents.rs example: primary-key fields use STRING.
      - Define methods:
          index_file(path: &Path, chunks: Option<Vec<BM25Chunk>>) -> Result<usize>
            If chunks provided: index each chunk as a document.
            If chunks=None: read file, generate BM25Chunks using 50-line sliding window fallback.
            Binary files: skip (log warning). Detection: null bytes in first 8KB.
          index_directory(root: &Path, dkg: Option<&DkgIndex>) -> Result<IndexStats>
            Walk directory. For each file: query DKG for node ranges, read content at those ranges
            to create BM25Chunks. If DKG has no nodes for a file, use line-level fallback.
            Return IndexStats { files_indexed, chunks_indexed, files_skipped_binary, elapsed_ms }.
          query(query_text: &str, limit: usize) -> Result<Vec<BM25Hit>>
            BM25Hit { path: String, line_start: u32, line_end: u32, score: f32,
                      chunk_kind: ChunkKind, snippet: String }
            snippet: first 200 chars of matching content (simple truncation, not tantivy SnippetGenerator).
          delete_file(path: &Path) -> Result<usize>  (returns docs deleted)
            Uses delete_term on STRING path field for exact match.
          update_file(path: &Path, chunks: Option<Vec<BM25Chunk>>) -> Result<usize>
            Atomic: delete_file + index_file in single writer.commit(). <5s for single file.
            Writer serialization note: Bm25Index holds a single IndexWriter. index_directory holds
            the writer for the entire batch commit duration. Concurrent update_file calls from other
            threads will block until the writer is released. This is by design (tantivy single-writer
            model) but callers must be aware that index_directory blocks all update_file calls.
      - Register module in .elai_cc/crates/knowledge/src/lib.rs
      - Create contract test stub: .elai_cc/tests/contracts/bm25_contract.rs with one test per
        public method of Bm25Index (index_file, index_directory, query, delete_file, update_file).
        Contract tests verify the public API contract, not implementation details.

  1B.4 IMPLEMENT BM25 INDEX
    PRE_GATE:
      - Step 1B.3 complete: failing tests exist
      - cargo test -p knowledge --lib -- bm25 2>&1 | grep -q "FAILED"
    TASK:
      CORE INDEX:
      - Implement tantivy index creation with schema:
          path:       STRING | STORED (untokenized — for exact delete_term)
          content:    TEXT | STORED   (tokenized — BM25 search target)
          line_start: u64 STORED
          line_end:   u64 STORED
          chunk_kind: STRING | STORED (from ChunkKind enum)
      - Index storage at {project_root}/.elai_cc/projects/{project_id}/bm25/

      INDEX_FILE (two modes):
      - With BM25Chunks (from DKG-derived conversion): each chunk becomes one tantivy document.
        chunk_kind = ChunkKind::Function.
      - Without chunks (line-level fallback): read file content, split into 50-line sliding windows
        with 10-line overlap. Each window becomes one document. chunk_kind = ChunkKind::LineBlock.
        Rationale: 50-line windows match vector embedding chunk size (spec L173: "50-line sliding window").
        10-line overlap prevents splitting a function across two chunks where neither has full context.
        NOTE (from audit): overlap is primarily beneficial for embedding-based search, not BM25
        (BM25 scores terms independently). The overlap is carried over from the vector layer for
        implementation simplicity and cross-layer chunk alignment. This is an UNGROUNDED design choice
        for BM25 specifically — the overlap adds ~20% more documents with no proven BM25 retrieval benefit.
      - Small files (<50 lines): index as single document. chunk_kind = ChunkKind::File.

      BINARY DETECTION:
      - Read first 8KB of file. If contains null byte (\0), classify as binary, skip, log warning.
      - Return count of skipped binary files in IndexStats.

      INDEX_DIRECTORY:
      - Walk directory recursively. Skip hidden dirs (.*), skip .elai_cc/ dir itself.
      - For each file: query DKG for node ranges, read content to create BM25Chunks.
        If DKG has no nodes, use line-level fallback.
      - Atomic commit: one writer.commit() after all files indexed (not per-file).
      - Writer serialization: index_directory holds the IndexWriter for the entire batch.
        No concurrent update_file calls possible during index_directory execution.
        Document this constraint in Bm25Index struct-level docs.
      - Return IndexStats.

      QUERY:
      - BM25 query via tantivy QueryParser on content field.
      - Return top N results sorted by score descending.
      - Each result: BM25Hit { path, line_start, line_end, score, chunk_kind, snippet }.
      - snippet: first 200 chars of stored content (simple truncation).

      DELETE_FILE:
      - delete_term on STRING path field for exact match. Return count deleted.
      - Single writer.commit() after deletion.

      UPDATE_FILE:
      - Atomic: delete_term(path) then add_document(new chunks) in single writer.commit().
      - Readers only see committed state — no intermediate state where file is absent.
      - Target: <5s for any single file (spec L265 invariant).

    DETERMINISTIC_CHECK:
      - All BM25 tests pass: cargo test -p knowledge --lib -- bm25 2>&1 | grep "test result: ok"
      - No warnings on bm25.rs: cargo check -p knowledge 2>&1 | grep -c "warning.*bm25" = 0
      - Existing DKG tests still pass: cargo test -p knowledge --lib -- dkg exits 0
    ADVERSARIAL:
      - If index_directory encounters a file deleted between walk and read, should skip gracefully.
        Test: simulate race, assert graceful skip + log warning (not panic).
      - If two Bm25Index instances opened for same project_id, tantivy lock file prevents second writer.
        Test: second Bm25Index::new returns Err (not panic or deadlock).
      - If 50-line window splits a function at line 48-52, query may return low-relevance results.
        Test: 10-line overlap ensures function appears in at least one chunk with full context.
      - If file is valid UTF-8 but contains only whitespace, still indexed (not binary).
        Test: whitespace-only file indexed, no error.
    ACCEPTANCE:

DECISIONS MADE IN THIS PHASE (to be recorded in workflow/reasoning/phase-1B-decisions.md)
  D1: Chunking fallback uses 50-line sliding windows with 10-line overlap.
      Why: matches vector embedding chunk size (knowledge.txt L173). Overlap prevents
      splitting functions across chunk boundaries where neither chunk has full context.
      CAVEAT: overlap is UNGROUNDED for BM25 specifically (BM25 scores terms independently).
      Carried over from vector layer for cross-layer chunk alignment and implementation simplicity.
  D2: Binary detection via null byte in first 8KB, not MIME type.
      Why: fast (no external dependency), reliable for source code repos. Same heuristic
      used by git (core.autocrlf detection). Binary files are the only zero-orphan exception.
  D3: BM25Hit includes chunk_kind field for downstream filtering.
      Why: later layers (reranker 1G, CatRAG 1E) may weight function-level chunks differently
      from line-block chunks. Carrying this metadata avoids re-parsing.
  D4: Index path follows .elai_cc/projects/{project_id}/bm25/ convention.
      Why: knowledge.txt L195 specifies this layout. All knowledge layers share the same
      project directory, enabling unified versioning (1I.7).
  D5: update_file is atomic (delete+insert in single commit).
      Why: prevents intermediate state where file is absent from index. Critical for
      EXECUTING -> AUDITING transitions where auditor must see current file state.
      NOTE: single-writer model means index_directory blocks concurrent update_file calls.
  D6: path field uses STRING (untokenized), not TEXT.
      Why: tantivy tokenizes TEXT fields, splitting paths on / . - characters. delete_term
      requires exact match on the stored term. Using TEXT would cause silent deletion failures.
      Verified from tantivy's deleting_updating_documents.rs example.
  D7: BM25Chunk is a BM25-owned type, distinct from DKG's DkgNode.
      Why: DkgNode stores AST metadata (kind, name, start/end lines) but not file content.
      BM25 needs content for indexing. Conversion from DkgNode to BM25Chunk (reading file
      content at DKG line ranges) is BM25's responsibility, keeping DKG decoupled.
  D8: project_id is passed explicitly to Bm25Index::new, not derived from project_root.
      Why: knowledge.txt L274 states "Query without project_id is rejected" — it is a first-class
      input, not a derived value. KnowledgeEngine (the caller) manages project_id assignment.
  D9: snippet uses simple 200-char truncation, not tantivy SnippetGenerator.
      Why: adequate for Phase 1B scope. tantivy's SnippetGenerator provides keyword highlighting
      which may be added in later phases if reranker or UI needs it. Deliberate simplification.
