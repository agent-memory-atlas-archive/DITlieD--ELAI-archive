  1I.1 CIRCUIT BREAKER
    PRE_GATE:
      - cargo test --lib passes (Phase 1G baseline intact)
      - knowledge crate compiles: cargo check -p elai_knowledge
      - Cross-encoder reranker exists (Phase 1G deliverable): grep -r "cross.encoder\|rerank" .elai_cc/crates/knowledge/src/ returns matches
      - ClockProvider trait exists (entropy quarantine): grep -r "ClockProvider" .elai_cc/crates/core/src/ returns trait definition
    TASK:
      - Implement EmbeddingCircuitBreaker struct with states: CLOSED, OPEN, HALF_OPEN
      - Independent instance per ONNX model (GraphCodeBERT, Granite, cross-encoder, SPLADE)
      - Config: failure_threshold=3 (transient), failure_window=60s, half_open_timeout_base=30s
      - All time access via ClockProvider (entropy quarantine, deterministic testing)
      - Failure classification (Azure Architecture Center pattern):
          TRANSIENT (timeout, temporary OOM): count toward threshold (3 needed to open)
          PERMANENT (segfault, model file missing, invalid ONNX): open immediately after 1 failure
          Classification via error type enum, not string matching
      - Exponential backoff for successive OPEN timeouts (AWS Builders Library pattern):
          First OPEN: 30s. Second consecutive OPEN: 60s. Third: 120s. Cap: 120s.
          Deterministic jitter per model (hash of model_id, not random) to prevent
          thundering herd when multiple breakers recover simultaneously
      - State NOT checkpointed (resets to CLOSED on restart)
      - On OPEN: skip model, return fallback immediately
      - On HALF_OPEN: allow limited probe calls. Require 2 consecutive successes before
        CLOSED (Azure pattern: success counter with threshold prevents premature recovery
        on flaky models). Any failure -> OPEN (reset timer, increase backoff).
      - Fresh ONNX InferenceSession for HALF_OPEN probes (do not reuse potentially-corrupted
        session — ONNX Runtime issues #20043/#20354 show sessions can crash or hang)
    DETERMINISTIC_CHECK:
      - cargo test circuit_breaker -- passes
      - grep -r "EmbeddingCircuitBreaker" .elai_cc/crates/knowledge/src/ returns struct definition
      - grep -r "CLOSED\|OPEN\|HALF_OPEN" .elai_cc/crates/knowledge/src/ returns enum variants
    ADVERSARIAL:
      - If failure_window clock uses wall time instead of injectable time source, tests become non-deterministic. Test: inject mock clock, advance by 60s, verify breaker opens.
      - If circuit breaker state is shared across models, one model failure takes down all models. Test: fail GraphCodeBERT only, assert Granite breaker remains CLOSED.
      - If HALF_OPEN probe succeeds once but model is flaky, premature CLOSED causes immediate re-open oscillation. Test: 1 success then 1 failure in HALF_OPEN -> stays HALF_OPEN or re-opens (not CLOSED).
      - If all breakers use fixed timeout and recover simultaneously, all ONNX models reload at once causing GPU OOM. Test: 4 breakers with same failure time get different HALF_OPEN times (jitter).
      - If permanent error (segfault) is classified as transient, 2 more doomed retries waste time. Test: permanent error opens breaker after 1 call, not 3.
      - If HALF_OPEN reuses corrupted ONNX session, probe always fails -> breaker never recovers. Test: after OPEN, probe creates new InferenceSession (mock verifies new session constructed).
    ACCEPTANCE:
      - 3 transient failures within 60s opens breaker: test asserts state==OPEN after 3rd timeout error
      - 1 permanent failure opens immediately: test asserts state==OPEN after 1st segfault/missing-model error
      - Failures spread across >60s stay CLOSED: test with 3 failures at 0s, 61s, 122s
      - HALF_OPEN requires 2 consecutive successes for CLOSED: 1 success -> still HALF_OPEN, 2nd success -> CLOSED
      - HALF_OPEN failure after 1 success resets counter: success then failure -> OPEN, counter reset
      - Exponential backoff: first OPEN=30s, second=60s, third=120s (mock clock, verify timeout values)
      - Jitter is deterministic: same model_id always produces same jitter offset
      - Different models get different jitter: 4 models produce 4 distinct HALF_OPEN times
      - Fresh session on probe: mock verifies InferenceSession::new called during HALF_OPEN, not reused
      - Each model has independent breaker: test fails one model, asserts others remain CLOSED

  1I.4 STARTUP READINESS
    PRE_GATE:
      - 1I.1 circuit breaker exists
      - 1I.2 SearchMode cascade exists
    TASK:
      - Implement startup readiness sequence:
          1. Load ONNX models (GraphCodeBERT, Granite, cross-encoder, optionally SPLADE)
          2. Open SQLite databases (DKG graph, vector cache, BM25 index)
          3. Run canary query: embed("fn main()") + BM25 search("main") + rerank
          4. All layers must return non-error within 5s
          5. Canary embedding drift check: compute cosine similarity of embed("fn main()")
             against a reference vector stored at build time. If similarity < 0.85, model
             weights are likely corrupted or wrong version loaded. Fail canary, enter DEGRADED.
             Reference vector generated once during first successful startup and persisted
             in index_version.toml as canary_reference_vec.
             Evidence: embedding audit best practices — a model that loads but produces
             garbage embeddings silently corrupts all downstream retrieval.
          6. Report ReadinessStatus to orchestrator
      - ReadinessStatus enum: READY, DEGRADED, UNAVAILABLE
        READY: all layers passed canary query
        DEGRADED: ONNX models failed but BM25 operational -> BM25_ONLY SearchMode
        UNAVAILABLE: BM25 also failed (SQLite corrupt, disk error) -> total outage
        Invariant: DEGRADED implies SearchMode==BM25_ONLY (not HYBRID or SPARSE_ONLY)
      - If startup fails after 3 retries: enter DEGRADED mode (BM25_ONLY), log WARNING
      - If BM25 also fails: enter UNAVAILABLE, log ERROR, orchestrator blocks all transitions
      - Orchestrator gates FSM: IDLE -> PLANNING blocked until knowledge engine READY or DEGRADED
        UNAVAILABLE blocks all FSM transitions (no work possible without any search)
    DETERMINISTIC_CHECK:
      - cargo test startup_readiness -- passes
      - cargo test canary_query -- passes
      - grep -r "ReadinessStatus" .elai_cc/crates/knowledge/src/ returns enum with 3 variants
      - grep -r "readiness_check" .elai_cc/crates/knowledge/src/ returns fn implementation
    ADVERSARIAL:
      - If canary query hangs (ONNX model deadlock), startup blocks forever. Test: canary has 5s timeout, startup returns DEGRADED after timeout.
      - If ONNX model loads but produces garbage embeddings (wrong weights, corrupted file), false READY reported and all retrieval silently degrades. Test: swap model with random-weight ONNX, canary drift check detects similarity < 0.85, returns DEGRADED.
      - If reference vector doesn't exist yet (first startup), drift check can't run. Test: missing reference -> skip drift check, generate and persist reference after successful canary.
      - If 3 retries run sequentially without backoff, startup takes 15s minimum on transient failure. Test: verify total startup time <20s even with 3 retries.
    ACCEPTANCE:
      - Healthy system: readiness_check returns READY within 5s (integration test with loaded models)
      - All ONNX models fail: readiness_check returns DEGRADED after 3 retries, BM25_ONLY mode active
      - BM25 also fails: readiness_check returns UNAVAILABLE (not DEGRADED)
      - UNAVAILABLE blocks FSM: test asserts IDLE -> PLANNING transition rejected when UNAVAILABLE
      - Canary query timeout: readiness_check returns DEGRADED within 5s (not hanging)
      - Canary drift detection: cosine_sim(canary_vec, reference_vec) < 0.85 -> DEGRADED (not READY)
      - First startup (no reference): drift check skipped, reference vector persisted after success
      - DEGRADED implies BM25_ONLY: test asserts SearchMode==BM25_ONLY when ReadinessStatus==DEGRADED
      - ReadinessStatus is READY|DEGRADED|UNAVAILABLE: grep confirms enum has exactly 3 variants
    GROUNDING:
      - "canary: embed('fn main()') + BM25 search('main') + rerank" -> GROUNDED: knowledge.txt:L159
      - "within 5s" -> GROUNDED: knowledge.txt:L160
      - "3 retries then BM25_ONLY" -> GROUNDED: knowledge.txt:L164
      - "ReadinessStatus: READY | DEGRADED | UNAVAILABLE" -> GROUNDED: architecture-overview.txt:L99
      - "Estimated startup 5-15s" -> GROUNDED: knowledge.txt:L165

  1I.5 CROSS-ENCODER SEMAPHORE
    PRE_GATE:
      - Cross-encoder reranker exists and compiles (Phase 1G deliverable)
      - cargo test rerank -- passes (1G tests still green)
    TASK:
      - Add tokio::Semaphore(1) guard around cross-encoder ONNX session access
      - One reranking at a time. Queued requests wait in bounded channel (capacity 4).
      - Concurrency model: Semaphore(1) + bounded_channel(4) = max 5 in-flight (1 active + 4 queued)
      - 6th concurrent request overflows: returns unranked results immediately
      - Batching optimization: if multiple requests queued, merge candidate sets and rerank once
    DETERMINISTIC_CHECK:
      - cargo test semaphore -- passes
      - cargo test rerank_queue -- passes
      - grep -r "Semaphore" .elai_cc/crates/knowledge/src/ returns Semaphore(1) usage
    ADVERSARIAL:
      - If semaphore is not acquired before ONNX session access, concurrent rerank calls corrupt session state. Test: spawn 10 concurrent rerank calls, assert no panic/corruption.
      - If queue overflow silently drops results instead of returning unranked, caller gets empty response. Test: overflow returns original candidates in input order (unranked, not empty).
      - If batching merges candidate sets but returns results in wrong order per-query, callers get mixed results. Test: two concurrent queries with disjoint candidates, assert each caller gets only their candidates back.
    ACCEPTANCE:
      - Semaphore serializes access: 2 concurrent reranks, second starts after first finishes (timing assert)
      - 6th concurrent request overflows: 1 active + 4 queued = 5 in-flight, 6th returns unranked immediately
      - Overflow returns candidates (not empty): test asserts result.len() == input.len() on overflow
      - Batching merges correctly: 2 queued requests with 10 candidates each -> 1 rerank call with 20 candidates
      - Batching segregates results: each caller receives only their original candidates (reranked), not the merged set
