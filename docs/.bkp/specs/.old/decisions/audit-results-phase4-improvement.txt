BLOCK-1: IMPLEMENT section (4A.5) omits RLIMIT_FSIZE and RLIMIT_AS from rlimit spec
  File: phase-4A.txt line 257 vs orchestrator.txt line 524
  phase-4A.txt specifies only "RLIMIT_NPROC=1" for the agent process rlimits.
  orchestrator.txt L524 requires all three:
    RLIMIT_NPROC=1, RLIMIT_FSIZE=100MB, RLIMIT_AS=512MB (configurable).
  Effect of omission: an agent compiled from this spec has no disk write limit
  (RLIMIT_FSIZE) and no address space limit (RLIMIT_AS). A runaway agent or
  adversarial agent can:
    - Write unbounded data to /tmp scratch (filling the host disk despite orchestrator.txt
      S12's "100MB scratch space" requirement).
    - Allocate unlimited virtual address space (triggering OOM on the host or overcommit
      pressure across all agents).
  Both limits are in the authoritative spec. Both are absent from the phase file.
  Implementors reading only the phase file will not apply them.
  Fix: add "RLIMIT_FSIZE=100MB, RLIMIT_AS=512MB (configurable)" to 4A.5 IMPLEMENT
    Linux process isolation section. Add DETERMINISTIC_CHECK: verify /proc/PID/limits
    shows correct values after spawn.

BLOCK-2: IMPLEMENT section (4A.5) omits /proc masking and /sys unmounting
  File: phase-4A.txt lines 249-258 vs orchestrator.txt line 521
  orchestrator.txt L521: "/proc: masked (hidepid=2 or not mounted). /sys: not mounted."
  phase-4A.txt L255-258 describes the mount namespace as:
    "Bind-mount project source (RO) + scratch (RW). .elai_cc/ not mounted."
    (plus self-mod variant for locked paths)
  Neither /proc masking nor /sys unmounting appears.
  Effect: an agent process can read /proc/1/maps (its own map) and other /proc
  pseudo-files. More critically, if the PID namespace is entered via CLONE_NEWPID
  but /proc is not remounted for the new namespace, the old /proc remains visible.
  The agent could enumerate /proc/{low_pids}/ to probe the orchestrator's host-side
  process layout, leaking information about the enforcement environment.
  /sys exposes kernel subsystem state (hardware, power, block devices) that should
  not be visible to an agent.
  This is NOT merely a latent risk — implementing from this spec produces isolation
  weaker than what orchestrator.txt specifies.
  Fix: add to 4A.5 IMPLEMENT mount namespace section: "/proc: masked (hidepid=2 or
    not mounted). /sys: not mounted." Add to 4A.3 TEST: agent cannot read /proc/1/net/
    (hidden) or access /sys (ENOENT). Add to DETERMINISTIC_CHECK for 4A.5.

BLOCK-3: Prior audit WARN-3 (ShortCoder placement) is untracked — no deferral entry

  Phase-4A.txt has no mention of ShortCoder. The grounding doc (phase-4A-grounding.md)

WARN-1: GroundingRequest role-method restriction matrix not tested
  File: phase-4A.txt line 148 vs reasoning.txt section 9
  reasoning.txt S9 specifies per-role restrictions. TEST_CHECK is available only to
  executor and auditor. The test at L148 states "GroundingRequest with disallowed method
  for role -> rejected" but does not enumerate which method/role combination is under
  test. Concretely: context-compiler or memory-writer attempting TEST_CHECK should fail.
  prompt-engineer attempting TEST_CHECK should fail. These are the most probable
  accidental miscalls in practice (an agent tries to verify a claim by running a test,
  not knowing it lacks the permission).
  Fix: add specific test cases: "context-compiler sends GroundingRequest{TEST_CHECK}
    -> rejected with role-method error" and "executor sends GroundingRequest{TEST_CHECK}
    -> accepted". Both cited against reasoning.txt S9.

WARN-2: GroundingRequest with orphaned topic not tested (budget bypass vector)
  File: phase-4A.txt line 148
  reasoning.txt L152: GroundingRequest counts against per-topic budget. The adversarial
  battery in 4A.4 tests ThinkStep bursts but not GroundingRequest bursts with an orphaned
  topic (no active ThinkStep for that topic). If the orchestrator only counts
  GroundingRequests against active topics, an agent could send unlimited GroundingRequests
  using a synthetic topic name that has no budget entry yet, exhausting orchestrator
  web-search resources or rate limits without hitting any budget limit.
  Fix: add adversarial test: "send 100 GroundingRequest{WEB_CHECK, topic=X} where topic X
    has no active ThinkStep budget -> all 100 rejected or charged against a default budget".

WARN-3: 4A.3 TEST functional isolation uses "getpid == 1" — incorrect for current Linux
    kernel with CLONE_NEWPID
  File: phase-4A.txt line 116
  "Agent cannot see other agent processes (PID namespace, getpid == 1)"
  With CLONE_NEWPID, the first process in the new namespace gets PID 1 inside the
  namespace. This is correct. However: the test as written says "getpid == 1" which
  implies the test code will call getpid() from INSIDE the agent namespace to verify.
  This is valid. But the test description does not specify HOW the orchestrator verifies
  this — the agent could be asked to send its PID via IPC, and a compromised agent
  could lie. The correct test is: orchestrator reads /proc/PID_in_host_ns/status and
  verifies NSpid field == 1, not by trusting the agent's self-report.
  Fix: clarify the test mechanism: "orchestrator reads /proc/{spawned_pid}/status,
    verifies NSpid: 1". Do not rely on agent-reported PID.

WARN-4: DETERMINISTIC_CHECK for 4A.1 "exactly 15 variants (grep + count)" is ambiguous
  File: phase-4A.txt line 77
  The check does not specify the grep command. In Rust, counting enum variants via grep
  is fragile: the same pattern matches struct fields, match arms, and associated types.
  A reliable check requires either:
    - `cargo expand --package elai_cc_agent | grep -c 'IpcMessage::'`
    - A dedicated test: `assert_eq!(IpcMessageType::VARIANT_COUNT, 15);` using a
      const or discriminant count.
  As written, a developer runs an unspecified grep, gets ambiguous output, and either
  accepts a false positive or wastes time debugging the check.
  Fix: specify the exact shell command or require a compile-time const assertion.

WARN-5: Phase-4A has no explicit coverage mapping for prior WARN-7 (MAX_FRAME_SIZE
    enforced in frame reader before allocation)
  File: phase-4A.txt lines 169, 219-220
  WARN-7 from the prior audit called for MAX_FRAME_SIZE enforcement. The improved phase
  addresses this at the test level (L169: "Oversized frame (>10MB) -> rejected, no
  allocation") and in IMPLEMENT (L241: "check length prefix BEFORE alloc"). However,
  the adversarial test at L219 extends this to "send length=u32::MAX, verify no
  allocation" — which is correct and more stringent than L169's 11MB test.
  Gap: the test at L169 sends an 11MB frame. The test at L219 sends a u32::MAX-length
  frame (4GB claimed). These are different tests and both should be present and labeled.
  As written, L169 is in 4A.4 TASK and L219 is in 4A.4 ADVERSARIAL — but L169 says
  ">10MB" while L219 says "length=u32::MAX". A developer implementing only L169's test
  might allocate u32::MAX/2 (2GB) before rejecting. The u32::MAX test at L219 is
  critical (it tests the pre-allocation check, not just the size check). These two tests
  should both appear in the TASK section with explicit assertions, not split between
  TASK and ADVERSARIAL where the ADVERSARIAL one risks being treated as optional.
  Fix: move "send length=u32::MAX -> verify no allocation" into 4A.4 TASK as a required
    test, not into ADVERSARIAL.

WARN-6: 4A.3 GRC budget tests do not cover the phase transition from agent-enforced
    (phases 0-3) to orchestrator-enforced (phase 4A+)
  File: phase-4A.txt lines 136-139 vs orchestrator.txt lines 483-491
  orchestrator.txt L483-491 explicitly states that Phase 4A transitions GRC budget
  authority from agent-side GrcEngine to orchestrator IPC message counter. The same
  GrcBudget struct and AgentGrcConfig are used in both modes; only enforcement location

  shows 0 -> orchestrator injects convergence, agent must converge even though its local
  count disagrees". If the agent ignores the convergence signal when its local count
  is non-zero, the enforcement fails.
  Fix: add test: "agent local budget count != 0, orchestrator count == 0 -> orchestrator
    sends convergence signal -> agent must stop emitting ThinkStep messages regardless
    of local count". Cite orchestrator.txt L483-491.

ADVERSARIAL STRESS TEST GAPS (items the adversarial battery misses)
================================================================================

  GAP-1: No test for partial frame across two consecutive agent sessions
    orchestrator.txt L470-472 states partial frames are discarded by closing the fd.
    No test exercises: agent writes half a frame, crashes, orchestrator respawns a
    new agent to the SAME socket path (after unlinking). The partial frame bytes are
    in the kernel socket buffer. When the orchestrator closes the fd, are they
    discarded? The spec says yes (close discards), but no test verifies that the new
    agent's first message is not interpreted as a continuation of the partial frame
    from the dead agent. This is a correctness test, not just an adversarial one.

  GAP-2: No test for AF_UNIX socket creation from INSIDE the agent namespace
    The seccomp BPF checks "socket(AF_UNIX)" — but the agent is allowed to call
    socket(AF_UNIX). The test at L118 verifies "socket(AF_INET) returns EPERM."
    Missing: agent attempts to create a SECOND unix domain socket (to impersonate
    another agent or exfiltrate data to a co-located process). Is this blocked?
    The seccomp profile allows AF_UNIX for all roles (needed for IPC). A second
    AF_UNIX socket from inside the agent namespace could be used for covert channels
    between concurrent agents if they share a /tmp mount. The PID namespace prevents
    seeing other agents, but the mount namespace question is: do concurrent agents
    share the same /tmp/elai_cc_{session}/ directory or each get a private /tmp mount?
    If they share /tmp, one agent can create a socket and another can connect to it,
    bypassing the "concurrent agents cannot see each other" invariant.
    This test gap should be added: "two agents in same session cannot communicate via
    AF_UNIX socket in /tmp/elai_cc_{session}/" — or the mount design must be clarified.

  GAP-3: No test for ReplanRequest evidence hash collision
    4A.4 TEST L184 tests "MINOR replan with evidence -> auditor fast-track review."
    Missing: two ReplanRequests with identical evidence content (same hash) from the
    same agent within one phase. The spec says max 1 per agent per phase, which prevents
    the second. But what if the same evidence is sent as the first ReplanRequest in two
    consecutive phase restarts? The "max 1 per phase" counter must reset per phase, not
    persist across replans. If it persists, an agent can never trigger a second replan
    even after a legitimate phase restart.
