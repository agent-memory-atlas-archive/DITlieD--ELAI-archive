CRATE: knowledge/
Purpose: codebase understanding engine (DKG, BM25, vectors, CatRAG, A-RAG, PageRank).
Source: design_document.txt PART 4, design 31.7 (PageRank repo map).
Depends on: core/, providers/ (for embeddings)


1. RESPONSIBILITIES

  - Build and maintain dependency knowledge graph (DKG) from source code
  - Full-text search via BM25 (tantivy)
  - Vector similarity search (local embeddings or API)
  - Query-aware graph traversal (CatRAG) and hierarchical retrieval (A-RAG)
  - PageRank importance ranking for repo map generation
  - Incremental updates on file changes


2. LAYERS (5 major + 2 sub-layers: DKG, BM25, Vectors [+SPLADE 3.25, +PageRank 3.5], CatRAG, A-RAG)

  Layer 1 — DKG:
    tree-sitter AST -> SQLite graph.
    100% coverage of supported languages. <15s build. Incremental updates.
    Languages: Rust, Python, TypeScript, Go (start with these, extend as needed).

    Concept annotations (semantic topology):
      Each DKG node (file/function/struct) has a `concept TEXT` column in SQLite.
      Generated by context-compiler during MEMORIZING phase. One line max.
      Format: "[responsibility]. [why it needs its dependencies]."
      Example: "Spawns and checkpoints agent lifecycles. Needs ModelPool because
        agents require GPU allocation before reasoning can start."
      Included in PageRank repo map output alongside symbol signatures.
      Cost: ~3-5 tokens per node. 200-node project = ~800 extra tokens in repo map.
      Update trigger: file content hash changes -> concept marked stale -> regenerated.
      Stale concepts still served (better than nothing) until refresh completes.

    Effect tagging (supports GRAPH_REACHABILITY EFFECT_CHAIN queries in rules/):
      During DKG node insertion, tag functions with effect types:
        Effect::Unsafe      — contains unsafe block (Rust)
        Effect::Filesystem  — calls std::fs::*, open(), write() etc.
        Effect::Network     — calls std::net::*, reqwest::*, HTTP clients
        Effect::Database    — calls .query(), .execute() on DB connectors
        Effect::Auth        — calls auth/permission/session check functions
      Tagging is pattern-based (function name + import path matching).
      Configurable in elai_cc.toml [knowledge.effect_tags].
      Can be added incrementally in Phase 3F (does not require DKG schema change —
      effect is a text column on existing dkg_nodes table).
      Source: architectural-rule-engine.md section 6

  Layer 2 — BM25:
    tantivy full-text index. Sub-ms queries.
    Per-project index (not shared across projects).

  Layer 3 — Vectors (multi-model):
    Two embedding models per chunk (both stored, both queried):
      CODE vector: GraphCodeBERT (microsoft/graphcodebert-base, 768d) — structural code similarity.
      TEXT vector: granite-embedding-small (ibm-granite, 384d) — doc/comment/natural-language similarity.
    Both run via ort (ONNX Runtime) on GPU alongside main model's idle GPU.
    HNSW index (usearch or custom). Stored on disk per project.
    Vector cache: SQLite table (content_blake2s BLOB PK, code_vec BLOB, text_vec BLOB, cached_at INTEGER).
    Incremental update skips re-embedding for unchanged chunks (cache hit by content hash).

    Immediate cache invalidation on file_write:
      On SSB event action_type='file_write', immediately DELETE vector cache entries
      for all chunks belonging to that file (1 SQLite DELETE per file_write event).
      Prevents serving stale embeddings for files just edited by the executor
      in the current phase. Next query re-embeds the changed file on demand.
      Without this: executor edits file A, then agent queries for file A's semantics,
      gets pre-edit embedding from cache, reasons about stale code. Critical for
      EXECUTING -> AUDITING transitions where auditor must see current state.

  Layer 3.25 — SPLADE keyword expansion:
    Model: prithvida/Splade_PP_en_v1 (ONNX, ~500MB).
    Produces sparse vector per chunk (vocabulary-expanded term weights).
    Catches semantic synonyms BM25 misses ("error handling" matches try/catch code).
    Fused with BM25 + dense vectors via weighted RRF before PageRank.
    EVALUATE: measure retrieval improvement vs ONNX dep cost. Drop if <5% gain over BM25 alone.

  Layer 3.5 — PageRank Repo Map (design 31.7):
    Input: DKG graph (as in-memory DkgSnapshot) + task description + chat-relevant files.
    Source reference: derived from aider/repomap.py with deliberate divergences noted below.
    Process:
      0. SNAPSHOT: DkgSnapshot built from DkgEngine SQLite tables (dkg_nodes + dkg_edges).
         Self-edges (weight=0.1) added for nodes with zero incoming edges (orphan symbols).
         Source: aider adds self-edges for defined-but-unreferenced symbols to prevent zero rank.
      1. EDGE-WEIGHT BOOST: edges touching active files get weight *= 50.
         Applied to adjacency matrix BEFORE PageRank computation.
         Reference counts scaled by sqrt(ref_count) to prevent high-ref symbols (Result, Error)
         from dominating. Source: aider uses math.sqrt(num_refs).
      2. PERSONALIZATION VECTOR: nodes mentioned in task get 10x personalization.
         Biases random walk starting distribution. Normalized to sum=1.0.
      3. DANGLING NODE HANDLING: nodes with zero out-edges redistribute accumulated rank
         according to the personalization vector. Source: aider passes dangling=personalization
         to NetworkX. Without this, leaf nodes (constants, config structs) distort rankings.
      4. DENSITY GUARD: if graph density > 0.3, skip PageRank, return insertion order.
         Dense cyclic graphs produce near-uniform PageRank (no signal).
         NOTE: this is our addition. Aider has no density guard (uses try/except fallback).
         Justified by: test showing max_rank/min_rank < 1.1 on dense graphs.
      5. POWER ITERATION: damping=0.85, max_iter=100, tolerance=1e-6 (configurable).
         NaN/Inf guard: clamp to 0.0 and log warning.
      6. BINARY SEARCH TOKEN FITTING: ranked nodes fitted to max_map_tokens.
         Tolerance: +-15%. Uses sampling-based token estimation.
         Initial guess: min(max_map_tokens / 25, num_nodes). Source: aider optimization.
         Line truncation: signatures capped at 100 chars before token estimation.
         Source: aider truncates to prevent minified code from consuming budget.
    Special files (~100 items): Cargo.toml, Dockerfile, .gitignore, README, etc.
    Always included regardless of PageRank score (when token budget allows).

  Layer 4 — CatRAG:
    Query-aware graph traversal. Evidence chains from DKG.

  Layer 5 — A-RAG:
    Hierarchical retrieval: keyword -> semantic -> chunk.
    55-87% token savings on context retrieval.


3. QUERY PIPELINE

  query -> BM25 + SPLADE (RRF fused) -> dual-vector rerank -> PageRank importance filter
    -> CatRAG expand -> A-RAG filter -> cross-encoder rerank -> token-budget fit -> context

  Cross-encoder reranker (post A-RAG, pre token-fit):
    Model: cross-encoder/ms-marco-MiniLM-L-12-v2 (~120MB, ONNX fp32, CPU-only).
    Input: (query, candidate_chunk) pairs from A-RAG output.
    Output: joint relevance score. Re-sorts candidates before token budget fitting.
    Runs on CPU. Latency: <50ms for 50 candidates. No GPU contention.
    Applied only when candidate set > 10 (below that, ordering noise > signal).

    Reimplement algorithm in Rust natively. Phase 1C stores raw f32; quantization deferred.


5. GRACEFUL DEGRADATION

  Three search modes, cascading on failure:
    HYBRID:      dense + sparse + reranking (default, full pipeline)
    SPARSE_ONLY: BM25 + SPLADE (no dense vectors, no reranker)
    BM25_ONLY:   tantivy keyword search only (last resort)

  Cascade trigger: any layer failure (ONNX crash, OOM, timeout) drops to next mode.
  Mode restored automatically when failed component passes health check.
  Every mode change logged to SSB as action_type='knowledge_degradation'.

  Query input validation (before any embedding call):
    Max query length: 10,000 chars (prevents OOM in embedding model).
    Reject null bytes and control characters.
    Reject empty queries (zero tokens after whitespace split).
    Validation runs in <1ms, before any model invocation.


6. ONNX MODEL HEALTH AND CIRCUIT BREAKER

  Each ONNX model (GraphCodeBERT, Granite, cross-encoder, SPLADE) has independent circuit breaker.

  Circuit breaker states:
    CLOSED:    normal operation. Failures counted.
    OPEN:      failures >= threshold within window. All calls skip model, return fallback.
               Backoff timer starts.
    HALF_OPEN: after backoff timeout expires, limited probe calls allowed.
               2 consecutive successes -> CLOSED. Any failure -> OPEN (reset timer, increase backoff).

  Failure classification:
    TRANSIENT (timeout, temporary OOM): count toward threshold (default 3 within 60s).
    PERMANENT (segfault, model file missing, invalid ONNX): open immediately after 1 failure.
    Classification via error type enum, not string matching.
    Ref: Azure Architecture Center circuit breaker "Types of exceptions" guidance.

  Exponential backoff for successive OPEN periods:
    First OPEN timeout: 30s. Second consecutive: 60s. Third+: 120s (cap).
    Deterministic jitter per model: hash(model_id) mod window (not random).
    Prevents thundering herd when multiple breakers recover simultaneously.
    Ref: AWS Builders Library "Timeouts, retries and backoff with jitter."

  HALF_OPEN probes:
    Create fresh InferenceSession for probe (do not reuse potentially-corrupted session).
    Require 2 consecutive successes before CLOSED (success counter with threshold).
    Ref: Azure circuit breaker diagram (success count threshold); ONNX Runtime issues
    #20043/#20354 (sessions can crash or hang, entering unrecoverable states).

  Fallback per model:
    GraphCodeBERT failure -> TEXT-vector-only search (Granite).
    Granite failure -> CODE-vector-only search (GraphCodeBERT).
    Both fail -> SPARSE_ONLY mode (BM25 + SPLADE).
    SPLADE failure -> BM25_ONLY mode.
    Cross-encoder failure -> skip reranking, use vector similarity scores directly.

  Circuit breaker state NOT checkpointed. Resets to CLOSED on process restart.


7. STARTUP READINESS

  Before accepting queries, knowledge engine runs startup sequence:
    1. Load ONNX models (GraphCodeBERT, Granite, cross-encoder, optionally SPLADE).
    2. Open SQLite databases (DKG graph, vector cache, BM25 index).
    3. Run canary query: embed("fn main()") + BM25 search("main") + rerank.
       All layers must return non-error within 5s.
    4. Canary embedding drift check: cosine similarity of embed("fn main()") against
       reference vector stored in index_version.toml (canary_reference_vec field).
       If similarity < 0.85: model weights corrupted or wrong version loaded -> DEGRADED.
       First startup (no reference): skip drift check, persist reference after success.
       Ref: embedding audit best practices — silently-corrupt models have no error signal.
    5. Report ReadinessStatus to orchestrator.

  ReadinessStatus enum:
    READY:       all layers passed canary (including drift check).
    DEGRADED:    ONNX models failed but BM25 operational -> BM25_ONLY SearchMode.
                 Invariant: DEGRADED implies SearchMode == BM25_ONLY.
    UNAVAILABLE: BM25 also failed (SQLite corrupt, disk error) -> total outage.
                 Orchestrator blocks all FSM transitions.

  Orchestrator gates FSM: IDLE -> PLANNING blocked until READY or DEGRADED.
  If startup fails after 3 retries: enter DEGRADED (BM25_ONLY), log WARNING.
  If BM25 also fails: enter UNAVAILABLE, log ERROR.
  Estimated startup time: 5-15s (ONNX model loading dominates).


8. TREE-SITTER PARSE FAILURE FALLBACK

  If tree-sitter cannot parse a file (unsupported language, syntax errors, binary):
    1. File excluded from DKG graph (no AST nodes).
    2. File STILL indexed by BM25 (line-level keyword search).
    3. File STILL embedded by vector models (chunk-level, 50-line sliding window).
    4. PageRank treats file as leaf node (no edges, base rank only).
    5. Parse failure logged. Retried on next file change (syntax error may be fixed).

  Invariant: every file in project appears in at least BM25 index. Zero orphan files.


9. CONCEPT ANNOTATION BATCHING

  Problem: first indexing of large codebase may have hundreds of stale concepts.
  Regeneration via context-compiler (LLM call per node) is expensive.

  Batching strategy:
    Batch size: 20 nodes per LLM call (batch prompt with all 20 signatures).
    Priority: nodes touched by current task first, then by PageRank score descending.
    Budget: max 50 nodes per MEMORIZING phase. Remaining deferred to next session.
    Stale concepts served until refreshed (better than nothing).
    First full indexing: ~10 batches for 200-node project. ~2-5 min at local model speed.


10. INDEX VERSIONING AND MIGRATION

  Index version stored in .elai_cc/projects/{id}/index_version.toml:
    [index]
    version = 1
    dkg_schema_version = 1
    vector_dimensions = { code = 768, text = 384 }
    bm25_format = "tantivy_v21"
    onnx_model_path = ".elai_cc/models/onnx/"
    created_at = 1743811200

  On elai_cc upgrade, if index version < current:
    1. Read old index_version.toml.
    2. If schema change (DKG columns, vector dimensions): full rebuild from source.
    3. If format change only (tantivy version): rebuild BM25 only.
    4. If no change: reuse existing index.
    5. Old index archived to .elai_cc/projects/{id}/index_backup_{version}/ before rebuild.

  Full rebuild cost: proportional to project size. ~30s for 50K LOC (tree-sitter + embedding).
  User notified before rebuild starts. Not silent.


10A. INDEX STATISTICS EXPORT

  KnowledgeEngine::index_stats() -> IndexStats:
    IndexStats { total_files, total_chunks, avg_file_tokens, avg_test_tokens,
      total_dkg_nodes, total_dkg_edges, bm25_doc_count, vector_cache_size }

  avg_file_tokens: mean token count across all indexed files (sampling-based estimate).
  avg_test_tokens: mean token count across files matching test path patterns
    (*_test.rs, test_*.py, *.spec.ts, *_test.go).

  Fallback when index has < 10 files (bootstrap / new project):
    avg_file_tokens = elai_cc.toml [planning.sizing.default_avg_file_tokens] (default: 150)
    avg_test_tokens = elai_cc.toml [planning.sizing.default_avg_test_tokens] (default: 80)
  Used by orchestrator::SystemConstraints for L1 budget-aware decomposition
  and L2 Phase Sizing (pipeline-factory.txt).


11. CROSS-ENCODER CONCURRENCY

  Cross-encoder runs on CPU. Single ONNX session, not thread-safe for concurrent calls.

  Concurrency strategy:
    tokio::Semaphore(1) guards cross-encoder access. One reranking at a time.
    Queued requests wait. Max queue depth: 4. Overflow returns unranked results.
    Batching: if multiple requests queued, merge candidate sets and rerank once.
    Latency: <50ms per reranking. Queue wait acceptable for <4 concurrent agents.

  If contention measured >200ms p99 in production: evaluate ONNX session pool (2-3 instances).


12. KNOWLEDGE PIPELINE EXECUTION TRACING

  Every query through the 7-layer pipeline emits structured trace:
    QueryTrace {
      query_id: UUID,
      stages: Vec<StageTrace>,
      total_latency_ms: u64,
      mode: SearchMode (HYBRID | SPARSE_ONLY | BM25_ONLY),
      result_count: usize,
    }
    StageTrace {
      stage: String,  // "bm25", "splade", "code_vector", "text_vector", "pagerank", "catrag", "arag", "rerank", "token_fit"
      latency_ms: u64,
      input_count: usize,
      output_count: usize,
      error: Option<String>,
      circuit_breaker_state: Option<String>,
    }

  Traces logged via tracing crate at DEBUG level. Not stored in SSB (too verbose).
  Aggregated per-session statistics (p50/p99 latency per stage) stored in SSB at session end.
  Enables: identifying slow stages, validating degradation cascade, measuring reranker impact.


13. TESTABLE INVARIANTS

  - DKG covers 100% of parseable files in supported languages
  - Unparseable files still appear in BM25 index (zero orphan files)
  - BM25 query returns results in <10ms for indexes <100K documents
  - Dual-vector search returns results from both CODE and TEXT models
  - Vector cache hit rate >90% on incremental re-index (unchanged files skip embedding)
  - Cross-encoder reranker runs on CPU in <50ms for 50 candidates
  - SPLADE layer (if enabled) improves retrieval recall by measurable margin over BM25 alone
  - PageRank edge-weight boost applied before computation (not after)
  - Edge weights scaled by sqrt(ref_count), not linear ref_count
  - Personalization vector sums to 1.0 (valid probability distribution)
  - Dangling nodes redistribute rank via personalization vector (no rank sinks)
  - Orphan symbols (zero incoming refs) have self-edges and nonzero rank
  - Density guard activates at 0.3 threshold (falls back to insertion order)
  - Binary search converges within 10 iterations, initial guess = max_tokens/25
  - Signatures truncated to 100 chars before token estimation
  - Special files always present in repo map output (when token budget allows)
  - Incremental update after file change completes in <5s for single file
  - Circuit breaker opens after 3 transient failures within 60s window
  - Circuit breaker opens after 1 permanent failure (segfault, missing model)
  - HALF_OPEN requires 2 consecutive successes before CLOSED
  - HALF_OPEN probe uses fresh InferenceSession (not reused session)
  - Successive OPEN timeouts increase: 30s -> 60s -> 120s (cap)
  - Deterministic jitter: same model_id always produces same HALF_OPEN offset
  - Degradation cascade: HYBRID -> SPARSE_ONLY -> BM25_ONLY (never total failure)
  - DEGRADED ReadinessStatus implies SearchMode == BM25_ONLY
  - UNAVAILABLE ReadinessStatus blocks all FSM transitions
  - Query validation rejects empty, oversized, and control-char queries
  - Startup canary query completes within 5s or degraded mode entered
  - Canary embedding drift check: cosine_sim < 0.85 against reference -> DEGRADED
  - Cross-encoder semaphore prevents concurrent ONNX session access
  - Index version mismatch triggers rebuild with user notification
  - Concept annotation batching processes max 50 nodes per MEMORIZING phase
  - QueryTrace emitted for every query (DEBUG level)
  - Query without project_id is rejected (not silently defaulted to any project)
  - Search with project_id=A never returns results from project B's index
  - Ingest with project_id=A writes to A's index only, B's index unchanged
  - Physical file isolation: project A's knowledge.db is a different file from B's
  - Vector cache entries invalidated immediately on SSB file_write event for that file
  - No stale embedding served for a file edited in the current phase
  - index_stats() returns avg_file_tokens and avg_test_tokens
  - index_stats() with <10 files returns configured defaults from elai_cc.toml
  - ONNX model path in index_version.toml matches canonical .elai_cc/models/onnx/
  - Effect tagging: every function node with unsafe block tagged Effect::Unsafe
  - Effect tagging: configurable patterns in elai_cc.toml override defaults
  - DkgQuerier implemented by knowledge/ crate (Box<dyn DkgQuerier> for rules/)
