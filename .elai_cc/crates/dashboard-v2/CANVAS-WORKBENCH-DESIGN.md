# ELAI Canvas, Workbench Design (source of truth)

This file is the definitive spec for the canvas-workbench that replaces the orbit. It lives next to DESIGN.md and inherits every rule there: one accent (teal), hover-reveal chrome, the breath line as the only loader, deterministic seeded positioning, no spinners, no new heavy deps without a yes. DESIGN.md still governs *how things look*; this file governs *what the canvas is, what it shows, and how the model drives it*. Where the two ever disagree, DESIGN.md wins on pixels and this file wins on architecture.

When in doubt, follow the principle not the precedent. The orbit code that contradicts this file is migration debt, not a license to keep building 3D.

A note on honesty before anything else: this design leans on two unsound substrates, the DKG static call graph (which cannot see dynamic dispatch) and a live model drawing structured ops (which can be valid-but-wrong). Every place those substrates can lie to the user is called out inline, not buried. A spec that oversells its own ground truth is worse than no spec, so the caveats here are load-bearing, not hedging.

---

## 1. Vision

The canvas is a generative spatial work-surface the model drives and the user points at. One infinite 2D plane, dark and quiet, where every addressable thing in ELAI becomes a node and every real relationship becomes an edge. The model draws on it (model > canvas) to show what it sees and what it is doing, the user points at it (canvas > model) to give context without typing a paragraph. It is Figma-grade legibility wired to a live coding harness, not a 3D galaxy you watch from orbit.

The one-line thesis: **the canvas is a generative spatial work-surface the model drives and the user points at, replacing the orbit**.

This is the load-bearing reframe. The orbit answered "can a non-coder watch the engine work". The canvas answers a harder and more useful question: can a non-coder *steer* the engine, by seeing its intermediate state spatially and correcting it by pointing instead of prose. The research backs the upgrade directly: output-only human feedback on coding agents oscillates rather than converges (arXiv:2603.26942, the observability-gap paper), and convergence is restored only by exposing intermediate state to intervene on. The orbit shows the result. The canvas shows the work, and lets you touch it.

Everything ELAI already does becomes a *mode* of this one surface:

- the codebase graph from Project-Intelligence (ships first, the cheap thesis proof),
- the plan decomposition tree,
- the research tree,
- an architecture diagram the model draws to explain itself,
- a live app/website design surface where a page is a node you can click an element inside to edit **(web-first, React Native / Expo deferred to a separately-scoped later slice, see §8)**.

The canvas is not five tools, it is one primitive instanced five ways. The design-mode caveat is flagged here in the vision on purpose, because RN/Expo is ELAI's locked stack for the current gig and the deferral must not read as a shipped feature, the iframe path works for web and the native path is later and heavier (§8, §14).

## 2. Why the orbit goes

The orbit (ActivityWindow + OrbitCanvas + the three OrbitMode builders + the whole `scene/` three.js layer) was good at exactly one thing: it made a running engine feel alive to someone who couldnt read the code. The galaxy, the bloom, the breathing constellation, the tendrils reaching out in research mode, all of it sold the founding pitch that a non-coder can watch ELAI think. That emotional read is real and we keep it.

What it cost is everything else. It is watch-not-work: a beautiful 3D scene you observe and cannot meaningfully act on. Perspective and bloom trade legibility for theater, so a 2000-node codebase reads as a pretty cloud you cant navigate. The three.js stack (createThreeScene, UnrealBloomPass, troika-three-text billboarding, sky-dome shaders, star-points GPU buffers, the Fruchterman-Reingold galaxy layout) is heavy, hard to make deterministic, and impossible to turn into a Figma-style editing surface. Camera-distance interpolation is the wrong mental model for a flat work-surface. The user said it plainly: too much, watch-not-work, heavy 3D.

What we keep is the plumbing, all of which is zero-three.js and ports directly:

- The SSB event stream + Tauri/invoke layer (`api/stub.ts`, `api/types.ts`). DecompNode / VizData / ActivityEntry / FSM / GRC shapes are unchanged.
- The Svelte 5 runes state stores: `plan.svelte.ts`, `activity.svelte.ts`, `graph.svelte.ts`, `grc.svelte.ts`, `fsm.svelte.ts`, `motion.svelte.ts`, `workspace.svelte.ts`. None *should* depend on three.js, but this is asserted, not yet verified, and `graph.svelte.ts` is the one at risk because the orbit renders the graph. A pre-C1 verification step (§13, C1.B0) greps each store for any import from `scene/` or `orbit/three*` and is a hard gate: a store that imports a three.js type is not a drop-in and the reuse map in §11 is wrong until that import is severed. Uncertain until that grep runs, do not plan C1.B1 on the optimistic reading.
- Design tokens (`styles/tokens.css`) entirely, including the motion-scale media query and the reduced-motion override at `[data-motion]`.
- The window host + panel layout (AppShell / WindowHost / Panel / Sidebar / Rail / StatusBar), all DOM flexbox.
- The 200+ `lib/ui/` components and the 40+ drawers, all pure Svelte.
- The determinism doctrine: the LCG in `src/lib/orbit/lcg.ts` becomes the canvas seed source. Same task = same layout still holds, now over `(x,y)` instead of polar angle.

What dies with three.js: `scene/three-scene.ts`, `scene/three-orbit.ts`, `scene/three-orbit-modes.ts`, `StarCanvas.svelte` (the renderloop compositor), `sky-dome.ts`, `star-points.ts`, all mesh materials and geometries, troika billboarding. The starfield aesthetic survives as a cheap 2D layer (section 10), not as a GPU buffer.

What converts rather than dies: the ZoomState/ZoomTarget concept (camera distance becomes canvas pan-zoom transform), the OrbitCanvas zoom-frame ticker with easeOutCubic (target swaps from 3D camera to canvas viewport), the raycaster hit-test (becomes a 2D hitTest / cytoscape native picking), and the mandala projection in `node-mandala.ts` (variant-content derivation stays, output moves from troika to DOM/SVG positioning).

## 3. The core abstraction

One canvas. Typed nodes, typed edges, both drawn from real relationships, never decorative. A node is any addressable object in ELAI: a file, a symbol, an app screen, a plan node, a research node, a model-drawn shape. An edge is a real relationship: a call, an import, a navigation link, a plan dependency, a citation. The "dead code is visibly disconnected" property follows from this **for the edges the DKG can actually see**, with a critical caveat the whole §4 dead-code rule depends on: a node reachable only through dynamic dispatch (a Tauri `invoke()` string key, a `dyn Trait` call, an SSB event-bus hop) carries zero static edges and would float as a false orphan unless the entrypoints map (§4) re-attaches it. Disconnected-means-dead is true only after that supplement, never on the raw static graph.

The whole thing rests on a node/edge type registry. Every node carries a namespaced `type` (`code.file`, `code.symbol`, `plan.concept`, `plan.babystep`, `research.source`, `arch.service`, `design.page`, `design.element`) and every edge carries an `edge_type` (`call`, `import`, `def`, `alias`, `data_dep`, `type_ref` from the DKG, plus `nav`, `depends_on`, `cites`, `contains`). The registry is the single source for: what color/shape a node draws as, which mode owns it, what the inspector shows, and which model ops are allowed to touch it. New modes register new namespaces, they do not fork the renderer.

This is what makes the four ELAI surfaces *instances of one thing* rather than four separate screens:

- The codebase graph is `code.*` nodes + DKG edges, generated from the map (section 4).
- The plan is `plan.*` nodes (concept > phase > step > babystep) + `contains` and `depends_on` edges, read from `plan.svelte.ts`.
- Research is `research.*` nodes + `cites`/`contradicts` edges, read from the research tree.
- Architecture and design are model-authored `arch.*` / `design.*` nodes the model places via tools (sections 7-8).

The persisted state. The on-disk document is a custom `{ nodes[], edges[] }` schema **inspired by the JSON Canvas shape, not a JSON Canvas 1.0 superset**, and the earlier "superset" framing was wrong, so it is corrected here. JSON Canvas 1.0 (jsoncanvas.org/spec/1.0) defines node content as text/file/link/group only and defines edges with `id/fromNode/fromSide/toNode/toSide/color/label/fromEnd/toEnd`, there is no `type` namespace on nodes and no `edge_type` on edges. Our nodes carry `id/type/x/y/width/height` plus namespaced extras and our edges carry `id/fromNode/toNode/fromSide/toSide/edge_type/label`, which a real JSON Canvas reader (Obsidian and friends) would either ignore or choke on. So we claim shape-inspiration, not interoperability. If genuine JSON Canvas round-trip is ever wanted (export a plan to an Obsidian canvas), it goes through an explicit, documented, lossful translation layer that drops our `type`/`edge_type` and maps our nodes onto JSON Canvas `text`/`group` nodes, never an implicit "it just opens" promise. The portable, diffable, versionable on-disk format is still the win, we just own the schema honestly. The model never re-emits this whole document, it mutates it with ops (section 7). The store is what we save, render, and seed positions from.

## 4. Codebase graph from the map

This is the mode the user described first and most concretely: after Project-Intelligence indexing, a big graph where each node is a part of the codebase, every connection is the real plumbing, what calls what and what imports what, and dead code is literally visible as not-connected.

Data source, exact. The graph is built from two streams already flowing into the dashboard:

- `pagerank_nodes[]` (PageRankNodeStub: `id/name/score/file/effect_tags[]`) and `pagerank_edges[]` (DkgEdgeStub: `source/target/edge_type ∈ {call,def,import,alias,data_dep,type_ref}/weight`). This is the current Mode-2 feed and it ports unchanged.
- For symbol-level depth, the same Rust source behind `invoke('get_graph_view_data')` that GraphWindow already consumes via VizData. Mode-2 today only reads the PageRank stubs, so a fuller symbol-level call graph needs the symbol-graph stream exposed at canvas scope. That is the one new backend touch in this mode, and it is plumbing not a new subsystem, the DKG already has the edges.

B-29 / Project-Intelligence / DKG is the producer. The codebase map (dependency-cruiser `depGraph.json` + Mermaid + `forbidden.json` at `map/mapIndex.md`) is the secondary source for module/folder hierarchy and forbidden-edge violations, which we draw as a distinct red edge style.

Worst-case graph size is a hard pre-C1 measurement, not an open question. This is the change the perf critique forces: before C1.B1 ships, we measure the actual worst-case DKG of the real target ELAI project, both node count *and* edge count, because edge density is the frame killer not node count. The published cytoscape WebGL numbers (blog.js.cytoscape.org/2025/01/13/webgl-preview) are the budget reference: ~100+fps at 1,200 nodes / 16,000 edges, but only ~10fps at 3,200 nodes / 68,000 edges. 10fps is not headroom, it is the current ceiling, so the escape-hatch language in the earlier draft undersold the risk. The decision rule is concrete:

- If the measured worst-case stays under ~2,500 nodes at its real edge density, ship cytoscape WebGL with the semantic-zoom + LOD thresholds below, which keep the *drawn* element count inside the 16.6ms (60fps) budget regardless of total graph size.
- If the measured worst-case exceeds ~2,500 nodes at real density (a mid-size TS monorepo combining call + import graphs realistically hits 5k-15k nodes / 50k-200k edges), we commit to sigma.js from C1, accepting that sigma has no native hierarchical layout so we feed it dagre/elk coords ourselves. That is a from-C1 architecture choice, not a flag-flip rescue mid-project. The renderer choice is gated on the measurement, the measurement is C1.B0, and C1.B1 does not start until the number is known.

This kills the scope-death-by-optimism failure mode where C1 renders "the real graph" without knowing what the real graph is.

Semantic zoom + LOD, with concrete entry thresholds (the 60fps lever). We never just scale, we change *what* is drawn per zoom tier, grounded in the semantic-zoom literature (GraphMaps, arXiv:1906.05996; arXiv:2510.00003 software-city). The thresholds are pixel-size gates on the rendered element, not zoom-percentage guesses, so the count of drawn-with-chrome elements stays bounded no matter the graph size:

- Far tier (a node's on-screen footprint < ~8px): one super-node per folder/package, edges aggregated into bundled super-edges with counts. Flat colored quads, zero text, zero chrome. This is the tier that holds the 10k-node frame budget, because at far zoom the *drawn* element count collapses to folder count.
- Mid tier (~8px to ~40px): per-file nodes, labels paint only above the ~24px footprint threshold.
- Near tier (> ~40px): per-symbol nodes with full card chrome (name, effect tags, status). Card chrome (the n8n look) paints only when a node exceeds ~40 on-screen pixels, because text is the single most expensive per-element draw.

Cluster aggregation follows the module hierarchy folder > file > symbol, so a dead island stays its own cluster at every tier. The hard rule: labels and node chrome are hidden below their pixel threshold, always, with no exception, because LOD on text is the biggest 60fps lever there is. Viewport culling keyed off `cy.extent()` skips every off-screen element each frame on top of the LOD tiers.

Dead code, the exact visual rule, with its false-positive boundary stated up front. Two signals:

1. Topological: a node with zero inbound and zero outbound *static* edges after layout is an orphan candidate. We run fcose with component packing so each connected component lays out separately and packs, so any true orphan forms its own tiny island floating visibly apart from the connected core.
2. Runtime: a new `is_dead_code` + `coverage_count` field on PageRankNodeStub, fed from the entrypoint-coverage leg of the wiring gate (Layer 3 in wiring-enforcement.md). A node with `coverage_count == 0` and only test-file callers is wire-dark even if it has edges.

The honest boundary, mandatory before this visual is surfaced as authoritative. The DKG static call graph cannot see dynamic dispatch, and the wiring-enforcement doctrine in this very workflow says so explicitly: no sound static reachability for Rust with std + tokio + dyn Trait, static legs are approximations with false positives on trait-object / IPC-string / event-bus dispatch (SCIP has no call-graph edges for those). ELAI itself routes through exactly these patterns: Tauri `invoke()` string keys, the `generate_handler!` macro, `dyn` dispatch (the `CanvasDispatcher` trait this very doc introduces in §11), and the SSB event bus. A node reachable only through one of those shows zero static edges and would render as a dead island while being fully live. So the topological signal is necessary-but-not-sufficient (R5 in wiring-enforcement: a name in text is not a call, an absent edge is not absent reachability), and we treat it as such:

- An explicit entrypoints map (the same mitigant wiring-enforcement.md prescribes for trait-dispatch false positives) enumerates the dynamic-dispatch sites: Tauri command handlers, `dyn Trait` dispatch points, SSB action-type consumers. Edges from those entrypoints are injected into the graph before orphan detection runs, so a Tauri-invoked-only function is attached to its handler and does not float falsely.
- The runtime `coverage_count` signal is the authoritative backstop, because it is observed from the running binary not inferred from static text. A node that the entrypoints map cannot attach AND that has `coverage_count == 0` is dead with high confidence. A node with no static edges but `coverage_count > 0` is a known static false-positive and is drawn live, not dead.
- We surface a measured false-positive caveat in the mode itself: the dead-code overlay carries a small "static estimate, verified by coverage" affordance, and a node flagged dead purely topologically (no coverage data yet) renders in a distinct "unverified" treatment, not the full grave styling, so the user is never shown an unproven orphan as confirmed-dead. Confirmed-dead (coverage-backed) gets `--text-ghost`, desaturated, dashed `--border-subtle` outline, no pulse; topology-only-suspected-dead gets a lighter ghost with a dashed *amber-neutral* ring meaning "looks orphaned, not yet confirmed reachable-or-not". Live and reachable nodes get the teal treatment.

This is the canvas making the wiring doctrine visible, which is the whole point of that doctrine, but it refuses to launder a static guess as ground truth.

The perf stack recommendation (verified mid-2026, provisional-renderer caveat included). Keep ELAI's existing Cytoscape.js + dagre + fcose, and flip on the cytoscape WebGL renderer: `renderer: { name: 'canvas', webgl: true, showFps: true }`, requires cytoscape >= 3.31. The renderer is still officially marked **provisional** as of the 3.31 preview (the blog states the API and behaviour are subject to change until marked final), so the mitigation is concrete, not "re-test on upgrade":

- pin one exact cytoscape patch version in package.json (e.g. `3.31.x` locked, no caret),
- a frozen re-test protocol: an auditor-owned smoke test renders a fixture graph, asserts `showFps` reports >= the 60fps budget, and asserts the `webgl:true` + `showFps` options still exist on the renderer config object, run on every cytoscape bump as a gate before the bump merges,
- treat any WebGL API change (the flag, `showFps`, batching params) as a blocking upgrade, not a silent patch.

This reuses dagre, fcose, the style system, and the event model with near-zero migration and lifts the canvas-renderer ceiling from ~3-5k nodes to measured 100+fps at 1,200 nodes / 16,000 edges. dagre (or elkjs in a web worker if routing gets messy) lays out the connected import/call DAG top-down so call-direction reads as flow and back-edges stand out, fcose component-packing handles the orphan islands. Compute layout once, cache the coordinates, run it in a web worker, never re-layout on pan or zoom, only on graph mutation.

Component packing needs its plugin, stated as a real dependency. fcose component-packing is honored only when `cytoscape-layout-utilities` is registered, it is a separate npm package, not a native fcose flag, and if it is not registered the packing option is a silent no-op (orphans overlap the main component instead of islanding). So `cytoscape-layout-utilities` is an explicit entry in the §11 dependency list and is subject to the anti-slopsquatting check (verify name + version + last-published + license via `npm view cytoscape-layout-utilities version time` before it goes in package.json). The C1.B2 done-gate asserts the plugin is registered, not just that the flag is set.

Hard constraints the WebGL renderer imposes, design around them before flipping the flag: it supports straight / bezier / haystack edges only, center edge labels only, solid triangle arrows only. No dashed lines, no overlays/underlays, no hollow arrows, no taxi/segmented edges, no edge gradients, no source/target edge labels. Our dead-code dashed outline lives on the *node*, not the edge, so it survives, but any edge encoding that wanted dashes must move to color or weight.

Escape hatch hierarchy, with sigma promoted to a from-C1 option not a rescue. sigma.js v3/v4 (pure WebGL, ~100k-500k node ceiling) is the renderer we pick from C1 if the worst-case measurement above blows the cytoscape budget. sigma has no native hierarchical layout, so we feed it dagre/elk coords ourselves, which is exactly why "decide sigma at C1" beats "flag-swap to sigma later", the swap is a real migration either way, so the measurement decides it before code, not after a stall. cosmos.gl is for a whole-repo force-directed organism view only, force-only, hairball on a hierarchical DAG. React Flow is rejected for the graph canvas outright: it is DOM/SVG, the maintainer states it is not intended for 1000+ nodes, and community reports show browser failure near 200 nodes / 4k edges. We get the n8n card look by drawing it ourselves at the near-zoom tier, not from React Flow.

Verified against the code (2026-06-03, B-29 / B-33 / B-34 read end to end, all rated MOSTLY_DONE / HIGH in the B-plan verification reports). This pins what is real so the section above is not built on an optimistic reading.

## 5. The live layer

The canvas shows the live SSB and what ELAI is doing and where. This is how we recover what the orbit was genuinely good at, the calm sense of a living engine, minus the 3D theater.

The mechanism is an SSB overlay drawn on top of whatever mode is active. Today `activity.svelte.ts` is a linear log and the orbit modes get static fixture data at mount, so resolution-failure could never happen there because the fixtures were static. The live canvas is different and the failure path is specified, not assumed-away. We add a `CanvasActivityEvent` SSB variant that carries a spatial anchor plus enough fallback context to survive a miss: the target node id (file id, symbol id, plan node id), and *also* the raw `file_path` + `symbol_name` + `mode` so the overlay can act even when no matching node is on the canvas yet. The kind of touch (reading, editing, validating, researching) and a short label round it out.

Resolution-failure path, mandatory and explicit. The overlay store subscribes to SSB and resolves each event to a node already on the canvas. Three failure cases, each with a defined render so the user is never shown the agent doing apparently-nothing:

- Node exists in the active mode: glow it, this is the happy path.
- Node exists in the graph but in a non-active mode (e.g. the agent touches a plan node while CODE-GRAPH is showing): the follow-agent affordance surfaces a small off-frame indicator pointing toward the owning mode ("agent working in PLAN"), it does not silently drop, and clicking it switches mode and centers the node.
- Node not on the canvas at all (the agent touched a file Project-Intelligence hasnt indexed yet, or a symbol below the current LOD tier): we create a transient ghost node from the fallback `file_path` + `symbol_name` in the event payload, placed near the nearest resolvable ancestor (same folder super-node) and drawn in the unverified treatment from §4. The ghost is labeled, glows like any active node, and reconciles into a real node when indexing catches up (matching id replaces the ghost in place). A ghost that never reconciles within a timeout (default 30s) fades to a dropped-marker rather than vanishing, so a genuinely unresolvable event leaves a visible trace instead of a silent gap.

This means a live SSB stream that races ahead of indexing degrades to "agent is working over there on a file we havent fully mapped" instead of "agent appears frozen", which is the difference between a trustworthy live layer and a broken one.

What lights up, mapped onto existing signals:

- FSM state (`fsm.svelte.ts`: state, progress 0-1, history[]) drives an ambient focus ring on the active node. EXECUTING uses the same breath line as the status bar, the only loader. No spinner, ever.
- GRC (`grc.svelte.ts`: current_step, reasoning_confidence) draws a small confidence dot on the focused node, the same GRC token colors the orbit used, now positioned in 2D.
- Evidence gates (`evidence_gates[]` with verdict + confidence + issue_type WiringBlock/Contract/Build) flag the node they fired on: a verdict marker on the node, red `--fail` only on real failure, never as decoration.
- BubbleUp (`bubble_action`) draws a single colored ripple ring on the node it escalated from, ported from the orbit's `bubble-ring` motion, 2.6s, one ripple not a loop.

The calm ambient watch layout. The agent's current focus is the only thing that moves. The active node gets a slow halo (ported `halo-pulse` 4s + `halo-ambient` 7s) and the edge it is traversing gets the dash-flow the orbit used on the active baby-step path (1.6s). Everything else sits still at rest opacity. A "follow agent" toggle (default on) keeps the active node centered as ELAI walks the graph, so a non-coder literally watches the cursor of attention travel call by call, file by file. This is the orbit's emotional payload, the engine feels alive, delivered on a legible flat surface you can also act on. Turn follow off and you are free to pan anywhere while the overlay keeps glowing where the work is.

The deeper reason this matters: the live layer is the intervention surface. Because the agent's intermediate state is spatial and visible, the user can point at a node mid-run and correct it (section 9), which is the convergence fix the observability-gap research demands (arXiv:2603.26942, accurately cited here, the finding is that intermediate-state visibility restores convergence where output-only correction oscillates). The orbit showed you the work was happening. The live layer lets you reach into it.

## 6. File explorer + bidirectional sync

A VS Code-style file tree on the left, with the QoL the user asked for: open a project folder, select a node in the canvas and it highlights the file in the explorer, double-click to open, all the small comforts.

There is no file-tree state store today. GraphWindow opens files via cytoscape but nothing on the left mirrors selection. So we add:

- A `fileTree.svelte.ts` store: the directory tree for the open project, expand/collapse state, the currently selected path, the currently open path, and a list of *additional* mounted roots (see multi-root below). Svelte 5 runes, same shape as the other stores.
- A `FileExplorer.svelte` component that lives in the left `Sidebar` of the existing AppShell. It is a standard collapsible tree built from the `Tree` primitive already in `lib/ui/`, so this is composition not new chrome.

Bidirectional sync, the wiring:

- Canvas > explorer: selecting any `code.file` or `code.symbol` node publishes its `file` field to `fileTree.svelte.ts`, which expands the ancestor folders and scrolls the path into view, highlighted in teal. The PageRank/DKG nodes already carry `file`, so the join key exists.
- Explorer > canvas: clicking a file in the tree focuses and centers the matching canvas node (and selects it as model context, section 9). Double-click opens the file.

Multi-root / out-of-root paths, specified because the DKG spans more than the scoped folder. The DKG already indexes multi-project workspaces, so a `code.file` node's `file` field can point outside the single folder the user opened: a sibling package in a monorepo, a `node_modules` transitive dep, a Rust crate in another workspace member. Canvas-to-explorer sync against a single scoped root would silently highlight nothing for those, which is a hole. The rule:

- The explorer supports multiple mounted roots, not one. `open_project_folder()` sets the primary root, but the DKG's known root set is read at index time and every distinct root prefix among `code.*` node `file` fields is offered as a mountable root.
- When a selected canvas node's path is inside a mounted root: highlight as normal.
- When it is inside a *known-but-unmounted* root (a monorepo sibling): the explorer shows an inline "mount <root> to reveal" affordance at the top instead of silently failing, one click mounts that root (subject to the same scoped fs capability) and reveals the path.
- When it is outside every known root (a `node_modules` dep with no source root): the node is marked `external` in the registry, the explorer shows "external dependency, not in workspace" rather than a dead highlight, and the canvas node itself carries an `external` badge so the user knows up front it wont reveal in the tree.

The C2.B3 done-gate tests the cross-root case explicitly, not just a within-root file: select a node whose path is in a monorepo sibling and assert the mount affordance appears and resolves, plus select an `external` node and assert it shows the external state, not a silent no-op.

The Tauri filesystem capability needed. A real "open a project folder + walk its tree + open a file" needs the Tauri 2.x filesystem capability granted in the capabilities manifest: `fs:read-dir`, `fs:read-file`, scoped to the opened project root(s), plus `dialog:open` for the folder picker. Each additionally-mounted root is granted its own scoped capability at mount time, never a blanket disk grant. Double-click-to-open routes through a new `open_in_editor(path)` Tauri command (section 11) rather than the webview, so it respects the user's actual editor. This is a capability grant + a few commands, not a new subsystem, and it stays scoped per root so we never hand the webview the whole disk.

How it wires into AppShell/Panel: FileExplorer is a persistent left rail beside the canvas Panel, its width persisted in `workspace.svelte.ts` next to the existing panel split percentages. It follows the hover-reveal rule for its toolbar (new-file, refresh, collapse-all, mount-root at low opacity until the rail is hovered), the tree itself is always full opacity because it is primary.

## 7. How the model drives the canvas

The canvas is a tool the model calls. This is the part that makes it generative rather than a passive viewer, and it is grounded in the tldraw agent SDK pattern plus the constrained-decoding research.

The op representation, recommended. The model emits an incremental action-op stream, not a whole-document blob. Each op is one entry in a discriminated union keyed on a `_type` literal:

- `createNode { type, label, x?, y?, props? }`
- `updateNode { id, label?, props? }`
- `deleteNode { id }`
- `connect { from, to, edge_type, label? }`
- `disconnect { id }`
- `annotate { target_id, text }`
- `group { ids[], label }` / `createFrame { mode, label }`
- `move { id, x, y }`
- `fork { node_id, label }`, clones a node (and in design/plan modes its subtree) into a sibling frame for the branch-and-compare loop in §9, with a `forked_from` back-edge so version history is derivable from the op stream and not just visual arrangement. This op exists because §9 promises branch-and-compare and the schema must actually support it, an interaction the store cannot otherwise express.
- plus the narration ops `think`, `message`, `todo` so the model can talk on the canvas while it works.

Whole-document re-emit is rejected on purpose: it is token-expensive and it churns ids, destabilizing shapes the user is looking at. The op stream mutates the custom store from section 3. This is exactly the split tldraw's agent-template uses (ops author, document persists) and what the field converged on, the critic did not challenge it and it holds.

The exact tools the model calls. New ToolDefinition entries in `ProductionAgentRpcServer::build_tool_catalog` (production_agent_rpc.rs L266+, which today exposes 14 tools), following the same JSON `input_schema` + `convert_json_input_to_postcard` arm + `translate_tool_request` dispatcher arm pattern as the existing tools:

- `canvas_place_node(mode, type, label, near?, props?)`
- `canvas_connect_edge(from, to, edge_type, label?)`
- `canvas_update_node(id, label?, props?)`
- `canvas_delete_node(id)` / `canvas_delete_edge(id)`
- `canvas_annotate(target_id, text)` / `canvas_group(ids[], label)`
- `canvas_fork_node(id, label)`
- `canvas_render_diagram(mode, spec)` for bulk authoring of an architecture or plan view in one call
- `canvas_screenshot(region?)` so the model can read its own canvas back through the media validator (see the capture-path caveat in §11, the validator pipeline is reused but the capture mechanism is Tauri-native, not external Playwright navigation).

How ops flow model > SSB > dashboard. Every op also lands as an SSB row, because the SSB action-type model is the right transport and it is already what the dashboard subscribes to. Each canvas op maps to a new SsbActionType variant via the existing 9-tuple atomic-lockstep pattern (enum + SQL CHECK + as_sql_str + from_str + SsbPayload variant + action_type() + test_payload + all_test_payloads + action_type_lock.rs). New variants: `CanvasNodeCreated`, `CanvasEdgeConnected`, `CanvasNodeDeleted`, `CanvasEdgeDeleted`, `CanvasAnnotationAdded`, `CanvasLabelEdited`, `CanvasScreenshotCaptured`, `CanvasLayoutChanged`, `CanvasGroupCreated`, `CanvasNodeForked`. A new `CanvasPanel.svelte` (or the canvas root itself) filters on `action_type='canvas_*'` rows and applies them to the store, so the model's drawing streams onto the surface live, the user watching it happen exactly like tldraw streams agent actions.

How the model knows when and how to use it. Three levers, all existing ELAI machinery, with the FSM lever corrected (see below):

- Mode + design-active flag, NOT a new orthogonal FSM substate. The earlier draft introduced `CanvasDesigning` as an orthogonal FSM substate, which was wrong: an orthogonal dimension makes the FSM a product of two axes and silently creates compound states (what happens when design is active and BubbleUp fires, or the FSM is AUDITING) whose transitions are specified nowhere, and fsm.rs would have to enumerate every compound state. So we demote it. "Design ops available" is a plain mode flag on `canvas.svelte.ts` (`mode ∈ {code, plan, research, arch, design}`), it does not touch fsm.rs and creates no compound states. The existing FSM is untouched. What the flag gates is purely which op-namespace is admissible, and that gating is enforced in the `CanvasDispatcher` (a model op targeting `design.*` while `mode != design` is rejected by the dispatcher with a structured error, same as any invalid op), not by an FSM transition. The FSM still governs the *agent's* lifecycle (IDLE/EXECUTING/AUDITING/...) exactly as today; canvas ops are admissible whenever the agent is in a state where it can call tools at all, and the mode flag plus the dispatcher decide which ops are legal. This removes a whole class of unspecified-compound-state bugs and keeps the canvas a view-and-tool layer over the FSM, not a second FSM.
- Role/prompt. The tool descriptions (auto-injected from the ToolDefinition meta) tell the model what each op is for. The system prompt gains a short "you have a canvas, here is when to draw on it" stanza: draw an architecture diagram to explain a design before coding it, draw the plan to show decomposition, place nodes to externalize what you found in research.
- Tiered read-back. The model reads the canvas the way tldraw and the Figma MCP both do: three simplified tiers, Blurry (viewport: id/type/bounds/label only), Focused (full props on the selection), Peripheral (out-of-view clusters as bounds+count). This bounds token cost on a big canvas and is the same tiering we justified for semantic zoom.

Reliability via schema and constrained decoding, with the complex-schema cliff handled concretely. The op schema is a per-mode discriminated union, enforced with constrained/grammar-guided decoding (XGrammar, a default structured-output backend in vLLM/SGLang as of 2026). The win is real for *small* grammars: JSONSchemaBench (arXiv:2501.10868) shows constrained decoding can improve downstream quality and speed generation. But XGrammar has a published compilation-timeout cliff on complex grammars (the JSONSchemaBench work itself documents this), so the earlier "keep each grammar small" hand-wave is replaced with concrete budgets and a fallback:

- Per-mode grammar token budget. Each mode compiles its *own* grammar and only its own, never a combined all-modes grammar. The hard budget per mode is roughly the op union for that mode only: code/plan/research modes are tiny (node + edge ops over one namespace). The DESIGN mode is the fat one (`design.page`, `design.element`, nav edges, `data-oid` refs, two-tier writeback ops, mermaid-import outputs, screenshot region specs), so DESIGN is decomposed into *sub-grammars* selected by the current design sub-operation (placing vs editing-element vs importing), never one monolithic design grammar. The rule is a measured ceiling: any single compiled grammar that approaches the XGrammar compile-timeout in a benchmark fails the build and must be split further. We measure compile time per grammar in CI, not assume it.
- Mode-context scoping prevents cross-mode bleed. The model is never handed a grammar that spans modes. When the model is in `design` mode the active grammar admits only `design.*` ops; to touch another frame it must first switch mode (an explicit, cheap mode op), at which point the grammar swaps. A `connect` whose endpoints straddle two modes is rejected by the dispatcher (cross-mode edges are not a thing, edges live inside a frame), so the model cannot place a node in one frame and wire it into another outside a valid context. This is what stops the "mid-task frame switch needs the giant grammar" failure the critique flagged.
- Defined timeout fallback, never silent. If grammar compilation times out (a grammar slipped past the CI ceiling on some input), the tool call does NOT fail silently and does NOT fall back to free-form generation. It returns a structured `grammar_unavailable` error to the agent, the agent retries the op in a constrained sub-grammar (the smaller sub-operation grammar), and if that also fails the op is surfaced as a blocked tool call in the SSB stream with the reason, visible to the user. Unconstrained fallback is banned because an un-grammared op is exactly the malformed-op risk the grammar existed to prevent.

Constrained decoding guarantees structure not meaning, so a mandatory `sanitizeAction()` repair pass runs before any op is applied: it fixes hallucinated node ids, dedups new ids, normalizes coords, and rejects (does not silently fix) an op that references a node that doesnt exist, surfacing it as a blocked op. The grammar cannot catch a valid-but-dangling reference, the sanitize pass is where that dies.

## 8. The modes

One surface, many modes, keyed to what ELAI actually does. Modes are not separate screens, they are namespaced node/edge types living in their own clipping frame on the same plane, with shared chrome around them. The active mode (the plain flag on `canvas.svelte.ts`, §7) gates the model's writable type-namespace and the admissible op grammar, so modes never collide on ids or layout.

The catalog:

- CODE-GRAPH (`code.*`). The codebase graph of section 4. DKG nodes + edges, semantic zoom, the dead-code island read with its coverage-backed verification caveat, the live overlay. The default mode when a project is open and the agent FSM is IDLE.
- PLAN (`plan.*`). The decomposition tree from `plan.svelte.ts`: concept > phase > step > babystep as `contains`-nested nodes, `depends_on` edges between siblings, FSM position (active_concept_id / active_phase_id / active_step_id / active_baby_step_id) lighting the current node. This replaces OrbitMode1Plan, the same data, flat.
- RESEARCH (`research.*`). The research tree (ResearchTreeNode + children) with TendrilEvent sources as leaf nodes, `cites` edges, and `contradicts` edges drawn red between sources that disagree (the contradiction_with field). Replaces OrbitMode3Research, the tendrils-reaching-out feeling becomes edges fanning to source nodes at the periphery.
- ARCHITECTURE-DIAGRAM (`arch.*`). Model-authored. The model uses `canvas_render_diagram` / `canvas_place_node` to draw services, boundaries, and data flows to explain a design before or while building it. Text DSLs (mermaid, plantuml) are import-only through a blueprint parser > native-shape bridge (the tldraw @tldraw/mermaid pattern: the DSL engine supplies layout coords via offscreen SVG getBBox, our shape model supplies the editable output). The model never emits raw mermaid as its authoring channel, that path is unreliable (MermaidSeqBench) and we avoid the repair loop entirely by emitting validated ops instead.
- APP/WEBSITE-DESIGN (`design.*`). The richest mode and the user's original arc, **web-first, with React Native / Expo explicitly deferred to a later separately-scoped slice (C5 is web-only)**. A `design.page` node renders a live preview of an actual app screen or website page, `nav` edges connect pages into the real navigation graph, and you click an element *inside* a page node to edit it.

  The iframe embedding strategy, specified because it is the first wall you hit. A `design.page` preview shows a real running dev server (Next.js on localhost, etc), and you cannot just point a Tauri `<iframe>` at `localhost:3000` and expect it to render. Tauri's webview is not a browser, the embedded app ships its own `Content-Security-Policy` and `X-Frame-Options`, and `X-Frame-Options: DENY` / `frame-ancestors` will block embedding outright, and a Service Worker the embedded app registers can intercept requests and break the preview. Onlook (the cited web prior art) sidesteps this by running the app inside its own renderer, not inside a foreign app's iframe. So our strategy is concrete and it is a prerequisite for C5.B1, not an afterthought:
  - ELAI serves the design-target through its own dev-preview proxy on a dedicated port that ELAI controls. The proxy strips/relaxes `X-Frame-Options` and rewrites `frame-ancestors` so the Tauri webview is an allowed embedder, and it scopes Service Worker registration so the embedded app's SW cannot hijack the preview frame.
  - The `design.page` iframe loads that ELAI-controlled proxied origin, never the raw user dev server, so embedding is permitted by construction. The user's real dev server stays untouched, ELAI mediates.
  - C5.B1's done-gate is therefore gated on the proxy: "a real app's pages render as preview nodes" is verifiable only once the proxy serves a frameable origin, and the gate asserts the proxy is live and the frame actually paints the page (an off-agent screenshot of the rendered preview, not a 200 on the fetch).
  - Honest limit: this proxy works for web dev servers we can front. It does not magically embed an arbitrary deployed third-party site that sets a hard CSP we cannot rewrite (we only control origins we proxy), and that limit is stated rather than pretended away.

  Click-to-edit is the prior-researched mechanism, stated here as the spec:
  - Build-time stable-ID tagging: a `data-oid` attribute keyed to an AST range, not line numbers, injected at build time. React 19 removed Fiber `_debugSource`, so build-time tagging is mandatory, runtime DOM inspection is not enough.
  - AST format-preserving patch (recast) for writeback, two-tier: deterministic patches for style/text edits, the LLM only for structural changes. A style nudge never round-trips through the model.
  - Clicking an element resolves its `data-oid` back to the AST range and selects that source node as model context.
  - The honest RN caveat, repeated from the vision so it cannot be missed: React Native / Expo has no DOM, so the same click-to-edit there needs Fiber + `getInspectorDataForViewAtPoint`, a different and heavier path, and the live preview is a native render not an iframe. Web design-mode ships first, RN design-mode is a later, separately-scoped slice, and nothing in C5 promises it. Current canvas-to-code tools also cant do multi-page or diff-against-existing-codebase, they regenerate whole artifacts, so the scoped-diff writeback (below) is itself unproven prior-art territory and is prototyped before C5.B3 commits.
  - Design-mode primitives use token references not raw hex/px (fill/stroke/typography as tokens), adopting Figma's read=filtered-tiered-JSON / write=imperative-op split so the surface stays machine-maintainable and on-brand.

How one surface hosts them without becoming a mess. Frames as mode partitions: each mode-region is its own clipping frame, so code, plan, research, arch, and design subtrees are spatially and structurally isolated even when several are open. Shared chrome wraps all of them: one zoom control, one search (Cmd+F), one inspector panel, one breadcrumb, one follow-agent toggle. Mode switching is a segmented control in the shared top chrome (hover-reveal per DESIGN.md §7, the way the orbit's mode-toggle pill already hides until hover), and the model switches modes by setting the mode flag and entering the matching frame, not by navigating away. Bindings/edges are generic across modes, one edge primitive serves call edges, nav edges, and plan dependencies, only the `edge_type` and color differ, and edges never cross a frame boundary.

## 9. How this changes LLM interaction

This is the real-thought section. The canvas adds a spatial second channel to a relationship that today is a single one-dimensional pipe of text. Show-and-point instead of type-and-describe.

The core shift is deixis. Right now, to give the model context about "this function that the auth flow calls", a non-coder has to find it, name it, and describe it in prose, and the model has to guess which thing they meant. On the canvas they click the node. Pointing-as-input is a well-established HCI finding going back to Bolt's "Put-That-There" (1980) and the broad multimodal deictic-reference literature: pointing bypasses verbally describing spatial location, which is lower friction and far less ambiguous for "this thing here". (The earlier draft cited Ferret, arXiv:2310.07704, for this, that was a category error, Ferret is an MLLM architecture for accepting region inputs into a *model*, not a UX finding about *user* behavior, so the human-pointing claim is regrounded in the HCI deixis literature where it actually belongs. Ferret remains relevant only as evidence that a model *can* consume point/box/region inputs, which is the receiving end of this channel, not the justification for the human end.) Select a node, select an edge, lasso a cluster, and that selection *is* the context handed to the model. The Focused tier of the read-back (section 7) is literally what the model receives when you select.

Concrete interaction loops the canvas unlocks:

- Point-to-context: user clicks three nodes, types "these three are slow, why", and the model already has the exact symbols, their files, and their edges. No paragraph, no guessing.
- Watch-and-interrupt: the agent walks the call graph live (section 5), the user sees it heading down a wrong branch, clicks the node it is about to enter and says "not there, the bug is upstream". This is the process-level steering the observability-gap paper (arXiv:2603.26942) shows is the only thing that converges on hard coding tasks, output-only correction oscillates. The canvas makes early intervention possible because the intermediate state is visible and pointable.
- Show-not-tell design: in design-mode the user clicks a button on a page node, the model gets the exact element via its `data-oid`, and "make this bigger and teal" is a deterministic patch, not a prose round-trip that drifts.
- Branch-and-compare: fork a plan node or a design page (the `fork` op + `canvas_fork_node` tool from §7, with the `forked_from` back-edge so the lineage is in the op stream not just the pixels), run two approaches side by side, keep the winner. The 2D plane gives version history as spatial arrangement (source-left, results-right) backed by the fork edges, which a linear chat transcript destroys. This loop is only claimed because the schema actually carries the op to express it.

What gets faster and clearer. Specifying by pointing is faster than specifying by description and removes a whole class of "the model misunderstood which thing I meant". Seeing the work stream onto the canvas means the user catches a wrong turn at step 3 instead of judging a wrong result at step 30. The model showing its reasoning as a drawn architecture diagram is clearer than the same reasoning as a wall of text, and it persists so it can be revisited (the CHI-2026 finding that outputs on a shared spatial surface become attentional anchors that get revisited and reinterpreted).

Who it helps. The non-coder steering the harness, directly. The founding pitch was "a non-coder can watch the engine work". This mode upgrades it to "a non-coder can *steer* the engine by pointing", which is the unoccupied white space the survey identified: authoring canvases (OpenAI Agent Builder, Langflow) sit before a run, observability canvases (Honeycomb, AgentLens) sit around a run, but graphical mid-execution intervention for non-coders is open territory. ELAI is the right home because the live SSB stream, the DKG graph, cytoscape, and the B-29 impact API are already the substrate, the canvas is the integration that turns them into a steering surface.

The honest caveat: pointing must augment intent, never replace it. tldraw's make-real produces output that looks right but does nothing when given a drawing with no behavioral spec. So every point-selection is paired with an explicit intent channel, the user still says what they want done with the thing they pointed at, the canvas just removes the burden of describing *which* thing.

## 10. Aesthetic

Minimal modern 2D galaxy. We keep the soul of the orbit's look and drop its weight. Teal stays the one accent, stars stay as ambient depth, dark stays, determinism stays, breath stays, hover-reveal stays. Three.js, bloom, perspective, and GPU star buffers go.

The starfield becomes a cheap 2D layer behind the canvas, rendered into a single `<canvas>` 2D context (not hundreds of SVG `<circle>` elements, which carry per-element DOM paint cost that bites at 500+ stars and on 120Hz targets). The existing Starfield aesthetic (cool-white / pale-steel / pale-teal pinpoints, ~10% bright with halo, ~2% twinkle) draws as 2D-canvas points, not WebGL buffers. Same vignette feel via one smooth quadratic-stop gradient (never two stacked radial layers, they band, per DESIGN.md §12). Stars are ambient and unfocused, they say "deep space, quiet engine", they never compete with nodes. Idle shooting stars can still fire every ~14s when there is no active task, deterministically seeded per fire-counter via the LCG, the same calm idle heartbeat.

A calm node card. At near zoom a node is a small card, not a glowing sphere:

- Padding and radius from the tokens (`var(--r-md)`, the same card grid DESIGN.md §5 defines). Background transparent at rest, on hover a faint lift and a 1px low-opacity outline, no top-edge gradient line, no left color stripe.
- Mono name (JetBrains Mono), sans description, one effect-tag row if present. Status is carried by a single small marker, not by color-flooding the card.
- Teal is reserved for the active/selected/focused node and its traversed edge. Coverage-confirmed dead-code nodes are `--text-ghost`, desaturated, dashed outline, never pulsing; topology-only-suspected (not yet coverage-verified) nodes get the lighter unverified treatment from §4, distinct from confirmed-dead so the user never reads a guess as a fact. State, gate, GRC, tier, bubble tokens keep their dedicated meanings, never repurposed as decoration.
- At far zoom the card collapses to a flat colored quad with no text, the LOD rule from section 4. Chrome only paints above the ~40px threshold.

Layout and motion. Deterministic seeded positioning is the law: same task = same canvas, positions seeded from stable ids via the LCG, never Math.random. Motion is the orbit's motion language ported to 2D: constellation-breathe on a mode group, ambient dash-flow on inactive edges, dash-flow on the active edge, halo-pulse + halo-ambient on the focused node, one bubble-ring ripple on escalation, breath line during EXECUTING. All decorate, none load. Every animation keeps its `prefers-reduced-motion` escape. The result reads as a galaxy you can actually navigate and edit, calm by default, alive only where the work is.

## 11. Architecture + data flow

Component diagram in words. Rust orchestrator owns the SSB (append-only SQLite WAL) and the tool catalog. The model calls a `canvas_*` tool > `handle_tool_request` stashes the JSON args > `convert_json_input_to_postcard` deserializes to a struct > `translate_tool_request` dispatches to a new CanvasDispatcher > the dispatcher validates the op against the active mode + sanitize pass, mutates the canvas store and appends a `Canvas*` SSB row. The dashboard subscribes to SSB via the existing Tauri/invoke layer, the canvas store applies `canvas_*` rows, and Svelte 5 renders. The user's pointing on the canvas flows the other way: selection > model context on the next turn. The file explorer reads the disk through scoped, per-root Tauri fs commands. The design-mode preview loads through ELAI's dev-preview proxy (§8). The media validator renders design/arch frames to PNG and runs Tier2 VLM eval, emitting a feedback SSB row.

New SSB action_types (9-tuple lockstep each): `CanvasNodeCreated`, `CanvasEdgeConnected`, `CanvasNodeDeleted`, `CanvasEdgeDeleted`, `CanvasAnnotationAdded`, `CanvasLabelEdited`, `CanvasGroupCreated`, `CanvasNodeForked`, `CanvasScreenshotCaptured`, `CanvasLayoutChanged`, plus a `CanvasActivityEvent` for the live spatial overlay (section 5, carrying the `file_path` + `symbol_name` + `mode` fallback fields for ghost-node creation). Each gets a payload struct inline in ssb.rs.

The FSM is NOT touched. There is no `CanvasDesigning` FSM substate, the earlier draft's orthogonal substate is removed (§7). Design-availability is a mode flag on `canvas.svelte.ts`, op-namespace gating lives in the CanvasDispatcher, and fsm.rs is unchanged. This is a deliberate de-scope: the canvas is a view-and-tool layer over the existing FSM, not a second state machine, so there is no compound-state explosion to enumerate.

New Tauri commands: `open_project_folder()` (dialog + scoped fs root), `mount_root(path)` (scoped fs grant for an additional monorepo/workspace root, §6), `read_dir(path)`, `read_file(path)`, `open_in_editor(path)`, `get_symbol_graph_view(root_id, depth, filters)` (the fuller call graph beyond PageRank stubs), `start_design_preview(target)` (spins the dev-preview proxy with relaxed framing headers, §8), `capture_canvas_region(region)` (the Tauri-native screenshot for the validator, see capture caveat below). The fs commands require the Tauri fs + dialog capabilities in the capabilities manifest, scoped per opened/mounted root.

Screenshot capture is Tauri-native, NOT external Playwright navigation. The media_validator Tier1/Tier2 *evaluation* pipeline (PNG > VLM) is reused verbatim, but the *capture* path is corrected: the canvas is the interior of a Tauri window, not an external web page Playwright can navigate to by URL, and Playwright-against-a-Tauri-webview needs the CDP bridge that exists only in debug builds. So `capture_canvas_region` uses Tauri's own webview screenshot capability to produce the PNG, then hands that PNG to the existing media_validator for Tier2 VLM scoring. The validator is reused, the grab is native. This is resolved before C4.B3.

New Rust types: `CanvasDispatcher` trait, `CanvasNode`, `CanvasEdge`, `CanvasGraph`, the `Canvas*Payload` structs, and the new `ToolDefinition` entries. (Note for §4: the `CanvasDispatcher` trait is itself a `dyn` dispatch point and so is exactly the kind of edge the static DKG cannot see, which is why it goes in the entrypoints map.)

New Svelte components: `Canvas.svelte` (the cytoscape-WebGL host + pan/zoom + culling + LOD), `CanvasNodeCard.svelte`, `CanvasInspector.svelte`, `CanvasModeBar.svelte`, `FileExplorer.svelte`, `DesignPageNode.svelte` (the proxied-iframe live-preview + click-to-edit), `Starfield2D.svelte` (the single-canvas 2D star layer). New npm deps, each anti-slopsquatting-verified before it enters package.json (`npm view <pkg> version time license`): `cytoscape-layout-utilities` (required for fcose component packing, §4), and `sigma` v3/v4 *only if* the §4 worst-case measurement selects it. recast is already implied by design-mode writeback and is verified at C5 plan time. No dep is added from training memory.

Reuse map (what we do NOT rebuild): `api/stub.ts` + `api/types.ts`, the existing state stores (subject to the C1.B0 three.js-import verification, §2), `tokens.css`, AppShell / WindowHost / Panel / Sidebar / Rail / StatusBar, all of `lib/ui/`, all 40+ drawers, `workspace.svelte.ts` persistence (extended with canvas viewport + selection + mode + explorer width + mounted roots), the LCG seed, the zoom-frame ticker + easeOutCubic (target swapped to viewport transform), the mandala variant-content derivation, the media_validator Tier1/Tier2 *eval* pipeline (capture path native, §11), the existing cytoscape + dagre + fcose install, and the SSB 9-tuple lockstep pattern + tool-catalog dispatch pattern. The build is mostly wiring proven parts together, which is the whole reason ELAI is the right home.

## 12. Migration from the orbit

Incremental, no big bang, the orbit keeps running until the canvas earns its place.

The path:

1. Stand up `Canvas.svelte` as a new window type in WindowHost, alongside the orbit, not replacing it. It reads the same stores, so it is a parallel view of the same data. The orbit and the canvas coexist in tabs.
2. Ship CODE-GRAPH mode first against the existing `pagerank_nodes`/`pagerank_edges` feed (no new backend needed for v1), with cytoscape WebGL (or sigma if the §4 measurement demanded it) + fcose component-packing + the dead-code island read. This is the cheapest slice that proves the thesis (section 13).
3. Port PLAN mode and RESEARCH mode off `plan.svelte.ts` and the research tree, reaching feature parity with OrbitMode1 and OrbitMode3 as flat views.
4. Once the three read-only modes match the orbit, flip the default window from ActivityWindow to Canvas behind a workspace setting, orbit still available in a tab.

   Single-consumer SSB rule at the switch, specified because two live consumers double-apply. OrbitCanvas currently owns the live SSB subscription, and the canvas live-layer (§5) is a second consumer of the same stream. Running both at once double-applies events into any shared store. So the subscription is exclusive and tied to the active window: the active window owns the live SSB subscription, the inactive one is paused (its subscription suspended, not just hidden). Canvas active = orbit paused, orbit active = canvas live-layer paused. The switch in step 4 hands the subscription over atomically, it never leaves both live. This is part of the step-4 done-gate, not an afterthought.
5. Add the model-driven ops (ARCHITECTURE then DESIGN), the live spatial overlay, and the file explorer. These have no orbit equivalent, so they are pure addition.
6. Retire OrbitMode1/2/3 and the `scene/` three.js layer only after the canvas has been the default for a full release with no regressions, deleting `three-scene.ts`, `three-orbit*.ts`, `StarCanvas.svelte`, `sky-dome.ts`, `star-points.ts`, and dropping the three.js + troika + bloom deps. The starfield is already 2D by then so nothing visual is lost.

Each step ships independently and the orbit is the fallback at every step until the last, so there is never a moment where the dashboard is broken or feature-poorer than it was.

## 13. Phased build plan

Ordered sessions in the B/C-plan style. Each is a vertical slice (producer + its in-plan consumer + its smoke trigger in the same unit, per the walking-skeleton PRE_GATE), each has an observable_effect done-gate that drives a real entrypoint and measures an off-agent artifact the executing agent did not author, per the wiring-enforcement doctrine. Every model-driving and SSB done-gate below is auditor-driven against a pre-authored task and the gate fileset is frozen before the slice executes (wiring-enforcement R4/R8), so an agent cannot satisfy its own gate from inside the boundary.

C1, Canvas shell + CODE-GRAPH read-only (the thesis slice).
- B0 (pre-gate measurement + reuse verification, blocking, no code ships after a fail): (a) measure the real target ELAI project's worst-case DKG node *and* edge count and pick cytoscape-WebGL-vs-sigma by the §4 rule; (b) grep every reused store for any `scene/`/`orbit/three*` import and prove the §2 drop-in claim or sever the import. Done-gate: the measured worst-case numbers and the renderer decision are recorded, and the store-import grep is clean. This is the slice that kills scope-death-by-optimism, nothing renders until it passes.
- B1: `Canvas.svelte` mounts the chosen renderer as a new WindowHost window type, reads existing `pagerank_nodes`/`pagerank_edges`. Done-gate: open a project, the codebase renders on canvas at measured >=60fps for the real worst-case graph from B0 (`showFps` HUD is the off-agent artifact), the window is reachable from the real WindowHost tab bar; auditor-driven, gate frozen.
- B2: fcose component-packing (with `cytoscape-layout-utilities` registered and verified) + the dead-code island rule (topological orphans float apart) + the entrypoints-map supplement so dynamic-dispatch-only nodes are not false orphans + the confirmed-vs-suspected dead treatment. Done-gate: a known true orphan renders as a separate island verified against the map's `forbidden.json`/orphan list, AND a known Tauri-invoked-only function (zero static edges, live at runtime) does NOT render as dead because the entrypoints map attached it, AND the plugin-registered assertion passes (packing is not a silent no-op).
- B3: semantic zoom (folder > file > symbol tiers) + LOD labels at the pixel thresholds + viewport culling. Done-gate: pan/zoom stays >=60fps at the B0 worst-case node count, tiers swap at the pixel thresholds, `showFps` proves it.
This C is the cheap proof: it reuses the existing data feed and the existing cytoscape install (or commits to sigma up front from the B0 measurement), and it delivers "a big Figma-style graph where dead code is visibly disconnected" honestly, with the static-vs-verified distinction the user can trust.

C2, Live layer + file explorer.
- B1: `CanvasActivityEvent` SSB variant (with fallback `file_path`/`symbol_name`/`mode`) + `canvasActivity.svelte.ts` overlay, active node halo + traversed-edge dash-flow + follow-agent toggle + the ghost-node resolution-failure path (§5). Done-gate (auditor-driven, pre-authored task, frozen gate): run a real task, the focus marker travels the graph node-by-node from live SSB rows not fixture data, AND an event for an un-indexed file renders a ghost node that reconciles or fades to a dropped-marker, never a silent gap.
- B2: `FileExplorer.svelte` + `fileTree.svelte.ts` + scoped Tauri fs/dialog capability + `open_project_folder`/`mount_root`/`read_dir`/`read_file`. Done-gate: open a folder, the tree renders from disk, real fs commands fire.
- B3: bidirectional sync + multi-root handling + `open_in_editor`. Done-gate: select a within-root canvas node and the file highlights; select a *cross-root monorepo-sibling* node and the mount affordance appears and resolves; select an *external* (`node_modules`) node and it shows the external state not a silent no-op; double-click opens in the real editor.

C3, PLAN + RESEARCH modes + mode chrome.
- B1: PLAN mode off `plan.svelte.ts`, frames-as-partitions, mode bar (the mode flag on `canvas.svelte.ts`, no fsm.rs change). Done-gate: the live decomposition tree renders flat with the FSM-active node lit.
- B2: RESEARCH mode off the research tree with contradiction edges. Done-gate: a real research run renders sources + contradiction edges.
- B3: shared chrome (search, inspector, breadcrumb) + make Canvas the default window behind a workspace flag + the single-consumer SSB handover (§12 step 4). Done-gate: Canvas is the default, orbit still in a tab, AND only one window holds the live SSB subscription at a time (verified by asserting no double-application into a shared store when switching).

C4, Model drives the canvas.
- B1: canvas op schema (per-mode discriminated unions, no all-modes grammar) + `CanvasDispatcher` (mode-namespace gating + `sanitizeAction` repair) + the `Canvas*` SSB action_types (9-tuple lockstep) + `canvas_place_node`/`canvas_connect_edge`/`canvas_update_node`/`canvas_delete_node`/`canvas_fork_node` ToolDefinitions. Done-gate, auditor-driven and frozen-before-C4 (R4/R8): an AUDITOR (different agent) drives a real ELAI task authored *before* C4 began, and verifies the `Canvas*` SSB rows land AND the nodes render. The off-agent artifact is the SSB row + rendered node observed by the auditor, not the implementing agent's stdout and not the implementing agent's own test run. The gate fails if the dispatcher is wired to nothing in production even when a unit path runs.
- B2: ARCHITECTURE-DIAGRAM mode + `canvas_render_diagram` + mermaid import bridge + per-mode constrained-decoding grammars with the CI compile-time ceiling + mode-context scoping + the `grammar_unavailable` timeout fallback (§7) + tiered read-back. Done-gate (auditor-driven): the model draws an architecture diagram via ops to explain a design, the model reads it back via the Focused tier, AND a forced grammar-timeout surfaces a blocked op with a reason, never a silent free-form fallback.
- B3: `canvas_screenshot` > Tauri-native capture > Tier2 VLM eval reusing the media_validator eval pipeline (§11 capture caveat). Done-gate: a model-drawn frame is captured via the native path and VLM-scored, a feedback SSB row lands.

C5, APP/WEBSITE DESIGN mode (web-only, RN deferred).
- B0 (prerequisite): the dev-preview proxy that serves a frameable origin with relaxed `X-Frame-Options`/`frame-ancestors` and scoped Service Worker (§8). Done-gate: the proxy serves a real dev server's page and a Tauri webview can embed it (an off-agent screenshot of the embedded page paints, not just a 200).
- B1: `design.page` live-preview node (proxied web iframe) + nav edges. Done-gate: a real app's pages render as preview nodes wired by their real navigation graph, verified by a screenshot of an actually-painted preview.
- B2: build-time `data-oid` AST tagging + click-an-element selection. Done-gate: clicking an element in a page node resolves to its AST range and selects it as model context.
- B3: two-tier writeback (deterministic for style/text via recast, LLM only for structural). Prereq spike before commit: prove recast can produce an applyable scoped diff against a real large React codebase (the prior art cannot do multi-page diff-against-existing, §14). Done-gate: a style edit round-trips as a deterministic patch with no model call, a structural edit round-trips through the model and recast preserves formatting, both applied to a real codebase not a toy.

C6, Retire the orbit. Delete the three.js `scene/` layer and OrbitMode1/2/3 after a full release of Canvas-as-default with no regressions. Done-gate: build is green with three.js / troika / bloom deps removed and no orbit imports remain. This is the cleanest gate in the plan, purely mechanical, off-agent, and ungameable.

The first slice (C1.B0 then C1.B1) is the cheap thesis proof done honestly: measure the real graph, pick the renderer that survives it, one new window, the existing data, and you already have a clean modern 2D codebase graph that the orbit could never be. Everything after that is additive.

## 14. Open questions + risks

Scope death. This document describes six C-plans and a genuinely new product surface. The single biggest risk is that "one canvas for everything" becomes everything-at-once and ships nothing. Mitigation is the strict ordering: C1 alone is a complete, shippable win (the codebase graph the user asked for first), and every C after it is optional and additive. If the project stalls after C1, the user still got the thing they most wanted. Do not start C4/C5 before C1-C3 are the default.

Perf at scale, now gated not deferred. The cytoscape WebGL budget is real: ~10fps at 3,200 nodes / 68,000 edges, and edge density not node count is the killer, so a monorepo with high fan-in can blow the budget. This is no longer an open question deferred past the thesis, it is the C1.B0 blocking measurement: we measure the worst-case DKG before C1.B1 and pick cytoscape-WebGL-vs-sigma by the §4 rule, with concrete pixel-threshold LOD entry points that bound the *drawn* element count regardless of total graph size. Residual open question: ELAI's worst-case is project-dependent, so B0 must be re-run when ELAI is pointed at a materially larger codebase than the one measured, the renderer decision is data-bound not permanent.

Dead-code visual honesty. The orphan-island read is only as sound as the DKG, and the DKG cannot see dynamic dispatch (Tauri `invoke()` strings, `dyn Trait`, the SSB bus), which ELAI uses heavily including this design's own `CanvasDispatcher`. So topological orphan-ness is necessary-but-not-sufficient (R5), the entrypoints map re-attaches dynamic-dispatch-only nodes before orphan detection, and the runtime `coverage_count` is the authoritative backstop. The user is shown confirmed-dead (coverage-backed) and suspected-dead (topology-only, unverified) as visually distinct states, never a static guess laundered as ground truth. Open question: the false-positive rate for ELAI's specific dispatch patterns is a number we should measure on the real codebase and surface, not assume small.

Model-drawn-canvas reliability. Constrained decoding guarantees structure not meaning, and the grammar has a complex-schema compile cliff, so §7 splits grammars per-mode (DESIGN further into sub-operation grammars), measures compile time in CI against a ceiling, scopes mode context to prevent cross-mode bleed, and defines a `grammar_unavailable` fallback that surfaces a blocked op rather than silently going free-form. The sanitize pass catches dangling ids. The model can still draw an architecture diagram that is wrong-but-valid, and the media_validator VLM eval (C4.B3) is the backstop that judges *content* not just syntax. Open question, unchanged and honest: how good is Tier2 VLM at "is this architecture diagram correct" is unproven and needs its own eval before we trust model-authored diagrams in a real plan.

In-boundary gate risk on the model-driving slices. The danger in C4 is that the same agent writes the tool, the dispatcher, the SSB schema, and then the SSB row "proves" its own code ran (R4 in-boundary artifact). Mitigation is structural: every C4 done-gate is auditor-driven against a task authored before C4 started, with the gate fileset frozen before execution (R8), so the proof comes from a different agent driving a pre-existing path, not from the implementer's own run. C4.B1's gate explicitly fails if the dispatcher is wired to nothing in production even when a unit path passes.

Orbit-removal cost. The orbit is the current centerpiece and the founding emotional pitch. Deleting it is a real loss if the canvas hasnt fully recovered the alive feeling. Mitigation: the live layer (C2.B1) is specifically designed to recover it, and C6 only deletes after a full release of Canvas-as-default with no regressions, with the orbit available in a tab until then, the SSB subscription handed over single-consumer (§12). Open question: do we ever keep a "galaxy view" toggle as a permanent calm-mode, or is that just refusing to let go.

The work-surface-vs-pipeline-editor fork. There is a real design fork buried here: is the canvas a *work-surface* (you watch and point at a live run) or a *pipeline editor* (you author flows the way n8n / OpenAI Agent Builder do). The survey is clear that the unoccupied white space is the work-surface/steering layer, and this document commits to that, the model authors *within* the surface (arch/design frames), we do not build a node-and-wire flow authoring tool. Open question: if the user later wants to author agent flows visually, that is a different product and its own decision, not a quiet scope-creep into this surface.

Design-mode is the least-proven mode, web-first by necessity. The click-to-edit live-render path is the riskiest piece and it ships web-only (RN/Expo deferred, §1/§8). Three concrete unknowns are surfaced not hidden: (1) the iframe embedding needs ELAI's own dev-preview proxy to defeat `X-Frame-Options`/CSP/Service-Worker interception, which is a C5.B0 prerequisite with its own done-gate, not an assumption; (2) the closest web prior art (Onlook) runs the app in its own renderer not a foreign iframe, so our proxied approach is novel and gated on the B0 paint-test; (3) recast producing an applyable scoped diff against a real large React codebase is unsolved in the prior art (current tools regenerate whole artifacts, cant diff-against-existing or do multi-page), so C5.B3 is preceded by a prove-it spike and the two-tier writeback keeps the common case (style edits) off the model entirely so the unreliable structural path is rare. RN design-mode (Fiber + `getInspectorDataForViewAtPoint`, native render not iframe) is a later, separately-scoped slice and nothing in C5 promises it. Open question: can recast reliably produce the scoped diff at scale, prototype before committing C5.B3.

## 15. The reframe — the canvas as the model's general-purpose visual reply channel

This addendum (grounded 2026-06-03, run wf_42c9b2f3, 11-area prior-art sweep + adversarial verification, all 11 load-bearing claims CONFIRMED at high confidence; source ledger in §22) extends sections 1-14 with one idea that sits a level above the current design: the canvas is not only five fixed views of what ELAI does, it is **the model's general-purpose visual reply channel**. When prose or an ASCII diagram is the wrong medium, the model spawns an interactive view *as its answer*, and the user points back into it (click an element, drill into detail, ask a scoped follow-up) instead of re-reading text.

This is not a speculative leap, it is a field-converged and largely-shipped direction, and the strongest evidence is that **Anthropic already shipped exactly this**. "Custom visuals in chat and Cowork" (support.claude.com/en/articles/13979539, T1, beta to all web+desktop users; announced 2026-03-12 at claude.com/blog/claude-builds-visuals) routes at inference time: *"Claude decides when a visual would help based on what you're asking"*, with a user override (*"draw this as a diagram", "chart this data"*), rendered as interactive HTML+SVG, click-and-hover live. The hard part of this section's idea, the model itself deciding *text-vs-visual at reply time*, is a shipped, at-scale feature, not a research bet. The honest consequence for ELAI: a canvas is now table stakes (Anthropic, OpenAI, Vercel, tldraw, MCP all ship one), so the canvas alone is not the moat. The moat is the journaled, reproducible, provenance-tagged op-stream *underneath* it (§19), which is the same trust spine the F/G plans already bet the product on.

The reframe collapses the five modes (CODE-GRAPH, PLAN, RESEARCH, ARCHITECTURE, DESIGN, §8) into **instances of one primitive**: *the model emits an interactive view, chosen at reply time, as a first-class alternative to a text turn*. The five modes stop being a closed enum the dashboard hard-codes and become the seed entries of an open renderer registry. The one genuinely new abstraction this requires is a tool-catalog verb, call it **`spawn_view { view_type, seed_ops[] }`**, whose `view_type` is a discriminator selecting a registered renderer, the direct analog of Anthropic's content-type routing, MCP Apps' `_meta.ui.resourceUri`, and tldraw's `_type`. Everything else already exists in this design: the op stream (§7), the per-op SSB action-type transport (§11), the modes registry (§3), the tiered read-back (§7). `spawn_view` is the seam that turns "five hardwired panels" into "model picks/composes a view per reply".

## 16. Grounded prior art (verified 2026-06-03)

The field has independently converged on the architecture this design already uses, which de-risks it. Each item below was web-verified this pass; tier marks: T1 official docs/spec/vendor, T2 primary repo/eng-blog, T3 secondary.

- **Model decides to answer visually (the routing decision).** Anthropic custom visuals (support.claude.com/en/articles/13979539, T1; claude.com/blog/claude-builds-visuals, T1, 2026-03-12). The reverse-engineered routing rubric is *"should I respond with text, call a tool, or generate a visual component, and if a visual, which kind?"* mapping content-type to renderer (SVG / Chart.js trends / Mermaid schemas / D3 networks / Three.js 3D), rendered in a sandboxed iframe with a ResizeObserver reporting height (medium.com/@milesk_33, T3 for the internal mechanism only). ELAI can lift the rubric literally into the `spawn_view` system-prompt stanza.
- **Tool-call -> rendered component (the dominant safe pattern).** Vercel AI SDK Generative UI (ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces, T1): verbatim *"Generative UI is the process of connecting the results of a tool call to a React component"*; tools carry description + Zod `inputSchema` + `execute`; the client renders by switching on `message.parts` of type `tool-${toolName}` with states input-available / output-available / output-error and spreads `part.output` as props. Critically, the model emits a *tool call against a fixed catalog*, never raw JSX. The RSC/`streamUI` path is now officially experimental and "not recommended for production" (ai-sdk.dev/docs/ai-sdk-rsc, T1), so do not copy RSC specifically; the durable pattern is tool-call -> rendered component, which ELAI already has as its op catalog.
- **Constrained component spec against a catalog (the portable variant).** Vercel json-render (Apache-2.0, launched Jan 2026, ~13k stars by Mar 2026; infoq.com/news/2026/03/vercel-json-render, T3), Google A2UI v0.9 (framework-agnostic JSON UI declarations validated against a bring-your-own `CatalogConfig`, shipped 2026-04-17 alongside A2A 1.0; developers.googleblog.com/a2ui-v0-9-generative-ui, T1), Thesys C1 (OpenAI-compatible drop-in replacing the markdown renderer with a `<C1Component>`; docs.thesys.dev, T1). The model emits a JSON UI tree referencing only catalog entries; nodes not in the catalog do not render. This is the posture ELAI's op-catalog already occupies.
- **Incremental op-stream against a live document + tiered read-back.** tldraw agent starter kit (tldraw.dev/starter-kits/agent, T1; github.com/tldraw/agent-template, T2): verbatim *"Shapes get created, updated, and deleted incrementally as each action finishes streaming, so the canvas stays responsive"*; typed actions with an `applyAction` gated by `if (!action.complete) return` (per-action live mutation, not whole-doc re-emit); tiered read-back `BlurryShape` (viewport overview: id/type/bounds/text), `FocusedShape` (full props on the selection, also the write-out format), `PeripheralShapeCluster` (out-of-view, bounds+count). This is the closest 1:1 to ELAI's op stream + tiered selection context, and confirms the §7 citation is real. Excalidraw/tldraw-over-MCP servers do the same for coding agents (incremental `add_rectangle`/`update_element`/`add_arrow` against a live canvas the user edits and the agent re-edits in-session; nimbalyst.com/blog/best-ai-diagram-tools-2026, T3) — structurally identical to ELAI's model->canvas tool catalog.
- **Standardized model->UI->model loop (protocols).** MCP Apps, the first official MCP extension (SEP-1865, 2026-01-26; blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps, T1; modelcontextprotocol.io/extensions/apps/overview, T1): a tool declares `_meta.ui.resourceUri` -> a `ui://` resource bundling HTML/JS/CSS -> rendered in a host-controlled sandboxed iframe -> bidirectional JSON-RPC over `postMessage`, with **user-consent gating on UI-initiated tool calls** and the verbatim trust framing *"hosts can render apps without trusting the server author completely"*. CSP is an app-declared / host-enforced allowlist (`connectDomains`/`resourceDomains`/`frameDomains`; apps.extensions.modelcontextprotocol.io/.../csp-and-cors.html, T1). OpenAI Apps SDK corroborates the same `ui/* JSON-RPC over postMessage` bridge (developers.openai.com/apps-sdk/mcp-apps-in-chatgpt, T1). AG-UI (Agent-User Interaction Protocol; docs.ag-ui.com/concepts/events, T1; github.com/ag-ui-protocol/ag-ui, T2) defines the event union ELAI's SSB stream mirrors: RUN_*, TEXT_MESSAGE_CONTENT(`delta`), TOOL_CALL_START/ARGS/END/RESULT, **STATE_SNAPSHOT + STATE_DELTA (JSON Patch RFC-6902)**, MESSAGES_SNAPSHOT, RAW, CUSTOM, transport-agnostic JSON over SSE/WebSocket/HTTP.
- **The closest consumer analogs.** Claude Artifacts (artifacts can call the host model via `window.claude.complete(prompt)` returning a string, billed against the *viewer's* subscription, sandboxed under a separate origin with CSP blocking external fetch; simonwillison.net/2025/Jun/25/ai-powered-apps-with-claude, T2; claude.com/resources/tutorials/prototype-ai-powered-apps-with-claude-artifacts, T1; persistent storage + MCP added 2025-10-21). ChatGPT Canvas (model auto-opens or user forces with "use canvas"; highlight a region to scope a targeted edit; shortcut menus; version history with diff/restore; openai.com/index/introducing-canvas, T1). These are render-and-forget surfaces; the difference ELAI carries is the journal (§19).
- **HCI substrate (why point-and-drill beats prose).** Shneiderman's Visual Information-Seeking Mantra *"overview first, zoom and filter, then details-on-demand"* + the seven tasks (verified against the primary 1996 PDF, "The Eyes Have It", IEEE Symp. Visual Languages pp.336-343, DOI 10.1109/VL.1996.545307). Nielsen progressive disclosure (nngroup.com/articles/progressive-disclosure, T1, "improves learnability, efficiency, error rate"). Bolt 1980 "Put-That-There" deixis (verified verbatim: *"gesture aided by voice gains precision in its power to reference"*; ACM SIGGRAPH CG 14(3) pp.262-270, DOI 10.1145/965105.807503) + Oviatt CACM 1999 (95-100% of users prefer multimodal point+speak for spatial commands; dl.acm.org/doi/pdf/10.1145/319382.319398). Ink & Switch "malleable software" (inkandswitch.com/essay/malleable-software, T1) grounds the durable thesis that spatial, end-user-shapeable surfaces are a real medium beyond chat.

Reading: the canvas direction is grounded, the op-against-a-catalog architecture is the field's safe convergence point and ELAI already sits on it, and the model->canvas->model loop is proven, not speculative.

## 17. Reply-view taxonomy (beyond the five modes)

Each is a `view_type` the model emits via `spawn_view`, composed from the existing op vocabulary (`createNode`/`connect`/`updateNode`/`annotate`/`group`, §7). The point of each row is: what the model emits, what the user clicks, and why it beats ASCII/prose. Per §16 the model is constrained to the registered op catalog, never raw HTML, for every one of these.

- **explain-this-diagram.** Model emits an annotated subgraph (a DKG slice or an `arch.*` fragment) with callout labels. Click any node -> details-on-demand (provenance, taint, source span) handed back as deictic context. Beats ASCII because a labeled graph is the overview-first/details-on-demand pipeline (Shneiderman); ASCII cannot carry the relate/drill edges.
- **comparison / branch board.** N columns (approach A vs B, two git branches, or two run-artifacts) on a shared row axis, backed by the `fork` op + `forked_from` edges (§7). Click a cell -> "expand this tradeoff" or "pick this branch". Beats prose because the project's two-approaches-minimum rule becomes *pointable* instead of a bullet wall. This is the cheapest high-value first slice (§21).
- **data / metric view.** A chart from journaled measurements (SSB rows, bench results, the SAFEDELTA number from G-6). Click a datapoint -> the underlying run/row. Beats a number table because the shape is the point; this is exactly Anthropic's shipped trend->Chart.js routing.
- **decision board.** The model's options + grounding + recommendation as cards; the user's pick is a bound deictic choice. Click "choose / ground this further / reject". Beats prose because it converts an ambiguous "do you want X or Y" into a Put-That-There selection.
- **walkthrough / timeline.** The plan tree or execution timeline mid-run (the AuditTimeline / live FSM state). Click a step -> its SSB events, its diff, "intervene here". This is the intermediate-state-steering intuition (arXiv:2603.26942) — but that justification is motivating, not proven (§20, correction 2).
- **form / HITL request.** A typed form for an approve/reject/parameter decision the model needs cleared. Fields + submit -> captured input becomes the next tool result. Beats free-text parsing; this is literally AG-UI's human-in-the-loop shared-state mutation and MCP Apps' consent-gated UI action.

Design constraint carried from §16/§20: make "the right view + drill-down + shared referent" the value, not "interactive" per se. For some replies a clean static diagram, or even text, is better; restrict the canvas reply to structured/relational content and keep a "just tell me" suppress-canvas escape hatch.

## 18. Wiring the reply channel into the existing substrate

This rides three things this design already specifies, with one genuinely-new primitive.

1. **Op stream + tool catalog (§7).** `spawn_view { view_type, seed_ops[] }` is one new catalog verb plus the per-view-type op subsets already emitted. Constrained decoding (§7) enforces the op union *at decode time*, which is strictly stronger than tldraw/json-render's post-hoc Zod validate-and-retry; the field's named pain point (malformed canvas ops) is exactly what typed-tool + constrained decoding fixes here for free.
2. **SSB action_type union, 9-tuple lockstep (§11).** Add one Pattern-2 variant `CanvasViewEvent` with a `CanvasViewKind` arm set (`ViewSpawned` / `OpApplied` / `UiAction`), bumping SCHEMA_VERSION/TOTAL_VARIANTS under the golden-lock discipline already enforced. Each op is one append-only row, which *is* AG-UI's typed event union merged into the existing single-writer WAL. This is additive to the `Canvas*` action_types already enumerated in §11, or can subsume them; an H-plan should pick one and not maintain two.
3. **Modes registry -> renderer registry (§3).** Generalize the five-mode picker into a registry keyed by `view_type`; the `CanvasDispatcher` (§11) routes a spawned view to its Svelte5 renderer. The five existing modes register first, so this is a generalization not a rewrite.

**The one genuinely-new primitive: snapshot+delta reconciliation per tab.** AG-UI proves you need STATE_SNAPSHOT + STATE_DELTA (JSON Patch RFC-6902) with drift detection (re-request a fresh snapshot on divergence). ELAI must add per-tab sequence numbers + periodic SSB checkpoints so a late-joining/reconnecting dashboard rebuilds a tab from the journal *tail* rather than replaying every op, and so the user and the model provably see the *same* tab state. This last property is load-bearing for deixis: Monk 2003 (www-users.york.ac.uk/~am1/Monk2003CommonGrnd.pdf) shows pointing breaks down the moment the two parties look at a different version of the display. The SSB single-writer journal must be the synchronized source of truth and selection must hand the *exact current* node state to the model.

**Inbound leg (canvas -> model).** Mirror the MCP-UI / AG-UI action taxonomy as a typed event row, `CanvasUiAction { Select | Intent | Prompt | ToolCall | Link }`, so a click is *journaled*, not an ephemeral postMessage. Selection serializes via the §7 tiered read-back (selected = FocusedShape-equivalent full detail, viewport = Blurry, off-screen = clustered), copying tldraw's token-saving pattern verbatim for handing a clicked DKG/plan node to the model as a bound pronoun rather than re-described prose. This is the literal Put-That-There descendant the §9 deixis argument relies on.

## 19. The trust-spine differentiator (why ELAI's generative UI beats Artifacts/Canvas/MCP-Apps)

None of Artifacts, ChatGPT Canvas, MCP Apps, or tldraw carry provenance on the emitted UI; they render-and-forget. Every model-emitted view in ELAI is, by construction of riding the op-stream:

- **Journaled (SSB):** every op is an append-only action_type row, giving replay + audit. MCP Apps *prescribes* "every UI-initiated action goes through the same audit and consent path"; ELAI gets it *durably from the WAL* instead of an ephemeral postMessage log.
- **Reproducible (G-2 RRA):** a view is "produced by run X and reproduces from the journal", the believe-the-number control the consumer products structurally lack.
- **Provenance/taint-tagged (G-1):** each node carries a taint tag; a node rendered from web/untrusted content is marked.

That is the same auditable-reproducible wedge the whole G-plan and the GTM thesis bet on, applied to a new surface. Now the security risks, each mapped to the gate that catches it, with the honest "does not catch" cases stated:

- **Prompt-injection via rendered content (highest severity, CONFIRMED real).** The Claude Artifacts "Claudy Day" chain (oasis.security/blog/claude-ai-prompt-injection-data-exfiltration-vulnerability, T2; disclosed Oct 2025) exfiltrated conversation data through an *allowlisted* egress (api.anthropic.com) despite a strict separate-origin CSP, i.e. the CSP egress allowlist was itself the channel. The ELAI analog is the canvas->model handoff: when the user "points at" a node, untrusted rendered text becomes a re-injection vector. **Caught by the G-1 taint tag gating `CanvasUiAction::Select`** — a tainted node's content must not silently re-enter the prompt without the provenance flag. CSP/sandbox is necessary but not sufficient; treat any preview-iframe egress as an exfil path, never a safe one.
- **UI-initiated tool calls / token-billing abuse.** Any `CanvasUiAction::ToolCall` (the DESIGN-mode click-to-edit that mutates files, or a node re-invoking an agent) **must pass the write-time security gate + explicit user consent**, never auto-execute. This is MCP Apps' consent gate, which ELAI already has as write-gates (F-1/F-2).
- **Valid-but-wrong / "looks right but does nothing".** The trust spine cannot catch a plausible-but-semantically-wrong graph by rendering alone. tldraw's own author frames make-real as a prototyping tool, not production codegen (tldraw.substack.com/p/make-real-the-story-so-far, T2). **Caught only by exercising the depicted artifact** — wiring-enforcement R4 (measure the real objective, not a proxy) + the RRA. A rendered picture of a code-graph is not proof the graph is correct, which §4 already says about the DKG substrate.
- **Live-iframe DESIGN mode** is the one raw-untrusted-HTML surface (§8) and needs the double-iframe + CSP `frameDomains` + strict postMessage origin-check posture verbatim from ChatGPT/MCP Apps (dev.to/infoxicator ChatGPT-Apps reverse-engineering, T3; mcpui.dev/guide/protocol-details, T1 on the `targetOrigin` requirement and externalUrl SSRF mitigation).

## 20. Risks, honest limits, and corrections to this document

1. **Interactivity is not a free win (CONFIRMED counter-evidence).** Mosca et al. (arXiv:2103.01701, T3) found adding interaction to a static visualization did *not* improve reasoning accuracy and sometimes hurt it, and *"a well designed static visualization can be as, if not more, effective than an interactive one"*, moderated by base-visual quality and user spatial ability. Do not ban prose/ASCII. The value is the right view + drill-down + shared referent, restricted to structured/relational content. Over-triggering (a chart when text was wanted, a wrong renderer) is exactly why Anthropic ships custom visuals as beta; ship a cheap suppress-canvas escape hatch and default to text unless a routing-confidence bar clears.

2. **Correction to this document: §1/§5/§9 over-read arXiv:2603.26942.** Sections 1, 5, and 9 lean on the observability-gap paper (Wang & Wang, "The Observability Gap", 2026-03-27; arxiv.org/abs/2603.26942) as the spine of the "the canvas is a steering surface that restores convergence" thesis. The paper is real (anti-slopsquatting check passed, it is not a fabricated cite) and its finding is genuine, but it is n approximately 10, single domain (Blender 3D-scene generation), and *its positive result came from a human expert injecting code-level fixes, not from a UI merely displaying intermediate state*. So "surfacing mid-run state on a canvas restores convergence" is **Ungrounded conjecture** as stated, it is a hypothesis ELAI would be testing, not a proven result to headline. Recommended doc edit when an H-plan integrates this: soften the §1/§5/§9 language from "the convergence fix the research demands" to "an intervention surface motivated by (but not proven by) the observability-gap diagnostic", and keep the quantitative claim out of any done-gate. The deixis half of §9 (Bolt/Oviatt) remains strongly grounded and needs no softening.

3. **Standard-chasing / scope balloon.** A2UI is 0.x and actively churning; the MCP-Apps MIME/`_meta` spelling drifted across sources during this very sweep. Keep the SSB op catalog as the internal contract; "be MCP-Apps-compatible" or "be AG-UI-compatible" is a later, optional adapter, not a prerequisite. The value is the *internal* model->canvas->user loop, not protocol interop.

4. **Concurrency + accessibility are real net-new engineering.** User-edits-then-agent-re-edits has few battle-tested references (the Excalidraw/tldraw-MCP pattern is genuinely new in 2026 and thinly documented). Generated UI is a measured, persistent accessibility weakness (W4A 2025, mintviz.usv.ro/publications/2025.W4A.3.pdf, T3: LLM UI code consistently fails semantic structure, focus management, keyboard nav, live regions even with a11y-oriented prompts; automated checks passing is not evidence a disabled user can complete the flow). Neither is borrowable.

5. **The framing fork (decision for the H-plan).** §14 commits the canvas to "work-surface, not pipeline-editor". This addendum adds a *third* identity, "general visual reply medium". It is compatible (same op stream), but it widens the model's autonomy: the model now decides *when* to draw, not just *what*. That is the Anthropic-beta risk surface. Decide whether v1 wants that autonomy or wants every `spawn_view` user-requested first.

## 21. Phasing for an H-plan (cheapest first slice on top of C1-C4)

Build directly on C1-C4 (op stream + SSB journal + modes registry, already in this design's build plan, §13). Each slice is a vertical wire-dark-compliant slice (producer + its real entrypoint + its journal assertion in the same unit, per the §13 walking-skeleton PRE_GATE).

- **Slice H1 (proof).** Add the `spawn_view { view_type }` verb + the single `CanvasViewEvent` SSB action_type variant (9-tuple lockstep bump). Implement **one** new reply-view, **comparison/branch board** is the cheapest high-value pick (pure existing ops: columns + labels, no new renderer primitives). Done-gate (auditor-driven, gate frozen per wiring R4/R8): a real reply path emits a `ViewSpawned` row and the board renders, proven by an off-agent SSB row + a Layer-4 trace assert, not a unit test calling the function and not the implementer's stdout.
- **Slice H2 (the differentiator).** The inbound leg, `CanvasUiAction::Select` with tiered read-back, **gated by a G-1 taint check**, journaled. Done-gate: selecting a node hands its exact current state to the model as context, a tainted (web-sourced) node's content is flagged at the handoff, and the select event lands as an SSB row. This proves the deictic round-trip and the trust gate together, which is the part Artifacts/Canvas cannot do.
- **Slice H3 (the one new primitive).** Snapshot+delta reconciliation so a tab rebuilds from the SSB tail (per-tab sequence numbers + periodic checkpoints). Done-gate: kill and reopen the dashboard mid-run, the tab reconstructs from the journal, and a forced divergence triggers a fresh-snapshot request.

Defer until after H1-H3: the full taxonomy (§17), the model's autonomous text-vs-visual routing rubric (lift Anthropic's content-type matrix only once the suppress-canvas hatch exists), and any "publish/share a canvas" feature (it inherits the mass-exploitation auth class; build it behind G-8 attestation from day one or not at all).

Instrument a **canvas-spawn-vs-text rate** from H1 onward: the field publishes no benchmark for how often an agent *should* answer visually (Anthropic's split is feature/context dependent and unpublished), so judge this on ELAI's own measured comprehension/ambiguity delta, not faith.
