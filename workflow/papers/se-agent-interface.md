=== UNIT OF EVOLUTION ===

A TRAJECTORY (tau) — one complete sequence of agent actions taken on a single task instance.
NOT agent code. NOT a persistent agent archive. NOT a population of agent variants.
The population is a set of trajectories for the SAME task, evolved per-task and discarded after resolution.

=== Inputs ===

task t | natural language problem instance | single string | from SWE-bench Verified benchmark
initial_pool Gamma_0 | set of trajectories | list[trajectory] | generated by multi-planning + mutation
backbone_llm | LLM used as the agent | model identifier | any instruction-tuned model (Claude-3.7, DeepSeek-V3, GPT-4o, Qwen-2.5-72b, Llama-3.1-70b tested)
w1, w2, w3 | reward component weights | float in [0,1] | w1+w2+w3=1; paper does not publish exact values used
lambda | expert-eval weight inside TaskCompletion | float | not published
epsilon | convergence threshold | float > 0 | improvement below epsilon halts evolution
max_cycles | max evolution iterations | int | not explicitly stated; 10 candidates default

=== Outputs ===

best_trajectory tau* | the highest-reward trajectory after evolution | sequence of agent actions | passes selection across all cycles
reward_score | float | scalar per trajectory | Reward(tau,t) in [0, theoretical_max]
patch | code diff / solution artifact | string | produced by applying tau* to environment

=== Evolution Operators (on TRAJECTORIES, not on agents) ===

Revision | single-trajectory | self-reflection on failure -> new strategy -> re-execute -> new tau
  sub-ops: multi-planning (vary theta_p), mutation-based diversification (Mutate(tau, delta_m))
Recombination | multi-trajectory | combines segments from multiple trajectories into a new tau
  sub-ops: crossover (merge high-performing segments), transfer-learning (copy success to suboptimal), restructuring (global reorder)
Refinement | population-level | evaluates all tau in Gamma_k, selects elites, maintains diversity
  selection pool: Gamma_k union Gamma_k_prime union Gamma_k_new

=== Fitness / Verification Signal ===

Reward(tau,t) = w1*TaskCompletion(tau,t) + w2*ReasoningQuality(tau) + w3*Efficiency(tau)
TaskCompletion(tau,t) = AutoEval(tau,t) + lambda*ExpertEval(tau,t)
  AutoEval: rule-based structural validation (deterministic, e.g. syntax checks, file presence)
  ExpertEval: LLM-judge evaluation of solution quality (non-deterministic)
ReasoningQuality(tau): LLM-assessed quality of intermediate reasoning steps
Efficiency(tau): implicit, penalizes unnecessary steps (exact metric not disclosed)
CRITICAL: selection signal is a HYBRID of deterministic tests + LLM-judge. Not pure test-execution. Not pure LLM. Both.

=== Inter-Task Persistence ===

NONE. Per-task evolution only.
Each task instance generates its own Gamma_0, runs its own evolution loop, selects its own tau*.
No trajectory meta-information, no operator parameters, no population statistics are persisted to the next task.
The framework is stateless across tasks — it is a multi-sample inference strategy, not a self-improving system in the DGM/archive sense.

=== Convergence Condition ===

Termination when: (a) max_cycles completed, OR (b) max(Reward) improvement < epsilon for consecutive iterations.
No published values for max_cycles or epsilon in the experiments section.

=== Relation to DGM / SICA / HGM Archive-of-Agents ===

DGM (Flan et al.), SICA, and HGM maintain a GROWING ARCHIVE of AGENT VARIANTS (different programs, scaffolds, or weights) across a POPULATION OF TASKS. Improvement accumulates in the archive: what agent_v2 learned on task A is baked into a new agent that starts task B better. This is genuine cross-task, cross-time self-improvement of the agent itself.

SE-Agent does none of this. It evolves a population of TRAJECTORIES for ONE task. When that task is resolved, the population is discarded. The agent (backbone LLM + scaffolding code) is never mutated, never archived, never improved. The next task starts from scratch. SE-Agent is best understood as a structured beam search / MCTS variant that uses LLM operators instead of random rollouts. The "self-evolution" branding refers to trajectory-level search, not agent-level adaptation. It is lineage-agnostic: it produces no offspring that encode learned behavior. The prior-session rejection label "out-of-lineage (trajectory-optimization, NOT self-code/archive editing)" is CONFIRMED ACCURATE by this analysis.

=== Complexity ===

Time: O(K * N * C) where K=evolution cycles, N=trajectories per generation, C=cost per trajectory execution
Space: O(N) trajectory pool per task; no persistent store
Parallelism: trajectories within a generation are independent; can parallelize revision/recombination across pool
Token overhead: not disclosed; multiply-and-select pattern implies 5-15x token cost over single-trajectory inference

=== Failure Modes (from paper) ===

Single trajectory local optima: SE-Agent explicitly exists to escape these; without multi-trajectory pool, revision alone fails
LLM-judge reward hacking: ExpertEval is an LLM scoring an LLM's output; gaming risk not addressed in paper
Diversity collapse: without the diversity-preserving selection in Refinement, population converges to one strategy
Compute unboundedness: no hard token budget; convergence criterion epsilon can be set too tight

=== Implementation Pitfalls (do NOT do) ===

Do NOT treat the evolution as persistent learning — no state carries across tasks; any design that treats SE-Agent's trajectory pool as a knowledge base is a misread
Do NOT assume AutoEval alone drives selection — the hybrid reward (LLM-judge component) is load-bearing; removing ExpertEval degrades to structural-check-only
Do NOT use BatchSpanProcessor or async evaluation for the reward signal — timing non-determinism corrupts selection (same fail-open risk as tracing-test rule T-3)
Do NOT confuse pass@5 with pass@1 when citing numbers — the paper reports both; pass@5 assumes best-of-5 sampling which is not single-inference performance

=== ELAI Relevance (factual, no recommendations) ===

1. The hybrid reward function (deterministic AutoEval + LLM ExpertEval) is a verified signal design that drove SOTA results on SWE-bench Verified; the exact weighting is not published but the two-component structure is confirmed in the paper.
2. The three operators (Revision, Recombination, Refinement) are applied to TRAJECTORIES WITHIN ONE TASK — any ELAI use would need to re-scope the target object (from trajectories to agent scaffolds or prompts) to produce inter-task learning.
3. The crossover sub-operator (merge segments from multiple high-performing paths) is the most structurally novel mechanism; it is described in Section 4 and requires a trajectory representation that supports segment-level addressing.
