Summary:
Survey that reframes code from a generated artifact to the operational substrate for LLM-based agents.
Introduces a three-layer taxonomy: (1) harness interface, (2) harness mechanisms, (3) multi-agent scaling.
No original benchmarks or training procedures; coverage spans ~200+ cited methods.

Three-Layer Taxonomy:

Layer 1 - Harness Interface (Section 2):
  Code for Reasoning (2.1):
    - Program-delegated reasoning: PoT, PAL, CodeAdapt, CodeI/O
    - Formal verification and symbolic reasoning: ReProver, DeepSeek-Prover-V2, Lean4Agent, SATLM
    - Iterative code-grounded reasoning: NExT, CodePRM, CodeRL, RLEF, EG-CFG, R1-Code-Interpreter
  Code for Acting (2.2):
    - Grounded skill selection: SayCan, KnowNo, BOSS, LRLL, SkillVLA
    - Programmatic policy generation: CaP, RoboCodeX, Code-BT, CP-Agent, GenSwarm, NormCode, ALRM, RACAS
    - Lifelong code-based agents: Voyager, LYRA, ViReSkill, UI-Voyager, SkillsCrafter
  Code for Environment (2.3):
    - Structured world representations
    - Execution-trace world modeling
    - Code-grounded evaluation environments
    - Verifiable environment construction

Layer 2 - Harness Mechanisms (Section 3):
  Planning (3.1): linear decomposition, structure-grounded, search-based, orchestration-based
  Memory (3.2): working, semantic, experiential, long-term, multi-agent, context compaction / state offloading
  Tool Use (3.3): function-oriented, environment-interaction, verification-driven, workflow-orchestration
  Control (3.4): Plan-Execute-Verify loop; sandboxed execution; permissioned state transitions; deterministic sensors
  Optimization (3.5): deep telemetry as optimization substrate; evolution agent; governed harness mutation

Layer 3 - Scaling the Harness (Section 4):
  Multi-agent roles: program synthesis agents, understanding agents, verification agents, execution agents, planning agents
  Interaction modes: collaborative synthesis, critique-and-repair, adversarial validation, reasoning debate
  Workflow topologies: pre-defined heuristic, objective-driven and adaptive
  Feedback types: compiler/syntax, test pass/fail, fuzzer crash traces, static analysis warnings, performance profiling, simulation feedback
  Synchronization: shared blackboard, parallel branches with merge, structured context scheduling, hierarchical memory, agent pool scaling

Inputs:
task_specification | natural language or structured goal | string | mandatory; drives harness construction
code_artifacts | executable programs, scripts, configs | string/file | mandatory for execution-based harness
execution_environment | sandbox, interpreter, OS, simulator | runtime context | mandatory for action/verification layers
feedback_signals | compiler output, test results, static analysis | structured text | mandatory for control loop (3.4)
tool_registry | callable functions, APIs, external services | list of callables | optional; required for tool-use mechanisms (3.3)
shared_state | blackboard or shared memory across agents | key-value or structured | optional; required for multi-agent coordination (Section 4)

Outputs:
executable_artifact | verified program or policy | code | must be syntactically valid and pass specified tests
execution_trace | structured log of intermediate steps | structured text | must be inspectable; exposes intermediate computation
verification_result | pass/fail signal with evidence | bool + structured feedback | invariant: false negatives are dangerous in safety-critical contexts
harness_state | persistent task progress representation | serializable state | invariant: must be consistent and recoverable across agent steps
agent_coordination_signal | task assignments and results between agents | structured message | invariant: must not create silent conflicts in shared state

Hyperparameters:
planning_depth | not specified (survey) | 1..N | deeper planning increases coordination overhead vs. task horizon
memory_type | working|semantic|experiential|long-term | enum | lifelong agents require experiential + long-term; short tasks use working only
topology_complexity | heuristic|adaptive | enum | higher complexity inversely correlates with harness-state formality (Section 4 finding)
feedback_granularity | coarse (pass/fail)|fine (line-level traces) | enum | fine-grained preferred for repair; coarse sufficient for final evaluation
sandboxing_level | none|partial|full | enum | safety-critical actions require full sandboxed execution (Section 3.4)

Critical invariants (testable assertions):
# Executability: code artifacts must be syntactically valid and executable in the target environment
assert code_artifact_is_syntactically_valid(artifact) == True

# Inspectability: execution traces must expose intermediate computation, not just final output
assert len(execution_trace.intermediate_steps) > 0

# Statefulness: harness state must be serializable and recoverable across agent steps
assert harness_state == deserialize(serialize(harness_state))

# Verification completeness: verification must use deterministic sensors, not just LLM self-report
assert verification_result.evidence_source in ["compiler_output", "test_result", "static_analysis", "simulation_feedback"]

# Multi-agent consistency: shared state modifications must not produce silent conflicts
assert detect_semantic_conflicts(shared_state_before, shared_state_after) == []

Complexity:
Survey paper - no formal complexity analysis provided.
Control loop (3.4): Plan-Execute-Verify is iterative; complexity scales with planning depth and feedback latency.
Multi-agent scaling (Section 4): coordination overhead grows with agent count; topology complexity inversely correlates with state formality.
Context management overhead: "Context management is the tax of implicit shared state" - multi-agent shared state is the dominant cost.

Failure modes:
Textual-only reasoning: "purely textual reasoning provides little ability to verify intermediate states" (Section 1) - use code-grounded reasoning
Partial observability in action: "failures may emerge through invalid state transitions, delayed feedback, or silent execution errors" (Section 2.2)
Skill library rigidity: fixed skill libraries fail to generalize; addressed by dynamic synthesis (BOSS pattern, Section 2.2)
Context bottleneck: "context management is the tax of implicit shared state" in multi-agent settings (Section 4.4)
Coordination without formal structure: code-mediated channels alone do not eliminate coordination bottlenecks (Section 4.4)
Topology-formality tradeoff: more agents require explicit shared state or precision is lost (Section 4 finding)
Transactional conflicts: no general resolution mechanism for semantic conflicts when multiple agents modify shared code simultaneously (Section 5.2)
Regression in self-evolving harnesses: continuous harness improvement risks breaking prior functionality (Open challenge 3, Section 5.2)
Oracle adequacy: final-task-success metrics miss harness-level correctness; intermediate state evaluation is unsolved (Open challenge 1, Section 5.2)

Implementation pitfalls (do NOT do this):
Do NOT treat code generation as pure text generation - executability and verifiability are the key properties that differentiate code-as-harness
Do NOT skip sandboxed execution for safety-critical actions - permissioned state transitions are required (Section 3.4)
Do NOT use only pass/fail test signals when fine-grained feedback (line-level traces, static analysis) is available - coarse signals limit repair capability
Do NOT allow multiple agents to modify shared code state without conflict detection - transactional semantics are required (Section 5.2)
Do NOT evaluate agent systems only on final task success - intermediate harness state correctness is equally important (Section 5.2, Open challenge 1)
Do NOT conflate model-internal capabilities with harness infrastructure - these are distinct layers (Section 1 key distinction)
Do NOT use rigid pre-built skill libraries for lifelong or open-world agents - dynamic skill synthesis (Voyager pattern) is required
Do NOT assume LLM self-reported verification is sufficient - deterministic sensors and execution feedback are required (Section 3.4)

Acknowledged limitations (Section 5.2):
1. Harness-level evaluation and oracle adequacy: evaluation beyond final task success is unsolved
2. Semantic verification beyond executable feedback: execution signals do not capture semantic correctness
3. Self-evolving harnesses without regression: improvement risks breaking prior functionality
4. Transactional shared program state and semantic conflict resolution: multi-agent shared state is unsolved
5. Human-in-the-loop safety and accountability as harness state: human oversight for safety-critical actions
6. Multimodal code-harness systems: extending to visual, sensorimotor, and embodied modalities
7. Toward a science of harness engineering: no principled design methodology exists yet

Scope boundary (explicit):
"Code as a harness interface does not replace perception, embodiment, human goals, or model-internal latent reasoning."
