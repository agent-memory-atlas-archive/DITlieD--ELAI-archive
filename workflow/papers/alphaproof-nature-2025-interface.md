System Overview (neuro-symbolic combination):
AlphaProof = Proof Network (encoder-decoder transformer) + AlphaZero-style MCTS tree search + Lean 4 formal proof verifier + Formalization Network (separate LLM). All four components interact: network proposes tactics, Lean checks them, RL trains on verified proofs.

---

Inputs:

natural_language_problem | string | LaTeX-formatted theorem statement | mandatory; must be a well-posed mathematical claim with deterministic truth value
lean_tactic_state | structured proof state | current goals + hypotheses in Lean 4 syntax | mandatory at each search step; provided by Lean 4 environment after each tactic application
formalized_statement | Lean 4 code | valid Lean statement representing the theorem | output of Formalization Network; input to Proof Network; must compile in Lean 4 mathlib context
problem_variants | list[Lean 4 statements] | N related simpler theorems generated by LLM | optional; only used in Test-Time RL (TTRL) mode for hard problems; no fixed N in paper
search_budget | int | number of MCTS simulations per node | mandatory; scales with problem difficulty; paper uses gradually increasing budget across RL training; nanoproof uses 512 as practical upper bound
lean_mathlib_context | Lean 4 library snapshot | mathlib version pinned at training time | mandatory; proof validity is relative to this snapshot; changing mathlib can break trained proofs

---

Outputs:

formal_proof | Lean 4 tactic block | complete proof term that compiles in Lean 4 | invariant: Lean kernel accepts it without error (100% guarantee if output produced); no hallucination possible because Lean rejects invalid proofs
proof_status | enum {PROVED, DISPROVED, UNDECIDED} | per-formalization outcome | invariant: PROVED iff Lean kernel returns success; DISPROVED iff a counterexample is verified in Lean; UNDECIDED if search budget exhausted
value_estimate | float in [0, 1] | predicted probability of eventual proof success | used internally by MCTS; not a soundness guarantee — only a search heuristic
tactic_ranking | list[(tactic_string, score)] | ordered candidates for next proof step | top-N output of Proof Network; N is a hyperparameter; only the Lean-verified prefix of an application is retained

---

Hyperparameters:

pretraining_tokens_encoder | 12 trillion | not varied in paper | encoder side of encoder-decoder transformer; 50 epochs over mixed code + math corpus
pretraining_tokens_decoder | 3 trillion | not varied in paper | decoder reconstruction target tokens
pretraining_epochs | 50 | not varied in paper | unusually high; paper cites "high model FLOPs utilization (MFU)" as motivation
formalizations_per_problem | 80 | stochastic sampling + prompt randomization | Formalization Network generates 80 Lean candidates per natural-language statement; diversity critical for downstream RL coverage
rl_training_statements | 80 million | derived from 1 million informal problems x 80 formalizations | scale at which RL training operates; authors report increasing proof/disproof rates across compute
ttrl_variant_count | not fixed in paper | "millions" cited in popular press; LLM-generated | Test-Time RL variant count is problem-specific; no hard default given; described as "many variations"
value_target | tactics_remaining_to_proof_end | not a probability; uses inverse-depth signal | paper explicitly notes this differs from standard game-value targets; using raw win probability is a known pitfall
product_node_backprop | min(child_values) | hardest branch dominates | AND-node value = minimum value among all sub-goals; standard OR-node backprop is wrong for these nodes

---

Critical invariants (testable assertions):

assert lean_kernel_accepts(output_proof) == True  # if any proof is returned, it is valid; Lean is the ground truth; no post-hoc checking needed
assert proof_status == "PROVED" implies lean_kernel_accepts(proof) == True  # PROVED is never a soft label
assert proof_status == "DISPROVED" implies lean_kernel_accepts(negation_proof) == True  # disproofs also Lean-verified
assert product_node_value == min(child_node_values)  # AND-node backprop rule; using max() or avg() breaks proof completeness guarantee
assert sum(subgoal_proofs_complete) == len(subgoals) implies product_node_proved  # all children must be proved for product node to be proved; any single open sub-goal blocks the node
assert formalized_statement.compiles_in_lean4_mathlib(pinned_version) == True  # formalizations are invalid if mathlib version drifts
assert proof_network_output is not used as soundness certificate  # value estimate is heuristic only; Lean kernel is the sole soundness oracle

---

Complexity:

Pretraining: O(T * D^2) where T=12e12 tokens, D=model dimension; single large training run; not repeated per problem
Formalization: O(80 * inference_cost_per_statement) per problem; stochastic; embarrassingly parallel
RL training loop: O(N_statements * search_budget * tactic_inference_cost); 80M statements; multi-week wall-clock on TPU cluster (exact hardware not disclosed)
MCTS per problem: O(search_budget * branching_factor * tactic_inference_cost); depth-first with value-guided pruning; proven sub-goals skipped to reduce redundant compute
Test-Time RL: O(n_variants * rl_steps_per_variant); problem-specific; described as "millions" of variants for hardest IMO problems; extremely expensive
Space: proof tree grows with search budget; proven sub-goals pruned from active tree; full tree not retained after training iteration
Parallelism: actor-learner separation (separate worker nodes for proof search vs. gradient updates); nanoproof collapses to single multi-GPU process as simplification

---

Failure modes (cited in paper and verified sources):

Combinatorics gap: AlphaProof failed IMO 2024 P3 and P5 (both combinatorics); root cause = sparse Lean mathlib coverage for combinatorial objects; system cannot prove what mathlib cannot formalize
Formalization failure: if Formalization Network produces 80 invalid Lean statements for a problem, the RL loop has no training signal for that problem; coverage depends on LLM formalization quality
Disproof trap: if a valid problem is incorrectly formalized as a false statement, RL will train toward disproving it; "carefully track progress on each formalization; once we disprove an invalid formalization there is no point trying to prove it anymore" (paper)
Budget exhaustion: returns UNDECIDED if search budget exhausted; no fallback; not a correctness failure but a completeness failure
Mathlib version lock: proofs verified against pinned mathlib snapshot; upgrading mathlib can silently invalidate proofs (tactic names, lemma availability change)
Value estimate miscalibration: proof network value estimates are heuristic; high-value estimate does not guarantee proof exists; MCTS may over-explore dead ends based on poor value estimates
LLM bias inheritance: proof network inherits biases of pretrained LLM; algebraic/number-theoretic patterns overrepresented relative to combinatorial patterns in training corpus
Geometry blind spot: AlphaProof does not handle geometry; requires separate AlphaGeometry 2 system; geometry problems in Lean are not natively supported at the same scale

---

Implementation pitfalls (do NOT do this):

Do NOT use OR-node backprop for product (AND) nodes: back-propagate min(child values) not max or average; wrong backprop produces incorrect value estimates that mislead MCTS toward incomplete proofs
Do NOT accept LLM-generated proofs without Lean kernel verification: the entire correctness guarantee rests on Lean; any bypass (e.g. "the proof looks right") destroys the 100% accuracy claim
Do NOT treat value_estimate as a soundness signal: it is a search heuristic; a value of 0.95 does not mean the theorem is provable; only Lean acceptance is ground truth
Do NOT continue RL training on a formalization once it has been disproved: waste of compute and can corrupt the learned value function; track prove/disprove/undecided status per formalization
Do NOT assume proof transfers across mathlib versions: pin mathlib at training time and verification time to the same commit; library upgrades are breaking changes
Do NOT skip the product-node construction for multi-goal tactics: tactics like `constructor`, `induction`, `cases` in Lean split one goal into multiple; treating these as single OR-children loses the AND-structure and produces incomplete proofs
Do NOT use raw win probability as value target: paper explicitly uses "number of tactics remaining to end of proof" (inverse depth) as value target; switching to probability destabilizes training
Do NOT conflate auto-formalization accuracy with proof correctness: 80 formalizations per problem produces candidate statements; invalid formalizations must be tracked and discarded, not trained on

D-11 scope notes (constructive checker registry):

Lean-as-ground-truth pattern: AlphaProof's core design principle is that Lean kernel acceptance IS correctness; there is no separate "checker" layer — Lean is the checker. For D-11's constructive checker registry, this maps to: a formal proof checker entry should delegate final verdict to the Lean kernel (or equivalent verified proof checker), not to a neural model's confidence score.

Neuro-symbolic separation: the neural component (proof network) generates candidates; the symbolic component (Lean) verifies them; these roles must not be merged. A registry entry for a "formal proof checker" should represent the symbolic verification step, not the neural generation step.

Auto-formalization as a registry concern: the Formalization Network is a separate subsystem from the Proof Network. In D-11, if the registry includes "problem formalizer" entries, they should be treated as distinct from "proof verifier" entries with their own reliability characteristics.

Test-Time RL is inference-time training: TTRL blurs the train/inference boundary. A D-11 checker that uses TTRL semantics must account for the fact that the "checker" adapts its internal model during a single verification run. This is architecturally distinct from a static checker.

100% accuracy claim scope: AlphaProof's 100% accuracy claim applies only to proofs it DOES produce (Lean guarantees). It does NOT claim 100% recall (many valid theorems return UNDECIDED). A D-11 registry entry must distinguish precision (correct when it says yes) from recall (coverage over all theorems).
