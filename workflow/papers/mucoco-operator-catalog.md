## Operator catalog (11 operators, verbatim from Appendix B / Table 9)

Operators are grouped into three categories: Lexical (B.0.1), Syntactic (B.0.2),
Logical (B.0.3). Descriptions below are verbatim/paraphrased from Appendix B;
equation numbers are the paper's.

### B.0.1 Lexical Mutations

> "Lexical mutations refer to mutations involving renaming variable names,
> function names, or Python strings. These mutations modify the natural language
> names used in code without modifying the program logic."

**1. Random Mutation** — "replaces the function/variable names with random
strings" (Table 9 row 1). Example from Table 1: `def f(text, n)` →
`def dOdtZZSuisMB(TYesQRBm, mXDbZtJMZFV)`. This is the operator that triggered
the CruxEval-789 consistency error in 5 of 7 LLMs.

**2. Sequential Mutation** — "similar to random mutation, but it replaces
function/variable names with generic names. By default, the function name in the
function definition is renamed to `generic_function1` and first variable names
are replaced with `var1` and so on" (Table 9 row 2).

**3. Literal Format** — "replaces string single quotation marks (') with double
quotation (") and vice versa" (Table 9 row 3). **Python-specific**: explicitly
scoped to "Python strings" (Sec B.0.1). Not portable to Rust/Java/Go where ' vs
" are distinct char/string delimiters.

### B.0.2 Syntactic Mutations

> "semantic-preserving mutations that modify the program syntax with equivalent
> syntax."

**4. for-to-enumerate** — "replaces all for loop iterators with enumerate
iterators" (Table 9 row 4). **Python-specific idiom** (`enumerate()`).

**5. for-to-while Mutation** — "replaces all for loops with while loops"
(Table 9 row 5). Concept generalises but the paper only validates on Python.
Applicability check (Sec 3): requires a `for` loop in the program; if none,
SKIP (do not synthesise one).

### B.0.3 Logical Mutations

> "modifies the program logic in a manner that preserves the original program
> behavior, e.g., by decomposing a constant (5) into equivalent operations
> (4 + 1)."

**6. DeMorgan Mutation** — applies De Morgan's Law:
- `A and B` → `not (not A or not B)` (Eq 3, as written in Sec B.0.3 / interface file)
- `A or B`  → `not (not A and not B)` (Eq 4)
(Table 9 row 6). Note: the paper's Eq 3/4 text also states the simpler
`A and B → not A or not B` form in the prose; the interface file records the
double-negation-preserving form. Implementer must pick the form that preserves
semantics under Python's `not` and verify on the canonical test suite.

**7. Boolean Literal** — "transforms True and False, into semantically-equivalent
expression using negation" (Table 9 row 7), e.g. `True` → `not False`.
**Python-specific literal names** (`True`/`False`); Rust/Java/Go use `true`/`false`.

**8. Commutative Reorder** — "The order of variables in commutative expressions
(such as summation and multiplication) are reversed to form a new expression"
(Table 9 row 8), e.g. `a + b` → `b + a`, `a * b` → `b * a`. Caveat: unsafe under
operator overloading; the paper relies on the canonical test suite to catch
overload-induced semantic changes (Sec 3.1 / Sec 9 internal validity).

**9. Constant Unfolding** — "Integers are decomposed into two factors and
expressed using either multiplication or addition expressions" (Table 9 row 9),
e.g. `5` → `4 + 1` or `5` → `1 * 5`.

**10. Constant Unfolding (Add)** — "substitutes all valid constants with
equivalent addition expressions" (Table 9 row 10).

**11. Constant Unfolding (Multiplication)** — "replaces constants with equivalent
multiplication expressions" (Table 9 row 11).

## SkipReason taxonomy (every documented unsupported AST shape)

From Sec 3 (methodology) + Sec 9 (limitations) + Appendix B, an operator MUST
return a Skip (not panic, not synthesise) when:

- **NoForLoop** — for-to-while / for-to-enumerate require a `for` loop; none
  present → skip (Sec 3, explicit).
- **NoBooleanOp** — DeMorgan requires an `and`/`or` expression; none → skip.
- **NoBooleanLiteral** — Boolean Literal requires a `True`/`False` literal;
  none → skip.
- **NoCommutativeExpr** — Commutative Reorder requires a commutative binary op
  (`+`/`*` on non-overloaded operands); none → skip.
- **NoConstant** — Constant Unfolding (any variant) requires an integer
  constant; none → skip.
- **NoIdentifier** — Random/Sequential require a renameable function/variable
  name; none (e.g. `def f(): pass`) → skip.
- **NoStringLiteral** — Literal Format requires a string literal; none → skip.
- **NonPythonLanguage** — every operator: language != "python" → skip. The
  paper does not validate any other language.
- **SemanticPreservationFailed** — after mutation, the canonical test suite is
  re-run (Sec 3.1); if it fails, the mutant is DROPPED (this is NOT a
  consistency error). This is a runtime skip, not a static AST shape.
- **OperatorOverloadRisk** — Commutative Reorder / Constant Unfolding on
  operands whose type may overload the operator: the paper mitigates via the
  canonical test suite (Sec 9 internal validity); if no canonical suite is
  available, skip rather than assume.

## False-positive notes

- The paper's own false-positive control is the **canonical-test-suite re-run
  after mutation** (Sec 3.1): any mutant that fails the canonical tests is
  dropped before being shown to the LLM, so it can never register as a
  consistency error. C-36's pilot MUST replicate this gate or its
  false-positive rate is not comparable to the paper's.
- Random/Sequential renaming can silently change semantics if a renamed
  identifier shadows a builtin or an external symbol (interface file pitfall).
  The paper mitigates via the canonical test suite; without it, renaming is
  unsafe.
- Commutative Reorder is unsafe under operator overloading (e.g. `__add__` with
  side effects, or non-commutative `+` for string concat in some contexts).
  Python `+` on strings IS commutative (`"a"+"b" == "b"+"a"`), but `+` on
  lists is also commutative — the risk is custom `__add__`. Mitigate via
  canonical tests.
- DeMorgan on short-circuit semantics: Python `and`/`or` short-circuit. The
  double-negation form `not (not A or not B)` evaluates both `not A` and
  `not B` (no short-circuit on the inner `or` after negation? — actually
  `not A or not B` still short-circuits). The implementer MUST verify
  short-circuit equivalence on the canonical suite.
- LLM temperature MUST be 0 (Sec 4.5) for reproducibility; otherwise
  inconsistency detections conflate model nondeterminism with mutation effect.

## Evaluation methodology (Sec 4 + Appendix C)

- **Datasets:** HumanEval, CRUXEval, CodeMMLU, BigCodeBench (all Python).
- **Tasks:** MCQ, Input Prediction, Output Prediction, Code Generation.
- **Oracles:** Correctness oracle (run LLM output vs benchmark tests);
  Consistency oracle (pair original vs mutated; flag iff correctness outcomes
  disagree).
- **Metric (Eq 1):** Inc. = (N_inconsistent / N_test_cases) * 100.
- **LLMs tested (7):** Qwen2.5, Gemma-3, DeepSeek, LLaMA-3.1, GPT-5, GPT-4o,
  Codestral. Temperature = 0.

## Required runtime dependencies (Appendix G)
