SYSTEM OVERVIEW

MemPro treats the entire Memory Construction-Retrieval (MCR) pipeline as a single evolvable program
rather than adapting only the memory bank contents or prompt text. The Evolving Agent maintains a
version tree of runnable MCR implementations and iteratively evolves them via failure diagnosis.

MCR PIPELINE DECOMPOSITION (Section 3)

The MCR pipeline has two top-level stages, each containing multiple named components:

STAGE A: Memory Bank Construction
  Component A1: Segmenter
    Input: raw data D_t
    Output: structured segments S_t = {s_i^t}
    Role: converts raw session/conversation data into discrete storable units

  Component A2: Memory Agent (A_mem)
    Input: prompt I_mem, segments S_t, prior memory bank M_{t-1}
    Output: memory update delta M_t = A_mem(I_mem, S_t, M_{t-1})
    Formula: M_t = Update(M_{t-1}, delta_M_t)
    Role: decides what to store, merge, or discard

STAGE B: Memory Retrieval and Usage (iterative, K iterations max)
  Component B1: Retrieval (per iteration k)
    Input: prompt I_ret, query q, prior research state z_{k-1}
    Output: retrieval request r_k = A_res(I_ret, q, z_{k-1})
    Then: memory returns u_k = Retrieve(r_k, M)

  Component B2: Integration (per iteration k)
    Input: prompt I_int, query q, z_{k-1}, retrieved u_k
    Output: updated research state z_k = A_res(I_int, q, z_{k-1}, u_k)

  Component B3: Reflection (per iteration k)
    Input: (implicit, same A_res agent under prompt I_ref)
    Output: continuation decision b_k in {Continue, Stop}
    Role: sufficiency judgment that terminates retrieval loop

  Component B4: Answer Generation (terminal)
    Input: prompt I_ans, query q, final state z_K
    Output: answer y_hat = A_res(I_ans, q, z_K)

REPRESENTATION OF F_v (critical for implementation):
  The paper states each node v contains "a runnable implementation of an MCR pipeline F_v."
  Evidence from Appendix A.5: the Evolving Agent uses "OpenAI Codex coding harness" suggesting F_v
  is Python source code. The paper shows prompts as editable text (Figures 6-9) AND mentions
  "executable logic" implying code blocks. The representation is HYBRID: prompts (I_mem, I_ret,
  I_int, I_ref, I_ans) are text strings within F_v; retrieval algorithms and memory update logic
  are Python code. The exact serialization format is NOT explicitly documented.
  UNVERIFIED: exact file/string encoding of F_v (inferred, not quoted from paper).

MCR VERSION TREE DATA STRUCTURE (Section 4.1)

Tree: T = (V, E) where:
  V = set of nodes (MCR pipeline versions)
  E = set of parent-child edges (derivation history)

Each node v in V contains:
  F_v: runnable MCR pipeline implementation (Python + prompts, see above)
  L_v = (S_v, C_v, pa(v), A_v): evaluation log with four fields
    S_v: scalar float, overall average score on training set D_train (PRIMARY FITNESS SIGNAL)
    C_v: dict, category-level scores on D_train (e.g. for LongMemEval: Temporal Reasoning,
         Multi Session, Knowledge Update, Single User, Single Assistant, Single Preference)
    pa(v): node ID of parent (None for root)
    A_v: free-text string, "summarizes the major failure modes of v and possible improvement
         directions" (Section 4.1 verbatim) - generated by the Evolving Agent after evaluation

ROOT NODE: initialized from a manually authored baseline MCR pipeline implementation

TREE GROWTH: strictly branching (tree not DAG); each expansion appends one child node

BEST NODE SELECTION FOR DEPLOYMENT: the node with maximum S_v across the entire tree

EVOLVING AGENT SELECT/DIAGNOSE/REFINE LOOP (Section 4.2)

The loop has three phases executed per evolution iteration l:

PHASE 1: SELECTION
  (v*_l, R_l) = A_evo(I_sel, {L_v}_{v in V})
  Input: selection prompt I_sel, ALL evaluation logs in current tree
  Output: selected node v*_l to expand from, diagnostic analysis R_l
  Selection criterion: LLM-driven, NOT formula-based (no UCB, no score threshold)
  Stated guidance (Section 4.2): "high overall score, generalizable improvement directions,
    and frequent failure modes"
  CRITICAL: "generalizable improvement directions" is implicit in prompt I_sel, not
    mathematically defined. The selection is entirely LLM-judged.

PHASE 2: EXPANSION (edit-debug refinement loop)
  Inner loop indexed j = 0..J_max (J_max = 20)
  Initialize: F^(0)_{u_l} = F_{v*_l} (copy parent implementation)
               R^(0)_l = R_l (diagnostic from selection phase)

  At each step j, agent chooses a_j in {Edit, Debug, Terminate}:

  ACTION Edit: modify pipeline
    F^(j+1)_{u_l} = A_evo(I_exp, F^(j)_{u_l}, R^(j)_l)
    No re-evaluation on full training set during edit steps

  ACTION Debug: gather trace without modifying pipeline
    Select diagnostic example: x^diag_j = A_evo(I_exp, R^(j)_l, D_train)
      (criteria for example selection NOT specified in paper)
    Execute: tau_j = F^(j)_{u_l}(x^diag_j) (single example execution)
    Update analysis: R^(j+1)_l = A_evo(I_exp, R^(j)_l, tau_j) (no F change)

  ACTION Terminate: stop expansion, proceed to full evaluation

  DECISION RULE for a_j: emerges from prompt I_exp (not explicitly stated as rules)
  CRITICAL: the paper provides no rule-based logic for when to Debug vs Edit vs Terminate;
    this is fully LLM-driven and prompt-dependent.

PHASE 3: EVALUATION (full training set execution)
  Execute new pipeline on all training examples: Gamma_{u_l} = {F_{u_l}(x) | x in D_train}
  Summarize into log: L_{u_l} = A_evo(I_eval, F_{u_l}, Gamma_{u_l})
    This produces S_{u_l}, C_{u_l}, A_{u_l} for the new node
  Add node u_l with log L_{u_l} and edge (v*_l, u_l) to tree

FITNESS SIGNAL NATURE (critical question answered)

S_v = average LLM-as-Judge score on training set D_train
  - LLM judge: GPT-4o-mini for memory benchmarks (LongMemEval, LoCoMo)
  - Metric: word-level F1 for QA benchmarks (HotpotQA, NarrativeQA)
  - Computed AFTER full pipeline execution on training set
  - The fitness IS LLM-judged for the primary benchmarks (NOT execution-grounded in the
    sense of a deterministic oracle)
  - The judge is the same model used for final eval (not a separate stronger oracle)
  GAMEABLE: the LLM judge evaluates outputs of the same model being evolved;
    the Evolving Agent cannot see judge prompts (they are withheld), but the
    fitness signal is not from an independent, stronger oracle.

FAILURE MODE TAXONOMY (Section 4, focus question answered)

FINDING: There is NO explicit, enumerated failure taxonomy.

The paper uses FREE-FORM diagnosis only:
  - A_v field in the evaluation log: "summarizes the major failure modes of v and possible
    improvement directions" (LLM-generated text, not a structured enum)
  - C_v provides category-level score breakdowns, but these are dataset taxonomy categories
    (e.g. LongMemEval's 6 categories: Temporal Reasoning, Multi Session, Knowledge Update,
    Single User, Single Assistant, Single Preference), NOT failure mode categories

The failure analysis R_l produced by the Evolving Agent during Selection is free-text.
No paper section enumerates memory failure categories (retrieval failure, staleness,
duplication, capacity exhaustion, relevance mismatch, etc.) as a formal taxonomy.

IMPLICATION FOR HARNESS: if implementing MemPro-style evolution, the failure detection
signal must either (a) inherit dataset category scores as the only structured signal,
or (b) define a custom failure taxonomy not provided by the paper. The paper's A_v
is an unstructured LLM summary.

NON-GAMEABLE VERIFICATION ANALYSIS (Section 4, Limitations)

WHAT IS PROTECTED (explicit quote from paper):
  "evaluation data, gold answers, judge prompts, and held-out examples are not editable
  or exposed to the Evolving Agent"
  - The Evolving Agent can ONLY modify F_v (the MCR pipeline code/prompts)
  - Training labels D_train gold answers: withheld
  - Judge prompts: withheld
  - Held-out test set: separate, not seen during evolution

WHAT IS NOT PROTECTED / GAMEABLE:
  - The judge model (GPT-4o-mini) is the SAME model used for task inference; the pipeline
    could in principle be evolved to produce outputs that score well with GPT-4o-mini
    specifically rather than being genuinely better
  - No stronger oracle verifies evolved pipeline outputs
  - The fitness signal is LLM-judged, not execution-grounded (no deterministic oracle)
  - No formal proof of convergence or optimality bound

ASSESSMENT: The gate is reasonably hardened (agent cannot see test labels or modify the
  evaluator) but is not fully un-gameable in the wiring-enforcement sense. The fitness
  signal is a soft LLM score, not a deterministic executable specification. A pipeline
  optimized to satisfy GPT-4o-mini's preferences may diverge from ground truth on a
  stronger judge.

VERSION TREE REGRESSION PREVENTION:
  Tree branching from "strong historical versions" prevents linear-chain collapse.
  Final deployment = node with max S_v over entire tree (not just latest node).
  Ablation confirms: version tree > chain evolution > single iteration.

T (version tree) | directed tree | grows by 1 node per evolution step | invariant: S_best >= S_root (tree never deploys a worse-than-baseline node)

T_max | 15 | [5, 15] | higher = better performance, higher offline evolution cost (unreported)

# fitness is LLM-judged: no deterministic oracle assertion is possible for S_v values

Complexity:
Per evolution step: O(|D_train| * cost(F_v)) for evaluation + O(J_max * cost(A_evo)) for expansion
Space: O(T_max) nodes in tree, each storing F_v (code/prompts ~few KB) + L_v
Parallelism: full evaluation on D_train is parallelizable (each example independent); paper does not specify batch size
Evolution is OFFLINE (not real-time); task-time inference cost = single pipeline execution (K<=5 retrieval steps)
Offline evolution cost not reported; T=15 x J=20 = up to 300 Evolving Agent calls (gpt-5.4-medium) per benchmark

Failure modes:
Evolution cost hidden: paper excludes offline evolution cost from reported token numbers; total cost may be prohibitive
LLM fitness gameable: fitness is GPT-4o-mini judge score; evolved pipeline may overfit judge preferences not ground truth
Training set overfitting: paper does not explicitly warn about this; held-out set is the only mitigation
Failure diagnosis is free-text: no structured taxonomy; A_v quality depends entirely on the Evolving Agent's LLM capability
Selection is fully LLM-driven: no formula ensures the chosen node is actually the best expansion candidate
Edit-debug action policy undefined: the choice between Edit/Debug/Terminate is prompt-dependent with no stated rules
Diagnostic example selection unspecified: x^diag_j selection criteria are not documented
F_v representation ambiguous: hybrid code+prompts representation not formally specified; serialization unclear
Transfer requires retraining: models evolved with GPT-4o-mini on one benchmark need re-evolution for different agents

Implementation pitfalls (do NOT do this):
Do NOT include gold answers or judge prompts in the Evolving Agent's context (breaks the non-gameable gate)
Do NOT count test-set examples in D_train (held-out set must remain separate throughout evolution)
Do NOT use the latest node as the deployed pipeline; use argmax S_v over the entire tree
Do NOT report task-time token cost alone as "MemPro cost" - offline evolution adds substantial unreported overhead
Do NOT implement selection as random or score-only (LLM-driven selection over all logs is the design)
Do NOT skip the version tree in favor of a chain - ablation shows chain underperforms tree branching
Do NOT skip iterative expansion (multi-step edit-debug) in favor of single-step edits - ablation confirms this degrades
Do NOT assume failure taxonomy categories are enumerated - A_v is free-text; dataset categories (C_v) are the only structured signal
Do NOT implement Debug as re-running the full training set - Debug uses a SINGLE diagnostic example x^diag_j
Do NOT treat the fitness signal as execution-grounded; it is LLM-as-Judge and subject to judge model bias
