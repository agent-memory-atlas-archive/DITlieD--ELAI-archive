Algorithm: Program of Thoughts (PoT) Prompting
ArXiv: 2211.12588
Paper: Program of Thoughts Prompting: Disentangling Computation from Reasoning for Numerical Reasoning Tasks
Authors: Wenhu Chen, Xueguang Ma, Xinyi Wang, William W. Cohen
Published: TMLR October 2023

Inputs:
question | str | free-text | natural language math or financial QA problem
few_shot_exemplars | list[tuple[str,str]] | (question, python_program) pairs | 4-8 examples; 0 for zero-shot mode
model | LLM | code-capable LM | Codex (code-davinci-002) is primary; GPT-3.5, CodeGen-16B also tested
temperature | float | scalar | 0 for greedy decoding; 0.4 for self-consistency sampling
n_samples | int | scalar | 1 for greedy; 40 for self-consistency (K=40)
comment_suppression_bias | float | optional | -2 logit bias on '#' token for zero-shot mode to suppress comment-based reasoning

Outputs:
python_program | str | executable Python source | LLM-generated; semantically meaningful variable names required
execution_result | Any | Python interpreter stdout/return value | ground-truth numerical answer for most datasets
final_answer | str or float | scalar | extracted from execution_result; for AQuA: execution_result fed back to LLM for CoT answer selection
self_consistency_answer | Any | majority vote over n_samples | used when n_samples > 1

Hyperparameters:
few_shot_k | 4-8 | paper section 3.1 | fewer for simple datasets (FinQA: lower end), more for complex (AQuA: 8); low sensitivity if in range
temperature_sc | 0.4 | section 3.2 | used only when self-consistency enabled; greedy=0 is default for main results
k_sc | 40 | section 3.2 | number of completions for majority vote; authors fixed at 40 throughout
comment_bias | -2.0 | section 3.1 | zero-shot only; discourages '#' token so model uses variable assignment not comments

Critical invariants (testable assertions):
# LLM generates ONLY the program; computation is NEVER performed by the LLM token stream
assert callable(python_interpreter) and python_interpreter is not None  # external executor required

# Program must be syntactically valid Python before execution is attempted
import ast
ast.parse(python_program)  # must not raise SyntaxError

# Final answer comes from interpreter output, not from LLM-generated text after the program
assert final_answer == execute(python_program)  # not parsed from LLM prose

# For self-consistency: majority vote is taken over execution_results, not over program strings
# i.e., two different programs that produce the same numeric answer count as agreement
assert len(execution_results) == k_sc  # exactly K samples before majority vote

# AQuA hybrid: PoT computes intermediate numeric result, CoT then selects the multiple-choice answer
# The numeric result must be passed as input to the second LLM call, not guessed
assert aqua_intermediate_value == execute(pot_program)  # not re-derived

Complexity:
time | O(L) LLM generation where L = program length; O(P) Python execution where P = program ops | per query
space | O(K * L) for self-consistency (K=40 programs stored) | bounded by few-shot prompt + K program outputs
parallelism | K self-consistency samples are independent; trivially parallel across queries | no inter-sample dependency

Failure modes (from paper section 3.3, Figure 7):
Value grounding errors (47% of failures): LLM assigns wrong numeric value to a variable from question text
Logic generation errors (33% of failures): LLM generates incorrect computation graph / wrong formula
Combined errors (15%): both value and logic wrong simultaneously
Silent wrong-answer: program executes without exception but returns incorrect result; no runtime signal
AQuA hybrid fragility: if PoT intermediate is wrong, second-stage CoT answer selection is also wrong
Zero-shot degradation: without exemplars, model may generate comments instead of executable code (mitigated by '#' suppression)
Model sensitivity: smaller models (CodeGen-16B-mono) show larger PoT-vs-CoT gap on financial QA than math QA

Implementation pitfalls (do NOT do this):
Do NOT extract the answer from the LLM's text output after the program; only use interpreter execution result
Do NOT allow the LLM to perform arithmetic inline in text (e.g., "therefore 3 * 47 = 141") — delegate all computation to interpreter
Do NOT use CoT-style prompts with PoT exemplars; exemplars must be (question, python_program) pairs
Do NOT apply majority vote over program strings (lexical vote); vote over execution results (semantic vote)
Do NOT skip the Python interpreter and treat the program as documentation; execution is mandatory
Do NOT use temperature > 0 for greedy/single-answer mode; only set temperature=0.4 when K > 1
Do NOT hard-code variable names; PoT's correctness benefit comes from semantically meaningful variable names that ground reasoning

D-11 constructive checker registry binding:
PoT establishes Python interpreter as ground truth for arithmetic/numerical claims.
Executable check = generate Python snippet expressing the numerical claim, execute via subprocess or exec(), compare result to expected.
Value grounding (variable assignment from claim text) is the dominant failure mode (47%); checker must verify variable binding explicitly.
Self-consistency optional: for D-11 single-shot checks, greedy decoding (temperature=0) is sufficient and matches paper's main result setup.
