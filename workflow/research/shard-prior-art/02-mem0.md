2. PROBLEM IT SOLVES
====================================================================

Target failure mode (paper abstract): LLMs have fixed context windows, so they cannot maintain consistency across prolonged multi-session dialogues. Stuffing the full transcript into context (the "full-context" baseline) is accurate but slow and token-expensive; naive RAG over the raw transcript retrieves noisy chunks. [C1][C3]

Mem0's thesis: dynamically EXTRACT salient facts from conversation, CONSOLIDATE them (dedup/contradiction resolution), and RETRIEVE only the relevant subset — trading a small accuracy delta for a large latency/cost reduction at scale. The paper frames this as the practical-deployment tradeoff ("Production-Ready"). [C1][C3]

The full-context baseline it positions against: p50=9.870s, p95=17.117s latency, 26,031 tokens per query. Mem0 targets ~1,764 tokens and p95=1.440s. [C3]

3. HOW IT WORKS — ARCHITECTURE & KEY MECHANISMS
====================================================================

Two storage tiers exist: (A) the open-source self-hosted SDK (the `Memory` class) and (B) the hosted managed platform (`MemoryClient`). This dossier grounds (A) from source code + paper, and notes (B) from docs.

--- 3.1 Two-phase pipeline (paper method, Mem0 base) ---
[C3, paper HTML method section]

EXTRACTION PHASE: an LLM-based extraction function (denoted phi in the paper) processes the latest message pair (m_{t-1}, m_t) plus two contextual inputs:
  - a conversation summary S retrieved from the database ("global thematic understanding across the entire conversation")
  - a sliding window of recent messages {m_{t-m}, ..., m_{t-2}} ("granular temporal context")
The prompt is P = (S, {m_{t-m}...m_{t-2}}, m_{t-1}, m_t). A summary-generation module runs ASYNCHRONOUSLY so summary refresh is off the hot path. Output is a set Omega of candidate memories. [C3]

UPDATE PHASE: each candidate fact is compared against the top s=10 semantically-similar existing memories (vector retrieval), then an LLM tool-call (`ClassifyOperation` in the paper) chooses ONE of four operations: [C3]
  - ADD    — no semantically equivalent memory exists -> create new
  - UPDATE — augment an existing memory with complementary info
  - DELETE — remove a memory contradicted by the new info
  - NOOP   — candidate needs no change
This is the A.U.D.N. cycle. The LLM is the decision-maker; Mem0 supplies it the candidate + the k nearest existing memories and lets it pick the "tool". [C3][secondary C9]

Models used in the paper's reference config: GPT-4o-mini for LLM inference, text-embedding-3-small for embeddings. [C3]

--- 3.2 Graph-memory variant (Mem0^g) ---
[C3, paper HTML]

Structure: a directed labeled graph G = (V, E, L). Nodes V are entities (people, locations, concepts); edges E are relationships; L assigns semantic type labels. [C3]
Components:
  - Entity extractor — identifies key information elements
  - Relationship generator — derives relationship triplets between extracted entities
  - Conflict-detection module — flags potentially conflicting relationships when new info arrives
  - Dual retrieval — an entity-centric method AND a semantic-triplet method
Database: Neo4j is the underlying graph store. [C3]
Update strategy (verbatim spirit): for each new relationship triple, compute embeddings for source and destination entities, search for existing nodes with semantic similarity above a threshold t, and merge/attach accordingly. [C3]
Conflict handling is SEMANTIC (embedding-similarity over entity nodes + relationship contradiction), not syntactic string-match. [C3]

--- 3.3 Actual current source code (diverges from / extends the paper) ---
[C11, raw mem0/memory/main.py on main branch]

Classes: `Memory` (sync) and `AsyncMemory` (async).
Public methods (exact signatures from source):
  - add(self, messages, *, user_id=None, agent_id=None, run_id=None, metadata=None, infer=True, memory_type=None, prompt=None)
  - search(self, query, *, top_k=20, filters=None, threshold=0.1, rerank=False, **kwargs)
  - get_all(self, *, filters=None, top_k=20, **kwargs)
  - get(self, memory_id) / update(self, memory_id, data, metadata=None) / delete(self, memory_id)
  - delete_all(self, user_id=None, agent_id=None, run_id=None)
  - history(self, memory_id) / reset(self) / close(self)
Internal pipeline methods:
  - _add_to_vector_store(...)  — "handles batch pipeline with phases 0-8"; this is where ADD/UPDATE/DELETE are decided from the LLM's JSON response, with HASH-BASED DEDUPLICATION at Phase 5 preventing exact duplicates BEFORE the LLM is consulted. [C11]
  - _create_memory / _update_memory / _delete_memory / _search_vector_store
  - graph wiring: _upsert_entity, _link_entities_for_memory, _remove_memory_from_entity_store
Factory pattern for pluggable backends: `EmbedderFactory`, `VectorStoreFactory`, `LlmFactory`, `RerankerFactory`. History is persisted in SQLite via `SQLiteManager`. [C11]

KEY DIVERGENCE FROM PAPER: the shipping code adds (a) a reranker stage (rerank flag + RerankerFactory), (b) hash-based dedup as a cheap pre-filter at Phase 5, and (c) an explicit search `threshold=0.1`. None of these three appear in the paper's method description. The shipping pipeline is "phases 0-8", richer than the 2-phase paper abstraction. [C11 vs C3]

--- 3.4 Storage topology (hybrid) ---
Mem0 stores extracted facts across THREE store types: a vector DB (semantic retrieval), a key-value/SQLite store (history + metadata), and optionally a graph DB (relationships). The factory classes make each backend swappable (Qdrant is the hosted default vector store). [C2 README, C11 source, secondary C-search]

--- 3.5 Identity scoping ---
Memories are scoped by user_id / agent_id / run_id, so the same store partitions per-user, per-agent, per-session. Retrieval filters on these. [C11 signatures, C5 docs]

4. CORE API / USAGE (verbatim-in-spirit, from docs + source)
====================================================================

Open-source self-hosted (from docs quickstart [C5] and source [C11]):

    from mem0 import Memory

    m = Memory()                                # no required args; config via dict/env
    m.add(messages, user_id="alex")             # extract + consolidate (infer=True default)
    results = m.search("What do you know about me?", filters={"user_id": "alex"})

Fuller surface (signatures verbatim from main.py [C11]):

    m.add(messages, user_id=None, agent_id=None, run_id=None,
          metadata=None, infer=True, memory_type=None, prompt=None)
    m.search(query, top_k=20, filters=None, threshold=0.1, rerank=False)
    m.get_all(filters=None, top_k=20)
    m.get(memory_id) / m.update(memory_id, data) / m.delete(memory_id)
    m.history(memory_id)        # returns the change log for one memory (SQLite-backed)

infer=False bypasses the LLM extraction/conflict step and stores raw — docs WARN that mixing infer=True and infer=False for the same fact saves it twice (duplicate protection only runs in the inference path). [C8]

Hosted variant: `MemoryClient` / `AsyncMemoryClient` against the managed API (same verb surface, server-side stores). Docs note open-source vs hosted differ but the section fetched did not enumerate the delta. [C5 — partial]

7. VERSUS SHARD's MEMORY GOVERNANCE PILLAR
====================================================================

(SHARD specifics per requester brief. Mem0 facts per sections 3-5.)

7.1 STALENESS / AGING
  - SHARD: explicit quantitative staleness = (now - last_verified) / expected_lifetime, with flag>1.0 and quarantine>2.0. A first-class, computable, time-decay governance signal with a quarantine state.
  - Mem0: NO time-decay or expiration mechanism surfaced in docs or source. Conflict resolution is "latest truth wins" via LLM inference at write time. [C8] Memories carry history (SQLite via SQLiteManager [C11]) and can be UPDATE/DELETE'd, but there is no per-memory staleness score, no expected_lifetime, and no quarantine tier.
  - VERDICT: SHARD's staleness model is a capability Mem0 LACKS entirely. Mem0 governs by overwrite-on-contradiction, not by aging. This is SHARD's clearest differentiator on this pillar.

7.2 CONFLICT DETECTION
  - SHARD (per requester): repo implements only SYNTACTIC conflict detection.
  - Mem0: conflict detection is SEMANTIC — embedding similarity over candidate vs top-10 existing memories (base) and over entity nodes / relationship triplets (graph variant, threshold t). The LLM then classifies ADD/UPDATE/DELETE/NOOP. [C3][C11]
  - VERDICT: Mem0 is STRONGER here. SHARD's syntactic-only conflict detection is a simplification Mem0 already surpasses with embedding-based semantic matching + an LLM adjudicator. SHARD could borrow Mem0's top-k-then-LLM-classify pattern (the A.U.D.N. cycle) to upgrade from syntactic to semantic conflict detection.

7.3 COORDINATION (DECLARE-REVIEW-EXECUTE)
  - SHARD: a DECLARE-REVIEW-EXECUTE coordination protocol with semantic conflict detection across writers.
  - Mem0: no multi-writer coordination protocol. Concurrency safety is per-memory (hash dedup at Phase 5, last-write-wins). There is no declare/review staging. [C11]
  - VERDICT: SHARD's coordination layer is ABSENT in Mem0. Mem0 is single-pipeline write-through; SHARD adds a governance handshake Mem0 does not model.

7.4 TRUST TIERS (T1-T4)
  - SHARD: T1-T4 skill trust tiers.
  - Mem0: no trust/provenance tiering on memories. Scoping is by identity (user/agent/run), not by trust level. [C11]
  - VERDICT: trust tiering is SHARD-only. Mem0 treats all memories as equally authoritative once stored.

7.5 SAFETY-CONSTRAINED SELF-IMPROVEMENT
  - SHARD (per requester): safety-constrained self-improvement with .bak rollback + 0-3 scoring; composition.py cross-subsystem self-healing cascade. (Requester also notes SHARD's repo has NO self-improvement loop yet — i.e. designed but unimplemented.)
  - Mem0: no self-improvement loop, no scoring of its own edits, no rollback-of-policy. Memory history IS auditable (SQLiteManager.history) which is a rollback PRIMITIVE for data, but not a self-improvement controller. [C11]
  - VERDICT: neither system has a working self-improvement loop. SHARD has the design (rollback + 0-3 scoring) on paper; Mem0 has none. Even-to-SHARD here, leaning SHARD on intent.

7.6 WHAT MEM0 DOES BETTER (net)
  - Production hardening: pluggable backend factories (vector/graph/kv/reranker swappable), hosted+self-hosted parity, measured latency/token wins, 186M API calls/quarter. [C4][C10][C11]
  - Semantic conflict resolution + graph relationship modeling out of the box. [C3]
  - Auditable per-memory history. [C11]

7.7 WHAT SHARD DOES BETTER (net)
  - Quantitative time-based staleness with quarantine (Mem0 has nothing).
  - Multi-writer DECLARE-REVIEW-EXECUTE coordination (Mem0 is last-write-wins).
  - Trust tiering (Mem0 is flat-authority).
  - Designed self-improvement w/ rollback+scoring (Mem0 has only data history, no controller).

7.8 CONCRETE BORROW LIST for SHARD (grounded suggestions)
  - Upgrade SHARD's syntactic conflict detection to Mem0's top-k-retrieve-then-LLM-classify A.U.D.N. pattern (raises recall on paraphrased contradictions). [C3]
  - Adopt Mem0's async summary-generation off the hot path so governance checks don't block writes. [C3]
  - Use a factory/adapter seam (like VectorStoreFactory/RerankerFactory) so SHARD's store backend is swappable without touching governance logic. [C11]
