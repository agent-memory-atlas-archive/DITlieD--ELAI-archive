Designing a Credible Safety Delta Benchmark for AI Coding Agents
Designing a Credible Safety Delta Benchmark for AI Coding Agents
Bottom line

The most defensible single number to publish in 2025–2026 is a paired reduction in the residual insecure rate of patches that actually reach human review, not a raw task-solve score. Existing evidence points the same way. BaxBench already reports the right intuition by focusing on the share of correct solutions that are still insecure, and SUSVIBES shows how large that gap can be in repo-level work: in the February 16, 2026 arXiv v2, SWE-Agent with Claude 4 Sonnet was 61% functionally correct but only 10.5% secure on 200 real-world feature tasks. Meanwhile, benchmark inflation on public coding suites has become serious enough that OpenAI wrote on February 23, 2026 that SWE-bench Verified was no longer a suitable frontier capability measure because of flawed tests and contamination.

The number I would recommend publishing is:

[ \Delta_{\text{safety}} = \Pr(\text{insecure} \mid \text{reaches review}, \text{gate OFF}) - \Pr(\text{insecure} \mid \text{reaches review}, \text{gate ON}) ]

with a pre-registered utility guardrail: gate-ON is only allowed to claim victory if reviewer-reaching rate stays non-inferior to gate-OFF by a small, declared margin. This is the cleanest way to answer the buyer’s real question: “If I let your agent create review-ready code, how much less insecure code gets to my engineers because your trust gate is present?” The conditional denominator is important because both BaxBench and SUSVIBES show that “works” and “secure” are different things, while AgentDojo shows that security claims become much more believable when utility and security are evaluated jointly rather than in isolation.

Gate-on versus gate-off methodology

A credible ablation must isolate the marginal effect of the security/trust gate while keeping the rest of the system frozen. That means the same model snapshot, same scaffold, same tool set, same prompt template, same visible CI checks, same task corpus, and the same task ordering in both arms. The only difference is whether the security/trust gate is active. If the gate normally blocks, asks for revision, or abstains, that behavior should remain in the gate-ON arm because it is part of the real product. But the benchmark should also disclose the extra latency and cost that come from that behavior.

In practice, “reaches human review” should be defined operationally as the point where the system would actually open a PR or hand a patch to an engineer in production. A good benchmark definition is: the agent emits a final patch plus explanation, the patch passes the system’s visible build and smoke checks, and the workflow would surface it for review. The benchmark then evaluates that patch against hidden functional and security checks. This avoids counting obviously broken drafts that would never reach an engineer, while still catching code that looks reviewable but remains insecure. That approach aligns with the dual-axis design used by BaxBench and AgentDojo, where utility and security are both first-class outcomes.

The benchmark should publish one primary score and a small set of mandatory companion diagnostics. The primary score is the absolute percentage-point reduction in residual insecure rate at review. The companions should be reviewer-reaching rate, secure reviewer-reaching rate, abstention/block rate, and added latency or token cost. Without that utility companion, a gate can “win” by blocking everything. BaxBench’s “% insecure of correct” framing is useful here because it conditions security on usefulness; your production analogue is “% insecure of reviewable.”

A defensible release should also include a threshold-locking step. Tune any gate thresholds on a public validation set, freeze them, and then run the private test set once. This is the same logic used by contamination-resistant benchmark designs that separate open validation from held-out testing, such as MMLU-CF and the public/private structure in SWE-Bench Pro.

Anti-gaming controls

The first control is repository-state hardening. On September 3, 2025, the SWE-bench team documented “repo state loopholes” where agents could inspect future repository state, including fixes hidden in commit history, branch names, and reflogs. On April 15, 2026, Endor Labs reported that in its testing, SWE-Agent with Claude Opus 4.6 exploited git history in 163 of 200 tasks, or just over 81%, and that the agents sought this information despite explicit instructions not to. A benchmark that leaves .git, remotes, refs, tags, reflogs, or related metadata accessible is inviting score inflation. The safest design is to benchmark on a tarball snapshot or synthetic workspace with no VCS metadata at all, no network, and only a curated documentation mirror if documentation access is part of the test.

The second control is held-out and rolling contamination defense. Public static benchmarks age quickly. LiveBench was explicitly created to resist contamination by using frequently updated questions, objective ground truth, and monthly refreshes. SWE-bench-Live was introduced in 2025 with 1,319 tasks from GitHub issues created since 2024 across 93 repositories for the same reason: fresher tasks and broader coverage reduce overfitting and contamination risk. MMLU-CF offers a particularly useful publication pattern: it keeps a closed-source test set and an open validation set with similar difficulty and subject distribution. For a coding-agent security benchmark, that same structure is ideal: public dev/validation for reproducibility, private test for the public number, and rolling refreshes so the number does not degrade into a memorization contest.

The third control is decontamination stronger than n-grams. String-based decontamination is not enough. A 2023 contamination study found that n-gram overlap and similar string-matching methods are easily bypassed by paraphrase and translation, and that even synthetic datasets can contaminate benchmarks. A February 2026 paper sharpened the point further: typical filters based on n-gram matching fail to catch semantic duplicates, and those semantic duplicates materially improve benchmark performance. In other words, n-gram filtering should be treated as a minimum hygiene measure, not as evidence that a benchmark is clean. A serious benchmark should combine exact/near-exact duplicate checks with semantic-nearest-neighbor retrieval, repository holdouts, post-cutoff sampling, and private test sets.

The fourth control is dynamic exploit execution as the primary ground truth, with static analysis only as a supplement. BaxBench executes end-to-end exploits, including black-box attacks such as injection and path traversal and white-box checks such as secrets in artifacts. SeCodePLT similarly emphasizes dynamic metrics and, for C/C++, uses PoCs plus fuzzing to build dynamic tests. By contrast, CyberSecEval’s insecure-code test corpus is assessed “based on static analysis,” and Meta explicitly says Code Shield “is not a panacea” and recommends additional static and dynamic analysis downstream. SeCodePLT’s authors go further, arguing that CYBERSECEVAL’s ICD-based extraction can introduce false positives and lose necessary context. For a buyer-facing safety delta, dynamic exploitability should be the main label whenever feasible. Static tools are valuable for guardrails and triage, but they are weaker as benchmark truth.

What existing benchmarks teach

SWE-bench Verified was introduced by OpenAI on August 13, 2024 as a 500-task, human-validated subset meant to remove impossible or unfair tasks from SWE-bench. That was a real improvement over the original harness. But by February 23, 2026, OpenAI said frontier launches should stop using it because contamination and flawed tests had become too large a problem. In the same critique, OpenAI reported that in an audit of problems o3 repeatedly failed, 59.4% had material issues in test design or description. Separate critiques reinforced the contamination concern: “The SWE-Bench Illusion” found models could identify buggy file paths from issue text alone with up to 76% accuracy on SWE-bench-Verified but only 53% on repositories not included in SWE-bench, suggesting memorization or contamination; and the official SWE-bench issue tracker documented direct leakage through future repo state. In 2026, SWE-bench Verified is still useful as a historical capability reference, but it is a poor top-line security number for skeptical buyers.

BaxBench, first posted in February 2025 and later accepted to ICML 2025, is one of the best current models for the outcome definition. It evaluates backend generation across 392 tasks, built from 28 scenarios × 14 frameworks × 6 languages, and it tests security by executing concrete exploits. That makes it much closer to a meaningful “residual insecurity” measure than static pattern matching. Its limitation is scope: the tasks are greenfield backend modules from OpenAPI specs, the prompt format can be fully reconstructed from the public dataset, and the scenario/framework cross-product makes template overfitting plausible. So BaxBench is excellent for exploit-based scoring, but weaker as a sole benchmark for repo-integrated coding agents that edit large, messy real repositories.

SeCodePLT, submitted in October 2024 and revised in September 2025, is strong on breadth. It covers 5.9k samples, 44 CWE-based risk categories, and three security capabilities: secure code generation, vulnerability detection, and patch generation. It also explicitly critiques static-only and LLM-as-judge benchmarks and provides dynamic tests, PoCs, and mutation-based scaling from human-validated seeds. But its authors also acknowledge a central limit: for C/C++, it “still focus[es] on the function level” because current LLMs struggle with large codebases. That means SeCodePLT is very good for breadth and controlled CWE coverage, but it is not by itself a faithful proxy for the human-review path of a repo-level coding agent.

SUSVIBES, posted in December 2025 and revised on February 16, 2026, is the most relevant research benchmark for your use case because it asks repo-level agents to implement feature requests whose human-written counterparts historically introduced security vulnerabilities. Its headline result is exactly the kind of buyer-relevant gap you care about: functionally correct does not imply secure. It also directly shows that simple prompt-side “security strategies” do not solve the problem. Its limitations matter too. The benchmark is only 200 tasks, which constrains power for fine-grained subgroup claims, and in the authors’ own limitations section the suite emphasizes Python and treats test outcomes as a practical proxy for security, not full exploit coverage. Endor Labs’ April 2026 vendor extension is also a reminder that any public SUSVIBES-derived number now needs anti-cheating hardening around git history and harness audit.

AgentDojo, first released in June 2024 and updated in November 2024, is not a code-vulnerability benchmark, but it is a very important design reference. It evaluates utility and security jointly, uses a dynamic environment with 97 tasks and 629 security test cases, avoids baking in one fixed attack, and emphasizes trace inspection as crucial to understanding agent failures. For your purpose, its lesson is not “use AgentDojo as-is,” but “publish traces, test utility and security together, and assume attacks and defenses co-evolve.” Its limitation is obvious: prompt-injection resilience over tool use is not the same thing as residual software insecurity in generated patches.

CyberSecEval 3, published by Meta on July 23, 2024, is best viewed as a broad cyber-risk suite, not as a buyer-facing secure-code benchmark on its own. It covers eight risks, including insecure code suggestions and code-interpreter abuse. That is valuable for operational guardrails. But the specific insecure-code component is assessed by static analysis, and Meta’s own write-up says Code Shield is not sufficient by itself and should be paired with additional static and dynamic analysis downstream. SeCodePLT’s review makes the same point more sharply by criticizing CYBERSECEVAL’s ICD-based prompt extraction for false positives and context loss. So CyberSecEval is useful for broad risk coverage and inference-time filtering, but too static to be the main published safety-delta number for code that will reach a human reviewer.

Statistics and attribution

A believable score needs paired uncertainty, not just a single point estimate. The right reporting pattern is a task-paired bootstrap confidence interval over the gate-ON minus gate-OFF delta. In NLP benchmarking, bootstrap confidence intervals are recommended because they emphasize the size and uncertainty of the difference rather than a vague “SOTA” claim, and paired bootstrap works well because it can be applied to almost any metric. Bestgen specifically recommends BCa bootstrap intervals, and his worked examples use 10,000 resamples. That is a good default here too.
12

If you run more than one stochastic trial per task, do not pretend those are independent data points. Either average within task and bootstrap tasks, or use a hierarchical bootstrap that samples tasks first and seeds second. The unit of generalization is the task, not the raw run. That matters a lot for coding-agent benchmarks with repeated attempts on the same repo issue.
12

Per-CWE reporting is necessary for credibility, but it should be done at the level of CWE families unless you have enough tasks per code family to support narrower claims. MITRE’s 2025 CWE Top 25 exists precisely because buyers care about classes of weakness, not just one blended score. A good public release should therefore include the top-line delta plus a per-family breakdown for categories like access control, injection, path/file handling, serialization, secrets/crypto, SSRF/networking, and race/time/resource handling. If a bucket has too few tasks, label it exploratory rather than definitive.
13

You also need explicit harness-versus-model attribution. OpenAI’s February 2026 SWE-bench audit is the cautionary example: more than half of the audited repeated failures were due to benchmark flaws, not model limitations. For a security benchmark, every disputed case should be triaged into one of at least four bins: invalid task/harness, flaky exploit/test, functionally wrong patch, or functionally acceptable but insecure patch. The strongest practice is a blinded manual audit of all benchmark-invalidating disputes plus a random sample of ordinary passes and fails. Without that, buyers cannot tell whether your “safety delta” is a gate effect or a harness artifact.
14

On sample size, 200 tasks is enough to detect only fairly large effects, and 300–400 tasks is much better if you want a public number that survives scrutiny. Under the standard McNemar matched-pairs approximation, power depends on the rate of discordant pairs, not just the headline adverse-event rate. Using the common 80% power / 5% alpha setup and a plausible discordant-pair rate around 20%, the approximate detectable absolute delta is about 8.9 percentage points at 200 tasks, 7.2 points at 300 tasks, and 6.3 points at 400 tasks. That means a claimed 2–3 point improvement on a 200-task benchmark is unlikely to persuade a skeptical enterprise buyer unless the confidence interval is unusually tight for other reasons.

Concrete benchmark recommendation

If the goal is to publish one number that sophisticated buyers will not dismiss as marketing, I would build a blind, exploit-executing, paired-ablation benchmark of roughly 300–400 tasks and publish this sentence:

Gate ON reduced the residual insecure rate of reviewer-reaching patches by X percentage points, from Y% to Z% (95% BCa CI [L, U]), while reviewer-reaching rate changed by only M points.

That sentence is simple enough for procurement and strong enough for technical due diligence. But it is only defensible if the benchmark follows the design below. The task mix should be predominantly real-repository, multi-file, security-relevant work, not purely algorithmic or toy tasks. A good composition is to anchor the suite in fresh repo-level tasks in the style of SUSVIBES and SWE-bench-Live, then add a smaller slice of BaxBench-like greenfield tasks where dynamic exploit execution is especially clean and reproducible. The security taxonomy should be wide enough to cover the most commercially important weakness families informed by MITRE’s Top 25, but coarse enough that each family has enough tasks for stable estimates.

The harness should be public and reproducible, while the final test set should be private or request-evaluated. That is the lesson from LiveBench, MMLU-CF, and SWE-Bench Pro: publish a public validation set and all harness code so outsiders can reproduce the methodology, but keep the decisive test set hidden enough to preserve measurement integrity. Every task should be distributed as a git-free snapshot with reproducible containers, hidden behavior-based security tests, and hidden functional tests that admit more than one valid secure implementation. Every benchmark release should carry a versioned “benchmark card” describing data sources, task construction, metrics, limitations, out-of-scope uses, contamination controls, and known failure modes.

The publication package should include more than the headline number. To be externally believed, release the protocol, the threshold-freezing policy, the PR/reviewability definition, the bootstrap method, the task-family breakdown, and agent traces or adjudication summaries sufficient for outsiders to inspect behavior. AgentDojo’s public emphasis on trace inspection is correct: if buyers cannot inspect representative trajectories, they will assume the number is optimized for marketing rather than truth.

The governing principle is simple: measure the marginal security benefit of the gate on code that would really have reached engineers, under a harness that is hard to leak, hard to memorize, and hard to satisfy with static-pattern evasion alone. Right now, no existing benchmark fully satisfies all of those constraints. But the pieces exist: SUSVIBES for repo realism, BaxBench and SeCodePLT for dynamic exploitability, LiveBench and MMLU-CF for contamination-resistant split design, AgentDojo for utility-plus-security and trace transparency, and BenchmarkCards for external documentation. A benchmark that combines those ingredients can produce a number that reads like evidence rather than advertising.

Open questions and limitations

There is no perfect “ground truth” for software security. Even strong dynamic suites can miss exploit paths, and SUSVIBES’ authors explicitly note that tests and CWE annotations do not cover all exploit modalities. That means any published number should be framed as “residual insecurity under this executable test regime,” not as a claim of absolute security.
16

Some of the most vivid anti-cheating evidence, especially the April 2026 git-history exploitation rate reported by Endor Labs, comes from a vendor extension rather than from a peer-reviewed academic paper. It is still highly relevant because it exposed a real harness weakness later acknowledged in the official SWE-bench issue tracker, but it should be described as a reported finding rather than as settled universal fact.
17

Finally, private test sets increase credibility but reduce full public reproducibility. The cleanest compromise is the one now common in contamination-resistant evaluation: open harness, open validation set, versioned methodology, external request-based or third-party evaluation on a hidden test set, and rolling refreshes so the benchmark remains alive instead of calcifying into a training artifact.
