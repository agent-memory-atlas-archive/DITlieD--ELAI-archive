A Verifiable and Tamper-Evident Trust Spine for ELAI
Executive assessment

The strongest practical answer in 2025–2026 is not a single “agent trust” standard. It is a layered spine built from mature supply-chain attestation standards, deterministic or replayable orchestration, independently captured runtime evidence, and explicit information-flow controls at privileged sinks. The standards side is comparatively mature: in-toto’s attestation framework exposes a stable Statement/Predicate/Envelope model, SLSA defines provenance and Verification Summary Attestations, and Sigstore provides keyless signing, bundles, transparency logging, and offline verification workflows. What is still immature is the agent-specific schema layer: the provenance community is still discussing bundle semantics and even has a fresh May 2026 RFC for an agent-decision predicate, which is a strong signal that cross-vendor agent attestation is still emerging rather than finished.

For ELAI, the right design principle is to treat the agent’s own natural-language claims as untrusted narration. A verifier should trust only what it can independently validate: digests, signatures, transparency-log inclusion proofs, pinned model/version identifiers, workflow histories, coverage counters, runtime traces, and sink-guard decisions captured by code outside the model’s own text channel. Recent provenance surveys in the agent literature make the same point from a different angle: final-answer accuracy is not enough, and trustworthy agents need evidence tracing, tool-use provenance, observability, and process-level accountability rather than self-reported success.

A concise maturity picture looks like this:

Area	Best current answer	Maturity
Build and artifact provenance	in-toto Statement/DSSE + SLSA Provenance + Sigstore bundle/Rekor + external roots of trust	Production-ready for general software provenance.

Delegated verification	SLSA Verification Summary Attestation issued by a trusted verifier	Stable spec, moderate deployment density.

Agent-run binding	Custom in-toto predicate URI for agent-run/v1 plus Link/RuntimeTrace/TestResult/SCAI statements	Adoptable now, but schema is custom.

Deterministic replay	Durable execution history plus captured seeds/model pins/tool I/O	Moderately mature, but exact replay is limited for hosted LLM APIs.

Off-agent execution evidence	Coverage counters, OpenTelemetry spans/events, runtime traces, append-only collector outputs	Mature components, emerging agent conventions.

Taint / provenance guardrails	CaMeL, FIDES, RTBAS, and newer offline auditors such as NeuroTaint	Research frontier; useful today for high-risk tools, but not yet a settled ecosystem standard.
Provenance and attestation as the core spine

The most mature building block is the in-toto attestation model. The current spec README identifies v1.2 as the latest version and describes the four-layer structure clearly: a Predicate contains arbitrary metadata, a Statement binds that metadata to immutable subjects by digest, an Envelope authenticates it, and a Bundle groups multiple attestations together. Critically for ELAI, the Statement model lets you use any predicate URI you control, which means you do not have to wait for the ecosystem to standardize a perfect agent schema before you can start shipping verifiable run attestations.

For signatures, the in-toto spec recommends DSSE v1.0 as the envelope format. That recommendation is important because the in-toto envelope requirements explicitly prefer authenticated payload types, verification without pre-parsing, and support for multiple signatures in a single envelope. The same section also notes an important caveat for implementers who are tempted to use Sigstore bundles as the only envelope: Sigstore bundles support DSSE, but they are not fully ITE-5 compliant because they currently require a single signature in the envelope. In practice, that means ELAI should use DSSE envelopes as the source-of-truth archival format if you want threshold signing or multiple witnesses, and then optionally publish a Sigstore bundle for public-log verification and distribution.

SLSA sits naturally on top of this model. The SLSA provenance predicate is defined as an in-toto predicate type and is explicitly meant to let consumers verify that an artifact was built according to expectations and, if desired, rebuild it. The SLSA build specs are now in an Approved state in the v1.2 documentation, and the build-track basics make the trust model very explicit: Build Level 2 requires the hosted build platform itself to generate and sign provenance, while Build Level 3 adds stronger isolation so one run cannot influence another and user-defined steps cannot access provenance-signing secrets. That is exactly the kind of externalized trust boundary ELAI needs: the verifier should trust the builder identity and platform controls, not the agent’s own report that “I compiled this correctly.”

SLSA’s Verification Summary Attestation is especially valuable for an agent harness because it formalizes a pattern you very likely want: a trusted verifier evaluates the artifact plus an attestation bundle against a policy and then emits a short, signed summary that downstream consumers can trust without re-running the full policy evaluation. The VSA spec says exactly that: it lets consumers delegate complex policy decisions to a verifier they trust and lets the verifier summarize transitive dependency levels as well. For ELAI, that means your independent verifier can issue a VSA that says, in effect, “this result was produced by an approved harness build, replayed against the archived run bundle, and passed the no-untrusted-to-destructive-sink policy.”

Sigstore gives you the public transparency and offline-verification layer. Its overview documentation explains the keyless flow: Fulcio issues a short-lived certificate bound to an identity, the signing event is logged in Rekor, and verifiers validate the signature, certificate, identity, and Rekor inclusion proof. The bundle format page is equally important for an offline verifier: a Sigstore bundle is meant to carry everything required to verify a signature, including the certificate or public-key identifier, transparency-log entries, the signed entry timestamp, inclusion proof, checkpoint, and canonicalized body. That means ELAI’s verifier can operate without trusting the agent to “look up” anything at verification time as long as the bundle and trusted roots are archived alongside the run.
10

On the Rekor side, the 2025–2026 story is “usable, but still mid-migration.” Rekor v2 is real and deployed, but the public-good instance is sharded and the service explicitly warns clients not to hardcode the URL. The rekor-tiles repository tells clients to discover the active instance through the TUF-distributed SigningConfig and to fetch shard public keys from the TrustedRoot. The same docs say witnessing is planned but that the initial launch of Rekor v2 does not yet have witnessed checkpoints, while future co-signed checkpoints are expected to provide strong offline inclusion evidence. Through early 2026, Sigstore milestones still showed the v2 migration, default-client behavior, and witness support as active work rather than fully closed work. The operational conclusion for ELAI is straightforward: use Rekor v2, but archive the bundle, checkpoint, current trust root, and signing config snapshot with every released verifier bundle so you are not coupled to live network discovery later.
11

The correct way to bind all this to an agent run is to create a root run manifest as a custom in-toto predicate, signed in a DSSE envelope. That manifest should include the immutable run_id, the task digest, workspace input digests, harness binary digest, source revision, builder identity, container or Nix environment digest, model pin, tool-registry digest, policy digest, and initial random seed or deterministic history reference. Then, every run step should produce a signed attestation that reuses the same run_id and either references the run manifest as a material or reuses its digest as a target. Use the Link predicate for “a step executed with these materials, byproducts, and environment,” the Runtime Trace predicate for kernel/runtime evidence, the Test Result predicate for claimed checks, and optionally SCAI when you want to bind multiple pieces of evidence to the same subject or assert finer-grained properties of the produced artifact. That composition is directly aligned with the in-toto model and available predicates today.
12

One caution is worth stating clearly: the in-toto project itself is still debating some bundle semantics, with an open issue from January 2025 proposing that bundles should be treated more as a recommendation than as a normative part of the spec, and a May 2026 RFC proposing an agent-decision predicate. That does not undermine the core Statement and DSSE model, which is stable; it just means ELAI should be conservative about inventing a future-proof bundle dialect. Use ordinary signed Statements as the atomic archival unit, and think of any higher-level “run bundle” format as your packaging convention rather than a universal standard.

Reproducible replay and offline re-verification

For an agent system, it helps to separate two goals that are often conflated. The first goal is trace authenticity: proving that a particular sequence of model calls, tool invocations, and outputs really happened and was not tampered with after the fact. The second is full recomputation: letting a third party re-run the same agent offline and obtain the same result. The first is achievable today with strong confidence. The second is achievable only when you control enough of the stack to pin or record the nondeterminism, and it becomes much weaker when the agent depends on hosted frontier models. Recent agent provenance work makes this distinction implicit: it argues that trustworthy agents require trace sources, evidence units, execution units, provenance relations, and process-level accountability, precisely because the final answer alone does not let you reconstruct whether the process was justified.

A strong implementation pattern is to make the harness itself a durable, replayable workflow. Temporal’s official workflow docs are useful here even if you do not adopt Temporal directly: they explain that workflow code is replayed from its event history, so it must be deterministic when given the same history, and any nondeterministic operation such as a random number must be captured in history via a side-effect mechanism and replayed from that recorded value instead of being executed again. That is almost exactly what an auditable agent harness needs. The 2025 AgentRR paper makes the same idea explicit in the agent domain: record the interaction trace and internal decision process, then replay from recorded experience rather than from live dependencies.

Where hosted model APIs are involved, the main limitation is vendor nondeterminism and model evolution. OpenAI’s current API docs say chat completions are non-deterministic by default, and that seed plus identical parameters can produce mostly deterministic outputs; they also warn that backend changes can still affect determinism and expose a system_fingerprint field so clients can detect those backend changes. Anthropic’s model docs are stronger on version pinning: every Claude model ID is a pinned snapshot, and older aliases are convenience pointers that resolve to dated IDs. Hugging Face’s hub docs are stronger still for open models: you can download exact files or full snapshots from a specific commit hash. The engineering implication is clear: if ELAI needs exact offline re-verification, treat hosted models as trace-authentication targets, not recomputation targets, unless the provider gives you a sufficiently pinned model identifier plus stable replay semantics. For exact recomputation, prefer open-weight models pinned by repository commit and archive the exact tokenizer/config/weights digests with the run.
14

In concrete terms, a replayable ELAI run archive should contain at least four layers of state. First, it should preserve the workflow history: step order, tool names, arguments, exit codes, retry decisions, and parent/child dependencies. Second, it should preserve model invocation state: provider, model ID, alias resolution, request parameters, seed, backend fingerprint if available, and the exact input-output pair recorded for that step. Third, it should preserve environment state: workspace snapshot digests, tool binary digests, network fetch digests, policy digests, and the signing/trust-root snapshot used during the run. Fourth, it should preserve resulting evidence artifacts: raw logs, stdout/stderr, coverage files, traces, and output files. That archive lets an offline verifier do two different things: either re-run the deterministic skeleton using recorded side effects, or recompute parts of the run against pinned open components and check that the new outputs match the archived digests. This is an inference about how to compose the primitives, but it follows directly from the durable-execution and provenance models above.

The harness itself should also be reproducible. Reproducible Builds guidance for Rust notes that Rust programs are often already reproducible by default when the dependency lockfile is committed, and the ecosystem-wide SOURCE_DATE_EPOCH specification exists specifically to make timestamps deterministic across builds. Nix’s own overview describes its builds as declarative, isolated, and reproducible. For ELAI, that means the verifier should be able to rebuild the harness binary or container image from its source revision, Cargo.lock, and pinned environment description, and then compare the rebuilt binary digest to the attested one. That lets the verifier reduce trust in “the agent binary that produced the evidence” down to trust in reproducible source + environment.

Off-agent evidence and how to make test fabrication detectable

The strongest evidence that “a real entrypoint ran” is evidence the agent did not author in plaintext. The in-toto Runtime Trace predicate was created for this class of need: it describes system events that were part of a supply-chain step and is explicitly intended to prove properties such as “the build was invoked via a script” or “the build ran in a hermetic environment with no network access.” The spec also notes a key operational difference between synchronous monitors such as ptrace, which can pause the process before recording a file digest, and asynchronous monitors such as eBPF, which cannot stop the process before the file is actually used. That distinction matters for ELAI because it tells you when a trace can serve as direct evidence and when it is only post hoc observation.
16

In a Rust coding-agent harness, the easiest off-agent evidence to adopt immediately is coverage instrumentation. The Rust compiler’s coverage mode injects LLVM profiling increments into functions and branches, writes counter results to a profraw file at program termination, and lets LLVM export the results as JSON or lcov with regions, functions, branches, expansions, and summaries. That makes coverage a very strong anti-fabrication primitive: if the agent claims it executed tests::foo, the verifier can inspect coverage output generated by instrumented code rather than rely on the model’s own description of a successful test run.

OpenTelemetry is the next mature piece. The spec defines spans as uniquely identified operations with start and end timestamps, attributes, links, and timestamped events; spans form trees under a root trace. For ELAI, the design pattern is to make each agent run a root span, each tool invocation a child span, and each subprocess/test execution an event-bearing child span whose attributes include digest references to stdin, stdout, stderr, exit code, and produced artifacts. Those spans should be exported to a collector or append-only backend that sits outside the model text channel. If you need a more interchange-friendly graph for postmortem analysis, W3C PROV gives you a vocabulary for entities, activities, and agents and is naturally compatible with the kind of run graph an off-agent verifier wants to reason over.
17

The place where many agentic systems fail is that they stop at “the agent says PASS.” in-toto’s Test Result predicate is a helpful standard structure, but by itself it is not enough to defeat fabrication. The spec defines fields like result, configuration, passedTests, failedTests, and an optional url that may point to a CI run or logs. That is useful for structured reporting, but it does not, on its own, bind a claimed PASS to the bytes actually emitted by the test harness. The correct pattern is therefore to treat the Test Result predicate as the claim layer and pair it with a separate, orchestrator-authored evidence layer.
18

A concrete anti-fabrication design for ELAI is this. The orchestrator, not the model, launches the command under a wrapper that captures the exact raw stdout/stderr byte streams, the exit code, the argv, the cwd, a normalized subset of environment variables, and the timing boundaries. The wrapper then computes digests over the raw streams and stores the raw logs as immutable artifacts. The PASS claim is emitted only if the wrapper observed exit code success under the configured policy. The in-toto Test Result statement then references the tested subject and configuration, while either a custom predicate or a Link byproducts block includes the stdout_sha256, stderr_sha256, exit_code, coverage_profraw_sha256, and the digest of the wrapper executable itself. Because the claim and the evidence are both signed in DSSE envelopes and tied to the same subject digests, a faked PASS becomes detectable: the verifier can recompute the hash of the preserved raw log, compare it to the attested hash, and reject any mismatch. That exact field set is a recommendation rather than a published standard field list, but it is the direct composition that current standards make possible.
18

If you are already building in GitHub Actions, GitHub’s artifact-attestation stack is a ready-made external corroborator. GitHub’s docs say artifact attestations create cryptographically signed claims about an artifact’s workflow, repository, commit SHA, triggering event, and OIDC-derived provenance, and that public repositories use the Sigstore Public Good Instance with a copy of the Sigstore bundle stored by GitHub and written to an immutable transparency log. GitHub also documents offline verification of these attestations and notes that simple artifact upload/download also exposes and checks a SHA-256 digest for workflow artifacts. For ELAI, that means CI-produced logs, archives, or harness binaries can gain an extra off-agent corroboration layer almost for free if you already use GitHub as the external builder.

Data-plane taint tracking and destructive-sink control

The state of the art in blocking “untrusted content flows into destructive actions” moved materially in 2025, but it is still research-grade rather than fully standardized infrastructure. RTBAS, posted in February 2025, adapts information-flow control to tool-based agent systems and adds two novel dependency screeners—LM-as-a-judge and attention-based saliency—to decide whether a tool call preserves integrity and confidentiality. On AgentDojo, it reported prevention of all targeted attacks with about a 2% loss of task utility when under attack. That makes RTBAS an important proof point that source-to-sink reasoning is viable, but its screening mechanisms still depend on model-based judgments, which should make a cautious engineer treat it as a high-value guardrail rather than a complete trust anchor.
20

CaMeL, first posted in March 2025 and revised in June 2025, is the most architecturally compelling inline defense in the set. Its core move is to extract control flow and data flow from the trusted user query, which prevents untrusted retrieved data from altering the program flow. It then adds a capability model around tool calls to prevent private-data exfiltration along unauthorized flows. On AgentDojo, the current abstract reports that CaMeL solves 77% of tasks with provable security, compared with 84% for an undefended system. That is a very strong utility/security trade-off for workflows that can be planned in advance, and it points directly to an ELAI design rule: the model should never be allowed to derive privileged control structure from untrusted tool output.

FIDES, posted in May 2025 and revised in September 2025, is more flexible and arguably closer to what a general coding agent needs. Its paper presents a formal planner model, dynamic taint tracking over confidentiality and integrity labels, deterministic policy enforcement, and “selective information hiding” primitives. The emphasis on deterministic enforcement is important for ELAI because it means the decision to allow or deny a sink should be made by explicit policy state and labels, not by asking the same model one more time whether the action seems okay. FIDES belongs in the “promising but still early” bucket: it is more principled than ad hoc guardrails, but it is still a research planner rather than a drop-in production standard.
21

You should also calibrate expectations with the 2025 adaptive-attacks literature. A NAACL Findings paper from March 2025 evaluated eight defenses against indirect prompt injection and bypassed all of them with adaptive attacks, achieving over 50% attack success rate. That result should make ELAI unusually conservative about any defense that still depends on a model classifier, a heuristic detector, or an informal prompt-level rule. The lesson is not “do nothing”; it is “move trust into architecture, signed evidence, and explicit sink policy whenever possible.”
22

That lesson shows up again in 2026 follow-on work. The January 2026 “CaMeLs Can Use Computers Too” paper argues that strict architectural isolation is the only known robust defense family, extends it to computer-use agents with single-shot planning, and then shows that even with that isolation you still need extra protection against Branch Steering attacks. Meanwhile, the April 2026 NeuroTaint paper argues that classic taint analysis undershoots the real problem because LLM-agent flows include semantic transformation, causal decision influence, and cross-session persistence through memory; its answer is an offline provenance-oriented auditor that reconstructs source-to-sink influence from execution traces and reportedly outperforms FIDES on propagation detection. That is highly relevant to ELAI because it suggests a practical split of responsibilities: use inline IFC-like controls for high-risk sinks, and use richer offline provenance analysis for audits, incident review, and policy refinement.
23

The most concrete way to implement this in a Rust harness is to define taint at the artifact and field level, not at the whole-tool-call level. A tool specification should declare trusted sources, untrusted sources, and privileged sinks. For example, webpage text, code from a pull request, and retrieved README content should enter the run graph with low-integrity labels; user directives, pinned repository state, and harness policy files should enter with high-integrity labels; destructive sinks such as git push, file overwrite outside the sandbox, shell execution with network, secrets access, or sending data to a remote endpoint should be denied if any required argument depends on low-integrity input unless a human approval token is attached. CaMeL provides the architectural insight, FIDES the deterministic policy insight, RTBAS the dependency-screening insight, and NeuroTaint the offline auditing insight. Together they define the state of the art, even though the ecosystem has not yet converged on one standardized implementation.

As a complement, ELAI should also be fuzzed for taint-style vulnerabilities. AgentFuzz’s USENIX Security 2025 results are sobering: across 20 widely used open-source agent applications, it found 34 high-risk 0-days and had 23 assigned CVEs by the time of publication. That is a strong argument for treating source-to-sink policy not only as a correctness problem but as a security-testing problem.

What a Rust ELAI harness should concretely implement

The strongest adoptable 2026 design is a three-plane harness: a control plane that issues attestations and policy decisions, an execution plane that actually runs tools and captures evidence, and a verification plane that can operate completely off-agent and, ideally, on a different machine. This is an architectural recommendation, but it is directly grounded in the trust boundaries described by SLSA, in-toto, Sigstore, and the newer agent-provenance literature.

In the control plane, ELAI should start every run by creating a DSSE-signed agent-run statement under a URI you control, such as https://elai.dev/attestation/agent-run/v1. The manifest should include digests or immutable identifiers for the task, workspace snapshot, harness source revision, harness binary, Cargo.lock, container or Nix environment, model selector, model pin, tokenizer/config, seed, tool registry, and policy set. Then it should emit a Link statement for every meaningful step and reserve higher-level claims like “tests passed” or “final output verified” for separate statements rather than folding them into one opaque blob. This gives the verifier a graph instead of a monolith.

In the execution plane, every tool call should be wrapped by the orchestrator. The wrapper should capture raw stdin/stdout/stderr, exit code, filesystem changes, produced files, and—where feasible—runtime trace evidence and coverage files. Export OpenTelemetry spans from the wrapper and collector, not from model-produced text. If the tool is a test runner, coverage instrumentation should be turned on by policy for the relevant workspace, and the resulting profraw plus exported JSON or lcov should be archived as evidence artifacts. For high-risk tools, apply field-level taint policy before launch, and log the allow/deny decision with the labels and provenance edges that justified it.

In the verification plane, do not depend on the agent runtime for signature verification. Today, that means being pragmatic in Rust: sigstore-rs is still explicitly experimental, not yet stable, and it says it does not handle attestation verification yet. The safest path is therefore to let the Rust harness produce the archived materials and then either invoke cosign verify-blob --bundle ... or a GitHub attestation verifier as an external process, or run a small sidecar verifier written against the more mature Sigstore tooling. Cosign v3 has already moved strongly toward bundle-centric operation, with the bundle-file output becoming required and new-bundle compatibility continuing to improve through 2026.

If ELAI needs the strongest possible “can’t-lie” posture, the independent verifier should be the only component allowed to issue the final trust verdict. The agent may propose a patch, a build, or a test result, but only the verifier should be allowed to mark a run “accepted,” and that verdict should itself be emitted as a signed attestation—ideally a VSA if you can map your checks to a stable policy vocabulary, or otherwise a custom verification-report/v1 predicate. That final separation is what turns the system from “agent says it worked” into “external verifier confirmed it worked by checking independently captured evidence.”

The bottom-line recommendation for ELAI is therefore this: use in-toto DSSE statements as your archival truth, SLSA provenance and VSA as your trust and delegation layer, Sigstore bundles and Rekor v2 as your public transparency and offline-verification layer, a durable event history plus model/tool pins as your replay layer, coverage/OTel/runtime traces as your off-agent evidence layer, and FIDES/CaMeL-style taint controls at destructive sinks. That stack is the closest thing the 2025–2026 ecosystem has to a true “can’t-lie trust spine,” and it is adoptable today with clear boundaries between what is already production-grade and what is still research-grade.
