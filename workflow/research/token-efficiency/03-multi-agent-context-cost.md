Minimizing Inter-Agent Context-Passing Cost in Agentic Software Engineering
What the evidence now supports

The strongest 2026 evidence says the core cost problem in agentic software engineering is not first-pass code generation. It is repeated reading, re-reading, and validating context across turns and across agents. In Tokenomics (arXiv:2601.14470, measured academic), ChatDev traces over 30 software tasks showed that Code Review alone consumed 59.4% of total tokens, while the overall token mix was 53.9% input, 24.4% output, and 21.6% reasoning. In other words, the dominant bill is usually the cost of shipping context around the system, not the cost of producing final code. AGENTTAXO (ICLR 2025 workshop, measured academic) reaches the same qualitative conclusion from a different angle, describing duplicated inter-agent tokens as a “communication tax,” and follow-on synthesis papers summarize its observed input-to-output ratios around 2:1 to 3:1.

A second result matters just as much: spending more tokens in these loops often does not buy proportionate quality. How Do AI Agents Spend Your Money? (arXiv:2604.22750, measured academic) reports that agentic coding tasks consume roughly 1000× more tokens than ordinary code reasoning/code chat, that repeated runs on the same task can vary by up to 30× in total tokens, and that higher cost often saturates or even worsens accuracy rather than improving it. The same paper also reports substantial model-to-model efficiency gaps, with Kimi-K2 and Claude Sonnet 4.5 averaging more than 1.5 million tokens above GPT-5 on the same tasks. That means reducing inter-agent context-passing is not just a prompt problem; it is also a harness, architecture, and model-routing problem.

The source-quality split is important. The most reliable numbers below come from measured academic evaluations on benchmarks or instrumented traces. Anthropic and vendor docs/blogs are still useful, but I treat them as vendor operational guidance or internal evals, not neutral proof. That distinction matters because some vendor guidance about context artifacts is contradicted by newer academic measurement.

Fresh-context subagents and disposable contexts

For fresh-context spawning, the highest-confidence operational guidance is now fairly consistent: use isolated subagents when a side task will generate lots of logs, search results, or file reads that the parent agent will not need to keep verbatim. Anthropic’s Claude Code docs say subagents run in their own context window, are appropriate when a side task would “flood” the main conversation, and should return only a summary. The same docs also say the main conversation is better when the task needs frequent back-and-forth, shares substantial context across phases, is a quick targeted change, or when latency matters. Anthropic’s context-engineering guidance adds a concrete scale estimate: subagents may spend tens of thousands of tokens internally but return only a 1,000–2,000 token distillation. That is vendor guidance rather than controlled science, but it is directionally consistent with the academic findings below.

The key implication is an engineering one: a fresh-context spawn is usually token-positive only when the child agent’s working set has low overlap with what the parent must continue carrying. Put differently, spawning saves tokens when spawn prompt + compact handoff is much smaller than “keep all of that exploration in parent history and re-pay it every later turn.” The evidence behind that inference is strong: Tokenomics shows input/context dominates total spend; Anthropic’s guidance says subagents are most useful when the parent does not need the verbose trace; and AgentDiet (FSE 2026, measured academic) shows that aggressively removing useless, redundant, and expired trajectory content cuts input tokens by 39.9%–59.7% and total cost by 21.1%–35.9% without hurting task performance.

Garbage collection also needs to be explicit, not accidental. Anthropic’s docs say non-fork subagents start from a fresh isolated context, resumed subagents keep their full prior history, auto-compaction triggers around 95% of context capacity, and inactive transcripts are cleaned up according to cleanupPeriodDays with a default of 30 days. Their cost docs also recommend clearing context between unrelated tasks because stale context is paid again on every subsequent call. Translating that into orchestration design: respawn, don’t resume, when continuity is not actually valuable; and compact frequently enough that stale context never becomes “rent-bearing” input. Again, this is vendor operational guidance, but it aligns with AgentDiet’s measured finding that reducing trajectory waste during execution is materially beneficial, not just a last-resort recovery tactic at context-limit time.

A subtle but important extra point is startup overhead. Anthropic notes that built-in Explore and Plan subagents intentionally skip CLAUDE.md and git-status loading “to keep research fast and inexpensive.” That is a direct example of a principle you can generalize: if a spawned worker only needs a local task description and read-only retrieval, strip inherited repo-wide state from its startup. Fresh context only pays off when the spawn payload itself is minimal.

Compression and structured handoffs

The best current research result on inter-agent handoffs is What Should Agents Say? (arXiv:2606.05304, measured academic). Its core finding is that free-form natural-language forwarding is the wrong default. Across two MAS topologies, it found that no fixed “just summarize it” strategy is universally optimal, that passing the full content is consistently expensive and rarely best, and that the useful payload is normally action-centered state rather than the sender’s private reasoning. Its proposed protocol, PACT, transforms each agent output into a compact public record containing only action taken / next action, grounded task state, and reusable artifact, while keeping private deliberation off the shared channel. Measured results are strong: 38.7% average token reduction across baselines and model scales while preserving or improving task performance, and on coding harnesses PACT reduced tokens-per-resolved by 47% on SWE-agent.

PACT is especially relevant to your controller/sub-agent design because it gives a concrete answer to “what to pass vs. what to re-derive.” Pass only what changes the downstream public state: the task pointer, the artifact pointer, the current grounded facts, blockers, and the next required action. Do not pass the private reasoning transcript, verbose tool chatter, or every intermediate hypothesis. On SWE-bench Verified, PACT’s port into production coding harnesses improved OpenHands from 19.4% to 23.0% resolved while cutting tokens per resolved instance from 3.82M to 3.43M; on SWE-agent it cut input tokens by 50.4% and tokens per resolved from 2.46M to 1.30M, with a modest resolution drop from 25.6% to 24.2%. That is one of the clearest direct measurements that disciplined public-state handoffs can reduce the communication tax in actual coding loops.

Repository-level context artifacts are a more mixed story, and the contradiction in the 2026 literature is informative. On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents (arXiv:2601.20404, measured academic) found that, in a filtered sample of 10 repositories and 124 pull requests using Codex, the presence of AGENTS.md was associated with 28.64% lower median runtime and 16.58% lower output-token consumption, with comparable completion behavior. But Evaluating AGENTS.md (arXiv:2602.11988, measured academic) found almost the opposite in broader task-resolution experiments: developer-written context files gave only a 4% average lift over no file, LLM-generated context files caused a 3% average performance drop, and context files increased cost by more than 20%, while also increasing reasoning-token usage—for GPT-5.2 by 22% on SWE-bench Lite for LLM-generated files. The reconciliation is straightforward: focused, high-signal, non-redundant artifacts can help; broad, redundant “repo overviews” often just add more context to haul around.

So the best current practice is not “always add a blackboard file.” It is “treat the blackboard as an interface contract.” Make it sparse, bounded, and operational: entry points, commands, invariants, artifact locations, ownership, and stop conditions. If some fact can be cheaply re-fetched from tools, it is often better to re-derive it than to carry it forever in shared history. That inference follows from PACT’s action-state result, from the AGENTS.md contradiction, and from Anthropic’s broader context-engineering recommendation to keep only the smallest high-signal token set in play.

Verification and code review without expensive loops

The clearest token sink in software agents is verification. Tokenomics found that Code Review consumed 59.4% of all tokens on average, far above Coding at 8.6% and Design at 2.4%. The review phase was also strongly input-heavy at 51.4% input / 24.7% output / 23.9% reasoning, which is exactly what you would expect from agents repeatedly re-reading code and PR history to produce short critiques. This is the first thing to optimize because it is where your communication tax concentrates.
10

The best evidence that many review/critic loops are too expensive comes from The Cost of Consensus (arXiv:2605.00914, measured academic). In homogeneous debate setups, peer communication consumed 2.1× to 3.4× more tokens than isolated self-correction for equal or worse performance. The paper reports, for example, 16,275 vs. 5,407 tokens on GSM-Hard for Qwen+Llama debate versus self-correction (3.0×), and 20,904 vs. 9,337 tokens for Llama+Ministral (2.2×). For Qwen3-8B-think on MMLU-Hard, a single agent reached 85.0% at 1,473 tokens, while debate reached 90.0% at 21,472 tokens, a 14.6× cost increase for a 5-point gain. On GSM-Hard, debate even underperformed the no-communication baseline. The lesson is not that verification is useless; it is that iterative social verification is often a very expensive way to buy it.
11

A practical way to make review cheaper is to replace open-ended iteration with bounded review budgets. Agent Contracts (arXiv:2601.08815, measured early/workshop evidence) tested a coder↔reviewer workflow on 70 LiveCodeBench problems. A contracted mode with a 50K token budget and max 3 iterations cut mean token usage from 34,606 to 3,461 (−90%), reduced iterations by 43%, and halved LLM calls from 9.0 to 4.5, while the success-rate drop from 60.0% to 52.9% was not statistically significant in that study. Savings were even larger on medium-difficulty items (92% token savings). This is not a large mainstream benchmark, so I would treat it as promising rather than definitive, but it is one of the few direct measurements of review-loop governance in SE-like tasks.
12

The more scalable alternative is to move as much “review” as possible into deterministic gates and off-agent artifacts. Code Review Agent Benchmark (arXiv:2603.23448, measured academic) argues that textual similarity and LLM-as-judge are poor review oracles, and instead converts human review feedback into executable tests. On that benchmark, today’s review agents together solve only about 40% of tasks, and the authors argue for test-based evaluation because it is more stable, reproducible, and action-grounded than judge-model scoring. Pair that with Compiled AI (arXiv:2604.05150, measured but outside software-review specifically), which shows that when a workflow can be turned into deterministic code artifacts, runtime LLM invocation can drop to zero execution tokens, break even after about 17 transactions, and reach 57× fewer tokens at 1,000 transactions than direct-runtime inference. The design implication is clear: repeated policy checks, style checks, schema checks, type/build/test checks, and other recurrent validation logic should be pushed into deterministic artifacts first; use LLM review for the residual cases that are semantic, novel, or ambiguous.
13

One more code-review-specific finding is worth using tactically. Improving LLM-Based Go Code Review through Issue-List Generation and Context Augmentation (arXiv:2606.01859, measured academic) found that issue-list review with selective context beat single-primary-issue review, but more context was not always better. Its best configuration reached 28.00% refinement exact match, up 10.85 percentage points over primary-issue review with no added context (17.15%), while refinement-guided pruning cut average candidate count from 7.2 to 3.1 with nearly full benefit retained. That is not a token accounting paper, but it supports a cheaper review pattern: one good pass with selective context and candidate pruning is often better than repeatedly expanding the conversation.

When multi-agent is not worth the tax

If your software task is tightly coupled, sequential, and context-sharing-heavy, the burden of coordination often dominates the benefit of specialization. The cleanest general result here is When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail (arXiv:2601.04748, measured academic), which reports that skill-based single-agent systems matched multi-agent accuracy on GSM8K, HumanEval, and HotpotQA while reducing token consumption by 54% and latency by 50% on average. Its caveat is important: this works best when the skill library stays small and semantically distinct; large or confusable skill sets create their own scaling problems. Still, for controller/sub-agent systems with a small stable repertoire—context compiler, explorer, auditor, memory writer—this is strong evidence that “compile roles into skills” can outperform explicit role-to-role chat.
15

A second general result makes the same point from a budget-control perspective. Single-Agent LLMs Outperform Multi-Agent Systems on Multi-Hop Reasoning Under Equal Thinking Token Budgets (arXiv:2604.02460, measured academic) found that single-agent systems consistently matched or outperformed multiple MAS architectures under matched thinking-token budgets, and that MAS became competitive mainly when single-agent context utilization was degraded or when extra compute slipped in. That maps very directly onto software engineering: if your multi-agent architecture is not unlocking genuine parallel search, distinct tools, or separate failure domains, it is likely just converting reasoning into communication.
16

The software-engineering-specific baseline to keep in mind is still agentless. Agentless (arXiv:2407.01489; later FSE 2025 archival version, measured academic) deliberately avoids autonomous tool-heavy multi-agent loops and instead uses a structured localization → repair → validation pipeline. The later archival version reports 32.00% on SWE-bench Lite with 96 correct fixes at about $0.70 per issue; the original 2024 preprint reported 27.33% at $0.34. That is older than your requested window, but it remains the most influential proof that simpler, more constrained software pipelines can beat more agentic systems on the cost frontier. If a task looks like localized edit generation with deterministic validation, start from an agentless or single-agent baseline and make multi-agent justify itself empirically.
17

Anthropic’s own production write-up points in the same direction, though I would classify it as vendor internal evidence, not independent proof. In their research system, multi-agent orchestration beat a single-agent baseline by 90.2% on an internal research eval for breadth-first search tasks, but Anthropic also says multi-agent systems use about 15× more tokens than chats, that token usage alone explains 80% of performance variance on BrowseComp, and that most coding tasks are not a good fit today because they offer less real parallelism and require more dependent coordination. That is exactly the boundary condition you should use: multi-agent is worth the tax mainly for breadth-parallel discovery, search, and independent audit branches—not for tightly coupled edit-review-edit loops where everyone keeps needing the same repo state.

Measured deltas that should drive your design

The most actionable measured deltas from the current literature are these.

Token concentration in verification: Tokenomics (arXiv:2601.14470, measured) found 59.4% of tokens in Code Review, with overall spend split 53.9% input / 24.4% output / 21.6% reasoning.

Trajectory garbage collection works: AgentDiet (arXiv:2509.23586, FSE 2026, measured) cut input tokens by 39.9%–59.7% and total cost by 21.1%–35.9% with performance parity, at about 5%–10% reflection overhead.

Structured handoffs beat free-form forwarding: PACT (arXiv:2606.05304, measured) reduced token usage by 38.7% on average, cut tokens per resolved by 47% on SWE-agent, and improved OpenHands from 19.4% to 23.0% resolved while also lowering tokens per resolved.
Unbounded review loops are ruinous: Agent Contracts (arXiv:2601.08815, measured early/workshop) cut code-review pipeline token use 90% (34,606 → 3,461), iterations 43%, and LLM calls 50% with no statistically significant success drop in that study.

Consensus review is often a bad trade: The Cost of Consensus (arXiv:2605.00914, measured) found debate costs 2.1×–3.4× isolated self-correction with equal or worse accuracy, and in one reasoning setting debate cost 14.6× a single-agent baseline for only +5 pp accuracy.

Context artifacts help only when they are sparse and useful: AGENTS.md efficiency (arXiv:2601.20404, measured) found −28.64% runtime and −16.58% output tokens with comparable completion, while Evaluating AGENTS.md (arXiv:2602.11988, measured) found +20% to +23% cost, −3% average performance for LLM-generated files, and +22% reasoning tokens for GPT-5.2 on SWE-bench Lite.
Single-agent baselines deserve more respect: Single-agent with skills (arXiv:2601.04748, measured) cut 54% tokens and 50% latency on average versus MAS while maintaining comparable accuracy on representative tasks.
15
Model choice and cost variance are first-order: How Do AI Agents Spend Your Money? (arXiv:2604.22750, measured) found up to 30× same-task token variance and >1.5M-token gaps between models on the same tasks.

From those results, the most defensible architecture for minimizing inter-agent context-passing cost in software engineering is a small-team, sparse-public-state, bounded-iteration design: keep public messages to action/state/artifact records; isolate high-volume exploration in fresh disposable contexts; compact or delete stale trajectory content continuously; route simple checks to deterministic gates or cheap specialist models; and escalate to LLM review only on failure, ambiguity, or cross-file semantic risk. That recommendation is partly a synthesis rather than a single study, but it is the pattern most consistently supported by the measured evidence above.

Open questions and limitations

The evidence is already good enough to change system design, but it is not yet complete. Tokenomics instruments one SE multi-agent framework (ChatDev) over 30 tasks, so its exact percentages should be treated as an initial cost map, not a universal constant. AgentDiet is implemented on one top-performing coding agent. PACT is one of the strongest 2026 results, but its SWE-agent/OpenHands ports still sit on a specific model/harness pairing. Agent Contracts is promising but early and not yet a broad community standard. And the AGENTS.md literature is plainly contradictory, which likely means artifact quality, redundancy with existing docs, and harness behavior matter more than the mere presence of a context file.
10

The biggest unresolved research gap for your exact use case is this: there is still no large, standardized 2026 benchmark that isolates inter-agent handoff schema, artifact store design, deterministic-vs-LLM verification split, and spawn-vs-inline policy inside realistic software-engineering orchestration stacks. The best current answer is therefore not a single silver bullet. It is an evidence-backed bundle: fresh contexts for disposable work, structured action-state handoffs, aggressive trajectory garbage collection, bounded review budgets, and deterministic gates wherever the rule repeats.
