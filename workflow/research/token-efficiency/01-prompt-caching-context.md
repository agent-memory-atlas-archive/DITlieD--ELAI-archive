Prompt Caching and Context-Window Management for Anthropic-Based Agentic Coding Harnesses
Prompt Caching and Context-Window Management for Anthropic-Based Agentic Coding Harnesses
Executive takeaways

For a Claude Code-style coding harness that uses the Anthropic Messages API as its cloud lane, the biggest levers are not “better summarization prompts.” They are stable-prefix engineering, explicit cache boundaries, deferred tool loading, and deterministic removal of low-value observations before you ever rewrite history. Anthropic’s own API rules are strict: prompt-cache hits require exact prefix matching, the cache follows the hierarchy tools → system → messages, and changes in earlier layers invalidate all later layers. In the only public multi-turn agent benchmark I found that quantifies provider prompt caching, Claude Sonnet 4.5 cut API cost by 78.5% and improved time-to-first-token by 22.9% when the harness cached the system prompt only rather than naively caching everything.

The practical implication is straightforward. If you want the economics of Anthropic prompt caching to show up in a long-running coding agent, your harness should keep the top of the request as boring and identical as possible across turns, put volatile items at the tail, isolate stable layers with cache breakpoints, and prefer deterministic context-thinning methods that do not rewrite the stable prefix. Vendor blogs and docs from Anthropic, Cursor, Cline, Aider, and OpenAI all converge on that theme, even when they use different model providers or different terminology.

Anthropic prompt caching mechanics

Anthropic’s prompt cache is based on exact prefix reuse. The docs state that cache hits require 100% identical prompt segments, including text and images, up to and including the block marked with cache_control. The invalidation hierarchy is explicit: the cache is organized as tools → system → messages; changes to tools invalidate everything, changes to system invalidate system plus messages, and message-layer changes only affect message-layer cache reuse. Anthropic also documents that you can define up to 4 cache breakpoints, and that extra breakpoints are useful when different sections change at different cadences or when a growing conversation pushes a breakpoint 20 or more blocks past the last cache write. Breakpoints themselves do not add cost; cost comes from cache writes, cache reads, and uncached trailing input.

The default cache type is ephemeral with a 5-minute lifetime. Anthropic also offers a 1-hour TTL by setting {"type":"ephemeral","ttl":"1h"} inside cache_control. The docs explicitly say 5-minute cache writes cost 25% more than base input tokens and cache reads cost 10% of base input token price. Anthropic also states that the 1-hour cache is available at additional cost; in the pricing table excerpt visible on the prompt-caching page, Claude Opus 4 is shown at $15/MTok uncached input, $18.75/MTok for 5-minute cache writes, $30/MTok for 1-hour cache writes, and $1.50/MTok for cache reads. Anthropic’s usage accounting splits the billable prompt into cache_creation_input_tokens, cache_read_input_tokens, and input_tokens, and the total input tokens are their sum.

Anthropic’s docs also expose several underappreciated operational rules. A cache entry becomes available only after the first response begins, so parallel identical requests should wait for the first stream or response start if you want followers to hit cache. Cacheable content includes tool definitions, system messages, text messages, images/documents in user turns, and tool use/results; non-cacheable top-level exceptions include explicit thinking blocks, sub-content like citations, and empty text blocks. For coding agents that use extended thinking, previous thinking can still be carried and charged as input when it is brought back through prior assistant turns and tool-use flows. On Opus 4.5+ and Sonnet 4.6+, prior thinking is preserved by default even when non-tool-result user content is added; on earlier Opus/Sonnet variants and Haiku, earlier thinking can be stripped in those situations, which changes both context behavior and cache behavior.

For your “byte-stable prefix” question, Anthropic does not use that phrase in the docs, but operationally it means this: keep the serialized content of everything before the breakpoint exactly identical across turns. That includes tool definitions, text, images, block order, cache_control marker placement, and even JSON key ordering for tool_use content blocks. Anthropic explicitly warns that languages such as Swift and Go can randomize key order during JSON conversion and silently break cache hits. Anthropic also calls out tool_choice changes and changes in the presence or absence of images as cache-invalidating.

Two more nuances matter for production harnesses. First, minimum cacheable prefix sizes vary by model: on the Claude API and related Anthropic-hosted platforms, Opus 4.8, Sonnet 4.6, and Sonnet 4.5 can cache prefixes starting at 1,024 tokens, while Opus 4.7, Opus 4.6, Opus 4.5, and Claude Mythos Preview require 4,096 tokens. Second, as of February 5, 2026, Anthropic moved prompt-cache isolation to the workspace level on the Claude API, Claude Platform on AWS, and Microsoft Foundry beta; Bedrock and Vertex AI remain organization-level.

Cache-aware request layout and the silent ways harnesses bust cache

The correct Anthropic-native ordering is not a stylistic choice; it is the cache hierarchy. Stable tool definitions should be first, then the top-level system prompt, then message history. Anthropic’s own best-practices section says to place cached content at the beginning of the prompt, place the breakpoint on the last block that stays identical across requests, and use multiple breakpoints when different layers change at different rates. For a coding agent, that usually means: a stable tools layer; a stable system policy layer; slowly changing repo context such as repo map / read-only docs / architecture notes; then the multi-turn conversation; then the newest user message and the latest volatile tool outputs.

A good Claude-style harness therefore should separate stability tiers on purpose. Put the rarely changing tool schema and core harness rules in the top-level system and/or tools area, then put larger but still reusable repository context in its own cacheable block, then leave the live conversation and fresh observations to grow at the tail. Anthropic’s compaction docs make the same point from another angle: when compaction inserts a summary, that summary becomes new content that must be written to cache, so if you did not isolate the system prompt with its own breakpoint, you will end up re-caching the system prompt too. Anthropic recommends adding a cache_control breakpoint at the end of the system prompt so the system layer remains valid and only the summary needs to be rewritten after compaction.

The silent cache killers are mostly harness mistakes, not model mistakes. The most common ones in Anthropic’s docs are: putting timestamps or user-specific environment data before the breakpoint; placing the breakpoint on a block that actually changes every turn; changing tool definitions, tool names, descriptions, parameter schemas, or tool_choice; turning web search, citations, or speed settings on and off; changing whether images are included; moving cache_control markers; or serializing tool_use JSON with unstable key ordering. Anthropic also notes that if the request is too short to cross the model’s minimum cacheable threshold, the API simply won’t cache it and won’t throw an error; you have to inspect usage fields to notice.

Claude Code’s own docs show how these issues appear in a real harness. Claude Code structures requests as system prompt → project context → conversation, and says that the system prompt layer changes when loaded tool definitions change or Claude Code itself is upgraded; project context changes at session start or after /clear or /compact; and the conversation changes every turn. Its cache-safe actions include editing already-read repo files, editing CLAUDE.md mid-session, changing permission mode, invoking skills/commands, running /recap, rewinding a conversation, and spawning subagents. Its cache-busting actions include switching models, changing effort level, enabling fast mode, connecting/disconnecting an MCP server, enabling/disabling a plugin that changes the prefix, compacting the conversation, and upgrading Claude Code. That is a strong blueprint for your own harness: load durable rules at session start, delay volatile rule changes to known reset points, and do not mutate the top of the prompt in the middle of a task.

Anthropic has added one especially useful escape hatch for long-running sessions on Opus 4.8. The prompt-caching docs say you can add a new system instruction mid-conversation without invalidating the system or message caches by appending a {"role":"system"} message inside messages instead of editing the top-level system field. Anthropic’s Opus 4.8 announcement frames this as a way to update permissions, token budgets, or environment context without breaking prompt cache. If your harness needs runtime policy shifts, this is the Anthropic-native way to do them.

What the leading coding-agent harnesses publicly document

Claude Code is the most directly relevant reference if you are building a Claude Code-style harness on Anthropic. Public docs show a layered request layout, automatic prompt caching, explicit documentation of cache-invalidating actions, separate caches per model and effort level, 1-hour TTL by default on a Claude subscription, and API-level visibility into cache_read_input_tokens and cache_creation_input_tokens. Claude Code also makes clear that subagents get their own separate conversation and cache, while the parent session’s prefix remains intact. What Claude Code does not publish, at least in the sources I reviewed, is a public average cache-hit percentage.

Cursor publicly describes a similar high-level ordering—system prompt and tool descriptions first, then current conversation state, then the user’s request—but says its harness has shifted away from large static context and toward more dynamic, on-demand context. Cursor says it still injects some static context such as operating system, git status, and current/recently viewed files, and then lets the agent fetch more while it works. Cursor also says it tracks cache hit rate, token efficiency, and latency in online A/B tests, but it does not publish cache-hit percentages. It does, however, publish one important negative result: in one experiment, a more expensive model for context summarization made a negligible difference in agent quality and was not worth the higher cost.

Aider explicitly says it reorganizes chat history to make specific things cacheable: the system prompt, read-only files added with --read, the repository map, and the editable files added to the chat. It exposes --cache-prompts and --cache-keepalive-pings N, where Anthropic’s default 5-minute TTL can be kept warm with pings every 5 minutes for up to N*5 minutes after each message. Aider also notes that streaming can hide cache statistics/cost information, so it recommends --no-stream if you want to inspect them. I found no public Aider numbers for cache-hit rate or per-task savings.

Cline publishes several concrete context-management choices that are highly relevant to Anthropic-style caching. First, it removes older outdated file reads while keeping only the latest version of a file in context, because repeated reads of the same file clutter the window and increase error rates. Second, Cline says it takes a conservative approach to broader truncation because aggressively truncating older messages can break the cache and increase costs on subsequent turns. Third, Cline says that MCP instructions had previously consumed 30% of its system prompt, and that it is replacing about 8,000 tokens of static MCP documentation with an on-demand load_mcp_documentation tool. It also distinguishes persistent rules from on-demand workflows: rules append to every system prompt, while workflows inject instructions only when invoked, which is significantly better for token efficiency and cache stability. I found no published cache-hit percentages from Cline.

Codex is not Anthropic-based, but its public docs are still useful as a cross-vendor reference for harness design. OpenAI’s Codex guidance says long-running work should use one thread per coherent task, durable rules should move into AGENTS.md or skills rather than living in the transient prompt, subagents should offload bounded work from the main thread, and /compact should be used when a thread gets long. Codex also resumes conversations by reusing the original transcript, plan history, and approvals. OpenAI’s prompt-caching and cookbook docs add one especially transferable idea: naive just-in-time truncation shifts the start of the conversation slightly on every turn and causes frequent cache misses, so a larger-chunk retention policy can deliberately trade some memory depth for a more stable prefix. I found no public Codex cache-hit percentages either.

Deterministic compaction and observation-masking versus summarization

For Anthropic specifically, the most cache-friendly “compaction” is often not summarization at all. Anthropic’s context editing feature exposes two deterministic controls: tool result clearing and thinking block clearing. Tool result clearing replaces old tool results with placeholder text once the context crosses a threshold; thinking block clearing lets you preserve more or fewer prior thinking blocks. Anthropic is explicit about the cache tradeoff: tool result clearing invalidates cached prefixes when content is cleared, and thinking-block clearing invalidates the cache at the clearing point when those blocks are removed. Anthropic therefore provides clear_at_least so you only break cache when you are clearing enough tokens to make the cache break worthwhile. Conversely, setting thinking preservation to keep: "all" is explicitly described as maximizing cache hits.

That is why the best long-session harnesses tend to use a hybrid. Claude Code says it clears older tool outputs first, then summarizes only if needed. Cline says it removes redundant historical file reads first, while avoiding aggressive older-message truncation that would break cache. Anthropic’s managed-agents architecture makes the same architectural point at a deeper level: it stores durable context outside the live context window and lets the harness fetch slices of the event stream into the prompt, specifically so future harnesses can choose context organization that achieves a high prompt-cache hit rate. In practice, these are all forms of observation-masking or externalization: reduce volatile, low-value tokens without rewriting your stable scaffold.

Summarization is the opposite trade. Anthropic’s server-side compaction—available in beta on Opus 4.8/4.7/4.6, Sonnet 4.6, and Mythos Preview—automatically summarizes the conversation when a token threshold is reached, creates a compaction block, and then drops all earlier message blocks before that compaction block on subsequent requests. The default trigger is 150,000 tokens and the minimum trigger is 50,000. Anthropic’s own example shows an internal compaction pass with 180,000 input tokens producing a 3,500-token summary, after which the next visible message turn runs on a much shorter context. This absolutely helps context-window pressure, but by design it rewrites history and therefore creates a new prefix that must be written to cache. Anthropic’s docs explicitly warn that, without an end-of-system breakpoint, compaction will also force your system prompt to be re-cached.

The strongest public example of “summarization done well” is Cursor’s 2026 self-summarization work, but it still illustrates the core trade. Cursor trains Composer to self-summarize at a token trigger, then continue from the condensed context. Against a tuned prompt-based compaction baseline, Cursor reports that self-summary reduced compaction error by 50%, used one-fifth of the tokens, and produced summaries of about 1,000 tokens versus more than 5,000 tokens for the baseline. In a case study, an early Composer checkpoint worked for 170 turns and self-summarized more than 100,000 tokens down to 1,000. Those are strong vendor-published results for summary quality and token efficiency, but they do not change the Anthropic cache rule: once you replace raw earlier turns with a summary, you have created a different prefix than the old conversation and must build a new cache entry from there.

There is one more Anthropic-specific lesson for very long coding tasks: sometimes even good compaction is not enough. Anthropic’s March 2026 engineering write-up on long-running application development says that in earlier testing, Claude Sonnet 4.5 showed enough “context anxiety” that compaction alone was insufficient, and the harness needed context resets plus structured handoff artifacts to preserve long-horizon quality. That is not a cache-optimization technique per se, but it is an important reminder that maximizing cache hit rate is not the same as maximizing final task quality.

What is actually measured, and what is just vendor guidance

Measured, public benchmark: The strongest public evidence for provider prompt caching in long-horizon agents is arXiv:2601.06007, which evaluated over 500 agent sessions on DeepResearchBench using 10,000-token system prompts. Across providers, prompt caching reduced API cost by 41–80% and improved TTFT by 13–31%. For Claude Sonnet 4.5, the full per-strategy numbers were: 77.8% cost savings and 21.8% TTFT improvement for full-context caching, 78.5% cost savings and 22.9% TTFT improvement for system-prompt-only caching, and 78.1% cost savings and 20.9% TTFT improvement when tool results were excluded from caching. At 50,000 prompt tokens, Sonnet 4.5 achieved 88% cost savings, from $0.667 to $0.080 in that study. The same paper also shows a failure mode: below the minimum threshold, TTFT can regress, with 10–18% regressions reported at 500 tokens for GPT-4o, GPT-5.2, and Sonnet 4.5.

Vendor-internal measurement: Anthropic’s advanced tool-use post reports that loading 50+ MCP tools upfront consumed about 72K tokens for tool definitions and ~77K total context before any work began. Replacing that with the Tool Search Tool reduced the upfront tool load to ~500 tokens, loaded only 3–5 relevant tools at about ~3K tokens, and brought total context consumption to ~8.7K, which Anthropic describes as preserving 95% of the context window and reducing token usage by 85%. Anthropic also reports internal MCP evaluation gains from 49% to 74% for Opus 4 and from 79.5% to 88.1% for Opus 4.5. This is useful engineering evidence, but it is vendor-internal, not an independent benchmark.

Vendor-published but not independent: Cursor’s self-summarization post reports the 50% compaction-error reduction and 5× token reduction described above, and also says an expensive summarization model yielded negligible quality gains in one online experiment. Those findings are meaningful, but they come from Cursor’s own harness and eval stack, not an external benchmark. Independent research beyond Anthropic-specific APIs: The broader research literature reinforces the same design direction. “LLMs Get Lost In Multi-Turn Conversation” reports an average 39% performance drop from single-turn to multi-turn setups across six generation tasks, which is a strong argument for active context management. “MT-OSC” reports up to 72% token reduction in 10-turn dialogues while preserving or improving accuracy across 13 LLMs and several benchmarks. Those are valuable background results, but they are not direct measurements of Anthropic’s Messages API or your exact coding-agent workload.

Practical design pattern for your Anthropic coding harness

If I were optimizing an Anthropic Messages-API coding harness for June 2026, I would treat the request as four stability tiers. First, keep the tool layer tiny and durable: defer large tool libraries or adopt Anthropic’s Tool Search Tool so that only core tools sit in the static prefix. Second, isolate the system layer with a cache breakpoint at the end of the top-level system prompt. Third, put slowly changing repo context—repo map, read-only architecture docs, coding standards, stable environment facts—in its own separately cacheable block. Fourth, let the conversation layer grow at the tail, with volatile tool outputs placed after the last stable breakpoint or cleared later by context editing if they become dead weight. That pattern follows Anthropic’s cache hierarchy, Anthropic’s compaction guidance, and the best public Sonnet 4.5 benchmark result, which favored system-prompt-only caching.

I would also prefer deterministic context controls before summarization. For Anthropic-native long sessions, that means: cap oversized tool outputs at the tool layer; use pagination/range-selection/filtering so Claude sees only what it needs; consider context editing for stale tool results, but only with a meaningful clear_at_least threshold because every clearing event intentionally breaks cache at the clearing point; and preserve thinking aggressively if your priority is cache reuse rather than maximum free window space. Anthropic’s own guidance for tool design is to paginate, range-select, filter, and truncate large tool responses, and Claude Code itself clears older tool outputs before summarizing.
15

Summarization should be a last resort, not the first. When it becomes necessary, make it cache-aware: keep the top-level system prompt behind its own breakpoint; cache the resulting compaction block; and understand that you are deliberately trading old-prefix reuse for a shorter, cleaner active context. If you are on Sonnet 4.5, be especially cautious: Anthropic’s long-running-apps write-up suggests that resets and structured handoffs may outperform endless in-place continuation for some very long tasks. If you are on Opus 4.8, use mid-conversation role: "system" messages rather than mutating the top-level system prompt when runtime rules need to change.

Finally, instrument everything. Anthropic gives you cache_creation_input_tokens, cache_read_input_tokens, and input_tokens; Claude Code’s own docs recommend watching the read-to-creation ratio as the most direct signal that caching is working. Anthropic also ships cache diagnostics (beta) to compare consecutive requests and report exactly where the prefix diverged. If your harness is “supposed” to be stable and cache creation stays high across turns, that is usually a serialization or layout bug.

Open questions and limitations

The most important limitation in the public evidence is that I did not find public average cache-hit percentages for Claude Code, Cursor, Aider, Cline, or Codex. Cursor and Claude Code both say they track cache-hit or cache-read behavior, but they do not publish the percentages in the sources reviewed here.

The best quantitative prompt-caching evidence is the independent arXiv benchmark on DeepResearchBench, which is a tool-heavy research agent benchmark rather than a pure code-editing benchmark. It is highly relevant to long-horizon multi-turn agents, but it is not a direct measurement of your exact repo-editing workload.
