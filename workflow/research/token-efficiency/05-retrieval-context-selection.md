Token-Efficient Retrieval and Context Selection for Agentic Coding Assistants
What the current evidence says

The strongest 2026-era pattern is not “just use a bigger context window.” It is staged context acquisition: start with a cheap structural view of the repo, retrieve only a small candidate set, rerank or traverse structure to narrow it further, read signatures or snippets before bodies, deduplicate anything already seen, and compress or evict old tool outputs before they crowd out the current step. The best current primary evidence spans repo maps such as Aider’s tree-sitter-based symbol map, hierarchical agentic retrieval such as A-RAG, contextual hybrid retrieval from Anthropic, budget-aware compaction systems such as OpenDev and ContextBudget, and graph/LSP-based code retrieval such as LspRag, LocAgent, KGCompass, and SCIP-backed navigation.

The important caveat is that the evidence quality is uneven. Some claims are peer-reviewed or arXiv-backed and provide explicit numbers. Others are vendor blog benchmarks or OSS README measurements with useful but less neutral methodology. For code agents specifically, peer-reviewed papers are now starting to publish strong cost and accuracy numbers, but several widely used production ideas still have better architectural documentation than controlled ablation studies.

A practical takeaway emerges from the sources: if your assistant is still doing “search text → open whole file → open more whole files,” your largest easy win is almost always to replace that with a structure-first, snippet-first, body-on-demand pipeline. The gains are visible in three different ways across the literature: fewer retrieved tokens, fewer tool calls, and better retrieval/localization accuracy at the same or lower context cost.

Repo maps and symbol-ranked context

Aider’s repo map is the canonical “repo outline first” design. In Aider’s primary docs and blog, the assistant sends the model a concise repository map containing files plus the most important classes, functions, and call signatures, rather than dumping implementations wholesale. The map is built with tree-sitter, includes critical definition lines, and is explicitly meant to let the model recognize APIs and relationships before deciding which files to inspect in full. The optimization step uses a graph-ranking approach over dependency-connected files, and the default --map-tokens budget is 1k tokens, with dynamic expansion only when no files are yet in chat and the model needs more global context.

That design is directly aligned with your goal of “minimum necessary context per step.” Aider’s own explanation is blunt: sending whole files just to convey context is bulky and wastes the context window; the map should expose signatures and relationships first, and the model can then ask for specific files when it truly needs implementations. In other words, the repo map is a signatures-first, bodies-on-demand mechanism even before you add semantic retrieval.

On “PageRank-ranked” specifically, Aider’s public docs/blog describe a graph ranking algorithm but do not name PageRank in the primary writeups I found. An independent 2025 exploratory study of code-retrieval techniques describes Aider’s approach more concretely as tree-sitter AST parsing plus NetworkX PageRank for symbol-level visibility, and reports that Aider consumed roughly 8.5k–13k prompt tokens on the studied tasks, the lowest among the compared agents in that study. That is useful evidence, but it is secondary and exploratory rather than an official Aider benchmark.

There is also measured evidence that the representation of the repo map matters. In a 2025–2026 state-in-context replication and extension, a trie-style repository encoding achieved 87.67% recall at an average cost of $0.0360 per query, versus 90.56% recall and $0.0687 for a flat list representation; the authors summarize that as about a 48% reduction in ranking cost for roughly a 2-point recall drop. That is not an Aider paper, but it is highly relevant to repo-map token-budget fitting: compressed structural encodings can preserve most of the ranking signal while halving ranking-time token spend.

The missing piece is a strong official Aider ablation versus a naive full-file baseline. Aider documents the architecture and the token cap, and independent work suggests low token footprints, but I did not find an official controlled measurement saying “repo map saves X% vs full-file context.” For a survey intended for system design, I would treat Aider as architecture-strong, measurement-light: very credible as a pattern, but not yet as a published token-accounting benchmark.

Progressive disclosure and agentic retrieval

A-RAG is the clearest primary-source example of progressive disclosure done right. Its interface exposes three retrieval tools at different granularities: keyword_search, semantic_search, and chunk_read. The keyword and semantic tools return chunk IDs plus short snippets, and only after seeing those snippets does the agent decide whether to read full chunks. The paper is explicit that this is intended to “incrementally retrieve information on-demand” rather than “load large amounts of context indiscriminately.” It also includes a context tracker: if the agent tries to read a chunk that has already been read, the system returns a “This chunk has been read before” notification, consuming zero additional tokens.

The gains are real, but not uniform across every benchmark. On the GPT-5-mini backbone, A-RAG (Full) retrieved 2,737 tokens on HotpotQA versus 5,358 for Naive RAG, and 2,930 on 2Wiki versus 5,506 for Naive RAG. That works out to roughly 49% and 47% fewer retrieved tokens, respectively. On MuSiQue, however, A-RAG (Full) used 5,663 retrieved tokens against Naive RAG’s 5,387, so the token savings are not universal. The paper’s stronger claim is therefore “more accuracy at comparable or lower retrieved tokens on many tasks,” not “less context on every task.”

Accuracy improved at the same time. On GPT-4o-mini, A-RAG (Full) scored 46.1 versus Naive RAG’s 38.6 on MuSiQue, 77.1 versus 74.5 on HotpotQA, and 60.2 versus 42.6 on 2Wiki. That combination — better accuracy plus materially fewer retrieved tokens on several multi-hop tasks — is exactly the kind of evidence that supports progressive disclosure for coding assistants too.

The paper also matters because it separates “agentic retrieval” from “big prompt.” A-RAG’s naive agentic variant, which let the agent keep retrieving without the full hierarchy and controls, ballooned to 56,360 retrieved tokens on MuSiQue and 45,406 on 2Wiki, far above both Naive RAG and the full A-RAG system. That is a useful warning for coding assistants: simply giving an agent tools is not enough. You need a retrieval interface that encourages cheap reconnaissance first, expensive reads second, and reread deduplication throughout.

In code-agent terms, the transferable pattern is straightforward. First pass: repo outline, symbol signatures, or short matched snippets. Second pass: targeted full bodies only for the surviving candidates. Third pass: no-token or near-zero-token handling for anything already inspected. Among the sources I found, A-RAG is the strongest measured evidence for this pattern; many code-assistant products already use variants of it, but fewer publish controlled numbers.

Hybrid retrieval and contextual reranking

Hybrid retrieval remains the best-supported default for high-recall candidate generation: lexical retrieval for exact identifiers and rare strings, dense retrieval for semantic match, and a reranker for the final budget cut. Anthropic’s “Contextual Retrieval” blog is the current primary source people cite most often here. Their method adds chunk-specific context before both embedding and BM25 indexing, then optionally reranks the top 150 candidates down to the top 20. In Anthropic’s cross-domain tests, contextual embeddings reduced top-20 retrieval failure from 5.7% to 3.7% (a 35% reduction), contextual embeddings plus contextual BM25 reduced it to 2.9% (49%), and the reranked contextual stack reduced it to 1.9% (67%).

That result is about retrieval accuracy rather than direct token savings, but it has clear token implications. If your reranker selects a better top 20, your generator needs fewer “just in case” chunks. Anthropic also makes the cost tradeoff explicit: the contextualized text usually adds 50–100 tokens per chunk at indexing time, and their prompt-caching calculation estimates about $1.02 per million document tokens to generate contextualized chunks under their stated assumptions. So the trade is: more preprocessing tokens, fewer retrieval failures, and potentially fewer generation-time tokens wasted on dead context.

A useful 2026 counterpoint is the financial-doc benchmark “From BM25 to Corrective RAG,” which reports that a two-stage pipeline combining hybrid retrieval with neural reranking reached Recall@5 of 0.816 and MRR@3 of 0.605, outperforming single-stage methods; it also found that plain BM25 beat state-of-the-art dense retrieval on that domain, while contextual retrieval gave consistent gains. That result reinforces the practical lesson for codebases: exact-match lexical search is still very hard to beat for symbol names, error strings, config keys, and protocol identifiers, and dense retrieval should be added as a complement rather than as a replacement.

Late chunking is one of the best self-hostable ways to improve retrieval quality without increasing runtime prompt size. In the primary Jina paper, late chunking improved the aggregate nDCG@10 result for 256-token chunks from 52.2 to 54.0 across the evaluated setups, and on NFCorpus with jina-embeddings-v2-small it improved from 23.5 to 30.0. The same paper found no clear advantage for overlapping chunks in its tested setup. This matters for token efficiency because late chunking can improve candidate recall/precision at the same downstream chunk budget; the cost is paid mainly at indexing time, because long documents must be embedded before pooling into chunk vectors.

For rerankers, Jina’s jina-reranker-v3 is the best-documented self-hostable current option in the sources I reviewed. The paper reports a 0.6B-parameter model, 61.94 nDCG@10 on BEIR, 63.28 on code retrieval (CoIR), and a 4.88% improvement over jina-reranker-v2, with top-100 first-stage results passed into the reranker. That is a strong signal that a lightweight second stage can materially improve the final top-N that enters the generator context. The main token tradeoff is at rerank time: cross-document or query-document scoring costs scale with how many candidates you ask it to examine and how long those candidates are.

Voyage’s rerank-1 is a strong cloud-API option, but the evidence is more vendor-y. Voyage says rerank-1 outperforms Cohere and BGE rerankers over 37 domain-specific and 50 multilingual datasets, has an 8k context length, evaluates by reranking 100 first-stage candidates down to 10, and improves the CODE category when paired with voyage-large-2. That is directionally useful, but the public blog post is still a vendor benchmark rather than a neutral paper.

The same caution applies to Relace’s code-retrieval launch post. Relace claims Recall@k of 0.71 on UI generation tasks versus Voyage at 0.61, and a 47% reduction in input tokens. Those numbers are highly relevant to your use case, but they should be treated as measured marketing, not as the same evidence tier as an academic benchmark.

Context-budget allocation and eviction policy

The best primary-source guidance on “what to evict first” is now surprisingly specific. OpenDev’s 2026 technical report describes Adaptive Context Compaction with five pressure thresholds: warning at 70%, observation masking at 80%, fast pruning at 85%, aggressive masking at 90%, and full compaction at 99%. At 80%, older tool results are replaced with compact reference pointers, keeping the latest outputs at full fidelity; at 85%, older results outside a protected recency budget are replaced with [pruned]; at 99%, the entire history is archived to disk and only the middle portion is LLM-summarized, while recent messages are preserved verbatim. Measured result: ACC reduced peak observation-context consumption by about 54%, often avoiding emergency compaction in typical 30-turn sessions.
11

OpenDev’s report also quantifies an upstream optimization that matters a lot in coding assistants: per-tool summarization. File reads are turned into metadata summaries, and large outputs are offloaded to scratch files with short previews. The report says a single long-running test suite could previously consume 30,000 tokens in one tool call; the per-tool summarizer reduced most of those cases to under 100 tokens, and the added 8,000-character offloading threshold extended typical sessions from 15–20 turns to 30–40 turns before compaction. In budget-allocation terms, the evidence says: evict or compress tool outputs first, not user intent or recent operational detail.
11

The same report argues for a fixed-slot memory split: compressed long-range context plus verbatim short-range context. Its “dual-memory” design keeps an episodic summary capped at 500 characters and the most recent six exchanges verbatim. That is strong support for the “fixed-slot budgets with floors” idea: give strategic memory a hard cap, give recent working memory an immutable floor, and force older tool chatter to compete for the remaining space.
11

ContextBudget pushes that logic further by making compression policy budget-aware rather than static. BACM exposes the remaining context budget before loading the next observation and lets the agent choose among no compression, selective aggregation, or full aggregation depending on pressure. In the authors’ evaluation, the method stayed much more stable as budgets shrank from 16k to 4k tokens, and at a fixed 8k budget it beat MEM1 while using fewer compression calls on lighter workloads: for 2- and 8-objective tasks, F1 improved from 0.84 to 0.91 and 2.35 to 2.79 while compression calls fell 41.7% and 35.8%, respectively. On harder 16- and 32-objective settings, compression calls increased, but so did payoff: F1 improved by 67% and 143%.
12

A separate, coding-specific cost study gives a concrete answer to “what parts of code should be compressed first?” In the 2026 minification paper for state-in-context agents, source code accounted for more than 90% of repair-prompt tokens, and the authors achieved a 42% average reduction in input tokens with a 12-point drop in resolve rate. Their failure analysis is especially practical: most transformations caused at most a 4% performance decrease relative to baseline, but dedenting was the clear outlier that hurt performance much more. That suggests a useful eviction/compression order for code already selected as relevant: first remove comments, docstrings, redundant whitespace, and possibly imports; be much more cautious with indentation loss or aggressive symbol renaming.
13

Finally, the long-context placement problem still matters. “Found in the Middle” ties lost-in-the-middle degradation to a U-shaped positional bias and reports up to a 15-point improvement on long-context utilization and RAG performance after calibrating that bias. Even if you do not retrain or calibrate the model, the engineering implication is immediate: when you assemble the final context pack, place the most decision-relevant snippets at the edges of the prompt rather than burying them in the middle.

Graph and structural retrieval

If your goal is “precise context, not broad RAG,” the current evidence strongly favors language-aware structure over plain chunk similarity. MarsCode Agent explicitly states that it uses the Language Server Protocol for “global and precise code retrieval” on the user’s machine. LspRag takes the same idea into an academic setting: it reuses mature LSP servers to retrieve precise symbol definitions and references for every used symbol in a focal method, and reports line-coverage gains of up to 174.55% over the best baseline for multi-language real-time unit test generation.
15

That precision often translates directly into token savings. The agent-lsp OSS MCP server reports that structured LSP responses use 5–34x fewer tokens than grep/read workflows on the same tasks. Its most concrete benchmark says a blast-radius analysis on HashiCorp Consul used 17.7MB through grep versus 841KB through LSP, while reducing tool calls from 5,534 to 119. This is not a peer-reviewed paper, but it is one of the clearest published measurements of what many code-agent builders observe in practice: semantic code-intelligence queries massively outperform “grep then read more files” when the task is definition/reference/caller/callee lookup.
16

SCIP is the main standard here. Official SCIP sources define it as a language-agnostic protocol for indexing source code so tools can provide “go to definition,” “find references,” and related navigation. The repo lists indexers for Java/Scala/Kotlin, TypeScript/JavaScript, Rust, C/C++, Ruby, Python, C#/.NET, Dart, PHP, and more, and Sourcegraph documents cross-repository navigation driven by symbol IDs from SCIP indexes. There are no official token-savings numbers in the SCIP docs I reviewed, but SCIP’s value for code assistants is easy to state precisely: it gives exact symbol-level retrieval instead of similarity guesses.
17

Graph-based code retrieval papers now show that this structural precision can improve both localization accuracy and cost. GraphCoder’s code-context graph improved code-match exact match by an average of +6.06 and identifier match by +6.23 over baseline retrieval-augmented methods while using less time and space. That is strong evidence that graph-aware retrieval can beat sequence-only retrieval for repository-level code completion.
18

LocAgent goes further on issue localization. It parses a codebase into a directed heterogeneous graph over files, classes, functions, imports, calls, and inheritance edges, and reports up to 92.7% file-level localization accuracy. The paper’s abstract also states that its fine-tuned Qwen-based setup reaches comparable results to proprietary SOTA models at about an 86% cost reduction, and improves downstream issue resolution pass@10 by 12%. For your use case, that is one of the best current demonstrations that structural retrieval can simultaneously increase precision and reduce cost.
19

KGCompass is similarly compelling for repository repair. Its repository-aware knowledge graph links issues and PRs with files, classes, and functions, narrows the search to the top 20 relevant functions, and reports 45.67% repair performance, 51.33% function-level localization accuracy, and about $0.20 per repair on SWE-bench Lite. The paper also finds that 69.7% of successfully localized bugs required multi-hop graph traversals, which is exactly the kind of case where broad chunked RAG tends to overfetch and underfocus.
20

Newer systems such as Codebase-Memory are pushing this toward infrastructure: a persistent tree-sitter-based knowledge graph exposed via MCP, parsing 66 languages and supporting call-graph traversal, impact analysis, and community discovery. The abstract explicitly positions it as an alternative to token-heavy repeated file-reading and grep-searching. At the moment, though, this is still more an architectural direction than a mature published token-ablation benchmark.

Self-hosted and cloud-based stack choices

For self-hosted stacks, the best-supported recipe is: tree-sitter or SCIP indexing for symbols and references; BM25 or ripgrep for exact-match recall; dense retrieval only for broader semantic candidate generation; a self-hostable reranker such as jina-reranker-v3 for top-N trimming; and LSP or graph lookups as a verifier when the task is fundamentally structural. This stack keeps the expensive model window reserved for the final, already-trimmed evidence rather than for discovery. The strongest evidence behind it comes from Aider’s symbol map, Jina’s reranker paper, SCIP’s precise code navigation, GraphCoder/LocAgent/KGCompass, and the LSP token-efficiency measurements.

For cloud-API-heavy stacks, the main attraction is ease and retrieval quality without building a lot of local indexing infrastructure. Anthropic’s contextual retrieval plus a cloud reranker is a good example: it improves retrieval failure rates substantially, but it shifts some of your cost to preprocessing and reranking time. Voyage’s rerankers fit the same profile: easy to drop into an existing stack, very strong retrieval quality, but less transparent about token-cost curves and more exposed to recurring API spend.

In practice, the best compromise for large codebases is often mixed. Keep structure and first-stage recall local — tree-sitter, SCIP, BM25, ripgrep, maybe a local vector DB — then use a cloud reranker only on a small candidate set, and only after lexical and structural filters have already cut the search space down. That design is consistent with Anthropic’s “top 150 to top 20” workflow, Jina’s “top 100 into reranker” evaluation, and the general A-RAG lesson that progressive narrowing matters more than raw retrieval power.

Bottom line for an agentic coding assistant

If you want the shortest actionable synthesis, it is this: start with structure, not full files; retrieve snippets or signatures before bodies; combine lexical plus dense retrieval for candidate recall; rerank only a small candidate set; and make all post-retrieval context management budget-aware instead of waiting for overflow. That pattern is supported across Aider, A-RAG, Anthropic contextual retrieval, OpenDev ACC, ContextBudget BACM, and LSP/graph retrieval systems.

The most defensible “minimum necessary context per step” pipeline for a large-codebase assistant in mid-2026 looks like this: a repo map or SCIP/LSP symbol view for the whole project; exact-match plus dense candidate generation for maybe tens to low hundreds of items; reranking down to a small shortlist; snippet/signature exposure first; full body reads only on explicit demand; deduplication of anything previously read; and staged compaction of old tool outputs once the session crosses roughly the 70–80% budget zone. When you must pack the final prompt, keep system instructions and recent working context intact, and place the highest-value code evidence near the front or back of the prompt rather than the middle.

In terms of concrete numbers, the most useful ones in the current literature are these: A-RAG cuts retrieved tokens by about half on some multi-hop tasks while improving accuracy; Anthropic’s contextual retrieval stack cuts retrieval failures by up to 67% with reranking; OpenDev’s compaction cuts peak observation context by about 54%; state-in-context code minification cuts average prompt input by 42% with a measurable accuracy hit; agent-lsp reports 5–34x token savings for structured semantic queries; LocAgent reports about 86% cost reduction with stronger localization; and KGCompass localizes and repairs with a top-20-function graph filter at about $0.20 per repair. Those are the strongest “measured, not just argued” data points I found.

Open questions and limitations

The main limitation of the current evidence base is that many influential coding-assistant ideas still publish architecture before rigorous cost-accounting. Aider’s repo map, SCIP-backed navigation, MarsCode’s LSP retrieval, and systems like Codebase-Memory make strong structural arguments, but only some of them publish explicit token-vs-accuracy ablations against naive full-file context. By contrast, document-RAG papers and vendor blogs often have better published retrieval metrics than code-agent papers do.

A second limitation is transfer. Late chunking, contextual retrieval, and some budget-aware context-management work were measured on document QA, web search, or long-horizon agents rather than directly on repo editing. They are highly relevant and often clearly transferable, but they are not the same thing as a controlled benchmark on real code-editing sessions with tool-use traces.

The third limitation is source type. Some of the most practically relevant numbers — Relace’s 47% token reduction, Voyage’s reranker wins, and agent-lsp’s 5–34x token savings — come from vendor or OSS maintainers rather than neutral academic evaluations. I would absolutely use those results to prioritize experiments, but I would not treat them as final truth until they survive your own evals on your repositories, query mix, and step-by-step agent traces.
