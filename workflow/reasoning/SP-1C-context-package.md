1.3 M4 COMMIT PATH AUDIT -- FINDINGS

VERDICT: teikoku's integrator does NOT have the standalone engine's dirt-baseline silent-pile bug class. Three independent structural guards, all confirmed present in integrator.py (conductor/integrator.py, 477 lines):

1. Dirty-tree gate BEFORE any real-repo mutation: integrate_verified_task (line 84) calls self._repo_is_dirty() (line 437, `git status --porcelain` on repo_root) at the top of the try block; if dirty AND block_dirty_checkout (config.safety.block_dirty_integration_checkout, true in both lane configs), returns NEEDS_REVIEW "dirty_checkout_blocks_integration" immediately -- no patch computed, no worktree touched, no baseline read. This is the guard the plan calls "pre-existing dirt".
2. Every integration gets a FRESH git worktree branched from a freshly-read HEAD: `current_head = git rev-parse base_ref` computed live at integration time (not cached), then `git worktree add -b branch integration_path current_head` at a uuid4-suffixed path (`integrate_{task_id}_{uuid[:8]}`, never reused). The patch itself is `git diff source_base_commit` taken INSIDE the worker's own isolated source worktree, so a failed prior attempt's dirt (which would live only in ITS OWN now-abandoned worktree) can never leak into this diff.
3. Real-repo merge is `git merge --ff-only branch` (line ~230) -- fast-forward-only, so if repo_root moved between the dirty-check and the merge (a race), the merge fails and is caught by the outer `except Exception` (line ~256) -> NEEDS_REVIEW "ambiguous_integration_failure", never a silent blend. Concurrency is additionally serialized at the DB level: _start_integration (line 288) raises IntegrationBusy if another integration row is PENDING/APPLIED (line ~306-309), so only one integration runs at a time.

Scope guard CONFIRMED present (integrator.py ~line 128-146): when "elai" in self.packs, every `diff --git a/X b/Y` path in the patch is checked against `.elai_cc/` prefix; any path outside it -> NEEDS_REVIEW "diff_touches_non_elai_cc_path" (patch never applied). This is the exact structural fix for the incident already in this session's git log (commit 21df474 "untrack the three plan/reasoning docs the glm committer force-added").

maintainer-voice commit_message CONFIRMED wired, with one caveat: conductor_loop.py ~line 315-318 builds `_cmsg` from `task.objective`'s first line, `(_first[:1].lower() + _first[1:])[:100]` -- lowercases the first character only, truncates to 100 chars, passes as integrate_verified_task(commit_message=_cmsg). It imports only subprocess+Path -- no leases import, no reclaim call anywhere in the file.

leases.py has the exact primitives needed: reclaim_expired (line 380, unconditional TTL-based reclaim with mutation-evidence-aware disposition: NEEDS_REVIEW if disconnected_after_mutation or mutated, FAILED if attempts>=max_attempts, else READY-requeue) and reclaim_stale_heartbeats (line 441: marks any lease whose `heartbeat_at <= now-stale_after_seconds AND lease_expires_at > now` as expired-now, then delegates to reclaim_expired). conductor_loop.py lines 169-170 already call BOTH every normal pass: `scheduler.leases.reclaim_expired(utc_now())` then `.reclaim_stale_heartbeats(config.limits.heartbeat_stale_seconds, utc_now())` (600s per both lane configs). This periodic call is why the bug is TTL-shaped rather than permanent: a lease orphaned by a driver crash is only picked up once its heartbeat has been silent for heartbeat_stale_seconds (600s) -- during that window a restarted driver's new workers cannot acquire the held slot (worker_cap capacity hostage), exactly per the P8 handoff description.

Needs: import LeaseManager from leases; instantiate against the walk config's state_db + worktree_root (state/control.db, elai-worktrees per conductor.elai-walk.toml -- walk_control.py currently hardcodes neither, would need the same path constants diskguard.py already hardcodes as defaults); call `.reclaim_expired(now)` then `.reclaim_stale_heartbeats(0, now)` (threshold=0, not the configured 600s -- forces every currently-non-expired-but-owned-by-a-dead-process lease to be treated as stale immediately, which is semantically correct on a restart since we KNOW the prior driver is gone). Reuses the existing mutation-evidence-aware disposition logic (inspect_worktree_mutation, line 537) rather than a blind force-free, so an orphaned lease that had already mutated its worktree still routes to NEEDS_REVIEW appropriately instead of being silently re-queued. 1.4b SEAM -- P7 INFRA-FAILURE MISCLASSIFICATION

Confirmed NOT yet fixed, and confirmed there is currently NO "infra" concept anywhere in the live (non-venv, non-test) conductor source: grep for "Errno 5|Errno5|worktree-prep|worktree_prep|Input/output error" across all *.py hits only diskguard.py's own docstring (describing the historical incident, no handling) and one unrelated brain_store.py comment. grep for a literal `infra` field/flag across all *.py hits zero real matches (only venv noise + one unrelated "infra" = infrastructure comment in conductor_db.py). So the P7 handoff's "logged infra=False" is descriptive of the gap, not a real field being set wrong.

classify_error_category (worker_adapter.py line 804-828) returns one of: rate_limited, transient_provider_error, context_window_blocked, timeout, cancelled, allowed_write_violation, worker_failed, or None. The token lists backing rate_limited (classify_rate_limit, line 749: 429/quota/rate-limit/throttle/exhausted/concurrency-limit) and transient_provider_error (classify_transient_provider_error, line 792, _TRANSIENT_PROVIDER_TOKENS: 524/cloudflare/stream-disconnected/bad-gateway/connection-reset/etc, all HTTP/network-shaped) contain nothing filesystem/OS-error-shaped. An Errno5 IOError therefore falls through every check to the generic `worker_failed` category (or, if it hits during/after a worktree mutation, into scheduler.py's ambiguous-mutating-failure path -- see below), which is the exact P7 symptom.

The refund pattern to clone already exists and is proven: scheduler.py lines ~287-311, `is_transient_provider = error_category in TRANSIENT_PROVIDER_CATEGORIES or status_hint in TRANSIENT_PROVIDER_HINTS`; `if is_transient_provider and not mutated:` -> `self.budgets.refund_attempt_budget(task_id, "transient_provider_error_no_mutation")` + `self.leases.release(lease_id, "READY", ...)` + model cooldown. This is structurally exactly what an infra category needs (refund, READY, never NEEDS_REVIEW, never burn an attempt).

FIX SEAM (three call sites, all required together):
1. worker_adapter.py classify_error_category (line 804): add an infra-error check (Errno 5 / "Input/output error" / OSError-typed exception / a worktree-prep-stage failure signature) ahead of the generic exit_code!=0 fallback, returning a new category e.g. "infra_error".
2. scheduler.py category constants (lines 19-30): add `INFRA_ERROR_CATEGORIES = {"infra_error"}`, and a branch mirroring the transient_provider refund block (lines ~287-311) for it.
3. scheduler.py _is_ambiguous_mutating_failure (line 545-563): this function returns True (-> NEEDS_REVIEW) whenever `mutated=True` and error_category is in AMBIGUOUS_ERROR_CATEGORIES or TRANSIENT_PROVIDER_CATEGORIES, OR unconditionally when `exit_code != 0` (its final `return exit_code != 0`). A worktree-prep Errno5 that happened to leave partial files (mutated=True per inspect_worktree_mutation) would hit this function BEFORE reaching the plain refund branch and get routed to NEEDS_REVIEW regardless of category -- so the infra category needs an explicit carve-out added to this function's condition list too (return False for infra_error even when mutated), not just a new top-level refund branch. Missing this third seam would leave the fix incomplete for the exact "stage CONTEXT" case P7 describes.
