KEY DECISION 1 — "CoW" is conceptual, NOT a filesystem reflink (IC-9, binding):
NTFS has no reflink/copy-on-write at the FS API level. ReFS/Dev Drive block-cloning (Win11 22H2+) exists but needs the FSCTL_DUPLICATE_EXTENTS_TO_FILE path and is not universally available. The Tier-1 cross-platform default is pooled WARM git worktrees: source files isolated per worktree, cargo build artifacts shared via the workspace target-dir. This is directory isolation via `git worktree`, not an FS-level clone. NO reflink crate, NO NTFS clone API was introduced (verified: branch_workspace.rs uses only std::process::Command git subcommands + std::fs/std::path). Linux overlayfs/btrfs reflink is the Tier-2 Linux-gated additive impl behind the same trait; the E2B-class cloud-sandbox adapter is an optional trait impl, never a hard dep.

KEY DECISION 2 — git toplevel trap (the single riskiest mechanical fact):
`git rev-parse --show-toplevel` from inside F:/.ELAI_workflow/.elai_cc returns F:/.ELAI_workflow (the PARENT workflow root). .elai_cc is a SUBDIRECTORY of the parent repo, not a standalone repo. A `git worktree add` therefore registers worktrees against the parent repo. WorktreePoolImpl::resolve_toplevel runs `git rev-parse --show-toplevel` with cwd=anchor and uses the resolved toplevel as the git cwd; worktree roots live under toplevel/.wt-scratch/<session>/ which is OUTSIDE .elai_cc, so worktree creation never contaminates the project source tree. A worktree placed inside .elai_cc would corrupt the tree.

KEY DECISION 3 — trait is NOT dyn-compatible; thread the concrete type:
BranchWorkspace uses native-async-in-traits (RPITIT: methods return `impl Future`), which makes it NOT object-safe — `dyn BranchWorkspace` will not compile. The exploration's planned `Option<Arc<dyn BranchWorkspace+Send+Sync>>` on BspConfig is therefore unbuildable. Chosen fix: thread the CONCRETE Option<WorktreePoolImpl> through BspConfig. WorktreePoolImpl already derives Clone+Debug, so BspConfig keeps its derives; no boxing, no viral generic, no dyn dispatch. The trait abstraction is preserved for the contract test and the future Tier-2 overlayfs/cloud impls (open/closed); production has exactly one Tier-1 impl so it does not need dyn. Alternatives rejected: (a) Pin<Box<dyn Future>> boxing — allocates + ugly; (b) generic W: BranchWorkspace on BspEngine/BspConfig — viral param across all bsp tests + task_runner, large blast radius for zero benefit while there is one impl.

KEY DECISION 4 — ConflictEscalated halts (Tier-1); H-49 trunk-rollback DEFERRED:
The plan text (lines 18-19) is explicit: overlap => ConflictEscalated AND HALTS. barrier_merge orders branches by ascending SSB seq (GD-2), last-seq-wins on NON-overlapping relative paths, and on a same-path/differing-bytes overlap it emits ConflictEscalated, returns Err, and writes NOTHING to trunk (no partial write). The H-49 architecture::timetravel::materialize() trunk-rollback path is NOT wired here: materialize() needs a FileManifest + CAS root that the barrier does not hold, and full trunk rollback is heavyweight Tier-2 work outside this session's budget. This is a documented DEFER. NOTE: it is NOT a code stub (the conflict path is COMPLETE as a Tier-1 halt — there is no TODO marker and no DARK fn; every new pub fn is wired). A stubs.md row (I-2-h49-trunk-rollback, deferred_capability) was drafted but could NOT be written this session because the EXECUTING FSM path-gate blocks Edits under workflow/sessions/; the controller/auditor can add it. The ConflictEscalated SSB row is the load-bearing forensic artifact; rollback is the follow-on.

KEY DECISION 5 — merge order = SSB seq, sourced from write_payload's return:
There is no Ssb::current_seq() method. spawn writes the BranchWorkspaceEvent::Spawned row via write_payload, which RETURNS the assigned seq; that becomes BranchRoot.seq, the deterministic merge-order key. The pool holds an Option<Arc<Ssb>> (wired via with_ssb in production, mirroring InProcessSupervisor::ssb) so spawn/escape_check emit real rows. When no Ssb is wired (offline contexts) spawn falls back to the pool size as a deterministic monotonic local counter so ordering is still stable. GD-5 honesty: this is action-stream/byte-identical-merge determinism only — NOT a claim that the underlying agent generation is deterministic (temp=0 is not determinism, LM-7).

KEY DECISION 6 — escape_check wired as merge-time defense-in-depth (not left dark):
A production-caller self-check (manual grep; the off-agent checker was FSM-blocked in EXECUTING) found escape_check + pool_len had ONLY contract-test callers (R-7 dark). Resolution WITHOUT fabricating a call site: (1) escape_check is now called inside barrier_merge on every collected branch file before it is staged for trunk — an HONEST defense-in-depth gate (a symlink inside a worktree could otherwise smuggle out-of-root bytes into the merge), so escape_check is genuinely production-reachable via BspEngine::run (engine.rs:471) <- task_runner:7021. This adds real safety, it is not a meaningless wrapper. (2) pool_len had NO caller at all (the contract test uses .is_dir() not pool_len) so it was DELETED rather than marked dark — removing dead code beats a dark marker. Net: every new pub fn now has a non-test production caller; no WIRE-DARK marker is needed.
