THE PROBLEM (grounded, owner-confirmed by reading the live vault)
================================================================================
The shipped U9 leaderboard ranks EVERY modality (coding included) on hf-trending = HF trendingScore, a POPULARITY/download signal, not capability. The live coding page top-ranks "zai-org/GLM-5.2 | 535" and fills the rest with GGUF quants (verified: topics/models/leaderboards/coding/leaderboard-coding.md). It answers "what repo is hot on HF today," not "what model is best at coding." Root cause: A-4 assumed the real sources (LMArena, SWE-bench.com) were JS-only and unscrapable, and the one real source it tried (Aider) went through a flaky http_text->LLM extraction that fell back to popularity. This plan fixes both: it wires the STRUCTURED capability endpoints that DO exist (deterministic parse, no LLM extraction), adds a self-maintaining benchmark SCOUT, and surfaces a best-model-per-category headline.

LOCKED DESIGN DECISIONS (D-*)
================================================================================
D-1 DETERMINISTIC parse for STRUCTURED sources; LLM extraction ONLY for genuinely-unstructured HTML/text (D-1 research-machine: model extracts, python ranks). The lmarena datasets-server rows, the Aider YAML, and the SWE-bench JSON are all structured -> pure python parse, ZERO model tokens, no flaky extraction. This alone fixes the coding-board WARN.
D-2 NATIVE SCALE per modality; rank-aggregation WITHIN a modality only (GL-3). No global cross-modality score, ever. A modality's page carries one composite ranking + the per-source native tables behind it.
D-3 SOURCE REGISTRY is DATA not code (research-machine D-3 inherited): a benchmark-source registry (research_benchmarks.toml, or a [[benchmark_source]] array in research_topics.toml) = rows {id, modality, fetcher, url/params, format, score_type, scale, weight, staleness_days, enabled}. Adding a benchmark = one row, zero code, once its fetcher family exists. The SCOUT proposes new rows; the owner/gate enables them.
D-4 GUARDED upsert only (research-machine D-15/A-4 inherited): living pages written ONLY via brain_store_pages.upsert_page, machine-owned models/leaderboards/<modality>/ namespace, type=leaderboard; can never overwrite an owner page. No new file/delete surface.
D-5 STALENESS + CONFIDENCE gate: a source row whose data date is older than staleness_days (config) is FLAGGED stale on the page + excluded from "current best" (never silently ranked as current, dated-data discipline). A modality with only stale/popularity data says so on its page and in the best-per-category surface.
D-6 HONEST-DEGRADE (GL-4): a modality with no fetchable capability source keeps hf-trending LABELED popularity; the best-per-category surface says "popularity-only, no capability source yet" for it, never fabricates a capability rank. Missing source data defers, never guesses.
D-7 the SCOUT stays in the classify/extract lane (research-machine D-1): it DISCOVERS + VALIDATES sources, python ranks. It never writes a ranking or a plan file; validated candidates land as registry-candidate rows the owner/gate approves. It runs P3 (idle filler) on the existing 24/7 lanes; the grounding follow-ups (BigCodeBench, LiveCodeBench, VBench, the 12 un-curled lmarena configs, TTS_Arena) are its seed targets.
D-8 privacy/scope (research-machine E-8 inherited): no /mnt/f read, public endpoints only, all writes under TEIKOKU_BRAIN_DIR + the state dir. The scout's web search reuses the machine's existing fetch/SearXNG path.
D-9 BEST-PER-CATEGORY is a materialized machine-owned page (D-4): models/leaderboards/best-per-category.md, one row per modality -> current best model + score + benchmark + date + staleness/confidence flag. The owner's headline surface; also brain-RAG-indexed (BRAIN-RAG U1) so "brain, best coding model" retrieves it, and digest-surfaced on a change.
