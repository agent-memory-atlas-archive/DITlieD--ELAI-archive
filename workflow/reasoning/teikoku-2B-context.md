2. THE AUTO-INDEXER — design (the NEW tool 2.4 must build)
================================================================================
PURPOSE: read workflow/handoff/*.md and append each as memory event(s) into the P2-A log (grep+semantic+timeline+global), idempotently, so re-running does not duplicate.
LOCATION: conductor/handoff_indexer.py (lives beside memory_store.py; it is RUNTIME memory machinery, not a static gate. The .claude/tools/ dir is the frozen-gate home — do NOT put runtime memory code there). Expose a CLI main() so the memory-writer ROLE (and any cron/hook) drives it: `python3 handoff_indexer.py [--project <id>] [--handoff-dir <path>] [--file <one.md>]`.

GRAIN (decision, with lean): index per HANDOFF ENTRY, not per whole file. Rationale: a topic handoff (handoff-protocol.md) is ONE file appended across many sessions; per-file indexing re-ingests the whole growing file each run and gives one coarse blob. Per-entry gives one event per dated session entry (the natural changelog unit), stable IDs, and clean timeline granularity. Parse entries by the handoff-protocol structure: the INDEX block lines ("{date} session {id} - {hook}") + the dated entry blocks separated by the rule line ("----"). Each dated entry -> one event.
  - event_type = "handoff" (open text; distinct from the live grep_handoffs synthetic "handoff" tag so timeline filtering works). Optionally also emit event_type="changelog" alias is NOT needed — keep ONE type "handoff".
  - project_id: derive per handoff. The build handoff teikoku-build.md -> project "teikoku" (or "conductor"); a per-project handoff under a project's workflow/handoff/ -> that project's id. Default to the --project arg, else infer from path, else DEFAULT_PROJECT_ID. (For TEIKOKU build memory, project_id="teikoku".)
  - session_id: parse the "{date} session {id}" stamp from the entry header when present, else "".
  - payload: {"summary": <entry SUMMARY line(s)>, "topic": <slug from filename/title>, "source_file": <name>, "entry_date": <date>, "text": <full entry body>}. The body goes into payload so grep_events (SQL LIKE over payload_json) AND the semantic leg both see it.

IDEMPOTENCY (the hard requirement — re-index must not duplicate):
  deterministic event_id = stable_idem_key(["handoff", topic_slug, entry_date, session_id, sha256(entry_body_normalized)]). (models.py:38).
  Append-only triggers forbid overwrite, so the loop is: compute event_id -> SELECT 1 FROM events WHERE event_id=? (or memory_store.query/grep by id) -> if exists, SKIP; else append_event_memory(..., event_id=event_id). Including a content hash in the id means an EDITED entry (rare; entries are immutable history per handoff-protocol) yields a new id; an unchanged re-index is a no-op. Report counts: indexed / skipped / total.
  CURRENT-STATUS + INDEX are the only LIVING fields in a handoff (overwritten each session). Handle them by either (a) excluding the CURRENT STATUS line from the per-entry hash (it lives in the head, not in dated entries) — entries themselves are immutable so this is clean, OR (b) emit a single "state" event for CURRENT STATUS keyed by topic_slug only (no date), which a SELECT-first-then-append cannot update under append-only — so instead emit a fresh "state" event each run ONLY if the CURRENT STATUS text changed (hash-gated), giving an append-only history of status changes. LEAN: (a) for entries + (b)-hash-gated for CURRENT STATUS, so the timeline shows status drift without dupes.
