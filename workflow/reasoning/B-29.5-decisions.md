## p99 budget rationale (500 ms)

The 500 ms p99 budget maps to the user-facing Auditor `PostToolUse` hook
latency budget: a symbol-graph query that runs inside an audit hook must
return in under 500 ms p99 or the auditor stalls the edit loop. The contract
enforces `p99_ms <= 500` per tool per tier and `peak_rss_mb_during_workload
<= 2048 MB` per tier.

## p99 budget trip / B-29 reopen?

**No reopen triggered.** The contract-gating workload numbers for vscode and
postgres are within the 500 ms p99 budget. The raw cold-cache
`symbol_graph_scale` bench showed vscode impact_radius p99 = 689 ms and
symbol_context p99 = 5132 ms, but those are cold-probe worst cases on
high-fan-in targets, NOT the realistic workload mix the contract gates on.
If a future run measures a workload p99 > 500 ms on a real tier, B-29 must
be reopened per ACCEPTANCE — do NOT relax the budget.

## criterion-vs-stdlib decision

**RESOLVED to stdlib.** The existing benches use `std::time::Instant` +
`std::hint::black_box` with `harness=false` (Cargo.toml `[[bench]]` entries).
Adding `criterion` was REJECTED without user confirmation (no new deps). The
stdlib approach is sufficient for p50/p95/p99 measurement at the sample counts
used (20 per target for raw bench, 1000-query mix for workload).

## Memory measurement approach

**stdlib only.** RSS via `/proc/self/status` (Linux) or `wmic process get
WorkingSetSize` (Windows). `jemalloc` and `procfs` crate REJECTED without
user confirmation. The `MemorySnapshot::from_stats(rss, CacheStats)`
constructor (scale_memory.rs:28-46) snapshots process RSS + cache LRU state.
On Windows the wmic path is used; on Linux /proc is used; unsupported
platforms return 0 (documented, not silent).

## CI schedule policy

**Nightly, not per-commit.** Rationale: cloning linux/chromium is multi-GB
and indexing takes minutes-to-hours; running this on every commit would
block PRs. The contract test (`scale_p99_budget_contract`) runs per-commit
but SKIPs when `populated_at = "null"` or the file is absent, so a missing
metrics file does not fail CI. The nightly job populates the metrics file
with fresh measurements; a drift in p99 above 500 ms fails the nightly
contract gate and triggers a B-29 reopen investigation.

## Environment blocks (this run)

1. **linux + chromium clones did not complete** within the executor's
   per-step time budget (depth=1 clones of 36 M / 35 M LOC repos are
   multi-gigabyte and slow on this host's bandwidth). Marked UNVERIFIED with
   `skipped_reason = "clone_did_not_complete_in_executor_budget"`. No numbers
   fabricated.
2. **Bench project_id mismatch (FIXED).** The three benches
   (`symbol_graph_scale.rs`, `workload.rs`, `scale_memory.rs`) used literal
   tier names (`"vscode"`, `"postgres"`, ...) as the `SymbolGraphCache`
   project_id, but the CLI builder (`crates/cli/src/symbol_graph.rs:47`)
   writes the blake3-derived `project_id_from_path` (e.g.
   `proj-c1c546cbbdbe49c5`). Every tier was skipped with "no
   symbol_graph_meta row". Fixed by adding `use elai_core::project_id_from_path;`
   and computing the project_id from the fixture root path in all three
   benches. The `elai_self` tier (which pointed at the workspace's stale DB)
   was removed from the benches — the `populate_elai_self_metrics` test owns
   that synthetic tier.
3. **Metrics write path (FIXED).** The benches wrote to relative
   `metrics/...` paths, which failed when `cargo bench` set a different CWD.
   Fixed by resolving the output path from `CARGO_MANIFEST_DIR` ancestors.
