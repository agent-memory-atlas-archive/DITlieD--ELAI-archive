C. THE WAKE MECHANISM OPTIONS (the central fork: how does a waiter BLOCK and get WOKEN without polling + file-free, given SQLite has no LISTEN/NOTIFY)
================================================================================
The waiter and the waker may be the SAME process or DIFFERENT processes/sessions (the cross-process hazard, §F). Each option is judged on: file-free? / no-poll-spam? / cross-session (cross-process)?

OPTION 1 — In-process threading.Event / threading.Condition (Python).
  A waiter thread blocks on Event.wait(); the event-emit path (update_task_status DONE) calls Event.set(). file-free YES. no-poll YES (a real block). CROSS-PROCESS: NO — threading primitives do not cross OS processes. Only works if A and B are threads in ONE process (e.g. one conductor process with a thread pool). LEAN: viable ONLY for the single-process intra-loop case (one conductor draining its own frontier with worker threads); INSUFFICIENT for "session B = a separate CC/conductor process". Useful as the in-process leg of a hybrid.

OPTION 2 — A cross-process OS primitive on the events table: a named FIFO / OS pipe / eventfd.
  The waker writes a byte to a FIFO on DONE; the waiter blocks on read() (or select/poll on the fd). file-free: BORDERLINE — a named FIFO IS a filesystem node (mkfifo), but it is NOT "polled" and NOT the file being re-read for content; it is a blocking-read wake channel. Reasonable reading of D-07 "file-free" = "not an FS-WATCH / not a timed content re-read", which a blocking FIFO read satisfies (no timer, no content poll). no-poll YES (blocking read). CROSS-PROCESS YES (a FIFO crosses processes). RISK: FIFO semantics on WSL2 ext4 (verify); a writer with no reader blocks/discards; lost-wakeup if the DONE byte is written between the dep-check and the read (§F). LEAN: a CANDIDATE for the cross-process case, but "file-free" purism may reject a FIFO — controller to rule. eventfd is Linux-only + same-process-tree-ish (needs fd inheritance), weaker for independent processes.

OPTION 3 — A Unix-domain socket (the conductor as a tiny notify server).
  A small in-process notify server (the conductor already runs ThreadingHTTPServer at slice_api.py:8787 — slice_api.py:20 BaseHTTPRequestHandler/ThreadingHTTPServer, HOST/PORT 127.0.0.1:8787) accepts subscriber connections; on a DONE event it pushes a notification to subscribers blocked on recv(). file-free YES (a socket is not a filesystem file; a UDS path is, but an AF_INET localhost socket is fully file-free). no-poll YES (blocking recv / a long-poll the server holds open). CROSS-PROCESS YES. This is the MOST general + most aligned with D-08's "event log + index powers session comms" (the comms hub IS a server). It also forward-fits Phase 4.4 "Session comms hub: shared event log + mailbox" (master plan line 198) — a notify server in P3-D becomes the P4.4 hub. RISK: adds a server lifecycle (start/stop, the conductor must be running for the wake to fire); the emit path (update_task_status, a pure DB write today) must reach the notify server (in-process call if same process, or a localhost POST if cross-process). LEAN: STRONGEST for the cross-process + forward-compat goal, IF a long-running conductor/hub process is acceptable. Reuses the existing HTTP-server pattern (slice_api.py).

OPTION 4 — A short-lived SQLite poll (read events WHERE event_seq > last every N ms).
  file-free: events.db is a file, but this is reading the EVENT LOG not an FS-watch — D-08 sanctions reading the event log. no-poll: NO — this IS a poll (a timed re-read). D-07 EXPLICITLY says "kill the poll-spam" / "never poll-spams 'wait 5 more minutes'". A SQLite poll at any interval is the thing being killed. CROSS-PROCESS YES. LEAN: REJECT as the primary mechanism (it reintroduces exactly what D-07 forbids). ACCEPTABLE ONLY as a long-interval SAFETY-NET backstop against a lost wakeup (§F) — e.g. a 30-60s belt-and-suspenders re-check UNDER a real event-wake, so a missed event eventually self-heals without hanging forever. Whether even that violates "no poll-spam" is a controller call (a 60s safety re-check is arguably not "spam"; a 500ms one is).

OPTION 5 — asyncio.Event / asyncio.Condition (Python async) — same cross-process limit as Option 1.
  file-free YES, no-poll YES, CROSS-PROCESS NO. The conductor loop is SYNCHRONOUS (time.sleep, threads — conductor_loop.py uses concurrent.futures per 3A §G, not asyncio), so introducing asyncio is a structural mismatch. base-cc IS async (TS/Bun), so on the CC side an in-process Promise/event is natural — but cross-CC-process it still doesn't cross. LEAN: in-process only; mismatched with the sync conductor.

OPTION 6 — The scheduler wakes a lease when deps flip (the "wake the loop on DONE" same-process variant).
  Instead of a separate waiter, the DONE-emit path (integrator/update_task_status) directly RE-RUNS schedule_frontier (or signals the loop's Event) so the just-unblocked READY task is leased immediately, no next-iteration wait. file-free YES, no-poll YES, CROSS-PROCESS: only within the one loop process. LEAN: this is the clean fix for the CONDUCTOR intra-loop "wait for next iteration" gap, and composes with Option 1/3 for the cross-process leg. It is NOT sufficient alone for "session B (separate process) woken by session A".

THE BASE-CC SIDE (the "CLI local copy" D-07 names): base-cc is TS/Bun, file-inbox-polled (B.4). The CC-side wake options: (a) replace the print.ts:2512 `await sleep(500)` poll with an event-driven block (a Promise that resolves on a notify — e.g. a localhost SSE/websocket from the conductor hub [Option 3], or an fs-event the OS pushes [borderline file-free]); (b) use the stopHooks.ts seam to hold the turn and resume on a pushed event (mirrors the parent-harness mcp_session_wait INTENT, B.5); (c) a chokidar/fs.watch on the inbox file — REJECT, that is still file-based (an FS-watch is exactly "file", not "file-free").

CROSS-LAYER LEAN (controller to confirm at the fork): the dep-done EVENT is born in the CONDUCTOR (update_task_status DONE). The WAITER may be a conductor process (Option 6 + Option 1/3) and/or a base-cc/orchestrate session (needs a cross-process push = Option 3 the hub, or Option 2 a FIFO). The cleanest, most D-08/Phase-4.4-aligned answer is a small NOTIFY HUB (Option 3) that the update_task_status emit feeds and that conductor/CC/orchestrate waiters subscribe to (blocking recv, no timer), with an OPTIONAL long-interval SQLite safety re-check (Option 4-as-backstop) for lost-wakeup self-heal. The single-process conductor gap is closed by Option 6 (wake the loop on DONE). This is a MATERIAL FORK (mechanism + which layers) -> the executor picks with grounding or STOP+handoff (it is not pre-settled by Section 0; D-07 names no mechanism).
