# P-25 candidate-to-core scientific binding — V1 repair candidate

Status: PLANNING CANDIDATE. This document repairs a pre-M1 scientific data-contract defect. It authorizes no source, test, M1 freeze, fixture, smoke, benchmark, Git, or deployment action until the authoritative P-25/V4 architecture/RECON-2/procedure contracts are migrated and independently audited.

Decision ID: `P25-CANDIDATE-CORE-BINDING-V1`.

## 1. Defect and required invariant

The V3 planning set cannot freeze as M1. Exo-v1.1 cards contain descriptive public-triage fields only, while the settled N4 API is `dispatch_core(harness, fixture)` and every RECON-5 procedure stores its operations, transitions, or candidate rows in the pre-generation sealed fixture. A generated candidate therefore has no input edge to `CoreResultV1`; all six arms can receive task-constant core results. P1/P2 would not measure candidate quality.

The repaired invariant is:

`archived completion bytes -> six CandidateSlotV1 records -> scored set + pinned-context survivor receipt/projection -> dispatch_core(harness, sealed_fixture, scored_set, receipt, projection, slot) -> minimal CoreFixtureInputV1 + CoreCandidateInputV1 -> candidate-bound CoreResultV2 -> ScientificArtifactV2`.

M3 freezes the complete four-handler table before any fixture exists. After sealing, the fixture's closed `executor_kind` discriminator selects exactly one member of that already-verified table; it cannot name, locate, authenticate, or load code. Candidate bytes cannot select a kind, core, module, path, command, runtime, toolchain, timeout, evaluator, or trust identity.

## 2. Exo card V2 and parser

Each generation/revision response contains exactly six cards in ASCII-ID order `C1..C6`, no prose before/after, LF line endings, and one final LF. Each card is exactly:

```text
### CANDIDATE Cn
- id: Cn
- mechanism_family: <nonempty NFC single line>
- target_area: <nonempty NFC single line>
- target_units: <nonempty NFC single line>
- expected_effect: <nonempty NFC single line>
- falsifier: <nonempty NFC single line>
- payload_json: <one-line strict JSON object>
```

The six public fields remain the exact exo-v1.1 projection consumed by `conjecture_triage_core`; `payload_json` is never passed into public triage. Every public value is strict UTF-8/NFC, nonempty, single-line, has no leading/trailing ASCII whitespace, and contains no C0/DEL control scalar; U+0020 is the only ASCII whitespace permitted internally. Prompt, request body, response body, and extracted completion content are archived and bound by exact `CompletionRecordV1` raw hashes before parsing. Required IDs, headers, field order, and cardinality are exact. A global decode/framing/cardinality/order/trailing-content defect makes that call's six fixed slots candidate-invalid; an unambiguously isolated closed-payload defect invalidates only its slot. Nothing is silently dropped. Tool use, timeout, transport failure, or archive failure remains architecture ABORT.

`CandidateCardV2={candidate_id,expected_effect,falsifier,mechanism_family,payload,target_area,target_units,schema_version}` with `schema_version="p25-candidate-card-v2"`. `payload` is a closed `CandidatePayloadV1` union selected only by the already-sealed fixture kind. The candidate carries no `executor_kind` field. The parser receives that kind out of band and rejects a wrong payload union/version as pre-core `CANDIDATE_PAYLOAD_SCHEMA`; such a mismatch reaching `dispatch_core` is `INTERNAL_INVARIANT` ABORT, never scientific INVALID. The JSON token following the exact ASCII prefix `- payload_json: ` must byte-equal `P25-CANONICAL-JSON-V1` serialization of the parsed payload with its final LF used as that field line's LF; extra whitespace, alternate key order, or a second serialization is invalid. `candidate_card_raw_sha256` hashes the exact header-through-payload-line bytes, and `candidate_payload_raw_sha256` hashes exactly the JSON-token bytes plus that one LF.

`CandidateSlotV1={candidate_card,candidate_card_raw_sha256,candidate_id,candidate_payload_raw_sha256,completion_raw_sha256,invalid_detail,reason_code,schema_version,status}` with `schema_version="p25-candidate-slot-v1"` is always emitted exactly six times in `C1..C6` order. VALID requires a complete card, both slot raw hashes, matching ID, and null reason/detail. INVALID requires a null card, the exact archived completion hash, closed detail, and `CANDIDATE_CARD_SCHEMA` or `CANDIDATE_PAYLOAD_SCHEMA`; slot raw hashes are present only if exact spans were isolated. Pre-core INVALID slots emit no `ScientificArtifactV2` and are assigned endpoint value `0/1` by analysis.

The publisher canonically constructs and publishes exact `CandidateSlotSetV1={arm_id,candidate_task_view_sha256,completion_raw_sha256,completion_record_sha256,fixture_sealed_sha256,revision_call_input_sha256,schema_version,set_role,slots,task_id}` with `schema_version="p25-candidate-slot-set-v1"` before triage. `completion_record_sha256=H(P25_COMPLETION_RECORD_V1,[C(CompletionRecordV1)])` binds model, prompt/request/response/content hashes, and token accounting; its content hash must equal the set's. `candidate_task_view_sha256=H(P25_CANDIDATE_TASK_VIEW_V1,[C(CandidateTaskViewV1)])` binds the exact prompt-visible task projection, while `fixture_sealed_sha256` binds its sealed source and hidden counterpart. `revision_call_input_sha256` is nonnull exactly for SCORED_REVISED and points to the exact source-completion/evidence/prompt binding; it is null for SCORED_INITIAL and REVISION_SOURCE. `task_id` is a canonical globally unique selected draft ID equal to the view's task ID. The completion record's unique `call_id` must be `P25:<task_id>:<arm_id>:<set_role>`, and its record digest may not be consumed by another set. Distinct call IDs/records may return byte-identical content and share `completion_raw_sha256`; that equality is valid and is not record reuse. `set_role` is exactly `SCORED_INITIAL`, `REVISION_SOURCE`, or `SCORED_REVISED`; arms 1..4 have one scored-initial set, while arms 5..6 have one revision-source then one scored-revised set. Every set contains the six complete slots in `C1..C6` order and every slot copies its completion raw hash. `candidate_slot_set_sha256=H(P25_CANDIDATE_SLOT_SET_V1,[C(CandidateSlotSetV1)])` binds each call; only scored-role set digests feed endpoints or scientific artifacts. The parser receives and rehashes the complete typed task view, enforces structural/static closure plus benchmark candidate-field names/types, but leaves validly typed reference-domain and dynamic-work checks to the core so the closed scientific negatives remain reachable.

The call and length-control surfaces are closed before any candidate exists. M1 fixes endpoint `http://127.0.0.1:8810/v1/messages`, model `kimi-k2-7`, `max_tokens=1400`, operational timeout `240000` ms, and the architecture's exact non-normalizing `P25-REQUEST-JSON-V1`/`P25_REQUEST_BODY_V1` plus accepted response-entity schema and 1,048,576-byte/65,536-byte-chunk read cap. One direct POST uses explicit JSON/identity headers with redirects, proxies, compression, cache, retry, and follow-up disabled. `max_tool_turns=0` is a local no-loop invariant and is absent from the three-key request body; any tool/non-text/wrong-model/extra-field response aborts without a second request. The request profile preserves non-NFC original completion bytes embedded in a revision prompt, so a candidate-invalid first response still receives its mandatory revision call. Before every POST the N12-minted sink issues the next exact execution permit; promotion appends the record to that index, and only the expanded randomized eight-call sequence can finalize `TaskExecutionLogV1`. The closed completion record is constructed/canonicalized and rehashes the exact prompt, canonical request entity, response entity, and unmodified single text-block UTF-8 content while the exchange is staged; only then are all four origins atomically promoted before return; no caller can substitute constants or protocol behavior, and every completion record repeats the frozen model and budget. P-25 also replaces Q-10's live token meter with a zero-call deterministic envelope over exactly `(EXO_RELEVANT,EXO_SHUFFLED,PAD_MATCHED)`: `count=(len(exact_utf8_prompt_bytes)+2)//4`, target = maximum unpadded count, pad token = UTF-8 `envelope_pad`, each shorter arm uses the greatest pad-unit count that does not exceed target, and exact spread must be at most `1/50`. DIRECT and both revision arms are excluded. The independent checker reconstructs the pad decision from archived prompt bytes; arm/tolerance/counter/measurement inputs and meter calls do not exist, so guard lifecycle accounting remains exactly one call for arms 1..4 and two for arms 5..6.

Candidate strings are preserved byte-for-byte for evidence. `MechanismIdentityV1={candidate_payload_raw_sha256}` is the non-hashed executable identity; exact payload-digest equality deduplicates within arm/task, so a repeated executable payload is counted at most once even when prose differs. The normalized descriptive tuple `(mechanism_family,target_units,expected_effect,falsifier)` after NFC, outer trim, ASCII-whitespace collapse to one U+0020, and Unicode casefold remains diagnostic evidence only and cannot multiply P1. No semantic or embedding deduplication exists.

## 2.1 Frozen prompt-visible candidate task views

Generation must receive enough data to construct a valid candidate without seeing expected answers. The sealed fixture contains exactly one closed `CandidateTaskViewV1` union member, and only that member plus the M1-frozen kind-specific candidate schema may enter generation/revision prompts:

- `GrepCandidateTaskViewV1={documents,task_id,text,view_version}` exposes baseline document IDs and bytes; clauses remain hidden.
- `ParserCandidateTaskViewV1={cases,task_id,text,view_version}` exposes case IDs and typed inputs; reference operations and expectations remain hidden.
- `SimulationCandidateTaskViewV1={cases,task_id,text,view_version}` exposes case IDs, events, typed inputs, and required initial-state IDs; the reference machine and expected terminal/trace rows remain hidden.
- `BenchmarkCandidateTaskViewV1={baseline_rows,candidate_field_schema,task_id,text,view_version}` exposes pair IDs, baseline fields, and the exact required candidate field names/types; reference rows, filters, metrics, thresholds, labels, and gates remain hidden.

Each `view_version` is a fixed kind-specific V1 value, every view is recursively closed, and `task_id` byte-equals the containing draft/sealed fixture ID. The prompt renderer receives the typed view plus `VerifiedHarness`, derives its kind from the closed union, and resolves the corresponding exact M1-root-bound public `CandidateSpecV1` file internally. Evaluator-internal intrinsic/DSL specs are never prompt input. It accepts no caller kind/spec/digest and exposes no other fixture field. Every prompt block must strict-UTF-8 round-trip, contain no NUL, and already be NFC; otherwise the M2 draft is DATA_INVALID before a request. Prompt hashes, the view digest, the sealed-fixture digest, and the containing slot-set digest make that projection independently checkable.

The selected M1 candidate-spec is itself a prompt-public, task-independent construction contract. It contains only the finite candidate payload grammar, types, enums, caps, and canonicalization rules. Fixture instances, sealed inputs, reference rows/machines, expected values/traces, hidden filters/metrics/thresholds, task labels, conformance goldens, and evaluator code/paths are forbidden; TCB `GATE_SCHEMA_ENUM_COVERAGE`, `GATE_P25_BANS`, and the independent checker enforce that negative schema/content contract before any prompt is rendered.

## 3. Four candidate payload variants

Every object is recursively closed, uses signed-i64/canonical tagged exact numbers only, and is bounded by its M1 kind caps.

### 3.1 `grep_presence`

`GrepCandidatePayloadV1={amendments,payload_version}` with `payload_version="p25-grep-candidate-v1"`. `amendments` is an ordered nonempty array of exact `{document_id,max_replacements,new,old,operation_id}` rows. `old` is nonempty. The only operation is literal, case-sensitive, NFC-preserving, left-to-right, non-overlapping replacement up to positive `max_replacements`; no regex or expression exists. Document IDs must resolve in the sealed fixture. The core applies amendments in declared order to baseline documents, then evaluates the sealed clauses.

### 3.2 `parser_fixture`

`ParserCandidatePayloadV1={operations,payload_version}` with `payload_version="p25-parser-candidate-v1"`. `operations` is the closed M1 `ParserOperationV1` array. ### 3.3 `bounded_simulation`

### 3.4 `benchmark_delta`

No imputation or dropping exists.

## 4. Candidate-bound core and records

The N4 API becomes:

```text
dispatch_core(*, harness: VerifiedHarness, fixture: FixtureSealedV1, slot_set: CandidateSlotSetV1, slot_set_sha256: str, triage_receipt: TriageReceiptV1, triage_receipt_sha256: str, projection: bytes, slot: CandidateSlotV1) -> CoreResultV2
```

Dispatch rehashes its records and bytes, requires a scored-role set, proves that the selected slot is a contained VALID member and that the matching pinned-context projection row is a survivor, and verifies that the receipt binds the exact set, fixture, projection, context, and harness. Revision-source, pre-core-invalid, refuted, swapped, or unbound input is `INTERNAL_INVARIANT` before a handler runs. It then derives exact `CoreFixtureInputV1={executor_kind,expected,schema_version,scoring_input}`, where the kind-specific scoring projection contains only documents/clauses/limits, parser cases/limits, simulation cases/limits, or benchmark baseline/reference/candidate-field-schema/metric/limit data (metric rows retain their own filters) and excludes task ID/text, selection/retrieval identity, and parser/simulation reference generators. It also derives exact `CoreCandidateInputV1={candidate_id,candidate_payload,candidate_payload_raw_sha256,schema_version}` from only that slot's ID, parsed payload, and payload raw hash. The static table is indexed only by the core fixture's kind. Payload-union/version membership was already established by the pre-core parser; any mismatch at this boundary is `INTERNAL_INVARIANT` ABORT. Public card prose is triage-only and never reaches the handler; the core receives immutable verified scientific data records, never raw paths or capabilities.

After verification, dispatch calls the same typed member frozen by the goldens: `EvaluatorCoreV2(fixture: CoreFixtureInputV1, candidate: CoreCandidateInputV1) -> CoreResultV2`. Every positive distinction pair uses two C1 inputs with distinct payloads against one archived canonical core fixture; fixing both IDs to C1 prevents candidate-ID-only output differences from masquerading as candidate behavior. Same scientific fixture/payload with different card prose or outer seal/control-plane identities must preserve status, reason, result, checks, and value, so payload-only `MechanismIdentityV1` and manifest independence are executable noninterference boundaries.

`CoreResultV2={candidate_id,candidate_payload_raw_sha256,candidate_value,executor_kind,invalid_detail,passed_checks,reason_code,result,schema_version,status,total_checks}` with `schema_version="p25-core-result-v2"`.

- `candidate_payload_raw_sha256` is raw SHA-256 over the exact canonical `payload_json` bytes including final LF and is registered as raw bytes, not a new `H` domain.
- PASS/FAIL require positive `total_checks`, `passed_checks` in range, a complete nonnull result, null invalid detail, and exact reasons `ALL_CHECKS_PASS`/`CHECKS_FAILED`; PASS has all checks and FAIL has fewer.
- Their `candidate_value` is the reduced exact rational `passed_checks/total_checks`, so values are comparable in `[0,1]` across kinds without fusing other axes.
- INVALID has `result=null`, `passed_checks=total_checks=0`, value `0/1`, one closed scientific reason, and exact `CoreInvalidDetailV1={field,item,reason}`. A sealed-fixture defect that qualification should have caught is INTERNAL_INVARIANT ABORT, not INVALID.
- Grep checks are clauses; parser/simulation checks are cases; benchmark checks are metric gates.

`ScientificArtifactV2={candidate_card_raw_sha256,candidate_payload_raw_sha256,candidate_slot_set_sha256,core_output_sha256,core_result,fixture_sealed_sha256,harness_binding_sha256,schema_version,triage_receipt_sha256}` with `schema_version="p25-scientific-artifact-v2"`. It exists only for a VALID triage survivor that reaches the core; the two non-null candidate raw hashes, scored slot-set pointer, frozen triage receipt, and fixture pointer bind the complete candidate evidence chain to the core output. `ScientificReceiptV1` remains an acyclic pointer to the already-computed artifact digest; its schema version must bump only if its exact fields change.

The architecture registry must include raw completion/card/payload/projection/revision-render origins with occurrence-pointer semantics plus canonical `P25_CANDIDATE_TASK_VIEW_V1`, `P25_COMPLETION_RECORD_V1`, `P25_CANDIDATE_SLOT_SET_V1`, `P25_PUBLIC_TRIAGE_CONTEXT_V1`, `P25_TRIAGE_RECEIPT_V1`, `P25_REVISION_EVIDENCE_V1`, `P25_REVISION_CALL_INPUT_V1`, `P25_TASK_ENDPOINT_SET_V1`, scored/smoke guard, and run-config domains. `core_output_sha256` changes its canonical record input from `CoreResultV1` to `CoreResultV2`; `scientific_artifact_sha256` changes from V1 to V2. No unregistered digest is introduced.

## 4.1 Frozen triage and endpoint evidence

M3 captures exact pinned-Git `FileRowV1` bytes for `.claude/tools/elai.map` and `docs/thefinalglance/ELAI-FEATURE-MAP.md` in `PublicTriageContextV1={elai_map,feature_map,schema_version}`. Production triage supplies those verified bytes to the unchanged core loaders through the architecture's immutable `_PinnedContextText` adapter accepting only `exists()` and exact `read_text(encoding="utf-8",errors="replace")`; it never supplies a mutable working-tree `Path`.

Every parsed set receives exact `TriageReceiptV1={candidate_slot_set_sha256,fixture_sealed_sha256,harness_binding_sha256,projection_raw_sha256,public_triage_context_sha256,schema_version}`. The projection covers every VALID slot exactly once in C1..C6 order; pre-core INVALID slots are absent from projection bytes but remain derivable from the bound slot set. The receipt is atomically published before revision evidence, core dispatch, or endpoint construction. A scientific artifact copies its digest. Exact projection is `project_public_triage(*,harness:VerifiedHarness,slot_set:CandidateSlotSetV1)->bytes`; it resolves the pinned map/subsystem context internally and accepts no caller context bytes.

Each revision arm derives exact `RevisionEvidenceV1={candidate_slot_set_sha256,mode,permutation,projection_raw_sha256,rendered_raw_sha256,schema_version,task_id,triage_receipt_sha256}` from its REVISION_SOURCE set. The rendered candidate-invalid public row carries only `{field,reason}` and never the source slot's byte offsets, so shuffled evidence cannot be joined back to the original card span. Exact `RevisionCallInputV1={candidate_task_view_sha256,original_completion_record,prompt_raw_sha256,revision_evidence_sha256,schema_version,task_id}`, with nested standard pointer `original_completion_record={completion_record_sha256}`, binds the original archived candidates, typed view, payload-free evidence rendering, and revision prompt before the second call. The SCORED_REVISED set points to that call input and its completion record repeats its prompt raw hash; substitutions or a second revision abort before scoring.

Endpoint inputs are canonical, not an untyped dictionary. `ExactRationalV1={denominator,numerator}` has positive denominator and reduced signed numerator. `CandidateEndpointV1={candidate_id,candidate_slot_set_sha256,candidate_value,endpoint_state,mechanism_identity,schema_version,scientific_artifact_sha256,triage_receipt_sha256}` has exact state `CANDIDATE_INVALID|TRIAGE_REFUTED|CORE_PASS|CORE_FAIL|CORE_INVALID`; pre-core/refuted/core-invalid states carry `0/1`, only core states may name an artifact, and only a valid card has non-null `mechanism_identity`. `ArmEndpointV1={arm_id,best_candidate_value,best_target_value_delta,candidates,execution_validated_mechanism_yield,schema_version}` contains exactly C1..C6. `TaskEndpointSetV1={arms,schema_version,task_id}` contains all six arms in frozen order and hashes as `P25_TASK_ENDPOINT_SET_V1`. `BootstrapInputSetV1={rows,schema_version}` contains exact task-ID-sorted `{task_endpoint_set_sha256,task_id}` rows and hashes as `P25_BOOTSTRAP_INPUT_SET_V1`.

For every endpoint, `candidate_id` selects that exact slot in the named scored set. Candidate-invalid requires an INVALID selected slot and null identity/artifact; triage-refuted requires a VALID slot, payload-equal identity, and its exact refuted projection row; a core endpoint additionally requires a survivor row and an artifact whose candidate ID, card/payload raw origins, set, receipt, fixture, embedded core result/status, and candidate value all equal the selected evidence. Any slot/identity/artifact/receipt/value swap is `INTERNAL_INVARIANT`; hash validity alone is insufficient.

Family decisions also require canonical guard inputs, not an unbound cost-report dictionary. `GuardInputSetV1={bootstrap_input_set_sha256,rows,run_config_sha256,schema_version,sealed_corpus_sha256,violation_counts}` hashes as `P25_GUARD_INPUT_SET_V1`; its independently expected-digest-verified run config, M2 corpus, bootstrap set, and rows have one identical K=30 task domain. It has exactly one row for every endpoint arm, ordered by task ID then canonical global `SIX_ARMS=(DIRECT,EXO_RELEVANT,EXO_SHUFFLED,PAD_MATCHED,TRIAGE_REVISE,SHUFFLED_REVISE)`: `{arm_id,completion_records,grounded_receipt_slot_count,real_anchor_slot_count,scientific_receipt_rows,scored_candidate_slot_set,task_execution_log_sha256,task_id,total_input_tokens,total_output_tokens,triage_receipt_sha256}`. `completion_records` is the exact within-arm lifecycle-ordered array `{completion_record_sha256}` and `scored_candidate_slot_set` is exactly `{candidate_slot_set_sha256}`; these nested standard keys prevent unregistered plural/prefixed hash aliases. Every row repeats the matching `TaskExecutionLogV1` pointer, and the checker expands the verified `ArmOrderSetV1` into its exact eight call/role entries. The per-task arm-order row governs live execution only and never changes endpoint/guard/report serialization. The completion pointers encode the exact one-call or source-then-revised two-call lifecycle; receipt rows `{candidate_id,scientific_receipt_sha256}` identify every core-evaluated C-slot; all counts and token totals are recomputed from their registered primary evidence. `violation_counts` is exactly `{hidden_answer,leakage,manifest_binding,token_envelope}`. M4 instead uses one-task non-decision `SmokeGuardInputV1` and `P25SmokeReportV1` with the same canonical global arm order; it publishes no bootstrap/cost/family/result record and cannot satisfy or impersonate the scored K=30 schema.

G1 is the paired per-task `real_anchor_slot_count/6` treatment-minus-DIRECT lower bound; G2 is the paired `grounded_receipt_slot_count/6` lower bound; both must be at least `-1/20`. G3-A requires both EXO_RELEVANT/DIRECT aggregate call and total-token ratios at most `13/10`. G3-B requires both TRIAGE_REVISE/DIRECT ratios at most `5/2` and the paired lower bound of `(1000 * P1 / total_tokens)` at least `-1/20`. G4 requires all four violation counts to be zero. `bootstrap.json` and `results.json` carry the run-config, bootstrap-input, and guard-input digests. The independent checker requires the same external expected `run_config_sha256` and reconstructs endpoint, bootstrap/guard rows, scans, rates, retrieval classifications/collisions, costs, and decisions from primary evidence; a producer-supplied count is never trusted.

The output APIs are equally closed: every `PairedBootstrapResultV1` uses exactly 5,000 samples and the one M1-frozen seed `20260712`, fixed exactly-12-decimal strings, and the registered bootstrap-vector digest; `FamilyBootstrapReportV1` fixes every family/control comparison; `P25BootstrapReportV1` is the exact run-config/input-bound `bootstrap.json`; `P25CostReportV1` carries reduced call/token ratios plus artifact-grain classifier-derived retrieval diagnostics and an exact zero EXO_SHUFFLED same-subsystem collision count; `FamilyDecisionV1` has the exact SUPPORTED/NULL/REFUTED boolean/reason XOR; and `P25ResultsV1` has COMPLETE versus G4 INVALID XOR with the same run-config/bootstrap/guard/cost evidence. Mixed seeds or family/input/guard/cost/config swaps are invalid even when each record parses. G4 INVALID publishes no family decision or bootstrap report, while ABORT publishes neither output file; M4 publishes only its closed smoke report.

## 5. P1/P2 and failure accounting

For each task/arm endpoint, exactly the six slots in its scored-role set are retained. Revision arms additionally preserve the six-slot revision-source set as non-endpoint evidence.

- Triage-refuted, CandidateSlot-INVALID, or core-INVALID slots contribute zero P1 and candidate value `0/1`; their archived completion/slot evidence and closed reason remain in evidence.
- P1 `execution_validated_mechanism_yield` is the count of unique single-field `MechanismIdentityV1` payload identities whose public triage verdict is survivor and whose candidate-bound core status is PASS. A repeated payload can contribute at most one even if its descriptions differ.
- Per arm/task best value is the maximum of the six exact `candidate_value` rationals, including zeros.
- P2 `best_target_value_delta` is arm best value minus that task's DIRECT-arm best value. No additional normalization is needed because all kind values are exact pass fractions in `[0,1]`.
- `VALIDATION_MARGIN=0/1`; P1 requires PASS, and P2 support still requires the preregistered paired-bootstrap lower bound strictly greater than zero.

Transport/tool/timeout/trust/TCB/serializer faults remain ABORT and stop the batch; they are never converted to candidate zero. Plain completion text that archives successfully but violates card/payload grammar produces six canonical CandidateSlot records and does not abort the other tasks.

The pre-core CandidateSlot reason enum is exactly `CANDIDATE_CARD_SCHEMA` and `CANDIDATE_PAYLOAD_SCHEMA`; those are not scientific core INVALID reasons. Closed enum/operand/schema defects are pre-core, post-ELIGIBLE fixture/expected/metric-definition defects are `INTERNAL_INVARIANT`, and only the architecture's closed post-parse candidate reference/runtime-data/cap reasons are scientific INVALID. No failure is dropped, retried, or replaced.

## 6. Fixture/procedure split

The four RECON-5 procedures must version their payloads so candidate-owned bytes are no longer pre-frozen as task bytes:

- grep fixture: prompt-visible baseline documents/task text plus hidden clauses and limits; candidate: amendments;
- parser fixture: prompt-visible evaluation cases/task text plus hidden evaluation-only reference operations and limits; candidate: operations;
- simulation fixture: prompt-visible cases/events/inputs/required initial IDs/task text plus hidden evaluation-only reference machine and limits; candidate: states/transitions/logical clock;
- benchmark fixture: prompt-visible baseline rows/required candidate schema/task text plus hidden reference rows/metrics/limits; candidate: candidate rows; selection remains only in external M2 trust evidence.

M2 drafts and hidden generation remain after the M3 anchor. Prompt rendering exposes only the typed `CandidateTaskViewV1` and static kind payload schema. Clauses, reference rows/metrics, parser reference operations, simulation reference machine, hidden expectations, and core outputs are absent from all generation and revision inputs. Hidden generation never consumes candidate bytes. The verifier scans the full candidate-card and payload bytes against task-local hidden tokens.
