## 1. Decision and trust boundary

Fixture bytes are untrusted canonical data. They may describe prompt-visible candidate inputs, hidden evaluation inputs, cases, metric rows, parser operations, states, and transitions. The sole control discriminator they may carry is closed `executor_kind`, which indexes the already-M3-verified four-handler table. They MUST NOT name, locate, authenticate, replace, extend, or dynamically load evaluator code, evaluator hashes, trust-root hashes, commands, imports, modules, executables, runtimes, toolchains, gates, serializers, generators, publishers, or sandboxes.

M3 freezes and verifies all four repo-owned evaluators plus their exact static dispatch table before any fixture exists. After sealing, `fixture.executor_kind` indexes exactly one member of that immutable table; it is not a module/path/identity lookup and the candidate carries no such discriminator. A wrong or unknown fixture kind fails qualification, while a post-parse kind/payload mismatch is an internal invariant. The verified harness adds the registered `harness_binding_sha256` only after the evaluator has returned a manifest-independent core result.

locked prereg Git locators + anchors              FixtureDraftV1 bytes
        |                                                 |
        v                                                 v
root loader -> trust root -> M3 freeze record      closed structural + semantic schema

Scoring receives immutable captured bytes plus an already-verified evaluator handle. Evaluators have no filesystem, process, network, model, wall-clock, host-environment, or dynamic-code capability. Text that resembles source code remains inert data because no DSL handler can execute it. SHA-256 domains registered in section 3 and native Git object identities are authoritative for this control plane. P-25's stale generic BLAKE3 wording is a required later plan migration item and cannot authenticate any root, evaluator, fixture, seal, or scientific record defined here.

## 2. Exact canonical grammar and hash domains — `A3-CANONICAL-GRAMMAR`

All trust, manifest, fixture, result, dispatch, lease, and gate records use one profile, `P25-CANONICAL-JSON-V1`:

- Strict UTF-8, no BOM, no NUL, no lone surrogate, NFC strings, exactly one JSON value and one final LF byte `0x0A`.
- Objects have unique keys sorted by key UTF-8 bytes. Arrays retain declared order. Separators are `,` and `:` with no whitespace.
- Quote and backslash encode as `\"` and `\\`; U+0008/U+0009/U+000A/U+000C/U+000D encode as `\b/\t/\n/\f/\r`; remaining U+0001..U+001F encode as lowercase `\u00xx`; slash and all remaining scalars are unescaped.
- JSON numbers are signed 64-bit integers in grammar `0|-?[1-9][0-9]*`. Floats, exponents, nonfinite numbers, leading zeroes, plus signs, and integer `-0` are invalid. Sizes and versions use `0..2^63-1`; positive versions exclude zero. Exact decimals/rationals remain tagged data defined by the procedure schema.
- Every versioned schema sets `additionalProperties=false` recursively for every object. `null` is legal only where its field explicitly includes null.

Closed ASCII grammars are:

- `ID = [A-Z][A-Z0-9_.-]{0,127}`.
- `FIELD = [a-z][a-z0-9_]{0,63}`.
- `SESSION = s-[0-9]{1,12}`.
- `AGENT = [A-Za-z0-9_./-]{1,160}`.
- `PATH = SEG("/"SEG)*`, where `SEG=[A-Za-z0-9][A-Za-z0-9._-]{0,127}|\.[A-Za-z0-9][A-Za-z0-9._-]{0,126}`, total length `1..512` ASCII bytes. Thus an ordinary segment is alnum-leading and a dot segment has exactly one leading dot followed by an alphanumeric byte, so `.claude` is legal. Absolute paths, backslash, colon, empty segments, `.`, `..`, and every multiple-leading-dot escape form are forbidden.
- `SHA256 = [0-9a-f]{64}`. `git_object_format` is `sha1` or `sha256`; its lowercase Git OID is respectively 40 or 64 hex characters.

For byte parts `p1..pn`, `H(tag,parts)=SHA256(ASCII(tag)||0x00||u64be(len(p1))||p1||...||u64be(len(pn))||pn)`. The only legal tags are the exact tags in the registry below; a tag cannot be reused for another record type.

A Git blob OID uses the selected Git object algorithm over `ASCII("blob " + decimal_byte_length)||0x00||exact_bytes`. A Git tree OID uses that algorithm over `ASCII("tree " + decimal_tree_object_length)||0x00||exact_tree_object_bytes`. A Git commit OID uses that algorithm over `ASCII("commit " + decimal_commit_object_length)||0x00||exact_commit_object_bytes`. Git OIDs are not `H`; a path/OID binding means that path resolves to that exact blob in the named commit tree.

The loader executes this fixed order and stops at first mismatch:

1. For M3 work receive only exact M1/M3 locator bytes plus independently supplied expected locator digests, then resolve both anchors and every subject through the loader-owned native reader; for M4/M5 receive the `P25RunConfigV1` path plus independently supplied expected `run_config_sha256` and resolve its exact M1/M3/M2 locator, M2 anchor, and sealed-corpus bytes.

3. Load root/receipt/loader only from M1 artifact blobs; verify the current root and recursively resolve its nested predecessor-root anchor chain through the same native reader, never caller bytes.
4. Verify canonical profile, complete hash registry and its schema-field gate, contracts, principal policy, frozen controller-root dispatch, and TCB inventory.
5. Load the M3 manifest, controller log, gate result set, audit receipt, and outer freeze record only from M3 artifact blobs; recursively resolve the manifest's nested predecessor-M3-anchor chain through the same native reader before accepting its version.
6. Verify the controller log to its M1 root, principal bindings, manifest, TCB/dependency/toolchain closure, gate results, freeze payload, independent audit receipt, and outer freeze record in that acyclic order.
7. Load dispatcher/evaluator modules only from verified TCB file sets and construct `HarnessBindingV1` from verified origins.
8. Parse or qualify fixture data only after steps 1..7; enforce draft ordering while building M2, then require the verified M2 locator/anchor/corpus and all remaining first-parent predicates before M4/M5 candidate generation.

Working-tree swaps are irrelevant to pinned blob reads. No fixture field can change a locator, anchor, path, OID, root predecessor, controller root, or loader order.

Only if the two canonical `CoreResultV2` byte strings are identical does the verified serializer construct `ScientificArtifactV2`, copy the already-registered containing `candidate_slot_set_sha256` and matching `triage_receipt_sha256`, and inject `harness_binding_sha256`; any difference is `CORE_NONDETERMINISTIC` ABORT and publishes neither artifact nor receipt. `A4-NO-SELF-REFERENCE` reruns the same fixture/slot pair under two complete trusted `HarnessBindingV1` values: core bytes/hashes must remain identical and only wrapper/receipt bindings may differ. The atomic publisher publishes artifact plus receipt together or neither.

## 6. Scientific verdicts versus qualification ABORT

### 6.1 Pre-hidden semantic qualification

Before any hidden expectation is generated, `DRAFT_QUALIFIER` indexes the frozen handler table with draft `executor_kind`, runs that trusted member's closed structural/semantic checks against the pinned draft, and returns exact closed union `DraftQualificationV1={detail,draft_blob_oid,draft_sha256,executor_kind,harness_binding_sha256,reason_code,schema_version,status}` with `schema_version="p25-draft-qualification-v1"`:

- `ELIGIBLE`: `status="ELIGIBLE"`, `reason_code="SEMANTICALLY_QUALIFIED"`, and `detail=null`. The draft schema, executor-kind schema, retrieval binding, finite DSL/intrinsic semantics, operand types/ranges, and frozen count/depth/work caps all close without evaluating an expected value. Only this branch may reach expectation generation.
- `DATA_INVALID`: `status="DATA_INVALID"`, `reason_code` is one of `FIXTURE_CANONICAL`, `FIXTURE_SCHEMA`, `CAPTURED_DATA_HASH`, `RETRIEVAL_SPEC`, `DSL_OPCODE`, `DSL_OPERAND`, `DATA_TYPE`, `DATA_RANGE`, `DATA_DEPTH`, `DATA_COUNT_CAP`, or `DATA_WORK_CAP`, and `detail` is exact `{field,item,reason}`. It emits the canonical qualification record and `qualification_sha256`, emits no hidden bytes or scientific artifact, and permits same-stratum canonical-pool replacement before final seal.

Both branches bind the exact draft blob/digest, executor kind, and complete `harness_binding_sha256`. An infrastructure, root, TCB, evaluator, qualifier, gate, serializer, controller-log, or runtime fault emits no `DraftQualificationV1`; it is the existing `QUALIFICATION_ABORT`, stops the batch, and cannot exclude or replace a candidate. `EXPECTATION_GENERATION_FAILURE` likewise emits no qualification or scientific result and no hidden bytes. If any defect that the closed semantic qualifier was required to detect is discovered after `ELIGIBLE`, the only result is `INTERNAL_INVARIANT` ABORT; it cannot be relabeled DATA_INVALID.

### 6.2 Candidate-bound scientific result records

Only PASS, FAIL, and core INVALID are scientific. Exact completion bytes are archived before parsing and deterministically expand to six ordered `CandidateSlotV1` records, one for each fixed ID `C1..C6`. `CandidateCardV2={candidate_id,expected_effect,falsifier,mechanism_family,payload,target_area,target_units,schema_version}` has `schema_version="p25-candidate-card-v2"`; its six public fields are the exo-v1.1 triage projection and `payload` is a closed kind-specific `CandidatePayloadV1`. The already-sealed fixture kind, never the candidate, indexes the M3-frozen static handler table.

`CandidateInvalidDetailV1={byte_end,byte_start,field,reason}` is closed. `field` is exactly `completion|card|id|mechanism_family|target_area|target_units|expected_effect|falsifier|payload_json`; `reason` is exactly `UTF8|FRAMING|CARDINALITY|ORDER|TRAILING_CONTENT|FIELD_MISSING|FIELD_DUPLICATE|FIELD_VALUE|PAYLOAD_JSON|PAYLOAD_CANONICAL|PAYLOAD_KIND|PAYLOAD_VERSION|PAYLOAD_SHAPE`. Both byte offsets are null iff no exact offending span can be isolated; otherwise they are integers with `0<=byte_start<byte_end<=len(completion_bytes)`.

`CandidateSlotV1={candidate_card,candidate_card_raw_sha256,candidate_id,candidate_payload_raw_sha256,completion_raw_sha256,invalid_detail,reason_code,schema_version,status}` has `schema_version="p25-candidate-slot-v1"`. `status="VALID"` requires a complete `CandidateCardV2`, both candidate raw hashes, matching ID, and null reason/detail. The payload token must byte-match its `P25-CANONICAL-JSON-V1` bytes; card raw bytes are the exact header through payload-line LF, while payload raw bytes are the exact JSON token plus that LF. The parser receives sealed fixture kind out of band and validates exact payload union/version, fields, primitive/container types, opcode/guard/action enums, operand schemas, static ranges, and declared cardinality/depth caps. `status="INVALID"` requires null `candidate_card`, reason `CANDIDATE_CARD_SCHEMA` or `CANDIDATE_PAYLOAD_SCHEMA`, one exact `CandidateInvalidDetailV1`, and the archived completion hash; candidate raw hashes are present only where exact spans were unambiguously isolated. A global decode/framing/cardinality/order/trailing-content defect makes all six fixed slots INVALID; an isolated payload defect invalidates only its slot. Slot INVALID and public-triage refutation are pre-core evidence classes, not `CoreResultV2` INVALID, emit no scientific artifact, and contribute endpoint value `0/1` without disappearing.

`parse_candidate_slot_set` receives the complete verified `CandidateTaskViewV1`, not only its digest, plus exact arm/completion/fixture/role/task inputs. It rehashes that view, requires its task ID and kind to match the selected sealed fixture, and validates kind/version, closed union, enums/operands, static shape/ranges/caps, plus the complete benchmark `candidate_field_schema` names/types. It deliberately does not resolve prompt-visible reference IDs or apply candidate-side dynamic work: a structurally valid grep document reference, parser case reference, simulation required-initial-state reference, or benchmark pair domain reaches the minimal core and may yield the closed scientific `REFERENCE_MISSING|PAIR_MISSING|PAIR_EXTRA|DATA_WORK_CAP` result. A digest-only or fixture-hidden view substitute is forbidden. The resulting set stores the registered view digest after these checks.

The bound completion record's call ID must equal `P25:<task_id>:<arm_id>:<set_role>`, and no `CompletionRecordV1` origin may be consumed by two sets. Distinct call IDs/records may legitimately have byte-identical extracted content and therefore the same `completion_raw_sha256`; content equality is never reuse. Arms 1..4 each publish exactly one `SCORED_INITIAL`; arms 5..6 each publish one `REVISION_SOURCE` followed by one `SCORED_REVISED`. It is canonically published after each archive/parse and before that set's triage. Only a scored-role set is an endpoint input or may be named by a scientific artifact; the revision-source set exists solely to derive frozen revision evidence.

`CompletionRecordV1={call_id,completion_raw_sha256,input_tokens,max_tokens,model,output_tokens,prompt_raw_sha256,request_raw_sha256,response_raw_sha256,schema_version,total_tokens}` has `schema_version="p25-completion-record-v1"`. `call_id` is the exact derived string `P25:<task_id>:<arm_id>:<set_role>` for its sole consuming set; all four components use their closed grammars and the ID is globally unique in the run. Raw hashes cover exact archived prompt bytes, application request-body bytes, application response-body bytes, and extracted completion-content bytes respectively. Token fields are closed nonnegative integers with `total_tokens=input_tokens+output_tokens`. M1 freezes `P25_COMPLETION_ENDPOINT="http://127.0.0.1:8810/v1/messages"`, `P25_COMPLETION_MODEL="kimi-k2-7"`, `P25_COMPLETION_MAX_TOKENS=1400`, and operational `P25_COMPLETION_TIMEOUT_MS=240000`, `P25_RESPONSE_MAX_BYTES=1048576`, and `P25_RESPONSE_READ_CHUNK_BYTES=65536`; the record must carry that exact model and max-token value; response caps remain operational only. Endpoint and timeout affect only success versus ABORT; endpoint, timeout, all HTTP framing and headers, latency, cache state, wall clock, and host are absent from scientific records.

`P25-REQUEST-JSON-V1` is the exact application-request profile and is deliberately distinct from record canonicalization. It retains `P25-CANONICAL-JSON-V1`'s strict UTF-8, unique/sorted keys, compact separators, signed-integer grammar, exact string escaping, one value, and one final LF, but waives NFC only for `messages[0].content`: that value may be any strict-UTF-8 scalar sequence with no NUL or lone surrogate, including non-NFC model output embedded in a revision prompt. Quote, backslash, controls, slash, and all other scalars use the exact section-2 escape rules; no normalization or replacement occurs, and JSON-decode(content) followed by UTF-8 encode must reproduce `prompt_bytes` byte-for-byte. `P25_REQUEST_BODY_V1(prompt_bytes)` is exactly that profile's serialization of `{"max_tokens":1400,"messages":[{"content":UTF8_DECODE_STRICT(prompt_bytes),"role":"user"}],"model":"kimi-k2-7"}`. The client performs exactly one direct HTTP `POST` to the frozen endpoint with explicit headers `Content-Type: application/json`, `Accept: application/json`, and `Accept-Encoding: identity` and that body. Redirects, environment/system proxies, authentication discovery, response compression, and transfer to another origin are disabled. The body has exactly the three top-level keys and the one two-key message above: no system message, tools, tool choice, temperature, top-p, metadata, streaming, stop sequence, cache control, or caller extension exists. `max_tool_turns=0` is a local control-flow invariant, not a request-body member: the client has no tool loop, and any tool-use response aborts without a follow-up request.

`CompletionArchiveSink` is a nonserialized N12-minted capability initialized from one `VerifiedRun`, its verified `ArmOrderSetV1`, and one private run-level sibling staging root. The transport rejects a declared `Content-Length` above `P25_RESPONSE_MAX_BYTES` before reading and otherwise reads the de-chunked entity in chunks of at most `P25_RESPONSE_READ_CHUNK_BYTES`, retaining at most `P25_RESPONSE_MAX_BYTES+1`; reaching the extra byte ABORTs with no staging or record. Only a complete entity of at most the cap exists. The client then immediately calls `stage_exchange` with that entity as `response_bytes` before interpreting status, media type, content encoding, or JSON semantics. `response_raw_sha256` covers those exact entity bytes before JSON parsing; it never covers status/header/chunk framing. The body is strict UTF-8 JSON with no BOM/NUL/lone surrogate, duplicate object key, leading byte, trailing byte, or second value. Its top-level key set is exactly `{content,id,model,role,stop_reason,stop_sequence,type,usage}`. `type="message"`, `role="assistant"`, `model="kimi-k2-7"`, `stop_reason` is exactly `end_turn|max_tokens`, and `stop_sequence=null`; `id` is a nonempty 1..160-scalar NFC string with no control scalar. `content` is exactly one object with exact key set `{text,type}`, `type="text"`, and a JSON string `text` that decodes without NUL or lone surrogate. `usage` has exact key set `{input_tokens,output_tokens}` with nonnegative signed-64-bit integers. Wrong status/media/encoding, malformed/extra/missing data, wrong model/role/type, multiple or non-text blocks, `tool_use`, or any other stop reason is ABORT.

Completion bytes are exactly `UTF8(text)` with no trim, concatenation, normalization, or added LF. While the exchange remains staged, the client constructs the closed `CompletionRecordV1`, canonicalizes it, and independently rehashes the exact in-memory prompt, request, response, and completion origins; any failure discards the staged exchange. Only after that succeeds does `promote(staged=...,completion_bytes=...,completion_record=...)` durably and atomically expose all four origins inside the private run staging root. That atomic promotion also appends the record pointer to the authorized execution index. The client then returns the already-constructed record and completion bytes. Any status/media/encoding/JSON validation, extraction, record construction/canonicalization/rehash, or promotion failure calls `discard(staged=...)` exactly once, leaves `out_dir` absent, removes the private run staging root during batch cleanup, and ABORTs; staged bytes are never scientific evidence. The client has no cache, retry, sleep, redirect, follow-up, fallback, or second POST.

The M4/M5 evidence directory has one frozen content-addressed grammar, not a producer-selected layout. Every non-report canonical record is stored once at `records/<schema_id>/<registered_sha256>.json`, where `<schema_id>` is the exact closed N1 `decode_record` identifier for those bytes and the filename is the digest from that schema's one registry row. Each singleton is byte-for-byte the corresponding canonical `P25SmokeReportV1`, `P25BootstrapReportV1`, `P25CostReportV1`, or `P25ResultsV1`. No report is also present under `records/`. The out directory otherwise contains only the `records/` and `raw/` trees above. Every component is a regular file or directory reached without symlink, junction, reparse point, hard-link alias, case-fold collision, alternate data stream, or path normalization change; producer staging lives outside the evidence root, and no temporary file survives publication.

For requested `out_dir`, the runner requires both it and the exact same-volume sibling `<out_dir.name>.p25-stage` to be absent, then creates only that sibling. The producer derives paths only from the frozen schema/raw-kind tables and verified digests, writes each file create-new beneath the sibling, reopens and byte-compares it, completes every required task/log/endpoint/guard/report cross-check, and writes the applicable singleton report last as the completion marker. It then fsyncs every file and directory required by the host, closes all handles, and performs one no-overwrite atomic same-volume rename from the sibling to `out_dir`; this rename is the sole evidence-publication event. Any ABORT before the rename recursively removes the sibling and leaves `out_dir` absent; cleanup failure is itself reported out of band and the sibling remains explicitly non-evidence because it has the reserved suffix and is never accepted by the checker. The independent checker rejects a reserved-suffix root and begins from the published singleton plus the externally expected run-config digest, reconstructs the exact reachable record/raw-origin graph for the M4 task or all M5 tasks (including retrieval artifacts, eight-call task logs, every completion lifecycle, revision input/render, slot/triage/core/scientific/endpoint/guard edge), computes every expected relative path itself, recursively enumerates all directory entries without following links, and requires actual regular-file paths to equal that expected set exactly. Thus `artifact_dir` is an opaque root only; no caller index, glob, filename, or traversal policy is trusted.

P-25 does not reuse Q-10's live `max_tokens=1` meter. M1 freezes `P25_ENVELOPE_MATCHED_ARMS=(EXO_RELEVANT,EXO_SHUFFLED,PAD_MATCHED)` in that order, `P25_ENVELOPE_TOLERANCE=ExactRationalV1{denominator:50,numerator:1}`, and `P25_PAD_TOKEN=UTF8("envelope_pad")`; DIRECT and both revision arms are outside this envelope. The independent checker rederives every count and pad choice from the archived prompt bytes; therefore preprocessing adds exactly zero completion calls and the arm lifecycle remains `1/1/1/1/2/2`.

All prompt bytes are closed before calls. A decimal length is ASCII `0|[1-9][0-9]*` with no sign or leading zero and counts the following raw byte block, not Unicode scalars. A framed block is `ASCII(label)||0x20||ASCII(length)||0x0A||raw_bytes`; parsing consumes exactly `length` bytes and the next literal begins immediately, so an embedded LF cannot terminate a block. `CandidateTaskViewV1` bytes use `P25-CANONICAL-JSON-V1`. `candidate_spec_ref/candidate_spec_raw_sha256/candidate_spec_sha256` is the executor-kind-matching M1-root-bound public `CandidateSpecV1` triple copied into the verified M3 manifest entry. Artifact inputs are either empty or exactly A1,A2,A3 in that order. Every task-view, candidate-spec, provenance, and artifact raw block must strict-UTF-8 decode and re-encode byte-identically, contain no NUL, and decode to NFC without normalization before an M2 draft can be ELIGIBLE; an artifact that fails is `DATA_INVALID/RETRIEVAL_SPEC`, so arbitrary non-UTF-8 or noncanonical source bytes never reach request serialization.
