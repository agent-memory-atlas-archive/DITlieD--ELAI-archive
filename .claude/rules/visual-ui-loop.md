Visual UI loop (HARD RULE, schema-constrained)

Loaded by: any task iterating on the dashboard's visual output where the agent screenshots, compares, and adjusts (Svelte component layout polish, the 3D orbit/graph views, matching a mock, fixing a visual regression). Pairs with the conditional-routing.md Dashboard/frontend trigger and dashboardRules.md for component rules. Note: dashboardRules.md is written in React terms but the real dashboard is Svelte 5 + Vite + Tauri v2 (dashboard-v2); read it for the component/state doctrine, not the framework API.

Why this exists

If there is no design target yet (no mock, golden frame, or brief because the look is still undecided), this loop has nothing to score against: cook (.claude/skills/cook/SKILL.md) is the discovery front-end that produces the design brief this loop builds and screenshots against. Offer it first (cook is user-invoked only, never auto-fired), then run design-taste.md's pre-flight, then this loop. Cook's renders are a decision baseline, never the shipped pixels; the real screenshot-vs-render judgement is this file's job.

An agent that screenshots its own UI and asks itself "does this look right" rubber-stamps. VLMs are biased toward "pass", are weak at visual regression, and miscount small repeated elements. The loop below removes the freestyle judgement: a deterministic diff runs first and decides WHERE to look, a perception scaffold gives the model resolved layout facts it cannot read off a screenshot, the vision call is forced into a pass|fail|unknown schema with unknown treated as fail, and only one fix lands per loop so cause and effect stay legible.

THE PIPELINE (run in this order every iteration)
1 CAPTURE the current state. Pixels: the existing CDP capture harness at .elai_cc/crates/dashboard-v2/screenshots/cdp_*.mjs (Chrome on --remote-debugging-port=9222, dev server on http://localhost:1420, Page.captureScreenshot). Resolved layout facts (the perception scaffold, web analog of a Unity layout dump): node .claude/tools/visual/ax-scaffold.mjs --url http://localhost:1420 --out <dir>/scaffold.json. It crosses Accessibility.getFullAXTree (role + accessible name) against DOM.getBoxModel (pixel box) into a compact [{role, name, bbox}] list. Reason over these facts, do not ask the VLM to read geometry or count off the screenshot.
2 DETERMINISTIC DIFF before any vision call: node .claude/tools/visual/ui-diff.mjs <candidate.png> <reference.png> --out <dir>. Returns verdict identical|changed, changed_fraction, diff_pixels (pixelmatch, anti-aliasing-aware), an overall bbox, grid hotspots (the evidence regions), heatmap.png/mask.png, and crops: native-resolution PNG cuts of the candidate at the bbox + top hotspot cells, each with its px_region. Exit 0 identical, 2 changed, 1 error (fail-loud, never read an error as pass). A size mismatch is exit 1 by design: a dimension change between candidate and reference IS a regression, it is not silently resized away. This is the cheap gate: verdict identical means done, spend no vision call. The diff ALWAYS runs on the raw lossless PNG captures, never on vlm-prep output.
3 PREP THE JUDGE INPUT. Look at the crops, not the full frame: a full screenshot read whole gets downscaled before the judge sees it, losing exactly the fine detail that changed (axis ticks, badge numbers, thin borders, dense graph labels). The crops from step 2 are already judge-ready. When a full frame IS needed (no reference to diff against, first capture, semantic/mock judgement), run node .claude/tools/visual/vlm-prep.mjs <screenshot.png> first (box-downscale to 1568px longest side) and read THAT, not the raw PNG.
4 VISION CRITIQUE only on the flagged regions, schema-constrained (below). The hosted judge is me (Claude); no extra model needed. Prompt construction is fixed: checklist + context line FIRST, image after (image-first prompting measurably hurts reasoning), and the context line names what the image is ("dashboard-v2 architecture graph view, dark theme" etc) so attention lands in the right domain.
5 ONE FIX, then back to 1.

THE CRITIQUE SCHEMA (mandatory, per checklist item)
Each checklist item gets exactly: { item, verdict: pass|fail|unknown, evidence_region: [x0,y0,x1,y1], note }.
- unknown is treated as FAIL. An item you cannot judge from the evidence is not passing. Re-capture a clearer shot or add an annotation, do not wave it through.
- evidence_region is mandatory and must be a real pixel box (from a ui-diff hotspot or the scaffold json). "looks fine overall" with no region is not a verdict.
- Derive the checklist from the actual target (the mock, the golden frame, the dashboardRules.md spec), not from vibes. When there is no pixel target (polishing an original surface, no mock), seed the checklist from the design-taste.md pre-flight (one accent, tinted neutrals, measured contrast, authored web font + hierarchy, focal layout not equal-thirds/divitis, motivated ease-out motion + prefers-reduced-motion, full state coverage, every anti-slop ban absent) so "looks fine" cannot pass as a verdict; each pre-flight line becomes one pass|fail|unknown item with a real evidence region.
- DESCRIBE BEFORE VERDICT on semantic/aesthetic judgement (mock matching, anything without a pixel reference): first list what is literally visible in the evidence region (elements, text verbatim, colors, spacing), THEN fill the schema. A verdict that cites something the description never mentioned is invalid. This kills describe-what-you-expect hallucination.
- NEVER COUNT VISUALLY past ~10 elements. VLM counting degrades sharply on many small items (table rows, chart series, graph nodes, badges). "all N rows present" comes from the ax-scaffold.json element list or a deterministic script, never from looking. A count-shaped checklist item with only visual evidence is unknown (= fail).

THE TASTE-RUBRIC SEED (mandatory first-class checklist items, not vibes)
The checklist is not free-form. Every line of the design-taste.md TASTE RUBRIC becomes ONE schema-constrained item here, with the same pass|fail|unknown + mandatory evidence_region + unknown=fail contract as above. Run the deterministic leg FIRST so a measured fail outranks a rubber-stamp pass (the liteGAME loop does the same with uss-taste-lint.py):
  0 DETERMINISTIC LEG before the vision pass: python .claude/tools/taste_check.py --files <changed .svelte/.css/.ts> --json. Exit 1 = a BLOCK-class tell is present (banned non-teal hue literal, glassmorphism, glow box-shadow, gradient decoration, etc); exit 2 = scan-config error (treat as fail, never as pass). Any BLOCK the checker reports is a `fail` item you do not get to overrule by eye; its evidence_region is the file:line it named. A clean checker run is NOT a pass — it only clears the mechanical subset; the F/B lines below still get judged.
  1 FLOOR-TIER items (F1-F11 from design-taste.md): each is one pass|fail|unknown item. A floor NO is BLOCK-class — the surface is not done. These are surface-agnostic; they apply to every ELAI view, work or brand.
  2 BRAND-TIER items (B1-B6 + the signature slot S1/S2 from design-taste.md): each is one pass|fail|unknown item. On a BRAND / entry surface (the boot screen, project-selection, marketing) the signature items S1/S2 are MANDATORY and unknown=fail — a brand surface that passes the floor but has no signature is "clean but generic", which is the exact de-slopped-but-tasteless failure this seed exists to catch. On a WORK surface, B1-B6 are mandatory and S1/S2 apply only where the design file scopes a signature onto that surface.
  3 The context line (step 4) MUST name the surface CLASS ("ELAI brand/entry surface" vs "ELAI work surface") so the judge knows whether the signature items are mandatory here.
Until the ELAI signature set is chosen and written into design-taste.md's S1/S2 slots, S1/S2 score unknown (= fail) on any brand surface — which correctly blocks a brand surface from being declared done before its signatures exist.

THE HARD CAVEATS (do not get these wrong)
- ONE fix per loop is not optional. Batching fixes destroys the ability to attribute a regression to a change and is how oscillation starts.
- TWO-PASS STOP GATE: declare done only after two consecutive full passes with zero fail/unknown items. One clean pass can be luck or a stale capture.
- OSCILLATION DETECTOR: if the same item flips fail->pass->fail across three loops, STOP and escalate (surface to maintainer). You are fighting a layout constraint, not polishing; more edits make it worse (anti-spiral, token-discipline.md).
- PIXEL-DIFF ONLY AGAINST KNOWN-GOOD ENGINE RENDERS. ui-diff.mjs is for regression vs a golden frame the dashboard itself produced (the ~80 golden PNGs in dashboard-v2/screenshots, or a prior accepted capture). Do NOT pixel-diff against a Figma export or a hand mock, those will never be pixel-identical and the diff is all noise. For mock targets use the vision critique with SEMANTIC judgement (spacing, hierarchy), not the pixel metric.
- VLMs rubber-stamp. The schema (forced pass|fail|unknown, unknown=fail, mandatory region) exists to fight that bias. Do not relax it to "looks good".

CAPTURE DETERMINISM (the diff is noise unless the capture is reproducible)
The CDP capture must be pinned or the diff flags font/AA churn on every run. Required, all verified:
- deviceScaleFactor: 1 in Emulation.setDeviceMetricsOverride (the existing cdp_orbit_capture.mjs already does this) — without it a HiDPI host silently emits 2x PNGs.
- fromSurface: true on Page.captureScreenshot — this is the fix for the empty-bottom-rows headless bug this project already hit (check_bottom.mjs detects it); a partial compositor frame otherwise.
- Launch Chrome with --font-render-hinting=none — subpixel text hinting differs across OS/runs and shows up as scattered low-magnitude diff pixels uniform across every text line. Signature: low changed_fraction but spatially smeared over text. Fix at capture, never by raising the diff threshold.
- Kill motion before the shot: Emulation.setEmulatedMedia prefers-reduced-motion + inject a zero-duration animation/transition style, and blur the active element (caret). Then settle two requestAnimationFrame ticks (ax-scaffold.mjs already settles; add the same to a screenshot path that captures mid-transition).
